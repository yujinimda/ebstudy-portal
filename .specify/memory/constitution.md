# 게시판 포털 Constitution

이 문서는 `specs/process.md`(단일 진실)의 **실행 가능한 요약**이다.
모든 스펙과 계획은 이 원칙과 대조되어야 한다.

전제: 프론트엔드 개발자 1명. 자바·백엔드 학습 시작 단계.
포트폴리오가 아니라 **실제 서비스**이므로 유지보수성과 확장성이 기능보다 우선한다.

## Core Principles

### I. 테스트 우선 — 역할 역전 TDD (NON-NEGOTIABLE)

테스트는 구현보다 **먼저** 작성한다. 그리고 **작성자를 분리한다** — 한 주체가 스펙만 보고
테스트를 쓰고, 다른 주체가 그것을 통과시킨다.

테스트 밀집도는 **API 통합 테스트 중심**(Testing Trophy)이다:

| 레벨 | 비중 | 대상 |
|---|---|---|
| 단위 | 낮음 | 복잡한 계산·검증 로직만 |
| 슬라이스 | 거의 없음 | — |
| **통합** | **주력** | HTTP 요청 → 실제 DB → 응답 |
| E2E | 총 5~10개 | 사람이 돌아다녀야 의미 있는 흐름만 |

응답·권한·경계값 검증은 E2E가 아니라 **API 통합 테스트**로 내린다.

**근거**: 단위 테스트를 주력으로 삼으면 의존성을 목(mock)으로 발라야 하고, 그러면 리팩터링마다
테스트가 깨지는데 정작 진짜 버그는 안 잡힌다. 목은 상상한 대로만 응답한다. 실제 버그는 실제
DB와 붙는 경계에서 나온다. 작성자를 분리하는 것은 "귀찮으니 구현 먼저, 테스트는 나중"이라는
TDD의 대표적 붕괴 지점을 **원리적으로** 막기 위한 것이다.

### II. 검증 가능한 인수기준 (NON-NEGOTIABLE)

모든 인수기준(AC)은 **Given / When / Then + AC-ID** 형식으로 쓴다. 사전조건(Given)을 반드시
명시한다.

```
### AC-3 빈 검색어 검색
 Given 로그인한 사용자가 있고
  When GET /api/posts?q= 를 요청하면
  Then 400이고 code=SEARCH_QUERY_REQUIRED
```

- "사용자가 검색할 수 있다" 같은 **실행 불가능한 문장은 금지**한다.
- AC-ID는 태스크·테스트·QA 기록을 상호 참조하는 키다. QA 기록의 `AC-3 FAIL`이 곧 테스트 이름이고
  태스크 번호로 역추적된다.

**커버리지 게이트: AC 커버리지 100%. 줄 커버리지는 게이트가 아니다.** *(1.3.0 추가)*

- **AC 하나도 빠짐없이 테스트를 가져야 한다.** 테스트 이름의 AC-ID로 센다.
  AC 하나당 테스트 하나 이상이며, 여러 AC를 한 테스트로 뭉치지 않는다.
- **줄 커버리지에 숫자 기준을 두지 않는다.** 측정해 리포트로만 남긴다.
- **근거**: 숫자가 목표가 되면 숫자를 채우는 테스트가 생긴다(`assert` 없이 호출만 하는 테스트).
  커버리지는 "이 줄이 실행됐다"만 세고 **"결과가 맞는지 확인했다"는 세지 않는다.**
  게다가 원칙 I의 통합 중심 전략에서는 한 요청이 전 계층을 통과하므로 **숫자가 특히 부정확하다.**
  AC-ID로는 누락을 **정확히** 셀 수 있고 그것이 의미 있는 수다.
- **한계**: AC로 명시되지 않은 코드 경로는 이 게이트가 잡지 못한다.
  그 경로가 중요하다면 **AC가 빠진 것이므로 스펙 결함으로 다룬다**(3번 게이트의 몫).

**근거**: AC 하나가 세 곳의 원천이다 — 테스트 작성, 기능 QA 체크리스트, 자동 테스트 승격.
사전조건 칸이 없으면 생략되고, 테스트를 쓰는 주체가 "로그인 상태"를 임의로 짐작한다.

### III. 되돌리기 비용이 큰 결정은 사람이 하고 ADR로 남긴다

- **판정 기준: 실재하는 선택지가 둘 이상인가?**

  | | 처리 |
  |---|---|
  | **선택지가 둘 이상** | **사람이 확정한다.** AI는 대안과 근거를 제시할 수 있으나 **선택은 사람이 한다.** 되돌리기 비용이 최상이면 **ADR 필수** |
  | **자명해서 선택지가 하나** | AI가 도출하고 사람이 검증한다 |

  **AI가 실재하는 대안을 빠뜨리면 그 자체가 위반이다.** 사람은 제시된 목록 밖의
  선택지를 볼 방법이 없기 때문이다.

- **DB 논리 설계(ERD)와 마이그레이션 SQL은 사람이 확정한다.** AI는 대안 제시와 문서화,
  리뷰를 담당한다. 사람이 구술하고 AI가 옮겨 적는 것은 허용하며, 그 경우 **구술 결정과
  AI 도출을 문서에 구분 표시한다.**
- ADR 작성 기준: **"나중에 바꾸면 여러 파일 / DB / 이미 쌓인 데이터를 손대야 하는가?"** → YES면 작성.
  위치는 `specs/decisions/`, 번호는 프로젝트 전역 연속.
- ADR은 **결정 직후** 작성한다. 사후 배치 작성을 금지한다.

**근거**: 스키마는 이 프로젝트에서 되돌리기 비용이 가장 높은 결정이다. 코드는 다시 쓰면 되지만
스키마는 운영 데이터가 들어 있는 상태에서 바꿔야 한다. 사후에 몰아 쓰면 이미 결과를 아는 상태라
흔들렸던 지점·버린 대안·몰라서 찍은 부분이 지워진다(사후 합리화).

### IV. 에러는 정보를 누수하지 않는다

전역 예외 핸들러 **하나**로 모든 예외를 받고, 두 종류로 가른다:

| | 예 | 응답 | 메시지 |
|---|---|---|---|
| 의도한 실패 | 검증 실패, 권한 없음, 없는 리소스 | 4xx | 노출 가능 |
| 예상 못한 실패 | NPE, DB 다운, SQL 오류 | 5xx | **절대 비노출** |

- 5xx는 `"일시적 오류가 발생했습니다"` + `traceId`만 반환한다. 원본 예외와 스택트레이스는
  **로그에만** 남긴다.
- 응답 포맷은 **RFC 9457 Problem Details + `code`/`traceId` 확장**을 MUST 사용한다.
- **리소스 존재 여부를 노출하지 않는다.** 남의 비공개 리소스 요청은 403이 아니라 404로 응답한다.

**근거**: 프레임워크 기본 동작에 맡기면 테이블명·인덱스명·DB 종류가 그대로 나가고, 최악은
"이 이메일은 이미 가입돼 있다"가 새는 것이다. 이를 반복하면 가입자 명단을 뽑을 수 있다
(계정 열거, account enumeration — 실제 취약점으로 분류된다).

### V. 관측 가능해야 한다

- 앱은 **stdout에만** 쓴다. 파일 생성·롤링·삭제를 앱이 하지 않는다(12-Factor).
  prod는 JSON 1줄, 로컬은 사람이 읽는 텍스트.
- 요청 진입 시 **traceId를 생성해 MDC로** 그 요청의 모든 로그에 박는다.
  원칙 IV의 에러 응답 `traceId`와 **같은 값**이어야 한다.
- **비밀번호·토큰·주민번호·카드번호는 로그에도 남기지 않는다.**

**근거**: traceId가 없으면 동시 요청들의 로그가 뒤섞여 한 요청의 흐름을 재구성할 수 없다.
그리고 응답에서 숨긴 값이 로그에 평문으로 쌓이면 똑같이 유출이다 — 사고의 상당수가
"DB는 안전했는데 로그가 털렸다"이다.

### VI. 스키마 변경은 되돌릴 수 있어야 한다

- 마이그레이션은 **Flyway 버전 파일**로 관리한다.
- `spring.jpa.hibernate.ddl-auto=update`를 **금지**한다. `validate`를 사용한다.
- **이미 적용된 마이그레이션 파일은 수정하지 않는다.** 새 번호를 추가해 고친다.
- 파괴적 변경(삭제·rename·타입 변경)은 **expand-contract로 2회 이상 배포로 분할**해,
  각 단계가 이전 버전 코드와 공존하게 한다.

**근거**: `ddl-auto=update`는 어떤 DDL이 실행될지 알 수 없고, 타입 변경·삭제 시 데이터를 날리며,
롤백 개념이 없다. 적용된 파일을 수정하면 로컬과 프로덕션이 영구히 갈라진다. 그리고 배포에
마이그레이션이 섞여 있으면 코드만 되돌려도 DB는 새 스키마여서 **롤백 버튼이 작동하지 않는다.**

### VII. 시크릿은 커밋되지 않는다

- `.env`는 `.gitignore`. `.env.example`만 커밋한다(키 이름만, 값은 빈칸).
- 배포 환경은 파일이 아니라 **플랫폼 환경변수**를 쓴다.
- 설정 파일(`application.yml` 등)에 값을 **하드코딩 금지**. 환경변수를 참조한다.
- GitHub Push Protection + CI gitleaks로 **커밋 전에** 막는다.

**근거**: git에 한 번 커밋된 시크릿은 지우는 커밋을 올려도 히스토리에 영구히 남는다. 대응 수단이
**키 폐기(rotate)밖에 없다.** 이 프로젝트에서 유일하게 복구 불가능한 실수이므로 사전 차단한다.

### VIII. 게이트는 사람 의지가 아니라 도구가 강제한다

- lint / build / test는 **CI가 돌리고**, 실패 시 브랜치 보호가 머지를 **물리적으로** 막는다.
- **"로컬에서 돌렸고 통과했다"는 보고는 게이트가 아니다.** 검증할 수 없다.
- 사람 게이트는 **스펙 명확화**와 **기능 QA** 두 곳에만 둔다. 그 외에는 도구가 판정한다.
- 사람이 통과시킨 AC는 **자동 테스트로 승격**해 회귀를 사람이 반복하지 않는다.

**근거**: 성실성에 의존하는 것은 게이트가 아니다. 그리고 수동 회귀 확인은 스토리가 쌓이면
붕괴하고(3개 10분 → 15개는 건너뛰게 된다), 건너뛴 순간부터 있으나 마나다.

## 보안 요구사항

원 요구사항 문서가 실서비스 기준에 미달하는 항목이 있다. 아래는 **스펙 단계에서 상향한 결과**이며
개별 스펙이 이를 낮출 수 없다.

| | 규칙 | 근거 |
|---|---|---|
| 비밀번호 저장 | **bcrypt 또는 argon2** (의도적으로 느린 해시). SHA2 등 빠른 해시 **금지**. **DB 함수로 해싱 금지** | 빠른 해시는 GPU로 초당 수십억 시도가 가능해 DB 유출 시 사실상 평문. DB 함수를 쓰면 평문이 SQL 쿼리 로그에 남아 원칙 V와 충돌 |
| 토큰 만료 | 인증 토큰은 **만료 시간이 반드시 있어야 한다.** 무기한 토큰 금지 | 만료가 없으면 한 번 탈취되면 영구 유효하고 폐기 수단이 없다 |
| 토큰 저장 | **`httpOnly` 쿠키.** LocalStorage 금지 | LocalStorage는 JS로 읽히므로 XSS 한 번에 유출된다 |
| 권한 검증 | **반드시 서버에서** 한다 | 화면에서 버튼을 숨기는 것은 권한 검증이 아니다. API를 직접 호출하면 그대로 통과한다 |
| 비밀번호 길이 | 최소 **8자** | — |

## 개발 워크플로 및 품질 게이트

게이트는 순서대로 통과한다. 각 게이트의 종료 조건이 충족되지 않으면 다음으로 넘어가지 않는다.

| 게이트 | 판정자 | 종료 조건 |
|---|---|---|
| 스펙 명확화 | 사람 | 미확정 항목 **0개** |
| DB 논리 설계 검증 | AI 크로스 검증 | APPROVED |
| 계획 크로스 검증 | AI 크로스 검증 | APPROVED |
| 태스크 정합성 검증 | AI 크로스 검증 | APPROVED |
| 코드 크로스 리뷰 | AI (read-only) | APPROVED |
| CI | 도구 | 전부 그린 — **실패 시 머지 물리 차단** |
| 기능 QA | 사람 | **전 AC PASS** |
| 회귀 | 도구 (CI) | 그린 |

**공통 규칙**

- `BLOCKED`의 **필수 수정 항목만** 수정한다. 권고는 판단해서 반영한다.
- **재검증하지 않는다.** 1차 검증의 지적을 반영하면 통과로 본다. `APPROVED` 도장을 받기 위해
  다시 돌리지 않는다. 대가는 **수정이 지적을 제대로 해소했는지 확인되지 않는다**는 것이며,
  이를 줄이기 위해 수정 내역을 문서와 커밋에 남긴다. 상세는 `specs/process.md` 5장.
- **핑퐁 2회 컷.** 그래도 논쟁이 남으면 사람이 판단한다.
- 소규모·저위험 변경(설정·문구·스타일)은 코드 크로스 리뷰를 스킵할 수 있다. 전 태스크 리뷰는 병목이다.
- 기능 QA를 통과한 AC는 같은 PR에서 자동 테스트로 승격한다(원칙 VIII).

## Governance

1. **`specs/process.md`가 단일 진실이다.** 이 constitution은 그 문서의 실행 가능한 요약이다.
   규칙이 바뀌면 **`process.md`를 먼저 고치고** constitution을 동기화한다. 역방향 금지.
2. 모든 스펙·계획은 이 원칙과 대조되어야 한다. 계획 단계의 Constitution Check를 통과하지 못하면
   Phase 0으로 넘어가지 않는다.
3. **원칙을 벗어나려면 그 이유를 ADR로 남긴다**(`specs/decisions/`). 근거 없는 예외는 없다.
   계획 문서의 Complexity Tracking 표에 위반 사항과 기각한 더 단순한 대안을 함께 기록한다.
4. 버전 정책(semantic versioning):
   - **MAJOR** — 원칙 제거 또는 하위 호환 불가한 재정의
   - **MINOR** — 원칙·섹션 신규 추가 또는 실질적 확장
   - **PATCH** — 문구 정리, 오타, 의미가 바뀌지 않는 다듬기
5. 준수 검토: 각 스토리 머지 후 회고(`specs/retrospective.md`)에 **"게이트가 무엇을 잡았고 무엇을
   놓쳤나"** 를 기록한다. 놓친 것이 원칙의 공백이면 이 문서를 개정한다.
