# Quickstart — 001 인증 검증 시나리오

> `/speckit-plan` **Phase 1 산출물.** **9.5 기능 QA가 로컬 프리뷰에서 이 문서를 따라간다**
> (`process.md` 4.5 — *"QA 체크리스트는 새로 만들지 않는다. 스펙의 AC를 그대로 실행한다"*).

**이 문서에 없는 것**: 구현 코드 · 마이그레이션 SQL · 테스트 전문.
**요청/응답 상세는 [`contracts/auth-api.md`](./contracts/auth-api.md)가 단일 진실이며 여기에 복제하지 않는다.**
여기는 **"어떻게 띄우고 무엇을 눌러 확인하는가"** 만 담는다.

**대상 독자**: 9.5 기능 QA를 실행하는 사람(= 나). 그리고 세션이 끊겨 다시 시작하는 나.

## 0. 사전 조건

| | 무엇 | 왜 |
|---|---|---|
| **Docker** | Docker Desktop(또는 동등한 런타임)이 **돌고 있어야 한다** | 로컬 기동과 통합 테스트가 **둘 다** Docker를 쓴다. `test-strategy.md` 5.1의 Testcontainers가 테스트 시작 시 컨테이너를 띄운다 |
| **JDK 25** | Java 25 LTS (`process.md` 6.1) | Gradle 래퍼가 이 버전으로 빌드한다 |
| **Node** | 프론트·E2E 실행용 | `frontend/`가 Next.js다 |
| **`.env`** | `cp .env.example .env` 후 값을 채운다 | `.env`는 **커밋하지 않는다**(원칙 VII). 값이 없으면 앱이 뜨지 않는다 |

`.env`에서 **반드시 채워야 하는 것**:

- `DB_URL` · `DB_USERNAME` · `DB_PASSWORD` — Docker Compose가 띄우는 Postgres를 가리킨다
- `JWT_SECRET` — 충분히 길고 무작위인 값. 사람이 지어낸 문자열을 쓰지 않는다
- `ADMIN_INITIAL_ID` · `ADMIN_INITIAL_PASSWORD` — **US1을 회원가입 없이 검증할 수 있게 하는 값**이다
  (`FR-022` 시작 시 시딩). 이 값이 없으면 아래 시나리오 3을 실행할 수 없다
- 자격증명 수명 · 남용 방어 임계값 키 — 비워두면 기본값을 쓴다. **시나리오 5는 값을 낮춰야
  현실적인 시간에 확인된다**(아래 참조)

> **관리자 초기 비밀번호는 저장소에 어떤 형태로도 남기지 않는다**(`FR-023`, `SC-008`).
> `.env`에만 두고, QA 기록(`qa.md`)에도 옮겨 적지 않는다.

## 1. 로컬 기동

```bash
docker compose up
```

**컨테이너 3개**가 올라온다 — `postgres` · `backend` · `frontend`.
**앱까지 Docker로 띄우는 이유**는 `process.md` 4.5다 — 9.5를 로컬 프리뷰로 내리며
*"내 컴퓨터에서만 된다"를 늦게 발견하는 것*을 완화하기로 했고, 그 조건이 이것이다.

**기동이 성공했다는 신호**

| | 확인 |
|---|---|
| 마이그레이션 | Flyway가 `V1`부터 순서대로 적용한 로그가 보인다 |
| **스키마 ↔ 엔티티 일치** | `ddl-auto=validate`가 통과한다. **어긋나면 부팅이 실패한다** — 이것이 `ADR-004`에서 JPA를 고른 결정적 근거다 |
| 관리자 시딩 | 관리자 계정이 없으면 생성, 있으면 아무 일도 없다(`FR-022` 멱등) |
| 접속 | 브라우저에서 프론트가 열린다. **`/api/*`는 프론트 오리진으로 호출한다** — Next.js rewrite가 백엔드로 넘기므로 브라우저에게는 **오리진이 하나**다(`research.md` 2) |

**정지·초기화**

```bash
docker compose down       # 정지 (데이터 유지)
docker compose down -v    # 볼륨까지 삭제 → 다음 기동에서 마이그레이션이 처음부터 다시 돈다
```

시나리오를 처음부터 다시 밟거나 **마이그레이션이 깨끗한 DB에서 도는지** 확인할 때 `-v`를 쓴다.

## 2. 자동 테스트 실행

```bash
./gradlew test        # 단위 + 통합. Testcontainers가 실제 Postgres 컨테이너를 띄운다
```

- **Docker가 꺼져 있으면 통합 테스트가 실패한다.** 도구 설정 문제이지 코드 결함이 아니다
- 통합 테스트는 `.env`의 `DB_URL`을 **쓰지 않는다** — Testcontainers가 접속 정보를 런타임에
  주입한다(`test-strategy.md` 5.1)
- **Testcontainers 이미지 태그와 Compose 이미지 태그는 같은 값으로 고정**한다
  (`ADR-003` 리스크 2)

```bash
pnpm test:e2e         # frontend/ 에서. @smoke 태그만 돈다
```

- **로컬에서 E2E 전체를 돌리지 않는다**(`test-strategy.md` 4장 규칙 5). 전체는 CI에서 돈다
- 첫 실행 전에 `auth.setup.ts`가 **1회 로그인해 `storageState`를 만든다**(4.1 1단계).
  그 파일은 **자격증명이므로 커밋하지 않는다** — `.gitignore`에 있다

**커버리지**: 게이트는 **AC 커버리지 100%**이고 줄 커버리지는 리포트만 남긴다
(constitution 원칙 II). **테스트 이름의 AC-ID로 센다.**

## 3. AC를 손으로 확인하는 절차 (9.5 기능 QA)

**주요 흐름 6개만 손으로 밟는다.** 나머지는 자동 테스트가 덮는다 —
`plan.md`의 `AC → 테스트 레벨 배정` 표가 어느 AC가 어느 레벨인지 정해뒀고,
**응답·오류코드·경계값은 전부 통합 테스트로 내렸다**(원칙 I).

각 시나리오는 `docker compose down -v` 직후의 **깨끗한 상태**에서 시작하는 것을 기준으로 쓴다.

---

### 시나리오 1 — 가입 → 로그인 → `/api/me`

**덮는 AC**: `AC-8` · `AC-1` · `AC-7`

| | 절차 | 기대 결과 |
|---|---|---|
| 1 | 회원가입 화면에서 아이디 중복확인을 누른다 | 사용 가능으로 응답한다 |
| 2 | 유효한 값으로 가입한다 | 가입이 성공하고 권한은 `USER`다 (`AC-8`) |
| 3 | 사용자 로그인 화면에서 그 계정으로 로그인한다 | 로그인된다 (`AC-1`) |
| 4 | **개발자 도구 → Network → 로그인 응답의 본문**을 본다 | **토큰 문자열이 본문에 없다** (`AC-1`·`FR-013`) |
| 5 | **개발자 도구 → Console에서 `document.cookie`** 를 실행한다 | **자격증명 쿠키가 보이지 않는다** (`AC-7` — `httpOnly`) |
| 6 | 로그인 상태에서 `/api/me`를 호출하는 화면(헤더의 로그인 정보 등)을 본다 | 아이디·이름·권한이 표시된다 |

> **5번이 이 시나리오의 핵심이다.** Network 탭에서는 `Set-Cookie`가 보이지만
> **Console에서 읽히지 않아야** 한다. 둘을 혼동하지 않는다 — 보이는 곳이 다르다.

---

### 시나리오 2 — 로그아웃하면 재발급이 막힌다

**덮는 AC**: `AC-5` (관련: `AC-4`)

**이것이 `ADR-001`에서 Refresh를 DB에 저장하기로 한 이유 그 자체다.**
서버가 Refresh를 보관하지 않으면 **로그아웃이 원리적으로 성립하지 않는다.**

| | 절차 | 기대 결과 |
|---|---|---|
| 1 | 로그인한 상태에서 로그아웃한다 | 자격증명 쿠키가 삭제된다 |
| 2 | 인증이 필요한 화면(`/api/me`를 쓰는 곳)을 다시 열어본다 | 미인증으로 처리된다 |
| 3 | **재발급을 시도한다** — 로그아웃 전 Refresh 쿠키를 되살려 넣거나, 개발자 도구에서 재발급 요청을 다시 보낸다 | **재발급이 거부된다.** `code`는 `AUTH_REFRESH_INVALID` (`AC-5`) |
| 4 | 다시 로그인한다 | 정상 로그인된다 — **계정이 잠기거나 손상되지 않았다** |

> **`AC-4`(Access 만료 후 자동 재발급)는 손으로 확인하기 어렵다.** 기본값이면 30분을 기다려야 한다.
> 통합 테스트가 **수명을 짧게 오버라이드해 검증**하므로(`plan.md` 배정 표) 손으로 밟지 않는다.
> 손으로 보고 싶으면 `.env`의 사용자 Access 수명을 1분 이하로 낮추고, **로그아웃 없이**
> 1분 뒤 화면을 조작해 **재로그인을 요구받지 않는지** 본다.

### 시나리오 3 — 관리자는 별도 진입점으로 로그인한다

**덮는 AC**: `AC-31` · `AC-32` · `AC-33`
**전제**: `.env`의 `ADMIN_INITIAL_*`로 시딩된 관리자 계정. 그리고 시나리오 1에서 만든 `USER` 계정.

| | 절차 | 기대 결과 |
|---|---|---|
| 1 | **사용자 로그인 화면과 관리자 로그인 화면의 경로가 다른지** 확인한다 | **다른 경로**다 (`FR-032`) |
| 2 | 관리자 로그인 화면에서 관리자 계정으로 로그인한다 | 로그인되고 관리자 화면으로 들어간다 (`AC-31`) |
| 3 | 로그아웃하고, **관리자 로그인 화면에** 시나리오 1의 `USER` 계정을 **정확한 비밀번호로** 넣는다 | **로그인이 실패한다** (`AC-32`) |
| 4 | 3번의 응답 메시지를 읽는다 | **`"관리자 권한이 없습니다"` 류가 아니다.** 시나리오 4에서 비교한다 |
| 5 | 관리자로 다시 로그인해 자격증명의 **만료 시각**을 본다(Application → Cookies의 Expires, 또는 재발급이 요구되는 시점) | **관리자 쪽이 사용자보다 짧다** (`AC-33`) |

> **3~4번이 이 시나리오에서 가장 중요하다.** *"관리자가 아니다"* 라고 답하면
> **그 아이디가 존재하고 일반 사용자라는 것**을 알려주게 되어, `AC-3`으로 막은 계정 열거가
> 이 경로로 새 나간다(`FR-034`).

### 시나리오 4 — ★ 실패 응답 3경로가 같은지 눈으로 비교한다

**덮는 AC**: `AC-2` · `AC-3` · `AC-32`
**`plan.md`가 "이 스토리에서 가장 깨지기 쉬운 요구사항"으로 지목한 항목이다.**

세 요청을 **연달아 보내고 응답을 나란히 놓고 본다.**

| | 요청 | 개발자 도구에서 볼 것 |
|---|---|---|
| A | 사용자 로그인에 **존재하는 아이디 + 틀린 비밀번호** | 상태코드 · `code` · `detail` |
| B | 사용자 로그인에 **존재하지 않는 아이디** | 상태코드 · `code` · `detail` |
| C | **관리자 로그인에 `USER` 계정 + 정확한 비밀번호** | 상태코드 · `code` · `detail` |

**기대 결과: A · B · C의 상태코드와 `code`와 `detail` 메시지가 전부 같다.**
`traceId`만 다르다(요청마다 다른 값이므로 정상이다).

> **하나라도 다르면 계정 열거가 뚫린다** — 아이디 존재 여부를 알아내 가입자 명단을 뽑을 수 있다.
> 세 경로는 **서로 다른 예외**에서 나오기 쉬워 핸들러가 다르게 잡을 위험이 크다.
> **각각이 통과해도 서로 다를 수 있으므로 이 비교를 사람이 눈으로 한 번 더 한다** —
> 통합 테스트에도 세 응답을 서로 비교하는 테스트가 따로 있지만, 이 항목은 값이 커서 이중으로 본다.

**응답 시간도 함께 본다.** A와 B의 소요 시간이 크게 다르면 **시간차로도 존재 여부가 새 나간다.**
스펙이 명시한 AC는 아니지만 발견하면 결함으로 올린다.

### 시나리오 5 — 반복 실패가 지연되고 결국 429가 된다

**덮는 AC**: `AC-29` · `AC-30`

**먼저 `.env`의 임계값을 낮추는 것을 권한다.** 기본값(6회 → 429 → 60초 차단)이면
차단이 풀리기를 60초 기다려야 한다.

| | 절차 | 기대 결과 |
|---|---|---|
| 1 | 같은 계정에 **틀린 비밀번호로 연속 로그인**을 시도한다. 매번 응답 시간을 본다 | 초반에는 지연이 없고, **횟수가 늘면서 응답이 점점 늦어진다** (`AC-29`) |
| 2 | 계속 반복한다 | **429**가 되고 `code`는 `AUTH_TOO_MANY_ATTEMPTS` |
| 3 | 차단 시간이 지난 뒤 **올바른 비밀번호로** 로그인한다 | **정상 로그인된다.** **계정이 잠기지 않았다** (`FR-027` MUST NOT) |
| 4 | 중복확인을 짧은 시간에 반복 호출한다 | 허용 빈도를 넘기면 **429** · `code`는 `CHECK_ID_TOO_MANY_REQUESTS` (`AC-30`) |
| 5 | **1·2번을 하는 동안 다른 브라우저 탭에서 다른 화면을 조작한다** | **서비스 전체가 멈추지 않는다** |

> **5번이 왜 있는가.** 응답을 지연시키려고 서버 스레드를 붙잡으면 **방어 장치가 그 자체로
> 서비스 거부 수단이 된다**(`research.md` 6의 함정). 가상 스레드를 켜서 막았고,
> 손으로 확인할 수 있는 유일한 방법이 **지연 중에 다른 요청이 살아 있는지 보는 것**이다.

> **3번이 이 시나리오의 결론이다.** 계정을 잠그면 아이디만 아는 공격자가 타인을 서비스에서
> 쫓아낼 수 있고, 001에는 비밀번호 찾기가 없어 해제 수단도 없다.

### 시나리오 6 — 목적지 복귀와 오픈 리다이렉트 차단

**덮는 AC**: `AC-24` · `AC-34`

| | 절차 | 기대 결과 |
|---|---|---|
| 1 | **로그아웃 상태**로 로그인이 필요한 화면(글 등록 등)에 직접 들어간다 | 로그인 화면으로 이동하고, **주소에 원래 목적지가 담겨 있다** |
| 2 | 그 화면에서 로그인한다 | **원래 가려던 화면으로 이동한다. 홈이 아니다** (`AC-24`) |
| 3 | 로그아웃하고, 주소창에서 **목적지를 외부 주소로 바꿔** 로그인 화면을 연다 | — |
| 4 | 로그인한다 | **그 외부 주소로 이동하지 않는다.** 우리 서비스 안(홈 등)에 머문다 (`AC-34`) |
| 5 | 목적지를 `//다른도메인` · `https:` 로 시작하는 값 등으로도 바꿔 3~4번을 반복한다 | 마찬가지로 이동하지 않는다 — **같은 출처의 상대 경로만 허용**한다 (`FR-035`) |

> **검증이 없으면 피싱 링크가 만들어진다** — 우리 로그인 화면을 거쳐 공격자 사이트로 보내는
> 링크가 성립한다. 사용자는 우리 도메인의 로그인 화면을 봤으므로 의심하지 않는다.
>
> **검증 위치가 화면인 것은 `FR-002`·`FR-019`의 예외가 아니다.** 그 둘은 **입력 검증**과
> **권한 검증**을 서버에서 하라는 것이고, 목적지 이동은 **브라우저가 수행하는 행위**이므로
> 막는 자리도 브라우저 쪽이다(`research.md` 11).

## 4. 이 문서로 확인하지 않는 것

| | 왜 |
|---|---|
| **`AC-25`** (인증 없이 문의게시판 목록 조회) | **001에 문의게시판이 없다. 006에서 검증한다** — `spec.md` AC-25 항목의 표기 참조. 스텁을 만드는 것을 기각했으므로 여기서 누를 대상이 없다 |
| `AC-9` (비밀번호가 평문이 아님) | **DB를 직접 조회해야** 확인된다 → 통합 테스트 |
| `AC-11`~`AC-19` (입력 검증 경계값) | 경계값 8종 × 직접 호출까지라 손으로 밟으면 오래 걸리고 매번 다르게 밟게 된다 → 전부 통합 테스트 |
| `AC-21`~`AC-23` · `AC-26` (권한 401/403/200) | 화면 없이 요청만으로 판정된다 → 통합 테스트 |
| `AC-27` · `AC-28` (`traceId` · 5xx 비노출) | **로그에서 같은 값을 찾는 것까지** 검증해야 한다 → 통합 테스트 |

**손으로 밟을 것과 자동으로 돌릴 것을 가르는 기준은 `process.md` 4.5다** —
*"사람이 돌아다녀야 의미 있는 흐름 → E2E / 응답·권한·경계값 → API 통합 테스트."*

## 5. QA 결과를 어디에 남기나

`specs/001-user-auth/qa.md` (9.5 산출물, `process.md` 3장).
