# API 계약 — 001 인증

> `/speckit-plan` Phase 1 산출물. **AC와 1:1로 대응시킨 계약**이며,
> 7번에서 코덱스가 **이 문서와 `spec.md`만 보고** 테스트를 작성한다(구현 코드를 보지 않는다).

**공통 오류 형식**: RFC 9457 Problem Details + `code`/`traceId` 확장 (`process.md` 4.8)

```json
HTTP 4xx/5xx
Content-Type: application/problem+json
{
  "type": "/errors/<범주>",
  "title": "...",
  "status": 400,
  "detail": "사람이 읽는 메시지",
  "instance": "/api/users",
  "code": "USER_ID_LENGTH_INVALID",
  "traceId": "a3f9c2",
  "errors": [{ "field": "username", "reason": "길이 오류" }]
}
```

**자격증명 전달**: 전부 **`httpOnly` 쿠키**. **응답 본문에 토큰 문자열을 담지 않는다**(`FR-013`·`AC-1`).

| 쿠키 | 담는 것 | 수명 |
|---|---|---|
| Access | JWT (서명만 검증, DB 안 봄) | 사용자 30분 / 관리자 15분 |
| Refresh | **256비트 랜덤 문자열** (DB에 SHA-256 해시로 보관) | 사용자 14일 / 관리자 1일 |

### 쿠키 속성 — 전부 명시한다 *(2026-07-29 추가, 5번 게이트 권고 2)*

> **원문은 `httpOnly` 하나만 적었다.** 나머지 속성은 프레임워크 기본값에 맡겨져 있었고
> **기본값이 우리 요구와 다른 것이 하나 있다(CSRF).**

| 속성 | 값 | 왜 |
|---|---|---|
| `HttpOnly` | **켠다** | `AC-7`·`FR-013`. 스크립트가 읽지 못한다 |
| `Secure` | **켠다** (로컬 http 개발만 예외) | 평문 연결로 쿠키가 나가지 않게 한다. **로컬 예외는 환경변수로 가르고 prod 기본값은 켠 쪽**이다 — 반대로 두면 배포에서 켜는 것을 잊는다 |
| **`SameSite`** | **`Lax`** | **★ 이것이 우리의 CSRF 방어선이다.** 아래 참조 |
| `Path` | Access는 `/`, **Refresh는 재발급·로그아웃 경로에만** | Refresh는 **재발급할 때만** 필요하다. 모든 요청에 실려 다니면 노출 표면이 넓어진다 |
| 삭제할 때 | **설정할 때와 같은 속성**으로 만료시킨다 | 속성이 하나라도 다르면 **브라우저가 다른 쿠키로 보아 지워지지 않는다.** `AC-5`(로그아웃 시 쿠키 삭제)가 조용히 실패하는 대표적 원인 |

**★ CSRF — 쿠키 인증을 고른 결과로 따라오는 것**

`ADR-001`이 자격증명을 **쿠키**에 담기로 했으므로 **브라우저가 요청에 자동으로 붙인다.**
그것이 편한 이유이면서 동시에 **CSRF(다른 사이트가 사용자의 쿠키로 우리 API를 호출)** 가
성립하는 이유다. Authorization 헤더 방식에는 없는 위험이고 **쿠키를 고른 대가**다.

| | 결정 |
|---|---|
| 1차 방어 | **`SameSite=Lax`** — 다른 사이트에서 시작된 **`POST`에는 쿠키가 붙지 않는다.** 001의 상태 변경은 전부 `POST`(가입·로그인·재발급·로그아웃)이므로 이것으로 덮인다 |
| 왜 `Strict`가 아닌가 | `Strict`면 **외부 링크로 우리 사이트에 들어올 때도 쿠키가 안 붙어** 로그인 상태가 아닌 것처럼 보인다. `AC-24`(목적지 복귀)와 부딪힌다 |
| CSRF 토큰 | **001에서는 도입하지 않는다.** `SameSite=Lax` + **상태 변경이 전부 `POST`** + **오리진이 하나**(research.md 2)라 표면이 좁다. **방아쇠: `GET`으로 상태를 바꾸는 엔드포인트가 생기거나, 크로스 오리진 요청이 필요해지는 시점**(다른 도메인의 프론트·네이티브 앱) |
| 정직한 기록 | **스펙에 CSRF를 다루는 AC가 없다.** `SameSite`가 규칙으로 적히지 않았으면 아무도 확인하지 않았을 항목이고, **5번 게이트가 잡았다.** AC로 올리지 않은 이유는 *"다른 사이트에서 요청을 보낸다"* 를 Given/When/Then으로 쓰려면 **두 번째 오리진이 필요**해 001의 테스트 환경 밖이기 때문이다 → **8번 코드 리뷰의 확인 항목**으로 남긴다 |

**오리진**: 브라우저는 항상 프론트 오리진의 `/api/*`를 호출한다.
Next.js rewrite가 백엔드로 넘긴다 → **CORS 설정이 없다**(research.md 2).

> ⚠️ **rewrite의 대가**: 백엔드가 보는 원격 주소가 **프록시 하나**가 된다.
> `AC-30`(중복확인 빈도 제한)이 클라이언트 단위 키를 쓰므로 **`X-Forwarded-For`의 클라이언트
> 홉을 신뢰 경계와 함께 처리해야 한다** — 안 하면 한 사람이 전체를 막는다(research.md 5).

## 1. `POST /api/auth/signup` — 회원가입

**인증**: 불필요

```json
{ "username": "newuser01", "password": "Study1234abcd", "name": "홍길동" }
```

| 응답 | 조건 | `code` | AC |
|---|---|---|---|
| **201** | 성공. 권한은 `USER` | — | `AC-8` |
| 409 | 아이디 중복 (**대소문자 무시**) | `USER_ID_DUPLICATED` | `AC-10` |
| 400 | 아이디 4자 미만 또는 12자 이상 | `USER_ID_LENGTH_INVALID` | `AC-11` |
| 400 | 아이디에 허용되지 않은 문자 | `USER_ID_FORMAT_INVALID` | `AC-12` |
| 400 | 사용불가 아이디 (**대소문자 무시**) | `USER_ID_NOT_ALLOWED` | `AC-13` |
| 400 | 비밀번호 8자 미만 또는 64자 초과 | `USER_PASSWORD_LENGTH_INVALID` | `AC-14`·`AC-15` |
| 400 | 비밀번호가 아이디 문자열을 포함 | `USER_PASSWORD_CONTAINS_ID` | `AC-16` |
| 400 | 같은 문자 3회 이상 연속 | `USER_PASSWORD_REPEATED_CHAR` | `AC-17` |
| 400 | 이름 2자 미만 또는 50자 초과 | `USER_NAME_LENGTH_INVALID` | `AC-18` |

**계약 주의**

- **`AC-19`** — 위 400 응답들은 **화면을 거치지 않은 직접 호출에도 동일**해야 한다.
  화면 검증은 편의일 뿐 **서버가 방어선**이다(`FR-002`)
- **비밀번호 앞뒤 공백을 제거하지 않는다.** 비밀번호의 일부일 수 있다(Edge Cases)
- 길이는 **문자 수**로 센다. 한글·이모지 허용
- **동시 가입 경합**: 같은 아이디로 두 요청이 동시에 오면 하나만 201, 다른 하나는
  409 `USER_ID_DUPLICATED`. **DB 유니크 제약이 판정한다**(코드로 막으면 깨진다 — 3.5 판단)

## 2. `GET /api/auth/check-id?username=<값>` — 중복확인

**인증**: 불필요

| 응답 | 조건 | `code` | AC |
|---|---|---|---|
| 200 | `{ "available": true \| false }` | — | `AC-20` |
| **429** | 분당 10회 초과 (**클라이언트 단위**) | `CHECK_ID_TOO_MANY_REQUESTS` | `AC-30` |

**`AC-20`**: 여기서 `available: false`인 아이디는 **가입에서도 반드시 409**여야 한다.
중복확인을 통과했는데 가입이 실패하면 사용자가 원인을 알 수 없다.

> **이 엔드포인트는 설계상 아이디 존재 여부를 그대로 알려준다.**
> 그래서 빈도 제한이 **필수**다 — 없으면 `AC-3`으로 막은 계정 열거가 이 경로로 뚫린다.

## 3. `POST /api/auth/login` — 사용자 로그인

**인증**: 불필요

```json
{ "username": "hong01", "password": "Study1234abcd" }
```

| 응답 | 조건 | `code` | AC |
|---|---|---|---|
| **200** | 성공. **쿠키 2개 설정. 본문에 토큰 없음** | — | `AC-1` |
| **401** | 비밀번호 틀림 | `AUTH_INVALID_CREDENTIALS` | `AC-2` |
| **401** | 아이디 없음 — **`AC-2`와 완전히 동일** | `AUTH_INVALID_CREDENTIALS` | `AC-3` |
| 429 | 같은 계정 실패 6회 이상 | `AUTH_TOO_MANY_ATTEMPTS` | `AC-29` |

> **`ADMIN` 계정이 이 진입점으로 로그인하면?** — **통과시킨다** *(2026-07-29 — 5번 게이트
> 권고 3. 원문에 명시가 없었다.)* 근거 2개:
> ① `FR-017`이 *"사용자와 관리자는 **하나의 인증 체계**를 사용해야 한다"* 를 MUST로 요구한다.
> `FR-032`가 분리하는 것은 **관리자 진입점**이고 *"사용자 진입점에서 관리자를 막는다"* 는
> 요구가 아니다. ② **막으면 `FR-011` 동일 실패 응답의 네 번째 경로가 생긴다** — 표면이 늘고,
> 늘어난 경로가 갈라지면 `AC-32`로 막은 것이 그쪽으로 샌다.
> **발급되는 자격증명 수명은 계정의 역할 기준**이다(`FR-033`) — 진입점과 무관하게
> `ADMIN` 계정은 짧은 수명을 받는다. **`AC-33`이 "관리자 계정"을 기준으로 쓰였으므로 일치한다.**

### ★ 이 계약의 가장 깨지기 쉬운 부분

**`AC-2`·`AC-3`·`AC-32`의 응답이 같아야 한다.** 메시지: `"아이디 또는 비밀번호를 확인해 주세요"`

**무엇이 같아야 하는지 못박는다** *(2026-07-29 — 5번 게이트 지적 4. 원문은 "상태코드·`code`·
메시지"만 적었고 **비교 대상이 불완전했다.** 전체 응답은 애초에 같을 수 없다 — `traceId`는
요청마다 달라야 하고 `instance`는 관리자 경로에서 다르다.)*

| | 항목 |
|---|---|
| **같아야 한다** | 상태코드(**401**) · `Content-Type` · `type` · `title` · `code` · `detail` · **`errors` 유무**(셋 다 없다) · **쿠키 동작**(셋 다 `Set-Cookie`를 보내지 않는다) · 인증 관련 응답 헤더 |
| **달라도 된다** | `traceId`(요청마다 다른 것이 정상) · `instance`(요청 경로 자체) |

**★ 응답 시간도 같아야 한다**

- **없는 아이디에서도 비밀번호 검증을 똑같이 수행한다** — **고정된 더미 해시**를 상대로
  검증하고 결과를 버린다. 건너뛰면 그 경로만 빨라져 **본문이 같아도 시간차로 존재 여부가 샌다.**
  **Argon2id는 느리므로**(`ADR-005`) 차이가 **더 크게** 드러난다
- **관리자 진입점(4번)은 비밀번호 검증을 먼저 끝내고 그 뒤에 권한을 본다.**
  권한을 먼저 보고 조기 반환하면 `AC-32` 경로가 빨라진다
- 검증은 `quickstart.md` 시나리오 4가 **사람 눈으로** 한다 — 자동으로 시간을 재면 CI에서
  불안정하다(`test-strategy.md` 4장이 `waitForTimeout`을 금지한 것과 같은 이유)

**★ 응답을 만드는 자리는 하나다**

- 하나라도 다르면 **아이디 존재 여부를 알아내 가입자 명단을 뽑을 수 있다**(계정 열거)
- 세 경로는 **서로 다른 예외**에서 나오기 쉽다 → 핸들러가 다르게 잡을 위험이 크다
- **그래서 각각 검증하는 테스트만으로는 부족하고, 세 응답을 서로 비교하는 테스트를 따로 둔다**
- **`@RestControllerAdvice` 하나로는 부족하다** — Security 필터 체인의 401/403은 컨트롤러에
  도달하기 전에 발생한다. **공통 Problem Details 생성기 1개**를 두고
  **`@RestControllerAdvice` · `AuthenticationEntryPoint` · `AccessDeniedHandler` 셋이 공유**한다
  (research.md 15 · `plan.md` Constitution Check 원칙 IV)

**점진적 지연** (`AC-29` · research.md 6): 1~2회 지연 없음 → 3회 1초 → 4회 2초 → 5회 4초 →
6회 이상 429 + 60초 차단. 윈도 15분, **성공 시 즉시 초기화. 계정은 잠기지 않는다.**

## 4. `POST /api/admin/auth/login` — 관리자 로그인 (**별도 진입점**)

**인증**: 불필요. **경로가 사용자와 다르다**(`FR-032`)

| 응답 | 조건 | `code` | AC |
|---|---|---|---|
| **200** | `ADMIN` 계정 성공. **수명이 사용자보다 짧다** | — | `AC-31`·`AC-33` |
| **401** | `USER` 계정이 **정확한 비밀번호로** 시도 | `AUTH_INVALID_CREDENTIALS` | `AC-32` |
| 401 | 비밀번호 틀림 / 아이디 없음 | `AUTH_INVALID_CREDENTIALS` | |

> **`"관리자 권한이 없습니다"` 로 답하면 안 된다.**
> 그 아이디가 **존재하고 일반 사용자라는 것**을 알려주게 되어, `AC-3`으로 막은 계정 열거가
> 이 경로로 새 나간다. **실패는 전부 같은 얼굴이어야 한다**(`FR-034`).
>
> 403이 아니라 **401**인 것도 같은 이유다. 403은 "인증은 됐고 권한이 없다"를 뜻하므로
> 계정이 존재한다는 사실을 노출한다.

## 5. `POST /api/auth/refresh` — 재발급

**인증**: Refresh 쿠키

| 응답 | 조건 | `code` | AC |
|---|---|---|---|
| 200 | 유효. **새 Access 쿠키 설정** | — | `AC-4` |
| **401** | 로그아웃되어 무효화됨. **쿠키 삭제** | `AUTH_REFRESH_INVALID` | `AC-5` |
| 401 | 만료됨 | `AUTH_REFRESH_EXPIRED` | `AC-6` |

**`AC-4`는 사용자가 개입하지 않는다**(`FR-016`) — Access가 만료되면 재발급이 일어나
원래 요청이 성공해야 하고, 사용자는 재로그인을 요구받지 않는다.

### ★ 누가 이 엔드포인트를 부르는가 — **프론트다** *(2026-07-29 — 5번 게이트 지적 2)*

> **원문에 흐름의 주체가 없었다.** 엔드포인트만 있고 *"백엔드가 만료된 Access를 보면 알아서
> 재발급하고 통과시키는지"* 가 정해지지 않아, **`AC-4`의 테스트 레벨도 정할 수 없는 상태**였다.

**결정: 백엔드는 만료된 Access에 대해 그냥 401을 준다. 재발급은 프론트가 부른다.**

```
프론트 → GET /api/me            → 401 AUTH_REQUIRED   (Access 만료)
      → POST /api/auth/refresh  → 200 (새 Access 쿠키)
      → GET /api/me  재시도      → 200
```

**기각한 대안**: 백엔드 필터가 요청 처리 중에 몰래 재발급하고 통과시키는 방식.
그러면 **모든 엔드포인트가 `Set-Cookie`를 보낼 수 있게 되어** 어떤 요청이 인증 상태를
바꿨는지 추적할 수 없고, **동시 요청 경합(요청 5개가 각자 재발급)** 을 다루는 자리가 없다.
그리고 **이 별도 엔드포인트가 정상 흐름에서 쓰이지 않게 된다** — 계약이 이미 프론트 주도를
전제하고 있었고 문장이 없었을 뿐이다.

**프론트 규칙 3개**

| | 규칙 | 없으면 |
|---|---|---|
| 1 | **재시도는 1회만.** 재발급 후에도 401이면 로그인 화면으로 | 무한 루프 |
| 2 | **동시 재발급을 한 번으로 합친다** — 여러 요청이 동시에 401을 받으면 재발급은 한 번만 하고 나머지는 그 결과를 기다린다 | 로그인 1회에 티켓이 여러 개 생기고 티켓 테이블이 부풀어 오른다 |
| 3 | **`/api/auth/refresh` 자신의 401은 재시도하지 않는다** | 1번과 같은 루프 |

→ **`AC-4`는 통합 + E2E 둘 다 필요하다.** 통합은 *"만료 Access → 401 / 유효 Refresh → 200"*
까지만 볼 수 있고, *"사용자가 재로그인을 요구받지 않는다"*(`FR-016`)는 **프론트 재시도까지
포함해야 성립**한다(`plan.md` 배정 표).

**무효화와 만료의 `code`가 다르다** — 전자는 로그아웃, 후자는 시간 경과다.
사용자에게 보여줄 안내가 다르므로 구분한다. *(계정 존재 여부와 무관하므로
`AC-2`/`AC-3` 통일 원칙과 충돌하지 않는다 — 이미 인증된 티켓에 대한 응답이다.)*

## 6. `POST /api/auth/logout` — 로그아웃

**인증**: Access 또는 Refresh 쿠키

| 응답 | 조건 | AC |
|---|---|---|
| 204 | **해당 Refresh만 무효화 + 쿠키 삭제** | `AC-5` · **`AC-35`** |

- **요청한 기기만** 종료한다(Assumptions 4). 다른 기기의 티켓은 유효하다
  → **`AC-35`가 이것을 검증한다**(2026-07-29 신설). `AC-5`만으로는 **로그아웃이 그 계정의
  티켓을 전부 지워도 통과**하므로, *"개별 무효화"*(`FR-014`)가 검증되지 않았다.
  **삭제 대상은 "이 요청이 제시한 Refresh 해시로 찾은 행 하나"** 이고, `유저 참조 = ?` 로
  지우면 안 된다 — 그것이 이 계약에서 가장 틀리기 쉬운 한 줄이다
- **쿠키를 지울 때 설정할 때와 같은 속성**을 쓴다(위 쿠키 속성 표) — 하나라도 다르면
  브라우저가 다른 쿠키로 보아 **지워지지 않는다**
- **이미 발급된 Access는 만료까지 유효하다**(Edge Cases). 재발급이 막히므로
  최대 Access 수명(30분/15분)만큼 뒤에 완전히 차단된다.
  → 즉시 차단이 필요해지면 `ADR-001`을 대체하는 새 결정이 필요하다

| 200 | `{ "username": "...", "name": "...", "role": "USER" }` | — | `AC-4` 검증 대상 |

## 8. `GET /api/admin/me` — 관리자 전용

**인증**: 필요 + **`ADMIN` 권한**

| 응답 | 조건 | `code` | AC |
|---|---|---|---|
| **401** | 미인증 | `AUTH_REQUIRED` | `AC-21` |
| **403** | `USER` 권한 | `AUTH_FORBIDDEN` | `AC-22`·`AC-26` |
| **200** | `ADMIN` 권한 | — | `AC-23` |

**`AC-26`은 `AC-22`와 같은 요청이지만 다른 관점**이다 — *화면에서 버튼을 숨긴 것이
권한 검증이 아니다*를 확인한다. **테스트를 따로 둔다**(원칙 II: 여러 AC를 한 테스트로 뭉치지 않는다).

## 모든 응답에 걸리는 계약

| | 요구 | AC |
|---|---|---|
| `traceId` | **모든 오류 응답**에 포함되고, 같은 요청의 로그를 그 값으로 찾을 수 있다. **Security 필터가 만든 401/403도 포함**한다 — 어댑터 3개가 같은 생성기를 쓰지 않으면 여기서 갈라진다 | `AC-27` |
| 5xx | 일반 안내 메시지 + `traceId`만. **화이트리스트로 규정한다** — 허용 필드(`type`·`title`·`status`·`detail`·`instance`·`code`·`traceId`)만 있고 `detail`은 **고정 안내문과 정확히 일치**해야 한다. 금지 문자열 목록(테이블명·컬럼명 등)은 **적지 않은 것을 놓친다**(예외 클래스명·SQL 조각·파일 경로) | `AC-28` |
| 로그 | 비밀번호 원문·해시 · 자격증명 원문·해시를 **로그에도 남기지 않는다** | `FR-026` · **`AC-36`** |

**`AC-28`이 막는 실제 사고**: 스프링 기본 동작에 맡기면
`Duplicate entry 'kim' for key 'user.uk_user_username'` 이 그대로 나가 **테이블명·인덱스명 +
"이 아이디는 이미 가입돼 있다"** 를 함께 알려준다. `AC-10`의 409는 **우리가 의도한 응답**이고,
이것은 **예기치 못한 예외가 새는 것**이라 다르다.

## 프론트 계약 (화면이 책임지는 것)

| | 요구 | AC |
|---|---|---|
| 쿠키 접근 불가 | 스크립트로 자격증명 쿠키를 읽을 수 없다 | `AC-7` |
| 목적지 복귀 | 미인증으로 인증 필요 화면 진입 → 로그인 후 **원래 화면**으로(홈이 아니다) | `AC-24` |
| **목적지 검증** | **외부 주소를 목적지로 넘기면 그 주소로 이동하지 않는다.** 같은 출처의 상대 경로만 허용 | **`AC-34`** |
| **자동 재발급** | 401을 받으면 `POST /api/auth/refresh` 후 원 요청 **1회** 재시도. 동시 재발급은 한 번으로 합친다 | `AC-4` |

> **`AC-34`의 목적지 판정은 순수 함수로 떼어내 단위 테스트로 변형을 훑는다**
> *(2026-07-29 — 5번 게이트 권고 4)*: 절대 URL(`https://evil.example`) ·
> **스킴 생략 형태(`//evil.example`)** · 역슬래시(`\\evil.example`) · **URL 인코딩된 변형** ·
> `https:` 로 시작하는 값 · 제어문자 포함.
> **`//evil.example`이 특히 걸리기 쉽다** — *"`http`로 시작하지 않으면 상대 경로"* 로 판정하면
> 그대로 통과하는데 브라우저는 이것을 **다른 출처로 해석한다.**
> E2E로 변형 전부를 돌리면 느리고, 판정은 입력·출력이 명확한 순수 함수라 **단위가 맞다**
> (`test-strategy.md` 3장 배정 기준: *"복잡한 계산·검증 로직만 단위"*).

> **`AC-34`의 검증 위치가 화면인 것은 `FR-002`·`FR-019`의 예외가 아니다.**
> 그 두 요구사항은 **입력 검증**과 **권한 검증**을 서버에서 하라는 것이다.
> 목적지 이동은 **브라우저가 수행하는 행위**이므로 막는 자리도 브라우저 쪽이다 —
> 서버는 이동에 관여하지 않으므로 서버에서 막을 대상 자체가 없다.
