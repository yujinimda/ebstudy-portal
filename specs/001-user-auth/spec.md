# 기능 명세: 001 인증 — 회원가입 · 로그인 · 로그아웃 · 권한 기반 접근제어

**브랜치 / 디렉터리**: `001-user-auth`

**작성일**: 2026-07-27 (최종 수정 2026-07-29)

**상태**: 3번 게이트(스펙 검증) 통과 — **미확정 0건**. 3.5 논리 설계 · 3.9 테스트 전략 ·
4번 기술 계획 완료. **4번에서 `AC-34`·`FR-035`가 추가됐다** (Clarifications 2026-07-29).

**규모**: **AC 34개 · FR 35개**. 001에서 검증하는 AC는 **33개** — `AC-25`는 **006에서 검증**한다(해당 항목 참조).

## 개요

게시판 포털의 첫 스토리. 이후 모든 게시판 스토리가 로그인과 권한을 전제하므로
**수직 슬라이스의 첫 줄기**로 인증을 완결한다.

**포함**: 회원가입 · 로그인 · 로그아웃 · 권한 기반 접근제어(미인증 차단, `USER`/`ADMIN` 구분) ·
**관리자 로그인 진입점 분리**(인증 메커니즘은 공유, 진입점과 정책은 분리)

**제외**: 회원정보 수정 · 비밀번호 찾기 · 회원 탈퇴 — 원 요구사항에 화면이 없고 없어도 서비스가 돈다

권한 기반 접근제어를 002로 미루지 않는 이유: 002(자유게시판)에서 "본인 글만 수정" 규칙을 만들 때
인증 코드를 다시 뜯어야 한다. **인증은 "누구인지 아는 것"과 "무엇을 할 수 있는지"가 한 덩어리다.**

> **AC 표기에 대하여**: 본 명세의 AC는 HTTP 상태코드와 오류 코드를 포함한다.
> 일반적인 명세 지침은 구현 세부를 배제하지만, constitution 원칙 II(NON-NEGOTIABLE)가
> **검증 가능한 인수기준**을 요구하고 이 AC들이 그대로 테스트와 QA 체크리스트가 되기 때문이다.
> 상태코드와 오류 코드는 프레임워크가 아니라 **API 계약**이므로 구현 세부가 아니다.
> 프레임워크·라이브러리·DB 종류는 이 문서에 등장하지 않는다.

## Clarifications

### Session 2026-07-27

- Q: 반복 시도 방어(무차별 대입·계정 열거)를 001 범위에 넣을 것인가, 넣는다면 방식은?
  → A: **점진적 지연 + 중복확인 빈도 제한.** 계정 잠금은 사용하지 않는다 — 아이디만 아는
  공격자가 타인의 계정을 잠글 수 있고(서비스 거부), 비밀번호 찾기가 001 범위 밖이라
  해제 수단이 없어 사용자가 영구 차단된다. 분산 공격(IP를 바꿔가며) 대응은 인프라 계층
  몫이므로 4번 계획에서 배포 환경 확정 후 보강한다.

- Q: 사용불가 아이디 목록을 어디에 두고 관리 화면을 001에 포함할 것인가?
  → A: **데이터(테이블)로 두고 관리 화면은 004로 미룬다.** 004가 이미 관리자 화면 스토리이고,
  관리자 화면 골격(좌측 메뉴·목록/등록 레이아웃)이 거기서 만들어진다. 001에 화면 하나만 먼저
  만들면 그 골격을 두 번 만들게 된다. 데이터로 두면 004에서 화면만 얹으면 되고, 하드코딩하면
  나중에 테이블로 옮기는 마이그레이션이 추가로 필요하다.
  초기 목록은 마이그레이션으로 제공한다(예약어는 비밀이 아니므로 커밋해도 안전 — 관리자
  비밀번호와 성격이 다르다).
  *(사용자가 판단을 Claude에 위임)*

- Q: 이름 길이 정책을 원 요구사항(2자 이상 5자 미만)대로 둘 것인가?
  → A: **2자 이상 50자 이하로 완화.** 5자 미만은 4자 성씨(남궁·황보·사공·서문)를 가진 한국
  이름과 외국인 이름을 배제한다. 검토 시 20자를 제시했으나 그것도 `Maria Consuelo Rodriguez`
  (24자)를 막는다. **이름 길이를 좁게 제한해서 얻는 것이 없다** — 저장 비용은 무의미하고
  보안과 무관하며, 막히는 것은 실제 사용자뿐이다.
  *(사용자가 판단을 Claude에 위임)*

- Q: 관리자 로그인을 사용자와 분리해야 하지 않는가? **← 사용자가 체크포인트 리뷰에서 발견한 결함**
  → A: **"따로"에는 두 층이 있고 층마다 답이 다르다.**
  **층 1 — 인증 메커니즘(토큰 발급·검증·해싱·쿠키 정책·Refresh 무효화)은 공유한다.**
  두 벌 만들면 취약점 표면이 두 배이고 한쪽을 고칠 때 다른 쪽을 잊는다. `FR-017` 유지.
  **층 2 — 진입점과 정책은 분리한다.** 이것이 최초 명세에서 빠져 있었다. 근거:
  ① 관리자 화면은 별도 경로이고 일반 사용자에게 노출하지 않는다
  ② 관리자는 위험도가 다르므로 자격증명 수명을 짧게 둔다(원 요구사항이 관리자 세션을
  30분으로 잡은 의도가 이것이다 — 사용자와 같은 14일 Refresh는 과하다)
  ③ 일반 로그인 화면에서 관리자가 로그인해 관리자 화면으로 튕기는 것은 혼란스럽다
  **관리자 로그인에 `USER` 계정이 정확한 비밀번호로 시도하면 로그인 자체를 실패시키되
  응답은 `AC-2`/`AC-3`과 완전히 동일해야 한다** — `"관리자 권한이 없습니다"` 로 답하면
  그 아이디가 존재하고 일반 사용자라는 것을 알려주게 되어 `AC-3`으로 막은 계정 열거가
  이 경로로 새 나간다.
  → `FR-032`~`FR-034`, `AC-31`~`AC-33` 추가. *(사용자 발견 · Claude 판단)*

- Q: 로그인 후 원래 목적지로 복귀시킬 때(`FR-020`·`AC-24`) 그 목적지를 검증해야 하는가?
  → A: **검증해야 한다. `AC-34`와 `FR-035`를 신설한다.** 목적지를 그대로 신뢰하면
  **오픈 리다이렉트 취약점**이 된다 — 외부 주소를 목적지로 넘길 수 있으면 **우리 로그인 화면을
  거쳐 공격자 사이트로 보내는 피싱 링크**가 만들어진다. 사용자는 우리 도메인의 로그인 화면을
  봤으므로 의심하지 않는다. **허용 범위는 같은 출처의 상대 경로뿐이다.**
  검증 위치가 화면인 것은 `FR-002`·`FR-019`의 예외가 아니다 — 그 둘은 **입력 검증**과
  **권한 검증**을 서버에서 하라는 것이고, 목적지 이동은 **브라우저가 수행하는 행위**여서
  서버에는 막을 대상 자체가 없다. *(Claude 발견 — `research.md` 11·12)*

- Q: `AC-25`(인증 없이 문의게시판 목록 조회)를 001에서 어떻게 검증하는가? 문의게시판이 001에 없다.
  → A: **AC 본문을 지우지 않고 "006에서 검증"을 표기하고 커버리지 계산을 006으로 이관한다.**
  문의게시판은 **006 스토리**이고 001에 그 리소스가 없다.
  **스텁(빈 목록을 반환하는 껍데기)을 만드는 것을 기각했다** — 실체가 없는 **테스트를 위한
  코드**이고 006에서 실제로 만들 때 그대로 버려진다. 껍데기를 통과하는 테스트는
  `FR-021`이 실제로 지켜지는지 아무것도 보장하지 않는다.
  **AC를 삭제하지 않는 이유**: `FR-021`은 유효한 요구사항이고, 지우면 006에서 다시 발견해야 한다.
  → 이 이관이 성립하려면 **커버리지 게이트에 규칙이 하나 필요하다** — 없으면 *미룬 AC*와
  *잊은 AC*가 구분되지 않는다. `test-strategy.md` **5.3에 규칙을 추가**했다.
  *(Claude 발견 — `research.md` 12)*

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 로그인 · 로그아웃 (Priority: P1) 🎯 MVP

계정을 가진 사람이 서비스에 들어오고 나갈 수 있다.

**Why this priority**: 인증의 뼈대다. 그리고 **관리자 계정은 시스템이 자동 생성**하므로
회원가입 없이도 독립적으로 검증할 수 있다 — 가장 먼저 완결 가능한 조각이다.

**Independent Test**: 자동 생성된 관리자 계정으로 로그인 → 인증이 필요한 요청 성공 →
로그아웃 → 같은 요청이 거부되는 것 확인.

**Acceptance Scenarios**:

> 원칙 II. `AC-N` ID는 스펙 전체 연속 번호, `Given` 필수.

- **AC-1** 올바른 자격증명으로 로그인
  - **Given** 활성 계정(아이디/비밀번호)이 존재하고 로그아웃 상태이고
  - **When** 그 아이디와 비밀번호로 로그인을 요청하면
  - **Then** 200이고 자격증명이 **`httpOnly` 쿠키로** 전달되며, 응답 본문에 토큰 문자열이 포함되지 않는다

- **AC-2** 비밀번호가 틀린 경우
  - **Given** 활성 계정이 존재하고
  - **When** 올바른 아이디와 **틀린 비밀번호**로 로그인을 요청하면
  - **Then** 401이고 `code=AUTH_INVALID_CREDENTIALS`, 메시지는 `"아이디 또는 비밀번호를 확인해 주세요"`

- **AC-3** 존재하지 않는 아이디 — **AC-2와 응답이 동일해야 한다**
  - **Given** `nosuchuser` 라는 아이디가 존재하지 않고
  - **When** 그 아이디로 로그인을 요청하면
  - **Then** 401이고 `code=AUTH_INVALID_CREDENTIALS` — **AC-2와 상태코드·code·메시지가 모두 같다**
  - *근거*: 응답이 다르면 아이디 존재 여부를 알아내 가입자 명단을 뽑을 수 있다(계정 열거)

- **AC-4** Access 자격증명 만료 후 자동 재발급
  - **Given** 로그인 상태이고 Access 자격증명은 만료되었으나 Refresh 자격증명은 유효하고
  - **When** 인증이 필요한 요청을 보내면
  - **Then** 재발급이 일어나 요청이 성공하고 사용자는 재로그인하지 않는다

- **AC-5** 로그아웃하면 재발급이 차단된다
  - **Given** 로그인 상태이고
  - **When** 로그아웃을 요청한 뒤 이전 Refresh 자격증명으로 재발급을 시도하면
  - **Then** 401이고 `code=AUTH_REFRESH_INVALID`. 쿠키가 삭제된다
  - *근거*: 서버가 Refresh를 보관하는 이유가 이것이다. 보관하지 않으면 로그아웃이 성립하지 않는다

- **AC-6** Refresh 자격증명 만료
  - **Given** Refresh 자격증명이 만료되었고
  - **When** 재발급을 시도하면
  - **Then** 401이고 `code=AUTH_REFRESH_EXPIRED`. 재로그인이 필요하다

- **AC-7** 자격증명이 스크립트로 읽히지 않는다
  - **Given** 로그인이 완료된 브라우저 상태이고
  - **When** 페이지의 스크립트로 자격증명 쿠키를 읽으려 하면
  - **Then** 읽히지 않는다(`httpOnly`)
  - *근거*: 스크립트로 읽히면 XSS 한 번에 자격증명이 유출된다

- **AC-27** 모든 오류 응답에 추적 식별자가 있다
  - **Given** 어떤 이유로든 오류가 발생하는 요청이고
  - **When** 그 요청을 보내면
  - **Then** 응답에 기계가 판별 가능한 오류 코드와 **추적 식별자**가 포함되고,
    같은 요청이 남긴 기록을 그 식별자로 찾을 수 있다
  - *근거*: 사용자가 "이 식별자로 오류가 났다"고 말할 수 있어야 원인을 추적할 수 있다 (FR-024)

- **AC-28** 예기치 못한 오류는 내부 정보를 노출하지 않는다
  - **Given** 서버 내부에서 예기치 못한 오류가 발생하는 상황이고
  - **When** 클라이언트가 응답을 받으면
  - **Then** 500대 상태코드와 일반적인 안내 메시지, 추적 식별자만 포함된다.
    예외 메시지·스택 추적·데이터 구조 정보(테이블명·컬럼명·제약조건명)가 **포함되지 않는다**
  - *근거*: 내부 구조가 새면 공격 표면을 알려준다. 원 요구사항을 그대로 두면
    중복 제약 위반 메시지에 테이블명과 가입 여부가 함께 노출된다 (FR-025)

- **AC-29** 인증 실패가 반복되면 응답이 점진적으로 지연된다
  - **Given** 같은 계정에 대해 인증이 연속으로 실패하고 있고
  - **When** 실패를 반복하면
  - **Then** 실패 횟수가 늘어남에 따라 응답까지 걸리는 시간이 증가하고, 기준을 넘으면
    429와 `code=AUTH_TOO_MANY_ATTEMPTS` 를 반환한다.
    **계정은 잠기지 않으며** 지연 시간이 지난 뒤 올바른 비밀번호로 정상 로그인된다
  - *근거*: 계정을 잠그면 아이디만 아는 공격자가 타인을 서비스에서 쫓아낼 수 있다.
    001에는 비밀번호 찾기가 없어 해제 수단도 없다 (FR-027)

- **AC-31** 관리자는 별도 진입점으로 로그인한다
  - **Given** `ADMIN` 권한 계정이 존재하고 로그아웃 상태이고
  - **When** **관리자 로그인 진입점**으로 그 계정의 아이디와 비밀번호를 요청하면
  - **Then** 200이고 로그인되며, 사용자 로그인 진입점과는 **다른 경로**다

- **AC-32** 관리자 진입점에 일반 사용자 계정 — **AC-2와 응답이 동일해야 한다**
  - **Given** `USER` 권한 계정이 존재하고
  - **When** **관리자 로그인 진입점**으로 그 계정의 아이디와 **정확한 비밀번호**를 요청하면
  - **Then** 401이고 `code=AUTH_INVALID_CREDENTIALS` — **AC-2·AC-3과 상태코드·code·메시지가 모두 같다**
  - *근거*: `"관리자 권한이 없습니다"` 로 답하면 **그 아이디가 존재하고 일반 사용자라는 것을
    알려주는** 셈이다. `AC-3`으로 막은 계정 열거가 이 경로로 새 나간다.
    실패는 전부 같은 얼굴이어야 한다 (FR-034)

- **AC-33** 관리자 자격증명 수명이 사용자보다 짧다
  - **Given** 사용자와 관리자가 각각 로그인했고
  - **When** 두 자격증명의 만료 시각을 비교하면
  - **Then** 관리자의 Access·Refresh 수명이 **사용자보다 짧다**
  - *근거*: 관리자 자격증명 탈취의 피해 범위가 훨씬 크다. 원 요구사항이 관리자 세션을
    30분으로 짧게 잡은 의도가 이것이다 (FR-033)

### User Story 2 - 회원가입 (Priority: P1)

새 사용자가 계정을 만든다.

**Why this priority**: 일반 사용자가 서비스를 쓰려면 계정이 필요하다. US1과 같은 P1이지만
US1이 먼저 완결 가능하므로(관리자 자동 생성) 두 번째에 둔다.

**Independent Test**: 가입 요청 → 성공 응답 → 그 계정으로 US1의 로그인이 되는지 확인.

**Acceptance Scenarios**:

- **AC-8** 유효한 입력으로 가입
  - **Given** `newuser01` 이 존재하지 않고 사용불가 목록에도 없고
  - **When** 아이디 `newuser01`, 비밀번호 `Study1234abcd`, 이름 `홍길동` 으로 가입을 요청하면
  - **Then** 201이고 계정이 생성되며 권한은 `USER` 다

- **AC-9** 저장된 비밀번호는 평문이 아니다
  - **Given** AC-8로 계정이 생성되었고
  - **When** 저장된 사용자 데이터를 조회하면
  - **Then** 입력한 비밀번호 문자열이 그대로 저장되어 있지 않고 되돌릴 수 없는 형태로 저장되어 있다

- **AC-10** 중복 아이디
  - **Given** `existuser` 아이디가 이미 존재하고
  - **When** 같은 아이디로 가입을 요청하면
  - **Then** 409이고 `code=USER_ID_DUPLICATED`

- **AC-11** 아이디 길이 미달 / 초과
  - **Given** 가입 요청을 준비했고
  - **When** 아이디가 3자(`abc`) 또는 12자 이상(`abcdefghijkl`)이면
  - **Then** 400이고 `code=USER_ID_LENGTH_INVALID` (허용: 4자 이상 12자 미만)

- **AC-12** 아이디에 허용되지 않은 문자
  - **Given** 가입 요청을 준비했고
  - **When** 아이디를 `user@01` 로 요청하면
  - **Then** 400이고 `code=USER_ID_FORMAT_INVALID` (영문·숫자 포함, `-`와 `_` 외 특수문자 불가)

- **AC-13** 사용불가 아이디
  - **Given** `admin` 이 사용불가 아이디 목록에 있고
  - **When** 그 아이디로 가입을 요청하면
  - **Then** 400이고 `code=USER_ID_NOT_ALLOWED`

- **AC-14** 비밀번호 최소 길이 미달
  - **Given** 가입 요청을 준비했고
  - **When** 비밀번호를 7자로 요청하면
  - **Then** 400이고 `code=USER_PASSWORD_LENGTH_INVALID` (허용: 8자 이상 64자 이하)

- **AC-15** 비밀번호 최대 길이 초과
  - **Given** 가입 요청을 준비했고
  - **When** 비밀번호를 65자로 요청하면
  - **Then** 400이고 `code=USER_PASSWORD_LENGTH_INVALID`

- **AC-16** 비밀번호가 아이디와 같은 문자열을 포함
  - **Given** 아이디를 `newuser01` 로 입력했고
  - **When** 비밀번호를 `newuser01xyz` 로 요청하면
  - **Then** 400이고 `code=USER_PASSWORD_CONTAINS_ID`

- **AC-17** 같은 문자 3회 이상 연속
  - **Given** 가입 요청을 준비했고
  - **When** 비밀번호를 `aaabcdefgh` 로 요청하면
  - **Then** 400이고 `code=USER_PASSWORD_REPEATED_CHAR`

- **AC-18** 이름 길이 위반
  - **Given** 가입 요청을 준비했고
  - **When** 이름을 1자 또는 51자로 요청하면
  - **Then** 400이고 `code=USER_NAME_LENGTH_INVALID` (허용: 2자 이상 50자 이하 — FR-029 참조)
  - *참고*: 4자 성씨(남궁·황보)를 가진 한국 이름과 외국인 이름이 통과해야 한다.
    `남궁민수`(4자), `Maria Consuelo Rodriguez`(24자)는 정상 가입된다

- **AC-19** 화면 검증을 우회한 직접 호출도 차단된다
  - **Given** 화면을 거치지 않고 가입 요청을 직접 보낼 수 있는 상태이고
  - **When** AC-11 ~ AC-18의 위반 값을 담아 직접 요청하면
  - **Then** 각 AC와 **동일한** 상태코드와 code로 거부된다
  - *근거*: 화면 검증만 있으면 직접 호출로 전부 우회된다. 화면 검증은 사용자 편의이고
    **서버 검증이 실제 방어선**이다

- **AC-20** 중복확인 결과와 가입 결과가 일치한다
  - **Given** `existuser` 가 이미 존재하고
  - **When** 중복확인을 요청하면
  - **Then** 사용 불가로 응답하고, 같은 아이디로 가입을 시도하면 AC-10과 동일하게 거부된다
  - *근거*: 중복확인을 통과했는데 가입이 실패하면 사용자가 원인을 알 수 없다

- **AC-30** 중복확인 남용은 차단된다
  - **Given** 짧은 시간에 중복확인을 반복 호출하는 클라이언트가 있고
  - **When** 허용 빈도를 넘겨 호출하면
  - **Then** 429와 `code=CHECK_ID_TOO_MANY_REQUESTS` 를 반환한다
  - *근거*: 중복확인은 설계상 아이디 존재 여부를 그대로 알려준다. 제한이 없으면
    `AC-3`으로 막은 계정 열거가 이 경로로 뚫려 가입자 명단을 뽑을 수 있다 (FR-030)

### User Story 3 - 권한 기반 접근제어 (Priority: P2)

권한에 맞는 것만 할 수 있다.

**Why this priority**: US1·US2가 있어야 검증 가능하다. 다만 002로 미루면 002에서 인증 코드를
다시 뜯어야 하므로 001 안에서 완결한다.

**Independent Test**: `USER` 계정과 `ADMIN` 계정으로 각각 관리자 기능을 호출해 한쪽만
통과하는지 확인.

**Acceptance Scenarios**:

- **AC-21** 미인증 사용자의 관리자 기능 접근
  - **Given** 로그인하지 않은 상태이고
  - **When** 관리자 전용 기능을 요청하면
  - **Then** 401이고 `code=AUTH_REQUIRED`

- **AC-22** 일반 사용자의 관리자 기능 접근
  - **Given** `USER` 권한으로 로그인한 상태이고
  - **When** 관리자 전용 기능을 요청하면
  - **Then** 403이고 `code=AUTH_FORBIDDEN`

- **AC-23** 관리자의 관리자 기능 접근
  - **Given** `ADMIN` 권한으로 로그인한 상태이고
  - **When** 관리자 전용 기능을 요청하면
  - **Then** 200이고 정상 처리된다

- **AC-24** 미로그인 상태에서 로그인이 필요한 동작 → 로그인 후 원래 목적지로 복귀
  - **Given** 로그인하지 않은 상태로 로그인이 필요한 화면(예: 글 등록) 진입을 시도했고
  - **When** 로그인 화면으로 이동해 로그인을 완료하면
  - **Then** 로그인 직후 **원래 가려던 화면**으로 이동한다(홈이 아니다)

- **AC-25** 로그인이 필요하지 않은 조회 — ⚠️ **006(문의게시판)에서 검증한다**
  - **Given** 로그인하지 않은 상태이고
  - **When** 문의게시판 목록 조회를 요청하면
  - **Then** 200이고 목록이 반환된다
  - **검증 스토리**: **006 문의게시판.** 001에는 문의게시판 리소스가 없으므로 001의 AC 커버리지
    계산에서 제외하고 **006으로 이관**한다. *(Clarifications 2026-07-29 · `test-strategy.md` 5.3)*
  - *스텁을 기각한 이유*: 빈 목록을 반환하는 껍데기를 001에 만들면 **실체가 없는 테스트용 코드**이고
    006에서 실제로 만들 때 그대로 버려진다. 껍데기를 통과하는 테스트는 `FR-021`이 실제로
    지켜지는지 아무것도 보장하지 않는다
  - *AC를 지우지 않는 이유*: `FR-021`은 유효한 요구사항이다. 지우면 006에서 같은 것을 다시 발견해야 한다

- **AC-26** 화면에서 감춘 기능도 서버가 막는다
  - **Given** `USER` 권한으로 로그인했고 화면에는 관리자 버튼이 보이지 않고
  - **When** 그 기능을 직접 요청하면
  - **Then** AC-22와 동일하게 403이고 `code=AUTH_FORBIDDEN`
  - *근거*: 화면에서 버튼을 숨기는 것은 권한 검증이 아니다

- **AC-34** 로그인 후 복귀할 목적지가 외부 주소면 그 주소로 이동하지 않는다
  - **Given** 로그아웃 상태이고 로그인 화면에 복귀 목적지가 **외부 주소**(다른 출처)로 지정되어 있고
  - **When** 로그인을 완료하면
  - **Then** **그 외부 주소로 이동하지 않는다.** 같은 출처의 상대 경로만 목적지로 허용되며,
    허용되지 않는 목적지는 무시하고 기본 화면으로 이동한다
  - *근거*: 목적지를 검증하지 않으면 **오픈 리다이렉트 취약점**이 된다. 외부 주소가 통하면
    **우리 로그인 화면을 거쳐 공격자 사이트로 보내는 피싱 링크**를 만들 수 있고, 사용자는
    우리 도메인의 로그인 화면을 봤으므로 의심하지 않는다. `AC-24`(원래 목적지 복귀)가
    이 위험을 만들었으므로 같은 스토리에서 막는다 (FR-035)
  - *참고*: 검증 위치가 화면인 것은 `FR-002`·`FR-019`의 예외가 아니다. 그 둘은 **입력 검증**과
    **권한 검증**을 서버에서 하라는 것이고, 목적지 이동은 **브라우저가 수행하는 행위**여서
    서버에는 막을 대상 자체가 없다

---

### Edge Cases

- **관리자 계정 초기 생성**: 관리자가 없을 때만 자동 생성되고 **이미 있으면 아무 일도 일어나지
  않는다**(여러 번 시작해도 안전). 초기 비밀번호는 소스 저장소에 남지 않는다.
- **동시 가입 경합**: 같은 아이디로 두 요청이 동시에 도착하면 하나만 성공하고 다른 하나는
  AC-10과 같이 거부된다. 중복확인 통과와 실제 가입 사이에 시간차가 있기 때문이다.
- **로그아웃 후 남은 Access 자격증명**: 로그아웃 직후에도 이미 발급된 Access 자격증명은 만료까지
  유효하다. 재발급이 막히므로 최대 Access 수명만큼 뒤에 완전히 차단된다.
  → 즉시 차단이 필요해지면 `ADR-001`을 대체하는 새 결정이 필요하다.
- **비밀번호의 공백·유니코드**: 앞뒤 공백을 제거하지 않는다(비밀번호의 일부일 수 있다).
  한글·이모지도 허용하며 길이는 문자 수로 센다.
- **쿠키를 차단한 클라이언트**: 인증이 성립하지 않는다. 오류 메시지로 안내한다.

## Requirements *(mandatory)*

### Functional Requirements

**회원가입**

- **FR-001**: 시스템은 아이디·비밀번호·이름으로 사용자 계정을 생성해야 한다(MUST).
- **FR-002**: 시스템은 모든 입력 검증을 **서버에서** 수행해야 한다(MUST). 화면 검증은 추가일 뿐 대체가 아니다.
- **FR-003**: 시스템은 아이디를 4자 이상 12자 미만, 영문·숫자를 포함하고 `-`·`_` 외 특수문자를 허용하지 않도록 검증해야 한다(MUST).
- **FR-004**: 시스템은 사용불가 아이디 목록에 포함된 아이디의 가입을 거부해야 한다(MUST).
- **FR-028**: 사용불가 아이디 목록은 **코드가 아니라 데이터로** 관리해야 한다(MUST). 초기 목록은 마이그레이션으로 제공한다. **운영자용 관리 화면은 001 범위 밖이며 004(관리자 화면) 스토리에서 제공한다.** *(Clarification 2026-07-27)*
- **FR-005**: 시스템은 아이디 중복을 거부해야 한다(MUST).
- **FR-006**: 시스템은 비밀번호를 8자 이상 64자 이하로 검증해야 한다(MUST).
- **FR-007**: 시스템은 아이디와 동일한 문자열을 포함하는 비밀번호, 같은 문자가 3회 이상 연속되는 비밀번호를 거부해야 한다(MUST).
- **FR-029**: 시스템은 이름을 **2자 이상 50자 이하**로 검증해야 한다(MUST). *(Clarification 2026-07-27 — 원 요구사항 "2자 이상 5자 미만"에서 완화. 4자 성씨를 가진 한국 이름과 외국인 이름이 배제되고, 이름 길이를 좁게 제한해 얻는 것이 없다)*
- **FR-008**: 시스템은 비밀번호를 **되돌릴 수 없는 느린 해시**(bcrypt 또는 argon2)로 저장해야 한다(MUST). 빠른 해시 및 데이터베이스 함수를 이용한 해싱을 금지한다(MUST NOT). *(constitution 보안 요구사항)*
- **FR-009**: 시스템은 중복확인 결과와 실제 가입 결과가 일치하도록 해야 한다(MUST).

**로그인 · 로그아웃**

- **FR-010**: 시스템은 아이디와 비밀번호로 인증해야 한다(MUST).
- **FR-011**: 인증 실패 시 시스템은 **아이디 존재 여부를 구분할 수 없는 동일한 응답**을 반환해야 한다(MUST). 상태코드·오류 코드·메시지가 모두 같아야 한다.
- **FR-012**: 시스템은 인증 성공 시 수명이 짧은 Access 자격증명과 수명이 긴 Refresh 자격증명을 발급해야 한다(MUST). 둘 다 만료 시간을 가져야 하며 무기한 자격증명을 금지한다(MUST NOT). *(constitution 보안 요구사항)*
- **FR-013**: 시스템은 자격증명을 `httpOnly` 쿠키로 전달해야 한다(MUST). 응답 본문에 토큰 문자열을 담거나 스크립트가 접근 가능한 저장소에 두는 것을 금지한다(MUST NOT). *(constitution 보안 요구사항)*
- **FR-014**: 시스템은 Refresh 자격증명을 서버 측에 보관해 **개별 무효화가 가능**해야 한다(MUST).
- **FR-015**: 로그아웃 시 시스템은 해당 Refresh 자격증명을 무효화하고 쿠키를 삭제해야 한다(MUST).
- **FR-016**: Access 자격증명이 만료되고 Refresh 자격증명이 유효하면 시스템은 사용자 개입 없이 재발급해야 한다(MUST).

**권한**

- **FR-017**: 시스템은 사용자에게 `USER` 또는 `ADMIN` 권한을 부여해야 한다(MUST). 사용자와 관리자는 **하나의 인증 체계**를 사용해야 한다(MUST).
- **FR-018**: 시스템은 관리자 전용 기능을 미인증(401)과 `USER` 권한(403)으로부터 차단해야 한다(MUST).
- **FR-019**: 모든 권한 검증은 **서버에서** 이루어져야 한다(MUST). 화면에서 요소를 숨기는 것은 검증으로 간주하지 않는다.
- **FR-020**: 로그인이 필요한 화면에 미인증으로 진입하면 로그인 화면으로 이동시키고, 로그인 완료 후 **원래 목적지**로 복귀시켜야 한다(MUST).
- **FR-035**: `FR-020`의 복귀 목적지는 **같은 출처의 상대 경로만** 허용해야 한다(MUST). 다른 출처를 가리키는 목적지로 이동하는 것을 금지하며(MUST NOT), 허용되지 않는 값은 무시하고 기본 화면으로 이동한다. *(Clarification 2026-07-29 — 검증하지 않으면 **오픈 리다이렉트**가 되어 우리 로그인 화면을 거쳐 공격자 사이트로 보내는 피싱 링크가 만들어진다. `FR-020`이 이 위험을 만들었으므로 같은 스토리에서 막는다)*
- **FR-021**: 문의게시판 목록 조회는 인증을 요구하지 않아야 한다. *(검증은 006 문의게시판 스토리 — `AC-25` 참조)*

**관리자 계정 · 진입점**

- **FR-032**: 관리자 로그인 진입점은 사용자와 **분리**해야 한다(MUST). 관리자 화면은 별도 경로 아래 두고 일반 사용자에게 노출하지 않는다. *(체크포인트 리뷰 2026-07-27)*
- **FR-033**: 관리자 자격증명(Access·Refresh)의 수명은 **사용자보다 짧아야 한다**(MUST). 구체 값은 4번 계획에서 확정한다. *(관리자 자격증명 탈취의 피해 범위가 크다)*
- **FR-034**: 관리자 로그인 진입점은 `ADMIN` 권한만 통과시켜야 한다(MUST). **`USER` 계정이 정확한 비밀번호로 시도해도 실패시키며, 실패 응답은 `FR-011`(아이디 존재 여부 구분 불가)을 그대로 따라야 한다**(MUST) — 권한 부족을 알려주면 그 아이디가 존재하고 일반 사용자라는 것을 노출하게 된다.
- **FR-022**: 관리자 계정은 가입 화면을 제공하지 않아야 한다(MUST NOT). 시스템 시작 시 환경 설정값으로 관리자 계정이 없을 때만 생성해야 하며 반복 실행해도 안전해야 한다(MUST).
- **FR-023**: 관리자 초기 비밀번호는 **소스 저장소에 어떤 형태로도 남지 않아야 한다**(MUST NOT). 해시된 값도 포함한다. *(constitution 원칙 VII — 저장소가 공개이므로)*

**오류 응답 · 로깅**

- **FR-024**: 모든 오류 응답은 프로젝트 공통 오류 형식을 따르고 기계가 판별 가능한 오류 코드와 추적 식별자를 포함해야 한다(MUST). *(constitution 원칙 IV)*
- **FR-025**: 예기치 못한 오류의 내부 정보(예외 메시지·스택 추적·데이터 구조)를 클라이언트에 노출하는 것을 금지한다(MUST NOT). *(constitution 원칙 IV)*
- **FR-026**: 비밀번호·자격증명을 로그에 남기는 것을 금지한다(MUST NOT). *(constitution 원칙 V)*

**남용 방어** *(Clarification 2026-07-27)*

- **FR-027**: 시스템은 같은 계정에 대한 인증 실패가 반복될수록 응답을 **점진적으로 지연**시켜야 한다(MUST). **계정 잠금 방식은 사용하지 않는다(MUST NOT)** — 아이디만 아는 공격자가 타인의 계정을 잠글 수 있고(서비스 거부), 비밀번호 찾기가 001 범위 밖이라 해제 수단이 없어 사용자가 영구 차단된다.
- **FR-030**: 시스템은 아이디 중복확인 요청의 **빈도를 제한**해야 한다(MUST). 중복확인은 설계상 아이디 존재 여부를 알려주므로, 제한이 없으면 `FR-011`(인증 실패 응답 통일)로 막은 계정 열거가 이 경로로 그대로 뚫린다.
- **FR-031**: 지연·빈도 제한이 발동해 요청이 거부되면 시스템은 429 상태코드와 기계가 판별 가능한 오류 코드를 반환해야 한다(MUST).

> **범위 경계**: IP를 바꿔가며 분산 시도하는 공격은 애플리케이션 안에서 막을 수 없다.
> 인프라 계층(리버스 프록시·WAF) 몫이며 배포 환경이 미정이므로 **4번 계획에서 보강**한다.
> 001은 "같은 계정·같은 클라이언트의 반복"까지를 책임진다.

> **미확정 항목 없음.** 3번 게이트(스펙 검증) 종료 조건 충족 —
> Clarifications의 **Session 2026-07-27**(4건)과 **Session 2026-07-29**(2건) 참조.

### Key Entities

- **사용자(User)**: 서비스를 이용하는 주체. 아이디(고유), 비밀번호(되돌릴 수 없는 형태), 이름,
  권한(`USER`/`ADMIN`), 생성 시각. 아이디는 변경하지 않는다.
- **Refresh 자격증명(Refresh Credential)**: 재발급 티켓. 소유 사용자, 만료 시각, 무효화 여부.
  **개별 삭제가 가능해야 하며 이것이 로그아웃의 근거다.**
- **사용불가 아이디(Reserved Identifier)**: 가입을 거부할 아이디 목록. → FR-028

> 구체적인 데이터 구조·관계·제약은 **3.5 DB 논리 설계**에서 사람이 직접 작성한다
> (constitution 원칙 III).

## Success Criteria *(mandatory)*

- **SC-001**: 사용자는 가입을 **2분 이내**에 완료할 수 있다.
- **SC-002**: 입력이 규칙에 어긋나면 사용자는 **어느 항목이 왜 잘못됐는지** 알 수 있다.
- **SC-003**: 로그인한 사용자는 Access 자격증명 만료를 **체감하지 못한다** — 이용 중 재로그인을 요구받지 않는다(Refresh 유효 기간 내).
- **SC-004**: 로그아웃한 사용자는 이전 자격증명으로 **재발급을 받을 수 없다**.
- **SC-005**: 인증 실패 응답만으로는 특정 아이디의 가입 여부를 **알아낼 수 없다**.
- **SC-006**: 화면을 거치지 않고 직접 요청해도 모든 검증과 권한 규칙이 동일하게 적용된다 — **화면 검증 우회로 통과하는 경로가 0건**이다.
- **SC-007**: 저장된 데이터가 전부 노출되어도 **비밀번호 원문을 되돌릴 수 없다**.
- **SC-008**: 관리자 초기 비밀번호가 소스 저장소 이력에 남은 건수가 **0건**이다.
- **SC-009**: 오류가 발생하면 사용자는 문의에 쓸 **추적 식별자**를 받고, 운영자는 그것으로 원인 기록을 찾을 수 있다.
- **SC-010**: 권한이 없는 요청은 **100%** 서버에서 거부된다.

## Assumptions

원 요구사항에 없거나 불명확해 합리적 기본값을 택한 항목이다. 4번 계획에서 확정되거나 뒤집힐 수 있다.

1. **자격증명 수명** — 사용자와 관리자를 다르게 가정한다 (`FR-033`)

   | | Access | Refresh |
   |---|---|---|
   | 사용자 | 30분 | 14일 |
   | **관리자** | **15분** | **1일** |

   실무 범위: Access 15분~1시간, Refresh 7~30일. 관리자는 그 범위의 짧은 쪽에 둔다.
   구체 값은 4번 계획에서 확정한다. AC는 "만료되었을 때"의 동작과 "관리자가 더 짧다"는
   관계만 규정하므로 값이 바뀌어도 AC는 유지된다.
2. **아이디 대소문자**: 구분하지 않는다고 가정한다 — `User01`과 `user01`은 같은 계정이며 중복으로
   처리한다. 구분하면 사용자가 자기 아이디를 잘못 기억해 로그인에 실패하는 일이 늘어난다.
3. **동시 로그인**: 같은 계정으로 여러 기기에서 동시 로그인이 가능하다고 가정한다. 기기 수 제한
   요구는 없었다.
4. **로그아웃 범위**: 로그아웃은 **요청한 기기만** 종료한다(전체 기기 로그아웃 아님).
5. **아이디 변경 불가**: 가입 후 변경하지 않는다. 원 요구사항에 변경 화면이 없다.
6. **비밀번호 재사용 제한 없음**: 회원정보 수정이 001 범위 밖이다.
7. **이메일·연락처 없음**: 원 요구사항의 가입 항목은 아이디·비밀번호·이름뿐이다. 따라서
   **비밀번호 찾기가 원리적으로 불가능**하며 별도 스토리에서 다룬다.

## Dependencies

- **선행**: 없음. 001이 첫 스토리다.
- **후행**: 002 이후 모든 게시판 스토리가 이 스토리의 인증·권한에 의존한다.
- **결정 의존**: `ADR-001`(인증 방식). 데이터 구조는 3.5 DB 논리 설계에서 확정.

전체 기기 로그아웃 · 로그인 이력 조회 · 관리자 계정 추가 생성 화면 ·
**사용불가 아이디 목록 관리 화면**(→ 004 관리자 화면 스토리) ·
