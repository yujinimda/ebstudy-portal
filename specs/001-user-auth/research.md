## 1. ORM — Spring Data JPA, 보조 조회 도구는 미룬다

**결정**: 기본 **Spring Data JPA(Hibernate)**. **복잡한 조회 도구(QueryDSL·JOOQ·MyBatis)는 추가하지 않고
필요해지는 시점까지 미룬다.** → **`ADR-004`**

**결정적 근거 → 보조 근거로 강등** *(2026-07-29, 5번 게이트 codex 지적 3)*

> **⚠️ 이 절의 근거는 5번 게이트에서 강등됐다.** 아래 원문의 논리는 **순환에 가깝다** —
> 규칙(`ddl-auto=validate`)이 ORM보다 먼저 쓰였고 **한쪽을 전제한 상태**였는데,
> 그 규칙을 결정의 **결정적 근거**로 썼다. codex가 독립적으로 같은 판정을 냈다.
>
> **JPA 채택은 유지되고 근거만 바뀐다.** 독립 근거 3개:
> ① 스프링 생태계 표준 — `@Id @GeneratedValue`가 `ADR-002`의 자동증가 숫자 PK와 맞물린다
> ② 자료·예제의 양 — 막혔을 때 찾을 것이 있는 것은 학습 단계에서 실질 비용이다
> ③ **001이 전부 단건 조회·삽입**이라 JPA의 약점(복잡한 조회)이 발동하지 않는다
>
> **`validate`는 "JPA를 골랐으니 따라오는 보조 안전망"** 이다. 규칙 쪽도 함께 고쳤다 —
> `process.md` 4.7과 constitution 원칙 VI(**1.4.0**)에서 조건부 항목으로 내렸으므로
> **이 순환은 구조적으로 재발하지 않는다.** 상세는 `ADR-004` 강등 주석.

**(원문 — 고치지 않고 남긴다)** `constitution` 원칙 VI와 `process.md` 4.7이
**`ddl-auto=validate`를 규칙으로 박아뒀다**:

> `ddl-auto=validate`로 둔다. 테이블을 만들지는 않지만 **"엔티티와 실제 스키마가 어긋났다"를
> 앱 부팅 때 잡아준다.** 공짜 안전망.

**`ddl-auto`는 JPA/Hibernate 기능이다.** MyBatis에는 대응 기능이 없다.
→ MyBatis를 고르면 **원칙 VI를 개정하고 그 안전망을 포기**해야 한다.

이 안전망이 특히 중요한 이유: 6.7에서 **마이그레이션 SQL을 사람이 손으로 쓴다.**
손으로 쓴 스키마와 자바 엔티티가 어긋나는 것이 **실제로 일어날 종류의 실수**이고,
`validate`가 그것을 **부팅 시점에** 잡는다. 런타임에 쿼리가 터지는 것보다 훨씬 이르다.

**기각한 대안**

| | 기각 이유 |
|---|---|
| **MyBatis** | *(2026-07-29 정정)* ~~`ddl-auto` 대상 기능이 없어 **원칙 VI 개정 + 안전망 포기**가 필요하다~~ → **원칙 VI가 조건부가 되었으므로 개정이 필요하지 않다.** MyBatis에는 비교할 *"엔티티 스키마"* 자체가 없어 그 자리를 **실제 DB에 붙는 통합 테스트**가 메운다(우리는 이미 그것을 주력으로 쓴다). **실제 기각 근거는 위 독립 근거 ①②③** 이다. 논리가 약한 대안은 아니었다 — *모든 SQL이 눈에 보인다*는 점은 `ADR-003`에서 대소문자 무시를 `LOWER()` 인덱스로 고른 이유(*"규칙이 스키마에 보이게"*)와 같은 취향의 연장이고, **그 취향을 이긴 것은 생태계 표준성과 자료의 양이었다** |
| Spring Data JDBC | 배울 것이 적고 SQL에 가깝지만 **`ddl-auto`가 없고** 실무 사례·자료가 적다. 막혔을 때 찾을 것이 적은 것은 학습 단계에서 실질 비용이다 |
| JPA + 보조 도구를 **지금** 함께 도입 | **001에 복잡한 조회가 없다.** 목록·검색·페이징이 없고 전부 단건 조회·삽입이다. 쓰지 않을 도구를 지금 넣으면 배울 것만 늘어난다 (YAGNI) |

**받아들인 대가 (명시)**

1. **학습 곡선이 크다** — 영속성 컨텍스트 · 지연 로딩 · N+1 문제. JPA를 "SQL을 안 써도 되는 도구"로
   이해하면 반드시 사고가 난다
2. **SQL이 자동 생성되어 눈에 안 보인다** — 학습 목표와 부딪히는 지점이다
   → 완화 두 가지: **① `local`·`test` 프로필에서 SQL 로깅을 켜서 생성된 SQL을 항상 본다.
   ② 통합 테스트가 실제 DB에 실제 SQL을 날리므로**(`test-strategy.md` 1장)
   **생성된 SQL이 실물로 검증된다.** 목(mock)으로 발랐으면 이 완화가 불가능했다
   - ⚠️ *(2026-07-29 정정 — 5번 게이트 codex 지적 8)* 원문은 `show-sql` **상시**였다.
     **prod에서 켜면 constitution 원칙 V와 충돌한다** — Hibernate `show-sql`은
     `System.out`으로 **직접** 쓰므로 JSON 1줄 구조화 로깅을 우회하고 `traceId`가 붙지 않는다.
     파라미터 로깅까지 켜면 **비밀번호가 로그에 새는 경로**가 된다(원칙 V 마스킹 위반 ·
     `AC-36`이 이것을 검증한다). → **prod에서는 끈다.** 학습 목적은 `local`·`test`에서
     전부 달성된다 — SQL을 보는 것은 개발 중의 일이다

**미룬 것의 방아쇠**: **002 자유게시판의 목록 + 검색 + 페이징**에서 판단한다.
그때 JPA만으로 불편한지가 실측된다. 지금 추측으로 도구를 고르지 않는다.

**`FR-032`(진입점 분리)가 경로 구조로 드러난다.** 같은 앱이지만 `/login`과 `/admin/login`이
다른 화면이고, 관리자 영역은 `/admin` 아래에만 있다.

### ★ 파생 결정 — 백엔드를 Next.js 뒤로 프록시한다

Next.js(Node)와 백엔드(자바)는 **다른 프로세스**다. 그러면 브라우저 입장에서 오리진이 둘이 되고,
**`httpOnly` 쿠키를 쓰는 우리 설계(`FR-013`)에 문제가 생긴다.**

**결정: Next.js의 rewrite로 `/api/*`를 백엔드로 넘긴다.** 브라우저에게는 **오리진이 하나**다.

| | 프록시 없이 (포트 둘) | **프록시 (채택)** |
|---|---|---|
| CORS 설정 | **필요** — `credentials` 허용 + 오리진 명시 | **불필요** |
| 쿠키 | 로컬에선 동작한다(쿠키는 포트를 구분하지 않는다). **배포에서 도메인이 갈리면 그때 깨진다** | 처음부터 같은 오리진 |
| 배포 시 | 오리진 구성을 다시 설계 | **그대로 간다** |

**"로컬에서는 되는데 배포에서 깨지는" 대표적 지점**이라 처음부터 프록시로 둔다.
`process.md` 6.2에서 호스팅을 미루기로 하며 *"로컬도 Docker로 띄워 이식성을 유지한다"* 고 한 것과
같은 성격의 판단이다.

**부수 이득**: `test-strategy.md` 4.1의 E2E `storageState`가 **오리진 하나만 다루면 되어 단순해진다.**

## 3. 티켓 식별 값 — 256비트 랜덤 문자열, DB에는 SHA-256 해시

**결정**: `SecureRandom` 256비트 → Base64url 문자열을 쿠키로. **DB에는 SHA-256 해시만** 저장.

**JWT를 쓰지 않는 근거**는 `data-model.md`에 이미 있었다 —
*"Refresh는 어차피 DB를 확인하므로 JWT일 필요가 없다."*
JWT로 만들면 **크기만 커지고 서명 검증 비용이 추가**되는데, 그 검증으로 얻는 것(DB 없이 판정)을
우리는 애초에 쓰지 않는다. 게다가 JWT 내용은 누구나 읽을 수 있어 담을 것도 없다.

### 왜 비밀번호는 bcrypt인데 티켓은 SHA-256인가

**뒤집힌 것처럼 보이므로 근거를 남긴다.**

| | 비밀번호 | 티켓 식별 값 |
|---|---|---|
| 값의 출처 | **사람이 만든다** → 추측 가능, 사전 공격 가능 | **256비트 난수** → 추측 불가 |
| 해시가 느려야 하나 | **✅ 느려야 한다** — 무차별 대입을 비싸게 만드는 것이 목적 | ❌ 느릴 이유가 없다. 대입할 공간이 없다 |
| 조회 방식 | `username`으로 행을 찾고 **그 행의 해시와 비교** | **해시로 행을 찾아야 한다** |

**결정적인 것은 마지막 줄이다. bcrypt는 솔트가 매번 달라서 같은 입력이 매번 다른 해시가 된다.**
그래서 `WHERE 해시 = ?` 로 **조회할 수가 없다.** 티켓은 해시로 찾아야 하므로 bcrypt를 쓸 수 없다.

SHA-256이면 같은 입력이 항상 같은 해시이므로 **유일 인덱스를 걸어 바로 찾을 수 있다.**
`data-model.md`가 티켓 식별 값에 유일 제약을 준 것과 맞아떨어진다.

## 5. 실패 횟수 저장 — 서버 메모리

**결정**: 서버 메모리(만료 기능이 있는 인메모리 캐시). **Redis를 도입하지 않는다.**

**근거**: `process.md` 6.2에서 호스팅을 미루고 로컬 우선으로 가면서 **서버가 1대로 확정**됐다.
`data-model.md`는 이미 *"실패 횟수는 사라지면 카운트가 0으로 돌아갈 뿐 → 영속 불필요"* 로 판정했다.
1대인데 Redis를 넣으면 **운영 대상이 하나 늘고 배울 것도 늘 뿐 얻는 것이 없다.**

**카운터는 둘이다** (`data-model.md` codex 권고 반영):

| 카운터 | 키 | 근거 |
|---|---|---|
| 인증 실패 횟수 | **계정 단위**(`username` 소문자 정규화) | `FR-027` 특정 계정을 노린 시도를 늦춘다 |
| 중복확인 호출 횟수 | **클라이언트 단위**(요청 출처 주소) | `FR-030` 계정이 특정되지 않은 열거를 막는다 |

### ★ 캐시에 상한을 둔다 — 방어 장치가 메모리 고갈 수단이 되지 않게

*(2026-07-29 추가 — 5번 게이트 codex 지적 5)*

만료만 있고 **최대 크기가 없으면** 공격자가 **매번 다른 `username`** 으로 실패를 쌓아
**만료 전까지 키를 무한히 늘릴 수 있다.** `research.md` 6의 함정(*"방어 장치가 그 자체로
서비스 거부 수단이 된다"*)과 **같은 종류의 문제**이고, 그 함정을 적으면서 이쪽을 놓쳤다.

| | 규칙 |
|---|---|
| **최대 엔트리 수** | 두 캐시 모두 **상한을 둔다.** 넘으면 **LRU로 퇴거**한다 |
| 상한을 넘었을 때의 성질 | **퇴거된 키는 카운트가 0으로 돌아간다** — 즉 상한을 넘는 규모의 공격에서는 지연 방어가 약해진다. **약해지는 쪽을 고른다** — 서버가 죽는 것보다 낫다 |
| 값 | **환경변수**(원칙 VII). 구체값은 7번에서 정한다 — 지금 정하면 추측이다 |

**★ 프록시 뒤에서 "요청 출처 주소"가 무엇인지 정해야 한다** *(codex 지적 5)*

`research.md` 2에서 **Next.js rewrite로 백엔드를 프록시**하기로 했다. 그러면 백엔드가 보는
원격 주소는 **전부 프록시 하나의 주소**다. 즉 **중복확인 빈도 제한(`AC-30`)이 전 사용자를
한 키로 묶어** 한 사람이 10회를 쓰면 모두가 막힌다 — **방어가 아니라 장애**가 된다.

| | 규칙 |
|---|---|
| 클라이언트 식별 | 프록시가 넘긴 **`X-Forwarded-For`의 클라이언트 홉**을 쓴다 |
| **신뢰 경계** | **신뢰할 프록시를 명시적으로 지정**한다. 지정 없이 헤더를 신뢰하면 **공격자가 헤더를 위조해 빈도 제한을 무력화**한다 — 방어가 있으나 마나가 된다 |
| 백엔드 직접 접근 | Docker Compose에서 **백엔드 포트를 호스트로 열지 않는다.** 프론트만 열고 백엔드는 내부 네트워크에 둔다 — 프록시를 우회하면 위 신뢰 경계가 무의미해진다 |
| 인증 실패 카운터 | **영향 없다.** 계정 단위로 키잉하므로 출처 주소를 쓰지 않는다 |

**받아들인 대가**: **서버를 재시작하면 카운터가 0으로 돌아간다.** 배포할 때마다 방어가 초기화된다.
공격자가 배포 시점을 알 수 없고 재시작이 잦지 않으므로 감수한다.
**방아쇠: 서버가 2대 이상이 되는 시점**(각 서버의 메모리가 갈라져 방어가 무의미해진다).
호스팅 방아쇠(`process.md` 6.2)와 같은 시점이다.

## 6. 남용 방어 임계값

### 인증 실패 — 점진적 지연 (`FR-027`·`AC-29`)

| 누적 실패 | 응답 |
|---|---|
| 1~2회 | 지연 없음 |
| 3회 | 1초 지연 |
| 4회 | 2초 지연 |
| 5회 | 4초 지연 |
| **6회 이상** | **429 `AUTH_TOO_MANY_ATTEMPTS`**, 60초간 차단 |

- 카운터 윈도: 15분. **로그인 성공 시 즉시 초기화**
- **계정은 잠기지 않는다**(`FR-027` MUST NOT). 차단 시간이 지나면 올바른 비밀번호로 정상 로그인된다

### ★ 함정 — "지연"이 그 자체로 공격 도구가 된다

응답을 지연시키려고 **서버 스레드를 붙잡고 기다리면**, 공격자가 일부러 실패를 쌓아
**스레드를 고갈시킬 수 있다.** 방어 장치가 서비스 거부 수단이 되는 것이다.

**대응 1 — 가상 스레드를 켠다**(`spring.threads.virtual.enabled=true`).
가상 스레드는 기다리는 동안 **OS 스레드를 점유하지 않는다.**

> **Java 25를 고른 것이 여기서 값을 한다.** 가상 스레드는 Java 21+ 기능이고
> `process.md` 6.1에서 25를 고른 이유는 지원 기간이었는데, **이 결정이 부수적으로
> OS 스레드 고갈을 막아준다.** 21로 갔어도 됐고 17이었으면 안 됐다.

### ⚠️ 정정 — 가상 스레드만으로는 해소되지 않는다

*(2026-07-29, 5번 게이트 codex 지적 5. 원문은 *"가상 스레드를 켜서 막았다"* 로 **끝났고
그것이 과한 주장이었다.**)*

가상 스레드가 해소하는 것은 **OS 스레드 고갈 하나**다. 지연 중에도 계속 점유되는 것이 있다:

| 계속 점유되는 것 | 그래서 무엇이 문제인가 | 대응 |
|---|---|---|
| **DB 커넥션** | 지연이 **트랜잭션 안**에서 일어나면 커넥션과 잠금을 붙잡는다. 커넥션 풀은 **가상 스레드와 무관하게 유한**하므로 **가상 스레드가 이것을 막아주지 않는다** — 오히려 스레드 제한이 사라져 **동시에 더 많은 요청이 풀을 두드린다** | **★ 지연은 트랜잭션 밖에서 한다.** 계정 조회·비밀번호 검증·카운터 갱신을 먼저 끝내고 **트랜잭션을 닫은 뒤** 응답 직전에 지연한다 |
| HTTP 커넥션 · 요청 메모리 | 커넥션 수 상한에 걸리면 정상 사용자가 연결하지 못한다 | 서버 커넥션 상한을 명시적으로 두고, **차단 상태(6회 이상)에서는 지연 없이 즉시 429**를 준다 — 차단된 요청까지 붙잡을 이유가 없다 |
| 카운터 캐시 키 | 위 5번의 상한·퇴거 규칙 | 위 5번 참조 |

**지연을 어떻게 구현하고 어떻게 테스트하나**

`plan.md`의 원래 배정은 *"지연 시간은 주입 가능한 시계로 검증"* 이었는데 **이것은 성립하지 않는다** —
`Clock`은 *"지금 몇 시인가"* 를 바꿀 뿐 **실제로 기다리는 행위를 대체하지 못한다.**

| | 규칙 |
|---|---|
| 추상화 | **지연을 담당하는 인터페이스를 따로 둔다**(*"얼마나 지연할지 계산"* 과 *"실제로 지연"* 을 분리). 테스트는 **계산**을 단위로 검증하고, **실제 대기는 테스트에서 무동작 구현으로 갈아 끼운다** |
| 통합 테스트가 보는 것 | 지연 시간의 정확한 초가 아니라 **① 횟수에 따라 계산된 지연이 증가하는가 ② 6회에서 429 · `AUTH_TOO_MANY_ATTEMPTS` 인가 ③ 차단이 풀린 뒤 정상 로그인되는가**(`AC-29`) |
| 왜 실제 시간을 재지 않나 | *"4초 걸렸는가"* 를 CI에서 재면 **느리고 불안정한 테스트**가 된다. `test-strategy.md` 4장이 `waitForTimeout`을 금지한 것과 같은 이유다 |

### 중복확인 빈도 제한 (`FR-030`·`AC-30`)

- **분당 10회**, 초과 시 **429 `CHECK_ID_TOO_MANY_REQUESTS`**

**받아들인 대가**: 회사·학교처럼 **여러 사람이 출처 주소를 공유하는 환경에서는 카운터도 공유**된다.
남의 호출 때문에 막힐 수 있다. 그래서 임계값을 너무 낮추지 않았다.
근본 해결은 출처 주소 단위 방어를 인프라 계층으로 올리는 것이고, 스펙이 이미
**IP 단위 분산 공격을 범위 밖**으로 명시했다.

## 13. 비밀번호 해싱 — **Argon2id** (bcrypt에서 변경)

**결정**: **Argon2id.** `FR-008`이 허용하는 두 후보(bcrypt / argon2) 중 argon2를 고른다.
→ **`ADR-005`**

**왜 바꿨나 — bcrypt가 스펙과 충돌한다.**

**bcrypt는 입력을 72바이트에서 자른다.** 그런데 스펙은 비밀번호를 **64자**까지 허용하고
**한글·이모지를 허용**하며 **길이를 문자 수로 센다**(Edge Cases). UTF-8에서 한글은 3바이트다.

```
한글 24자 → 72바이트 (경계)
한글 64자 → 192바이트 ← 스펙이 허용하는 값. 앞 24자만 쓰인다
```

**결정적인 것은 강도가 아니라 정확성이다.** 앞 72바이트가 같고 뒤가 다른 두 비밀번호는
bcrypt에게 **같은 입력**이다 → *"틀린 비밀번호로 로그인이 성공하는 입력이 존재한다"* →
**`AC-2`가 거짓이 된다.** 감수 대상이 아니다.

**Argon2id를 고른 이유**: 입력 길이 제한이 없고, **`FR-008`이 이미 허용하므로 스펙을 고치지
않고 해소되는 유일한 선택지**다. 기각한 대안(길이를 바이트로 재정의 / SHA-256 전처리 후
bcrypt / 절단을 감수)의 근거는 `ADR-005`.

**미확정 하나**: **Argon2 파라미터(메모리·반복·병렬도)** 는 하드웨어에 따라 달라 **7번에서
실측**한다. **환경변수로 둔다**(원칙 VII). 너무 높으면 로그인 경로가 6번의 지연과 겹쳐
**두 번 비싸진다** — 가상 스레드는 **대기**에는 듣지만 **해시 계산(CPU 점유)** 에는 듣지 않는다.

## 14. `AC-4` 자동 재발급을 **누가** 하는가 — 프론트가 한다

*(codex 지적 2 — 계약에 엔드포인트만 있고 **흐름의 주체가 없었다.**)*

**결정**: **프론트가 401을 받고 `POST /api/auth/refresh`를 호출한 뒤 원래 요청을 1회 재시도한다.**
백엔드는 만료된 Access로 온 요청을 **그냥 401로 응답한다** — 몰래 재발급해 통과시키지 않는다.

| | 프론트 주도 (**채택**) | 백엔드 필터가 투명하게 재발급 |
|---|---|---|
| 백엔드 책임 | 401을 주는 것까지 | 요청 처리 중에 쿠키를 갈아끼우고 계속 진행 |
| `Set-Cookie` 시점 | 재발급 응답에서 한 번 | **아무 요청에나 섞여 나갈 수 있다** |
| 문제 | 프론트에 재시도 로직이 필요하다 | **모든 엔드포인트가 인증 상태를 바꿀 수 있게 된다.** 어떤 요청이 쿠키를 갱신했는지 추적이 어렵고, 재발급 실패·경합(동시 요청 5개가 각자 재발급)을 다루는 자리가 없다 |

**채택 근거**: 계약에 **이미 별도 엔드포인트가 있다.** 백엔드가 투명하게 처리하면 그 엔드포인트가
정상 흐름에서 쓰이지 않는다 — **설계가 이미 프론트 주도를 전제하고 있었고 문장이 없었을 뿐이다.**
그리고 **재발급은 상태를 바꾸는 동작**이므로 명시적인 한 곳에 두는 것이 `ADR-001`의
*"로그아웃을 성립시키려고 Refresh를 서버에 둔다"* 는 통제 방향과 맞다.

**규칙 3개**

1. **재시도는 1회만.** 재발급 후에도 401이면 **로그인 화면으로 보낸다**(무한 루프 금지)
2. **동시 요청 중복 재발급 방지** — 여러 요청이 동시에 401을 받으면 **재발급을 한 번만** 하고
   나머지는 그 결과를 기다린다. 안 하면 로그인 1회에 티켓이 여러 개 생긴다
3. **`/api/auth/refresh` 자신의 401은 재시도하지 않는다**

**`AC-4`의 테스트 레벨이 바뀐다** — `plan.md` 배정 표 참조. 백엔드 통합 테스트는
*"만료된 Access는 401 · 유효한 Refresh로 재발급되면 200"* 까지만 검증할 수 있고,
**"사용자가 재로그인을 요구받지 않는다"(`FR-016`)는 프론트 재시도까지 포함해야 성립**하므로
**E2E가 함께 필요하다.**

## 15. 실패 응답 3경로 동일성 — **무엇을 비교하는지 못박는다**

*(codex 지적 4 — 계획이 *"상태코드·code·메시지가 같다"* 로만 적어 **비교 대상이 불완전**했다.)*

`AC-2`·`AC-3`·`AC-32`는 **전체 응답이 완전히 같을 수 없다** — `traceId`는 요청마다 달라야 하고
`instance`(요청 경로)는 관리자 경로에서 다르다. **그러면 무엇이 같아야 하는지 정의가 필요하다.**

| | 비교 대상 |
|---|---|
| **같아야 한다** | 상태코드 · `Content-Type` · `type` · `title` · `code` · `detail` · `errors` **유무**(셋 다 없어야 한다) · 인증 관련 헤더·쿠키의 동작(**셋 다 쿠키를 설정하지 않는다**) |
| **달라도 된다** | `traceId`(요청마다 다른 것이 정상) · `instance`(요청 경로 자체) |

**★ 응답 시간도 같아야 한다 — 없는 아이디에서도 해시 검증을 수행한다**

아이디가 없을 때 **비밀번호 검증을 건너뛰면** 그 경로만 빨라진다. **본문이 같아도 시간차로
아이디 존재 여부가 새 나간다** — `AC-3`이 막으려던 것이 측정으로 뚫린다.
느린 해시(Argon2id)를 쓰기로 했으므로 **차이가 오히려 크게 드러난다.**

| | 규칙 |
|---|---|
| 아이디가 없을 때 | **고정된 더미 해시**를 상대로 검증을 **똑같이 수행**하고 결과를 버린다 |
| 관리자 진입점에 `USER` 계정 | **비밀번호 검증을 먼저 끝내고** 그 뒤에 권한을 보아 **같은 실패로 매핑**한다. 권한을 먼저 보고 조기 반환하면 그 경로가 빨라진다 |
| 검증 | `quickstart.md` 시나리오 4가 **A·B의 소요 시간을 눈으로 비교**한다. 자동 테스트로 시간을 재는 것은 CI에서 불안정하므로 **사람이 보는 항목으로 남긴다** |

**★ `@RestControllerAdvice` 하나로는 부족하다**

`plan.md`가 *"전역 예외 핸들러 하나로 단일화"* 라고 적었지만, **Spring Security 필터 체인의
401/403은 컨트롤러에 도달하기 전에 발생**하므로 `@RestControllerAdvice`가 잡지 못한다.
그대로 두면 **`AC-21`·`AC-22`의 응답이 다른 오류들과 형식이 갈린다**(`traceId` 누락 등).

| | 규칙 |
|---|---|
| **공통 Problem Details 생성기를 하나 둔다** | 오류 응답을 만드는 **유일한 자리**. 아래 셋이 **모두 이것을 공유**한다 |
| 세 진입점 | ① `@RestControllerAdvice`(컨트롤러 이후) ② `AuthenticationEntryPoint`(401) ③ `AccessDeniedHandler`(403). JWT 검증 필터의 오류도 ②로 보낸다 |
| 원칙과의 관계 | constitution 원칙 IV의 *"전역 예외 핸들러 **하나**"* 는 **응답 형식이 한 곳에서 결정된다**는 뜻이다. 스프링에서 그것을 실현하는 형태가 **생성기 1개 + 어댑터 3개**다 — 위반이 아니라 **구현 형태**다 |

**`AC-28`은 화이트리스트로 검증한다** — *"테이블명·컬럼명·제약조건명 문자열이 없다"* 는
블랙리스트는 **적지 않은 것을 놓친다**(예외 클래스명·SQL 조각·파일 경로 등).
→ **5xx 응답이 허용된 필드만 갖고 `detail`이 고정 안내문과 정확히 일치하는지** 검증한다.
