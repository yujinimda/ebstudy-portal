## Summary

**만들 것**: 아이디·비밀번호로 가입하고 로그인하며, `USER`/`ADMIN` 권한에 따라 접근이 갈리는
인증 체계. **관리자는 진입점과 자격증명 수명을 분리**한다(메커니즘은 공유).

**기술 접근**: `httpOnly` 쿠키로 전달하는 **짧은 Access(JWT) + 긴 Refresh(랜덤 문자열, DB 보관)**.
Refresh를 DB에 두는 이유는 **로그아웃을 성립시키기 위한 것 하나**다(`ADR-001`).
모든 검증·권한 판정은 서버에서 하고, 실패 응답은 **아이디 존재 여부를 구분할 수 없게 통일**한다.

**이 스토리를 관통하는 설계 축**: **실패는 전부 같은 얼굴이어야 한다.**
`AC-2`(틀린 비밀번호) · `AC-3`(없는 아이디) · `AC-32`(관리자 진입점에 `USER` 계정)가
**상태코드·오류코드·메시지가 모두 같아야** 한다. 계정 열거를 막는 것이 이 스토리의
가장 깨지기 쉬운 요구사항이고, 세 경로 중 하나만 달라도 뚫린다.

## Constitution Check

*GATE: Phase 0 이전 통과 필수. Phase 1 이후 재검토.*

**현행 constitution 기준**(버전은 `.specify/memory/constitution.md` 하단 참조 — 이 문서에

위반이 있으면 Complexity Tracking 표에 근거를 적고 ADR을 남긴다.

- [x] **I. 테스트 우선** — 7번 레인에서 **코덱스가 스펙만 보고 테스트를 먼저 작성**하고
      클코가 통과시킨다. 밀집도는 통합 주력이며 **응답·오류코드·권한·경계값을 전부 통합
      테스트로 내렸다**(아래 테스트 배정 표). E2E는 **6개**로 5~10개 범위 안이다.
- [x] **II. 검증 가능한 인수기준 + 커버리지 게이트** — AC 37개 전부 `Given/When/Then + AC-ID`다.
      **AC 하나당 테스트 하나 이상**을 배정했고 묶음 AC(`AC-19`)는 **참조하는 `AC-11`~`AC-18`
      각각에 따로** 잡았다. **줄 커버리지 숫자 게이트를 세우지 않았다**(리포트만).
      → `AC-25`는 001에 리소스가 없어 **006에서 검증하도록 명시 이관**한다(research.md 12).
      → **5번 게이트에서 AC 없는 FR 3건이 드러나 `AC-35`·`AC-36`·`AC-37`을 신설했다**
      (`FR-014` 개별 무효화 · `FR-026` 로그 마스킹 · `FR-022` 시딩 멱등성).
      **"AC가 없으면 커버리지 분모에 들어가지 않으므로 아무도 세지 않는다"** 가 이 3건을
      찾아낸 기준이다 — 원칙 II를 원칙 II로 검사한 셈이다.
- [x] **III. 사람이 하는 결정** — 논리 설계는 3.5에서 사람이 작성 완료.
      **마이그레이션 SQL은 6.7에서 사람 단독**으로 배정됐다.
      되돌리기 비용이 큰 결정에 ADR 4건(`ADR-001`~`004`).
- [x] **IV. 에러 누수 차단** — **공통 Problem Details 생성기 1개**가 오류 응답을 만드는
      유일한 자리이고, **어댑터 3개**(`@RestControllerAdvice` · `AuthenticationEntryPoint` ·
      `AccessDeniedHandler`)가 그것을 공유한다. 예외 2분류(4xx 노출 / 5xx 비노출).
      RFC 9457 + `code`/`traceId`.
      → *(5번 게이트 지적 4)* 원문은 *"`@RestControllerAdvice` 하나로 단일화"* 였는데
      **Security 필터 체인의 401/403은 컨트롤러 전에 발생해 Advice가 잡지 못한다.**
      그대로 두면 `AC-21`·`AC-22`의 응답 형식이 갈린다. 원칙 IV의 *"핸들러 **하나**"* 는
      **응답 형식이 한 곳에서 결정된다**는 뜻이므로 생성기 1개 + 어댑터 3개가 그 실현 형태다.
      **`AC-28`은 화이트리스트로 검증한다** — 금지 문자열 목록(블랙리스트)은 적지 않은 것을
      놓치므로, **5xx 응답이 허용된 필드만 갖고 `detail`이 고정 안내문과 일치하는지** 본다.
- [x] **V. 관측 가능성** — stdout JSON 로깅, MDC `traceId`(오류 응답과 동일 값 — `AC-27`),
      **비밀번호·토큰 마스킹**(`FR-026`) → **`AC-36`이 이것을 직접 검증한다**(신설).
      **SQL 로깅은 `local`·`test` 프로필에서만 켠다** — `show-sql`은 `System.out`으로 직접 써서
      JSON 구조화를 우회하고, 파라미터까지 켜면 비밀번호가 로그에 샌다 *(5번 게이트 지적 8)*.
- [x] **VI. 되돌릴 수 있는 스키마** — Flyway 버전 파일, **앱이 DDL을 실행하지 않음**,
      적용된 파일 수정 금지. JPA를 쓰므로 **`ddl-auto=validate`** 를 보조 안전망으로 둔다.
      → *(5번 게이트 지적 7)* 원문은 *"`validate`가 `ADR-004`에서 JPA를 고른 **결정적 근거**"*
      였는데 **그 근거는 순환에 가까웠다**(규칙이 ORM보다 먼저, JPA를 전제한 상태로 쓰였다).
      규칙 쪽을 고쳤다 — `process.md` 4.7과 constitution 원칙 VI(**1.4.0**)에서 `validate`를
      **조건부 항목**으로 내렸고, JPA 채택 근거는 `research.md` 1의 독립 근거 3개로 옮겼다.
      001은 신규 테이블 생성만이라 **파괴적 변경이 없어** expand-contract가 발동하지 않는다.
- [x] **VII. 시크릿** — `.env.example`에 키 이름만. `JWT_SECRET` · `ADMIN_INITIAL_*` ·
      DB 접속 정보 + 이번에 추가하는 수명·임계값 키. **설정 파일에 하드코딩 없음**(`${KEY}` 참조).
- [x] **VIII. 도구가 강제하는 게이트** — CI에 `build` / `test`(단위+통합) / `e2e`(@smoke) /
      `coverage-report` 잡을 추가하고 **필수 상태 체크에 등록**한다.
      사람 게이트는 스펙 명확화·기능 QA 둘만 유지(늘리지 않음).
- [x] **보안 요구사항** — **Argon2id**(빠른 해시·DB 함수 금지 — 원 요구사항의 `SHA2()`를 8.2에서
      기각), Access·Refresh 둘 다 만료 있음, `httpOnly` 쿠키, 권한은 서버 검증,
      비밀번호 최소 8자.
      → *(5번 게이트 지적 3)* **원문은 bcrypt였고 스펙과 충돌했다.** bcrypt는 입력을
      **72바이트에서 자르는데** 스펙은 비밀번호 **64자 + 한글·이모지**를 허용한다(한글 1자 =
      3바이트 → 64자 = 192바이트). 앞 72바이트가 같은 두 비밀번호가 **같은 입력**이 되어
      *"틀린 비밀번호로 로그인이 성공하는 입력이 존재"* 하게 되고 **`AC-2`가 거짓이 된다.**
      `FR-008`이 argon2를 이미 허용하므로 **스펙을 고치지 않고 해소된다** → **`ADR-005`**.
      → **티켓 식별 값에 SHA-256(빠른 해시)을 쓰는 것이 예외처럼 보이지만 아니다.**
      보안 요구사항은 **비밀번호** 해싱을 규정한다. 티켓은 256비트 난수라 무차별 대입 대상이
      아니고, **bcrypt는 솔트가 매번 달라 조회에 쓸 수 없다**(research.md 3).

**결과: 위반 0건.** Complexity Tracking 비움.

## AC → 테스트 레벨 배정

`test-strategy.md` 3장의 배정 기준을 적용했다. **AC 하나당 최소 하나, 묶음은 참조마다 따로.**

| AC | 무엇 | 레벨 | 비고 |
|---|---|---|---|
| AC-1 | 로그인 성공 + 쿠키 전달 + **본문에 토큰 없음** | 통합 | |
| AC-2·3 | 실패 응답 **동일성** | 통합 | **두 응답을 서로 비교하는 테스트를 따로 둔다** |
| AC-4 | Access 만료 후 자동 재발급 | **통합 + E2E** | 수명을 짧게 오버라이드해 검증. **재발급은 프론트가 수행하므로**(research.md 14) 통합만으로는 *"사용자가 재로그인을 요구받지 않는다"*(`FR-016`)가 성립하지 않는다 — **통합은 "만료 Access → 401 / 유효 Refresh → 200"까지, E2E가 재시도까지** |
| AC-5 | 로그아웃 후 재발급 차단 | 통합 | |
| **AC-35** | **로그아웃은 요청한 기기만 종료** (신규) | 통합 | **세션 2개를 만들고 하나만 로그아웃.** `AC-5`만으로는 "전부 지워도 통과"한다 |
| AC-6 | Refresh 만료 | 통합 | |
| AC-7 | 스크립트로 쿠키 못 읽음 | **E2E** | 브라우저가 있어야 의미가 있다 |

## 구현 순서 — 테스트가 먼저 (원칙 I)

스펙의 우선순위를 따른다. **US1이 관리자 자동 생성 덕에 회원가입 없이 완결 가능**하다.

| 순서 | 무엇 | 왜 이 순서 |
|---|---|---|
| 0 | 6.7 마이그레이션 SQL (사람) · Docker Compose · CI 잡 | 스키마가 전 레인 공유 지점 |
| 1 | **첫 실패 경로(로그인 실패)의 실패 테스트 → 그것에 필요한 공통 기반**: `traceId` 필터 · **공통 Problem Details 생성기** · `@RestControllerAdvice` · 오류 코드 | `AC-27`·`AC-28`이 **모든 응답에 걸린다.** 나중에 넣으면 전부 고쳐야 한다 |
| 2 | **US1** 로그인·로그아웃·재발급 + 관리자 초기 생성 | 관리자 계정이 자동 생성되므로 가입 없이 검증 가능. **여기서 `AuthenticationEntryPoint`·`AccessDeniedHandler`를 1번의 생성기에 연결**한다 |
| 3 | **US1** 관리자 진입점 분리 (`AC-31`~`33`) | 2번의 메커니즘을 공유하고 진입점만 분리 |
| 4 | **US2** 회원가입 + 중복확인 | |
| 5 | **US3** 권한 접근제어 | US1·US2가 있어야 검증된다 |
| 6 | 남용 방어 (`AC-29`·`AC-30`) | 로그인·중복확인이 있어야 얹을 수 있다 |
| 7 | 프론트 화면 + E2E | |

**1번을 먼저 하는 이유를 강조한다.** `AC-27`(모든 오류에 추적 식별자)과 `AC-28`(내부 정보 비노출)은
**특정 기능의 AC가 아니라 모든 응답에 걸리는 AC**다. 기능을 다 만든 뒤에 넣으면 이미 만든
모든 오류 경로를 다시 손대야 한다.

> **★ 1번의 정의를 고쳤다** *(5번 게이트 지적 8 — 순서 자체는 타당하다고 판정됐다)*.
> 원문은 *"공통 — 전역 예외 핸들러"* 였는데 **"전역 핸들러를 먼저 완성"은 성립하지 않는다.**
> 오류 경로는 **기능이 생길 때마 생긴다** — Security 필터(2번) · Bean Validation(4번) ·
> DB 제약(4번). 1번에서 다 만들려면 아직 없는 기능의 오류를 상상해서 써야 하고,
> 그것은 **원칙 I(테스트 우선)과 수직 슬라이스에 반한다.**
>
> → **1번은 "독립 공통 인프라 구현"이 아니라 "첫 실제 실패 경로에 포함된 기반"** 이다.
> 로그인 실패 테스트를 먼저 쓰고, 그것을 통과시키는 데 필요한 만큼의 생성기·필터를 만든다.
> **어댑터는 해당 오류 경로가 생기는 단계에서 붙인다**(2번에 Security, 4번에 Validation·DB).
> **`AC-27`·`AC-28`의 전 오류 계약 매트릭스는 마지막에 한 번 훑는다** — 그때가
> 모든 오류 경로가 존재하는 첫 시점이다.
>
> **바뀌지 않은 것**: *"공통 기반을 1번에 둔다"* 는 위치. 바뀐 것은 *"완성한다"* → *"필요한 만큼
> 세운다"* 다.

## 위험과 대응

| 위험 | 왜 위험한가 | 대응 |
|---|---|---|
| **실패 응답 3경로가 갈라진다** | `AC-2`·`AC-3`·`AC-32` 중 하나만 달라도 계정 열거가 뚫린다. 예외 종류가 달라서 핸들러가 다르게 잡기 쉽다 | **세 응답을 서로 비교하는 테스트를 따로 둔다.** 각각 통과해도 서로 다를 수 있다. **비교 대상을 research.md 15에 못박았다**(`type`·`title`·`code`·`detail`·`errors` 유무·쿠키 동작이 같아야 하고 `traceId`·`instance`만 다르다) + **공통 생성기 1개 + 어댑터 3개** |
| **★ 응답 시간으로 아이디 존재 여부가 샌다** | 없는 아이디에서 해시 검증을 건너뛰면 그 경로만 빨라진다. **본문이 같아도 측정으로 `AC-3`이 뚫린다.** Argon2id는 느리므로 차이가 **더 크게** 드러난다 | **없는 아이디도 고정 더미 해시로 검증을 똑같이 수행**한다. 관리자 진입점은 **비밀번호 검증을 끝낸 뒤** 권한을 본다(먼저 보면 그 경로가 빨라진다). `quickstart.md` 시나리오 4가 사람 눈으로 A·B 시간을 비교한다 — **자동으로 시간을 재면 CI에서 불안정하다** |
