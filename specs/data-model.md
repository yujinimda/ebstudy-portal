# 데이터 모델 — 논리 설계

> **프로세스 3.5.** constitution 원칙 III — **DB 논리 설계는 사람이 직접 작성하고 AI는 리뷰만 한다.**
> 스키마는 이 프로젝트에서 되돌리기 비용이 가장 높은 결정이다. 코드는 틀리면 다시 쓰면 되지만
> 스키마는 이미 운영 데이터가 들어 있는 상태에서 바꿔야 한다.

**범위**: 논리 설계만 — 엔터티 · 관계 · 정규화. DBMS·ORM과 무관하다.
컬럼 타입 · 인덱스 · 제약 문법 같은 **물리 설계는 4번 계획**에서 다룬다.

**누적 문서**: 스토리마다 이어 붙인다. 아래는 001 인증 분량.

## 판단 도구 3개

그리다 막히면 이 세 질문으로 돌아온다.

### 도구 1 — "이 둘은 같은 개념인가?"

같은 개념이면 **한 테이블 + 구분 컬럼**. 다른 개념이면 **별 테이블**.

| | 판단 |
|---|---|
| 관리자와 사용자 | 둘 다 **"로그인하는 사람"**. 같은 개념의 다른 역할 → 한 테이블 + `role` |
| 게시글과 첨부파일 | 다른 개념 → 별 테이블 |

정규화는 "많이 쪼개기"가 아니라 **"개념 단위로 정확히 자르기"** 다.
쪼개야 할 것을 붙여두면 조회·수정이 안 되고, 붙여야 할 것을 쪼개면 유일성을 DB가 보장할 수 없다.

### 도구 2 — 카디널리티는 양방향으로 묻는다

```
A 하나가  →  B 몇 개를 가지나?
B 하나가  →  A 몇 개에 속하나?
```

| 답 | 관계 | 결과 |
|---|---|---|
| 1 ↔ 1 | 1:1 | 한쪽에 FK |
| 여러 개 ↔ 1 | **1:N** | **N쪽에 FK** |
| 여러 개 ↔ 여러 개 | N:M | **중간 테이블이 필요해진다** |

**이 답은 대개 스펙에 이미 있다.** 없으면 스펙이 덜 정해진 것이다.

### 도구 3 — "한 컬럼에 값이 여러 개 들어가는가?"

들어간다면 쪼갠다. 콤마 구분 문자열(`"tag1,tag2,tag3"`)로 두면
**그중 하나만 조회·수정·삭제하는 것이 불가능**해지고, 코드에서 문자열을 파싱해 때우기 시작한다.

### 테이블: 재발급 티켓 (Refresh)

**왜 테이블인가 (구술 확인)**: 로그인마다 티켓이 하나 생기고, 로그아웃할 때 **그 티켓만**
지워야 한다 → 여러 개가 생기고 하나씩 지워야 하는 목록 = 테이블.

**왜 DB인가**: 사라지면 각 사용자의 Access 만료 시점에 재발급이 거절되어 순차적으로 전원
로그아웃된다. **서버를 재시작할 때마다(= 배포할 때마다) 그 일이 벌어진다.**
메모리 저장이 안 되는 이유가 이것이다.

| 컬럼 | 필수 | 유일 | 근거 |
|---|---|---|---|
| `id` | ✅ | ✅ (PK) | 전역 규칙 |
| 유저 참조 (FK) | ✅ | — | `FR-014` 누구 것인지 |
| 티켓을 식별하는 값 | ✅ | ✅ | 재발급 요청이 이 티켓인지 판정 |
| 만료 시각 | ✅ | — | `FR-012` 만료 필수 |
| 무효화 여부 | ✅ | — | `FR-015` 로그아웃 시 무효화, `AC-5` |

**논리 제약**

- **티켓 식별 값을 원문 그대로 저장하지 않는다.** DB가 유출되면 그 값으로 남의 계정에
  그대로 접속할 수 있다 — **비밀번호와 같은 성질**이므로 해시해서 저장한다.
- Access 토큰은 **저장하지 않는다.** 무상태이며 서명만 검증한다.
- 티켓 식별 값의 **형태**(JWT / 랜덤 문자열)는 4번 계획에서 정한다.
  Refresh는 어차피 DB를 확인하므로 JWT일 필요가 없다 — 실무에서 랜덤 문자열로 두는 경우가 많다.

**"기기마다 하나"가 아니라 "로그인마다 하나"다** *(codex 권고 반영)*

이 모델이 보장하는 것은 **로그인 1회 = 티켓 1개**뿐이다. 같은 기기에서 두 번 로그인하면
티켓이 두 개 생기고, 모델은 그 둘을 구분하지 못한다.

**어느 기기인지는 저장하지 않는다.** 스펙에 그런 요구가 없고 `로그인 이력 조회`는
Out of Scope다. 티켓이 여러 개 생긴다는 사실만 중요하다.

→ 진짜 기기 단위 종료(예: "이 기기에서 로그아웃")가 필요해지면 **별도 요구사항**으로
스펙에 추가해야 한다. 지금 모델로는 할 수 없다.

**4번 계획으로 넘기는 운영 과제**

- 만료된 티켓 행이 계속 쌓인다. DB에는 TTL(자동 삭제)이 없으므로 **주기적으로 지우는 작업이
  필요하다.** 테이블을 만들면 청소 책임이 따라온다.
- **유저가 삭제되면 그의 티켓을 어떻게 하는가.** 회원 탈퇴가 001 범위 밖이라 당장 발생하지
  않지만, 외래키 삭제 규칙은 물리 설계이므로 4번 계획에서 정한다.

### 테이블: 사용불가 아이디

**왜 코드가 아니라 테이블인가**: `FR-028`. 004에서 관리 화면을 붙이려면 데이터여야 한다.
코드에 박으면 운영자가 화면에서 바꿀 수 없고, 목록이 늘 때마다 배포해야 한다.
유저 테이블에 넣을 수도 없다 — **가입하지 않은 아이디**라서 유저 행이 존재하지 않는다.

| 컬럼 | 필수 | 유일 | 근거 |
|---|---|---|---|
| `id` | ✅ | ✅ (PK) | 전역 규칙 |
| 금지 아이디 | ✅ | ✅ **대소문자 무시** | `FR-004`, `AC-13` |

컬럼 하나짜리 테이블이며 정상이다. 값 목록만 담는 테이블은 흔하다.
초기 목록은 마이그레이션으로 제공한다(예약어는 비밀이 아니므로 커밋해도 안전).

**논리 제약 — 금지 여부 판정도 대소문자를 무시한다** *(확정 2026-07-28)*

`admin`이 목록에 있으면 `Admin` · `ADMIN` · `AdMiN` 도 모두 가입이 거부되어야 한다.

> **codex 검증에서 지적된 실제 구멍이었다.** `username`에만 대소문자 무시를 걸고
> 금지 목록에는 걸지 않아서, **`admin`이 금지여도 `Admin`으로 가입하면 통과**했다.
> `AC-13`을 대문자 하나로 우회할 수 있었다.

금지 목록의 목적이 **사칭 방지**이므로, 대문자 하나로 우회되면 목록 자체가 무의미해진다.
`username`의 대소문자 무시 정책과 같은 규칙을 적용하는 것이 일관된다.

### 논리 모델에 들어가지 않는 것 — 남용 방어 카운터

`FR-027`(점진적 지연)과 `FR-030`(빈도 제한)은 실패 횟수를 기억해야 성립한다.
HTTP 요청은 서로 독립적이라 서버가 "몇 번째 실패인지" 스스로 알 수 없기 때문이다(무상태).

**그러나 이것은 영속 데이터가 아니다.**

| | 사라지면 |
|---|---|
| 재발급 티켓 | 전원 로그아웃 → **영속 필요** |
| 실패 횟수 | 카운트가 0으로 돌아갈 뿐 → **영속 불필요** |

수명이 짧고(몇 분), 자주 읽고 쓰며, 영구 보존할 가치가 없다.
**어디에 둘지(서버 메모리 / Redis)는 4번 계획**에서 정한다 — 서버 대수와 호스팅 환경에
달려 있고 둘 다 미정이다. Redis가 이 용도에 맞는 이유는 **TTL**(넣을 때 자동 삭제 시각을
함께 지정)이 기본 기능이라는 점이다. DB에는 그 기능이 없어 청소 코드를 직접 만들어야 한다.

→ **테이블은 3개다.**

## 물리 설계 — 4번 계획 (2026-07-29)

> **위 논리 설계는 사람이 작성했고 고치지 않는다.** 이 절은 그 위에 **DBMS 의존 부분만**
> 얹은 것이다 — `process.md` 4.7이 *"물리 설계 — 컬럼 타입, 인덱스, 제약조건, 네이밍.
> DBMS 의존. → 4번 plan 이후"* 로 가른 그 경계다.
>
> **근거는 `001-user-auth/research.md`와 `ADR-003`·`ADR-004`에 있고 여기에 복제하지 않는다.**
> 이 절은 **6.7에서 사람이 마이그레이션 SQL을 쓸 때 보는 표**다.
>
> **여기에 DDL 전문은 없다.** SQL 작성은 6.7이고 **사람 단독**이다(constitution 원칙 III).

**전제**: `ADR-003` PostgreSQL · `ADR-004` Spring Data JPA(Hibernate) · `ddl-auto=validate`.

### 1. 전역 표기 규칙

| | 결정 | 근거 |
|---|---|---|
| 기본키 | **`BIGINT GENERATED ALWAYS AS IDENTITY`** | **`ADR-002`의 논리 결정(자동증가 숫자)은 그대로 유지**되고 **DDL 표기만 Postgres 형태**가 된다. `ADR-002`의 `AUTO_INCREMENT`는 DBMS 미정 시점에 쓴 MySQL 문법 예시였다(그 ADR에 주석으로 남아 있다) |
| 식별자 표기 | **`snake_case`** | Postgres가 따옴표 없는 식별자를 소문자로 접으므로 관례와 일치한다. 따옴표로 감싸 대문자를 살리는 방식을 쓰지 않는다 — 그러면 모든 쿼리에 따옴표가 따라온다 |
| 시각 컬럼 | **`TIMESTAMPTZ`** | 시간대를 포함해 저장한다. `TIMESTAMP`(시간대 없음)로 두면 **어느 시간대의 값인지 데이터가 스스로 말하지 못하고**, 서버·DB·클라이언트의 시간대가 갈리는 순간 조용히 틀린 값이 된다. 자격증명 만료 판정이 시각 비교이므로(`AC-6`) 틀리면 **인증이 틀린다** |

### 2. 대소문자 무시 유일 — 논리 제약을 어떻게 실현하는가

논리 설계가 *"`username`의 유일성은 대소문자를 구분하지 않는다"* 와
*"금지 여부 판정도 대소문자를 무시한다"* 를 제약으로 확정하고 **구현 방법을 4번으로 넘겼다.**

| 대상 | 방법 |
|---|---|
| 유저`.username` | **`LOWER(username)`에 함수 유니크 인덱스** |
| 사용불가아이디`.금지아이디` | **같은 규칙 — `LOWER()` 함수 유니크 인덱스** |

- **`CITEXT` 확장은 쓰지 않는다.** 확장 의존을 늘리면 Testcontainers 이미지와 이식성에
  조건이 붙는다(`ADR-003` 파생 규칙).
- **소문자로 정규화해 저장하는 방식도 쓰지 않는다.** 사용자가 입력한 표기를 그대로 보존하고
  **유일성 판정만** 대소문자를 무시한다.
- **판정 쿼리도 같은 규칙을 써야 인덱스를 탄다.** 인덱스가 `LOWER(username)`인데 조회를
  `username = ?` 로 하면 인덱스를 쓰지 못하고, 무엇보다 **대소문자가 다른 값을 못 찾는다.**

> **`ADR-003` 리스크 1을 여기서 그대로 받는다**: `ddl-auto=validate`는 컬럼 존재는 검증하지만
> **함수 인덱스 일치는 검증하지 않는다.** 엔티티에 `unique = true`만 걸어두면 실제 인덱스와
> 어긋난 채 부팅이 성공한다.
> → **`test-strategy.md` 5.2의 동시 가입 경합 테스트에 `Kim` vs `kim` 경합을 포함하는 것이
> 이 인덱스를 확인하는 유일한 장치**다.

### 3. 티켓 식별 값 — SHA-256 해시 + 유일 인덱스

논리 설계가 *"티켓 식별 값을 원문 그대로 저장하지 않는다 — 비밀번호와 같은 성질"* 로 확정했고,
**형태와 해시 방식을 4번으로 넘겼다.**

| | 결정 |
|---|---|
| 쿠키에 담는 값 | **256비트 난수**(Base64url 문자열). **JWT가 아니다** — Refresh는 어차피 DB를 확인하므로 서명 검증으로 얻을 것이 없다 |
| DB에 저장하는 값 | **그 값의 SHA-256 해시.** 원문은 저장하지 않는다 |
| 인덱스 | 해시 컬럼에 **유일 인덱스** (논리 설계가 이 컬럼에 준 유일 제약의 물리 표현) |

**★ 왜 bcrypt가 아닌가 — 비밀번호와 규칙이 달라 보이므로 근거를 남긴다**

| | 비밀번호 | 티켓 식별 값 |
|---|---|---|
| 값을 만드는 주체 | **사람** → 추측·사전 공격 가능 | **256비트 난수** → 추측 불가. **무차별 대입할 공간이 없다** |
| 해시가 느려야 하나 | ✅ 느려야 한다. 대입을 비싸게 만드는 것이 목적 | ❌ 느릴 이유가 없다 |
| 조회 방식 | `username`으로 **행을 먼저 찾고** 그 행의 해시와 비교 | **해시로 행을 찾아야 한다** |

**결정적인 것은 마지막 줄이다. bcrypt는 솔트가 매번 달라서 같은 입력이 매번 다른 해시가 된다.**
그래서 `WHERE 해시 = ?` 로 **조회 자체가 불가능**하다 — 전 행을 꺼내 하나씩 비교해야 한다.
SHA-256은 같은 입력이 항상 같은 해시이므로 **유일 인덱스로 한 번에 찾는다.**

> **constitution 보안 요구사항의 "빠른 해시 금지"에 걸리지 않는다.**
> 그 규칙은 **비밀번호** 해싱을 규정한다. 근거가 *"사람이 만든 값은 GPU로 초당 수십억 시도가
> 가능하다"* 인데, **256비트 난수에는 그 전제가 성립하지 않는다**(`plan.md` Constitution Check).

### 4. 재발급 티켓의 외래키 — `ON DELETE CASCADE`

논리 설계가 넘긴 과제다 — *"유저가 삭제되면 그의 티켓을 어떻게 하는가."*

**결정: 유저 참조 외래키에 `ON DELETE CASCADE`.** 유저가 삭제되면 그의 티켓도 함께 삭제된다.

**근거**: 티켓은 **유저에 종속된 개념**이고 **유저 없는 티켓은 의미가 없다.**
남겨두면 그 티켓으로 재발급을 시도할 때 유저를 찾지 못해 오류가 난다 —
**고아 행이 그대로 장애 원인이 된다.**

**기각한 대안**

| | 기각 이유 |
|---|---|
| `ON DELETE RESTRICT` (티켓이 있으면 유저 삭제를 막는다) | 탈퇴하려면 **모든 기기에서 로그아웃부터 해야** 한다. 사용자가 이해할 수 없는 제약이고, 코드가 먼저 티켓을 지우고 유저를 지우게 되어 **결국 CASCADE와 같은 일을 손으로 하는 것**이 된다 |
| `ON DELETE SET NULL` | 유저 참조가 **필수(NOT NULL)** 이므로 문법적으로 성립하지 않는다. 성립시키려면 논리 설계의 필수 판정을 뒤집어야 한다 |

**회원 탈퇴가 001 범위 밖이라 당장 발생하지 않지만 지금 정한다** — 외래키 삭제 규칙은
물리 설계이고, 테이블을 만드는 6.7에서 함께 써야 나중에 `ALTER`로 고치지 않는다.

### 5. 만료된 티켓 행 청소

논리 설계가 넘긴 과제다 — *"DB에는 TTL(자동 삭제)이 없으므로 주기적으로 지우는 작업이
필요하다. 테이블을 만들면 청소 책임이 따라온다."*

| | 결정 |
|---|---|
| 무엇을 | 만료 시각이 지난 티켓 행. **무효화된 행도 만료 시각이 지나면 함께** 지운다 |
| 어떻게 | **스프링 스케줄러로 하루 1회.** **만료 시각 인덱스**를 탄다(5.5의 5번) |
| **한 번에 얼마나** | **배치로 쪼개 반복 삭제한다** *(2026-07-29 추가 — 5번 게이트 권고 5)*. 한 트랜잭션에서 전량을 지우면 **행이 많을 때 잠금과 WAL이 커지고 그 시간 동안 로그인·재발급이 같은 테이블에서 경합**한다. 청소가 그 자체로 장애 요인이 되는 것이라 `research.md` 6의 함정과 **같은 종류**다. 배치 크기는 **환경변수**로 두고 7번에서 정한다 |
| 왜 하루 1회 | 만료된 행은 **인증 판정에 영향을 주지 않는다**(만료 시각을 함께 보므로). 급할 이유가 없고, 자주 돌리면 삭제가 인덱스와 경합하기만 한다 |
| **전제** | **서버 1대**(`research.md` 5 — 호스팅을 미루며 확정됐다). 여러 대면 같은 작업이 동시에 돌아 **잠금 경합**이 생긴다 |
| **방아쇠** | **서버가 2대 이상이 되는 시점.** 그때 분산 잠금 또는 단일 실행 보장이 필요해진다. `process.md` 6.2의 호스팅 방아쇠와 **같은 시점**이다 |

**청소를 안 하면 무엇이 나쁜가**: 로그인 1회당 행 1개가 쌓이고 지워지지 않는다. 정확성은
깨지지 않지만 테이블과 인덱스가 단조 증가한다 — **조용히 나빠지는 종류**라서 방아쇠 없이
미루면 알아차리지 못한다.

### 5.5 인덱스 전수 — **유일 인덱스 외에 필요한 것** *(2026-07-29 추가, 5번 게이트 지적 7)*

> **이 절이 없었다.** 위 2·3절이 **유일 인덱스**만 정하고 **조회 성능을 위한 인덱스**를
> 다루지 않았는데, `process.md` 4.7이 물리 설계의 범위로 *"컬럼 타입, **인덱스**, 제약조건,
> 네이밍"* 을 명시했으므로 **선언한 범위를 채우지 못한 상태**였다.
> 6.7에서 사람이 SQL을 쓸 때 **이 표가 없으면 인덱스가 빠진 채 테이블이 만들어지고**,
> 그때부터는 `ALTER`로 고쳐야 한다.

| # | 대상 | 종류 | 왜 필요한가 |
|---|---|---|---|
| 1 | 유저`.username` | **`LOWER()` 함수 유니크** | 2절. 대소문자 무시 유일성 |
| 2 | 사용불가아이디`.금지아이디` | **`LOWER()` 함수 유니크** | 2절. 같은 규칙 |
| 3 | 재발급티켓`.식별값 해시` | **유니크** | 3절. **해시로 행을 찾는다** — 이 인덱스가 없으면 재발급마다 전 테이블 스캔이다 |
| **4** | **재발급티켓`.유저 참조(FK) 컬럼`** | **일반 인덱스 (누락됐던 것)** | **PostgreSQL은 FK 컬럼에 인덱스를 자동으로 만들지 않는다.** 없으면 ① 4절의 **`ON DELETE CASCADE`가 유저 1명 삭제마다 티켓 테이블 전체를 훑는다** ② `AC-35`(요청한 기기만 종료)와 *"이 유저의 티켓들"* 조회가 전부 전체 스캔이 된다 |
| **5** | **재발급티켓`.만료 시각`** | **일반 인덱스 (누락됐던 것)** | **5절의 하루 1회 청소가 `만료 시각 < 지금` 으로 지운다.** 인덱스가 없으면 매일 전 테이블 스캔이고, 테이블이 커질수록 나빠진다 — 5절이 *"조용히 나빠지는 종류"* 라고 적은 그 성질이 **청소 작업 자체에도 적용된다** |

**★ FK 인덱스가 자동이 아니라는 것이 왜 함정인가**
PostgreSQL은 **참조되는 쪽(부모의 PK)** 에는 인덱스를 요구하지만 **참조하는 쪽(자식의 FK 컬럼)**
에는 만들지 않는다. 그런데 `ON DELETE CASCADE`가 도는 방향은 **자식을 찾는 방향**이다.
즉 **CASCADE를 쓰기로 한 결정(4절)이 이 인덱스를 요구한다** — 두 결정이 짝이다.

**인덱스도 이름을 정한다** — `process.md` 4.7의 물리 설계 범위에 *"네이밍"* 이 있고,
**`AC-28`이 제약조건명·인덱스명 비노출을 검증**하므로 이름이 응답에 새면 안 되지만
**로그와 실행 계획에는 그대로 나온다.** 규칙만 정하고 실제 이름은 6.7에서 사람이 붙인다:

| | 규칙 |
|---|---|
| 유니크 | `uk_<테이블>_<의미>` |
| 일반 인덱스 | `ix_<테이블>_<컬럼>` |
| 외래키 제약 | `fk_<테이블>_<참조테이블>` |
| CHECK 제약 | `ck_<테이블>_<의미>` |

**001에 필요 없다고 판정한 인덱스** (적어두지 않으면 나중에 "빠뜨린 것"과 구분되지 않는다):

| | 왜 필요 없나 |
|---|---|
| 유저`.권한` | 값이 2종(`USER`·`ADMIN`)뿐이라 **선택도가 낮아** 인덱스가 도움이 안 된다. 그리고 001에 *"관리자 전체 조회"* 같은 요구가 없다 |
| 유저`.이름` | 001에 이름으로 찾는 기능이 없다. **방아쇠: 004 관리자 화면의 회원 검색** |
| 재발급티켓`.무효화 여부` | 값이 2종이고, 조회는 항상 **식별값 해시로 단건**이다. 무효화 여부는 그 행을 찾은 뒤 보는 값이다 |

### 5.6 컬럼 타입 · NOT NULL · 기본값 · CHECK *(2026-07-29 추가, 5번 게이트 지적 6)*

> 위 1절이 **전역 표기 규칙**(PK · 식별자 · 시각)만 정하고 **컬럼별 결정**을 남기지 않았다.
> **여기에 DDL 전문은 없다** — SQL 작성은 6.7이고 **사람 단독**이다(원칙 III).
> 이 표는 그 사람이 **보고 쓰는 표**다.

**유저**

| 컬럼(논리) | 타입 | NULL | 기본값·제약 | 근거 |
|---|---|---|---|---|
| 기본키 | `BIGINT GENERATED ALWAYS AS IDENTITY` | NOT NULL | PK | 1절 · `ADR-002` |
| 로그인 아이디 | `VARCHAR(11)` | NOT NULL | 유일은 `LOWER()` 함수 인덱스(2절) | `FR-003`이 **12자 미만**이므로 최대 11자다. **길이 제약을 DB에도 둔다** — `FR-002`(서버 검증)의 마지막 방어선이고, 스펙 위반 값이 어떤 경로로든 들어오는 것을 막는다 |
| 비밀번호 해시 | `VARCHAR` (길이 제한 두지 않음) | NOT NULL | — | **Argon2id 해시 문자열은 파라미터를 자기 안에 담아 길이가 파라미터에 따라 변한다**(`ADR-005`). 고정 길이를 박으면 **파라미터를 올리는 순간 저장이 실패한다** — bcrypt(항상 60자)를 전제해 `CHAR(60)`으로 두면 안 되는 이유다 |
| 이름 | `VARCHAR(50)` | NOT NULL | — | `FR-029` 2~50자. 길이는 **문자 수**이고 Postgres `VARCHAR(n)`도 문자 수로 센다 — 한글에서도 어긋나지 않는다 |
| 권한 | `VARCHAR` + **`CHECK`(`USER`·`ADMIN`만)** | NOT NULL | — | **`ENUM` 타입을 쓰지 않는다** — Postgres `ENUM`은 값을 추가할 때 타입을 `ALTER`해야 하고 **JPA 매핑도 까다롭다**. `CHECK`는 마이그레이션으로 자연히 바뀌고 **제약이 SQL에 그대로 보인다**(`ADR-003`의 *"규칙이 스키마에 보이게"* 와 같은 취향) |
| 생성 시각 | `TIMESTAMPTZ` | NOT NULL | `now()` | 1절 |

**재발급 티켓**

| 컬럼(논리) | 타입 | NULL | 기본값·제약 | 근거 |
|---|---|---|---|---|
| 기본키 | `BIGINT GENERATED ALWAYS AS IDENTITY` | NOT NULL | PK | 1절 |
| 유저 참조 | `BIGINT` | NOT NULL | **FK → 유저, `ON DELETE CASCADE`** + **인덱스**(5.5의 4번) | 4절 |
| 식별값 해시 | **`BYTEA`** | NOT NULL | **유니크** | **SHA-256은 정확히 32바이트**다. `BYTEA`로 두면 **길이가 그 자체로 검증**되고 저장이 절반이다. hex 문자열(`CHAR(64)`)로 두면 **대소문자 표기가 갈릴 수 있다**(`AbC` vs `abc`가 다른 행이 되어 유니크가 무의미해지는 함정) → **바이트로 둔다** |
| 만료 시각 | `TIMESTAMPTZ` | NOT NULL | **인덱스**(5.5의 5번) | 1절 · 5절 |
| 무효화 여부 | `BOOLEAN` | NOT NULL | **`false`** | **기본값이 있어야 한다** — 없으면 삽입할 때마다 명시해야 하고 한 번 빠뜨리면 `NULL`이 되어 *"무효화됐는지 알 수 없는 티켓"* 이 생긴다 |
| 생성 시각 | `TIMESTAMPTZ` | NOT NULL | `now()` | 1절 |

**사용불가 아이디**

| 컬럼(논리) | 타입 | NULL | 기본값·제약 | 근거 |
|---|---|---|---|---|
| 기본키 | `BIGINT GENERATED ALWAYS AS IDENTITY` | NOT NULL | PK | 1절 |
| 금지 아이디 | `VARCHAR` | NOT NULL | 유일은 `LOWER()` 함수 인덱스(2절) | **유저 아이디와 달리 11자 제한을 두지 않는다** — 금지 목록은 *"입력이 이것과 같으면 거부"* 하는 데이터이고, 12자 이상을 금지어로 등록하는 것 자체가 무의미하지 않다(길이 검증이 먼저 걸러낸다) |

**공통 판단 — 왜 `NOT NULL`을 최대한 거는가**
`NULL`은 *"값이 없다"* 가 아니라 *"모른다"* 이고, 비교·집계·유니크 판정에서 **직관과 다르게
동작한다**(`NULL = NULL`은 참이 아니다). 001의 모든 컬럼은 **가입·로그인 시점에 값이 반드시
정해진다**(3.5 논리 설계의 *"필수 여부"* 판정). 나중에 `NULL`을 허용하는 것은 쉽고
**금지하는 것은 이미 들어온 `NULL`을 처리해야 해서 어렵다** — 좁게 시작한다.

### 6. 4번으로 넘겼던 과제 — 논리 설계가 넘긴 3건은 해소, **물리 설계는 5번 게이트에서 보완**

> ⚠️ *(2026-07-29 정정 — 5번 게이트 지적 6·7)* 이 절의 원래 제목은 *"**전부 해소**"* 였는데
> **그 선언이 과했다.** 아래 표의 3건(논리 설계가 **명시적으로** 넘긴 과제)은 실제로 해소됐지만,
> `process.md` 4.7이 물리 설계의 범위로 선언한 **인덱스·컬럼 타입·기본값·제약**이
> 비어 있었다. **"넘겨받은 과제를 다 풀었다"와 "선언한 범위를 다 채웠다"는 다른 것이고,
> 앞의 것만 확인하고 뒤의 것을 확인하지 않았다.** → **5.5·5.6절을 신설해 채웠다.**

논리 설계가 명시적으로 4번에 넘긴 것이 3건이었고, **그 3건은 남은 것이 없다.**

### 7. 테이블은 여전히 3개

물리 설계에서 테이블이 늘지 않았다. 남용 방어 카운터·수명 값·탐색 상태는 전부 **테이블이
아닌 곳**에 착지했고, 논리 설계의 *"→ 테이블은 3개다"* 판정이 그대로 유지된다.

**6.7에서 쓸 마이그레이션 파일도 그 구조를 따른다** — 유저 · 재발급 티켓 · 사용불가 아이디.
파일 번호와 분할 방식은 6.7에서 사람이 정한다.
