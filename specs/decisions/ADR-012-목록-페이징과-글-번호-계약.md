# ADR-012 목록 페이징 방식과 글 번호 계약 — 오프셋 · 0 기반 · 결과 총건수 기준

- **상태**: **제안 — 사람 확정 대기** ★ 5단계(프론트 공통) 전 결정 필요
- **날짜**: 2026-07-31
- **관련**: `specs/002-free-board/spec.md` ADR 후보 3 · `FR-008`·`FR-009`·`AC-12`~`AC-14` ·
  003 `FR-009` · 006 `FR-007` · 요구사항 1.1
- **되돌리기 비용**: **중~상** — 응답 형식이 바뀌면 **화면과 API 계약이 함께** 바뀐다.
- **왜 이 ADR이 커졌나**: 002 후보 3(오프셋/커서)만으로는 부족했다.
  **통합 단계 교차 검사에서 003·006이 002와 다른 페이징 계약을 쓰고 있는 것이 드러났다.**

---

## 맥락 — 교차 검사가 실제로 잡은 것

`page` 파라미터와 글 번호의 정의가 **게시판마다 달랐다.**

| 항목 | 002 (소유자) | 003 | 006 |
|---|---|---|---|
| `page` 기준 | **0 기반**, 기본 `0` | 1 기반, 기본 `1` | 1 기반, 기본 `1`, **0·음수는 400** |
| 정렬 방향 이름 | **`direction`** | `order` | `direction` |
| 범위 초과 페이지 | **200 + 빈 목록** (`AC-13`) | 미정의 | Edge Cases가 400으로 읽힘 |
| 기간 상한 | **1년** | 1년 | **365일** |
| 글 번호 분모 | **결과 총건수** | 고정 노출분 제외 전체 건수 | 전체 게시글 수 |

**003·006 계약 문서 모두 머리글에 *"파라미터는 002가 소유한다"* 라고 적어 놓고 값이 002와
달랐다.** 5단계의 공통 목록 훅이 보내는 첫 요청(`page=0`)이 006에서는 **400**이 된다.

→ **통합 단계가 002 기준으로 통일했다**(각 계약 문서에 정정 표기). 이 ADR은 그 통일된 계약을
확정 대상으로 올린다.

## 검토한 대안

### A. 오프셋 페이징 + 0 기반 + 결과 총건수 기준 번호 — **권고 · 현재 통일된 계약**

- 요구사항이 `<< < 1~10 > >>` 를 명시한다. **총 페이지 수를 알아야 그릴 수 있고**,
  그것은 오프셋에서만 나온다.
- 0 기반은 백엔드 도구의 기본값과 맞아 변환 코드가 없다.
- **대가 1**: 페이지를 넘기는 사이 새 글이 들어오면 **같은 글이 두 페이지에 보이거나 건너뛴다.**
  002 Edge Cases가 이미 이 대가를 적었다.
- **대가 2**: 뒤쪽 페이지가 느려진다. 오프셋이 커지면 DB가 앞부분을 세고 버린다.
- **대가 3 (화면)**: 화면은 1부터 세는데 요청은 0부터 센다. **어긋나는 자리가 하나 생긴다.**

### B. 커서 페이징 — 기각

- 새 글이 들어와도 중복·누락이 없고 깊은 페이지도 빠르다.
- **기각 이유**: **`<< < 1~10 > >>` 를 그릴 수 없다.** 커서는 *"다음"* 만 안다.
  요구사항이 명시한 화면을 만들 수 없으므로 실재하는 선택지가 아니다 — 다만
  **무엇을 감수했는지 기록으로 남기기 위해** 여기 적는다.

### C. 1 기반 오프셋 — 기각

- 화면과 요청의 숫자가 같아 헷갈리지 않는다.
- **기각 이유**: 002가 이미 0 기반으로 AC(`AC-12`·`AC-13`)와 계약 예시를 확정했고,
  003·006은 계약 머리글에서 002를 소유자로 인정했다. **소유자가 이미 정한 값을 뒤집는 것**이
  세 문서를 다시 고치는 일이 된다. *(뒤집고 싶다면 지금이 마지막 시점이다.)*

## 결정하지 않으면 무엇이 막히는가

- **5단계 프론트 공통 목록 훅**을 쓸 수 없다. 게시판마다 페이지 기준이 다르면 훅이 4벌이 된다.
- 6번 태스크 분해에서 *"공통 목록 계약"* 태스크의 입력이 비어 있다.

## 남은 리스크

1. **오프셋의 중복·누락은 테스트로 잡히지 않는다.** 순차 실행이라 재현되지 않는다.
   → 기록으로만 남긴다. 사용자 문의가 오면 이 ADR을 근거로 설명한다.
2. **깊은 페이지 성능**은 데이터가 쌓여야 드러난다.
   → 방아쇠: 목록 응답이 체감되게 느려지는 시점. 그때 `ADR-013`과 함께 다시 연다.
