# ADR-030 오류 코드 네임스페이스와 `common/ErrorCode`의 소유권

- **상태**: **제안 — 사람 확정 대기.** ⚠️ **통합 단계가 이미 문서에 적용했다**(아래)
- **날짜**: 2026-07-31 (통합 단계 교차 검사에서 신설)
- **관련**: `specs/002-free-board/plan.md` 미해결 3 · 006 미해결 8 ·
  002·003·005·006 계약 문서 · 요구사항 9장(병렬 경계 — **`common/` 수정 금지**) ·
  constitution 원칙 IV(응답 포맷 = Problem Details + `code`)
- **되돌리기 비용**: **중** — `code` 값은 **프론트가 분기하는 계약**이다.
  바꾸면 계약 문서·백엔드·프론트가 함께 움직인다.

---

## 맥락 — 교차 검사가 잡은 것

같은 실패에 게시판마다 **다른 `code`** 가 붙어 있었다.

| 실패 | 002(소유자) | 003 | 005 | 006 |
|---|---|---|---|---|
| 기간 1년 초과 | `BOARD_SEARCH_PERIOD_TOO_LONG` | 002 상속 ✅ | (미정의) | `INQUIRY_SEARCH_PERIOD_TOO_LONG` |
| 허용 안 된 `size` | `BOARD_PAGE_SIZE_NOT_ALLOWED` | 002 상속 ✅ | (미정의) | `INQUIRY_PAGE_SIZE_INVALID` |
| 제목 없음 | `POST_TITLE_REQUIRED` | `NOTICE_TITLE_REQUIRED` | (미정의) | `INQUIRY_TITLE_REQUIRED` |
| 글 없음 | `POST_NOT_FOUND` | `NOTICE_NOT_FOUND` | `GALLERY_POST_NOT_FOUND` | `INQUIRY_NOT_FOUND` |
| 비활성 분류로 등록 | `POST_CATEGORY_NOT_SELECTABLE` | `NOTICE_CATEGORY_INACTIVE` | — | — |
| 다른 게시판 분류로 등록 | `POST_CATEGORY_NOT_SELECTABLE` (**같은 코드**) | `NOTICE_CATEGORY_NOT_FOUND` (**다른 코드**) | — | — |

★ **마지막 두 줄이 단순한 이름 문제가 아니다.**
002는 *"비활성"* 과 *"다른 게시판"* 을 **의도적으로 한 코드로 합쳤다** —
> *"나누면 어느 게시판에 어떤 분류가 있는지를 응답이 알려준다."* (002 계약 주의 3)

**003은 그것을 둘로 나눠서 정확히 그 정보를 흘린다.** 원칙 IV(정보 누수 금지)에 걸린다.

## 통합 단계가 적용한 것 (사후 승인 대상)

**002를 소유자로 보고 003·005·006의 문서를 고쳤다.** 총 19종 · 63곳.

| 대상 | 규칙 |
|---|---|
| **공통 목록 파라미터 실패** | `BOARD_*` (기간·`size`·`sort`·`page`·검색 분류) |
| **게시물 공통 CRUD 실패** | `POST_*` (제목·내용·없음·소유자 아님·분류 필수/선택불가) |
| **게시판 고유 실패만 고유 접두사** | `NOTICE_PINNED_LIMIT_EXCEEDED` · `GALLERY_IMAGE_*` · `INQUIRY_PASSWORD_*` · `INQUIRY_ANSWER_*` · `COMMENT_*` · `ATTACHMENT_*` · `CATEGORY_*` · `AUTH_*` |
| 분류 코드 | 003의 `INACTIVE`/`NOT_FOUND` 분리를 **`POST_CATEGORY_NOT_SELECTABLE` 하나로 합침** |

## ★ 병렬 경계와 부딪힌다 — 이것이 이 ADR의 두 번째 이유

**요구사항 9장이 `common/` 수정을 절대 금지한다**(1·2·5 단계 이후 아무도 만지지 않는다).
그런데 **오류 코드는 `common/ErrorCode`에 모인다.**

- 002 혼자 **22개**를 추가해야 하고, 003·005·006도 각자 추가한다.
- 즉 **병렬 레인 4개가 같은 파일을 고치게 된다** — 경계 규칙이 성립하지 않는다.

### 선택지

| | |
|---|---|
| **A. 2단계(공통 백엔드 기반)에서 4종의 코드를 전부 한 번에 넣는다** | 경계가 지켜진다. **2단계 시점에 모든 코드를 알아야 한다** — 이 문서의 표가 그 목록이다 |
| **B. 코드를 게시판 패키지별로 분산 정의한다**(`common`은 인터페이스만) | 병렬이 자유롭다. **코드 목록이 한곳에 없어 중복·충돌이 늦게 발견된다** |
| **C. `common/ErrorCode`만 예외로 병렬 수정 허용** | 가장 쉽고 **가장 자주 충돌한다.** 머지 충돌이 상시 발생한다 |

**권고: A.** 코드 목록이 이미 4개 계약 문서에 다 나와 있으므로 2단계에서 한 번에 넣을 수 있다.

## 남은 리스크

1. **같은 코드를 여러 게시판이 쓰면, 프론트가 게시판별 문구를 내려면 코드 외의 단서가 필요하다.**
   → Problem Details의 `instance`(요청 경로)로 구분할 수 있다. 계약에 명시할지 확인 필요.
2. 통합 단계의 치환은 **문자열 치환**이었다. 각 계약 문서의 설명 문장이 옛 이름 기준으로
   쓰여 있을 수 있다 — **6번 태스크 분해에서 계약 문서를 한 번 더 읽어야 한다.**
