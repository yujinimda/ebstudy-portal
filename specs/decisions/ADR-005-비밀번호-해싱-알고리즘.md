# ADR-005 비밀번호 해싱 알고리즘 — Argon2id

- **상태**: 채택
- **날짜**: 2026-07-29 (5번 게이트 codex 크로스 검증에서 결함이 드러나 작성)
- **관련**: `specs/001-user-auth/spec.md` `FR-006`·`FR-008` / `.specify/memory/constitution.md`
  보안 요구사항 / `specs/process.md` 4.1·8.2 / `specs/001-user-auth/research.md` 13
- **되돌리기 비용**: **최상** — **이미 저장된 해시는 되돌릴 수 없다.**
  알고리즘을 바꾸면 기존 비밀번호를 재해싱할 방법이 없어 **전원 재설정**을 요구해야 한다.
  001에는 비밀번호 찾기가 없으므로 그 시점에 **계정 복구 수단이 아예 없다.**

> **이 ADR은 원래 쓰여 있어야 했다.** `process.md` 4.1의 ADR 대상 표가
> *"비밀번호 해싱 알고리즘"* 을 명시하고, **8.2가 원 요구사항의 MySQL `SHA2()`를 기각하며
> *"둘 다 ADR 대상이다"* 라고 직접 적었는데도 ADR이 작성되지 않았다.**
> 5번 게이트가 알고리즘 선택의 실제 결함을 지적해 그 누락이 함께 드러났다.
> → **`process.md` 4.1의 "결정 직후 작성" 규칙이 어겨진 사례**로 기록한다.

## 맥락

`FR-008`이 *"되돌릴 수 없는 느린 해시(**bcrypt 또는 argon2**)"* 를 요구하고,
constitution 보안 요구사항이 같은 문장을 규칙으로 갖는다. 4번 계획은 그중
**bcrypt**를 골랐다 — 근거는 *"스프링 시큐리티 기본이 bcrypt"* 였다(`process.md` 8.2).

**5번 게이트에서 그 선택이 스펙과 충돌한다는 지적이 나왔다.**

| 스펙이 요구하는 것 | 어디 |
|---|---|
| 비밀번호 **8자 이상 64자 이하** | `FR-006` · `AC-14` · `AC-15` |
| **한글·이모지 허용**, 길이는 **문자 수**로 센다 | `spec.md` Edge Cases *"비밀번호의 공백·유니코드"* |
| 앞뒤 공백을 제거하지 않는다 | 같은 항목 |

**bcrypt는 입력을 72바이트에서 자른다.** 알고리즘의 성질이고 구현 문제가 아니다.
그런데 **UTF-8에서 한글 1자는 3바이트, 대부분의 이모지는 4바이트**다.

```
"1234abcd"        ×  8자 →  8바이트   문제 없음
한글 24자          × 24자 → 72바이트   경계
한글 64자          × 64자 → 192바이트  ← 스펙이 허용하는 값. 앞 24자만 쓰인다
```

**무엇이 실제로 깨지는가**

1. **긴 비밀번호가 조용히 짧아진다.** 한글 64자를 넣은 사용자는 실질적으로 24자를 쓴다.
   보안이 즉시 무너지는 것은 아니지만(24자도 충분하다) **사용자가 모른다.**
2. **★ 서로 다른 비밀번호가 같은 계정을 통과한다.** 앞 72바이트가 같고 뒤가 다른 두
   비밀번호는 **bcrypt에게 같은 입력**이다. 즉 *"틀린 비밀번호로 로그인이 성공한다"* —
   `AC-2`(틀린 비밀번호는 401)가 특정 입력에서 거짓이 된다. **정확성 결함**이다.
3. **경계가 문서에 없다.** 스펙은 "문자 수"로, 저장은 "바이트"로 세는데
   그 환산이 어디에도 적혀 있지 않았다. **아무도 이 경계를 테스트하지 않는다.**

**이것은 스펙 결함이 아니라 계획 결함이다.** `FR-008`이 이미 argon2를 허용하고 있었고,
계획이 두 후보 중 **스펙과 맞지 않는 쪽**을 골랐다.

## 검토한 대안

### A. Argon2id — **채택**

- 스프링 시큐리티 `Argon2PasswordEncoder`. **입력 길이 제한이 없다.**
- 2015년 Password Hashing Competition 우승 알고리즘이고, **메모리까지 비싸게 만든다**
  (bcrypt는 CPU만) — GPU·ASIC 병렬화에 더 강하다.
- `id` 변종을 쓴다: `d`(GPU 저항) + `i`(사이드채널 저항)를 겸한다.
- **`FR-008`이 이미 허용하는 선택지다.** 스펙 개정이 필요 없다.
- **단점**: 스프링 시큐리티에서 BouncyCastle 의존성이 필요하다.
  파라미터(메모리·반복·병렬도)를 직접 정해야 하고 **너무 높게 잡으면 우리 서버가 먼저
  죽는다** — 특히 `research.md` 6의 점진적 지연과 겹치면 로그인 경로가 두 번 비싸진다.
  → 값은 **7번에서 실측**한다(`research.md` 13에 방아쇠).

### B. bcrypt 유지 + 비밀번호 길이를 **바이트로** 재정의 — 기각

- `FR-006`을 *"8자 이상, UTF-8 72바이트 이하"* 로 고치면 절단이 원리적으로 사라진다.
- **기각 이유**: **사용자에게 설명할 수 없는 규칙이다.** 화면에 *"한글은 3자로 계산됩니다"*
  라고 쓰게 되고, 같은 64자 입력이 언어에 따라 통과/거부로 갈린다.
  **저장 방식의 한계가 사용자 인터페이스로 새는 것**이고, 스펙 Edge Cases가
  *"한글·이모지도 허용하며 길이는 문자 수로 센다"* 로 명시한 판단을 뒤집는다.
  **알고리즘 때문에 요구사항을 낮추는 방향**이라 8.2(*실서비스 기준으로 상향*)와 반대다.

### C. bcrypt 유지 + SHA-256 전처리 후 bcrypt — 기각

- `bcrypt(base64(sha256(비밀번호)))`. 입력이 항상 44바이트로 고정되어 절단이 사라진다.
  Dropbox 등이 쓴 알려진 패턴이다.
- **기각 이유**: **암호 구성을 직접 조립하는 것**이고, 그 조립이 맞다는 근거를
  **우리가 검증할 수 없다.** (base64 없이 raw 바이트를 넘기면 널 바이트에서 잘리는
  함정이 있다 — 실수 하나가 조용한 취약점이 된다.) **`FR-008`이 argon2를 이미 허용하는데
  직접 만든 조합을 쓸 이유가 없다.** 배울 것이 늘고 리스크가 늘고 얻는 것이 없다.

### D. bcrypt 유지 + 절단을 문서에 적고 감수 — 기각

- 한글 64자도 24자 상당이므로 엔트로피는 충분하다는 논리.
- **기각 이유**: 위 "무엇이 깨지는가" **2번을 감수할 수 없다.** *"틀린 비밀번호로 로그인이
  성공하는 입력이 존재한다"* 는 것은 강도 문제가 아니라 **`AC-2`가 거짓이 되는 것**이다.
  발생 확률이 낮은 것과 규칙이 성립하지 않는 것은 다르다.

## 남은 리스크

1. **Argon2 파라미터를 너무 높게 잡으면 우리 서버가 먼저 죽는다.**
   로그인 경로에는 이미 `research.md` 6의 **점진적 지연**이 얹혀 있어 **같은 경로가 두 번
   비싸진다.** → 완화: 파라미터를 **환경변수로 두고**(원칙 VII) 7번에서 실측해 정한다.
   가상 스레드는 **대기**에는 듣지만 **해시 계산(CPU 점유)** 에는 듣지 않는다 —
   `research.md` 6의 수정된 문구와 같은 구분이다.
2. **파라미터를 나중에 올리면 기존 해시는 옛 파라미터로 남는다.**
   Argon2 해시 문자열은 파라미터를 자기 안에 담으므로 **검증은 계속 되지만**
   옛 계정은 약한 설정을 유지한다. 근본 해결은 로그인 성공 시 재해싱(upgrade-on-login)이고
   **001 범위 밖**이다 → **방아쇠: 파라미터를 처음 올리는 시점.**
3. **`FR-008`은 알고리즘 종류만 규정하고 파라미터는 규정하지 않는다.**
   즉 *"argon2를 쓰지만 파라미터가 너무 약하다"* 는 상태가 **스펙상 위반이 아니다.**
   AC로 검증할 방법도 없다(*"충분히 느린가"* 는 Given/When/Then으로 쓸 수 없다).
   → 정직하게 적어둔다. 이 항목은 **테스트가 아니라 코드 리뷰(8번)의 몫**이다.
