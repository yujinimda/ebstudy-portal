## 맥락

`FR-031`: 답변은 문의당 **1건**. `AC-45`: **관리자 둘이 동시에 답변을 등록**하면 하나만 성공해야 한다.

## 검토한 대안

### A. 별도 테이블 1:1 (`inquiry_id`에 UNIQUE) — **006 계획의 권고**

| | |
|---|---|
| 정규화 | ✅ `process.md` 4.7 — 한 테이블이 두 개념을 겸하지 않는다. 질문과 응답은 **작성자·작성 시점·권한이 전부 다르다** |
| NULL | ✅ 답변이 없으면 **행이 없다** |
| **`FR-031`(1건)** | ✅ **`inquiry_id`에 UNIQUE → DB가 보장.** `AC-45`의 동시 경합이 **DB에서 판정된다** |
| 다건 확장 | 쉽다(UNIQUE 제거) |
| 대가 | 목록의 답변 상태 표기에 **조인/EXISTS**가 붙는다 |

★ **결정적인 이유는 세 번째 줄이다.** `AC-45`를 **코드로 막으면 관리자 둘이 동시에 누를 때
깨진다.** 001이 *"코드로 막으면 동시 요청에서 깨진다"* 며 아이디 중복을 DB에 맡긴 판단과 같다.

### B. 문의 테이블의 컬럼 3개(내용·답변자·답변일시)

| | |
|---|---|
| 정규화 | ❌ 질문과 응답이 한 행에 섞인다 |
| NULL | ❌ 미답변 글에서 **3컬럼이 항상 NULL** — `data-model.md` 리뷰 체크리스트가 *"항상 비어 있는 컬럼은 테이블을 잘못 나눈 신호"* 로 규정한 모양 |
| **`FR-031`** | △ 자연히 1건이지만 **경합 시 나중 쓰기가 앞을 조용히 덮어쓴다**(409가 아니라 손실) |
| 다건 확장 | 마이그레이션이 크다 |
| 대가 | 조인이 없다 |

## 006 계획이 제안한 컬럼 (사람 확정 대상)

| 컬럼(논리) | NULL | 제약 | 근거 |
|---|---|---|---|
| 기본키 | NOT NULL | PK | `ADR-002` |
| 문의 참조 | NOT NULL | **FK → 문의, `ON DELETE CASCADE` + UNIQUE** | `FR-031`. **CASCADE인 이유**: 문의 없는 답변은 의미가 없고 남으면 고아 행이 장애가 된다(001 티켓과 같은 근거) |
| 내용 | NOT NULL | `VARCHAR(3999)` | `FR-032`(4000자 **미만**) |
| 답변자 참조 | NOT NULL | FK → 유저 | 답변자 이름 표시 |
| 답변일시 · 수정일시 | NOT NULL | `now()` | `FR-034` |

★ `uk_answer_inquiry`(UNIQUE)는 **조회 인덱스이자 `AC-45` 동시 경합의 판정자**다 —
하나의 제약이 두 가지 일을 한다.

## 남은 리스크

1. **`ON DELETE CASCADE`가 `ADR-010`과 부딪힐 수 있다.** 문의글을 소프트 삭제로 바꾸면
   CASCADE가 발동하지 않아 답변이 남는다 — 그 상태가 옳은지 그때 다시 봐야 한다.
2. 목록의 답변 상태 표기가 **조인/EXISTS**를 요구한다 → `ADR-013`(집계 전략)의 대상이다.
