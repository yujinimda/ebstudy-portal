# ADR-022 관리자 화면을 물리적으로 분리할 것인가

- **상태**: **제안 — 착수 후 결정 가능.** 현재 전제(경로 분리)로 004를 끝낼 수 있다
- **날짜**: 2026-07-31
- **관련**: `specs/004-admin/spec.md` ADR 후보 1 · `process.md` 6.2 미룬 것 3(**방아쇠가 004**) ·
  001 `FR-013`(`httpOnly` 쿠키) · `FR-032`(관리자 진입점 분리) · 요구사항 8장 5번
- **되돌리기 비용**: **중~상** — 되돌리려면 **배포 구성 · 쿠키 도메인 · 라우팅 · 빌드**가
  함께 움직인다.

---

## 맥락

원 기획서는 **관리자 MPA / 사용자 SPA** 였다. 요구사항 8장 5번이 그것을 뒤집어
**Next.js 하나 + 경로 분리**로 확정했다(4번 계획에서 사용자가 결정).
001 `FR-032`는 **관리자 로그인 진입점 분리**로 이미 충족됐다.

`process.md` 6.2가 이 항목의 **방아쇠를 004로** 예고했고, 004가 왔다.

## 검토한 대안

### A. 같은 앱의 경로 분리 유지 — **현재 전제 · 권고**

- 배포가 하나. 공통 컴포넌트·타입·API 클라이언트를 그대로 쓴다.
- `httpOnly` 쿠키가 **같은 오리진**이라 인증이 그대로 성립한다.
- **단점**: 관리자 화면 코드가 사용자 번들과 같은 저장소·같은 빌드에 있다.
  경로 보호를 잘못 쓰면 관리 화면이 노출될 수 있다(**서버 차단은 001이 이미 하므로
  데이터는 새지 않는다** — 새는 것은 화면 껍데기다).

### B. 별도 앱으로 분리

- 관리자 코드가 사용자 빌드에 섞이지 않는다. 배포 주기를 분리할 수 있다.
- **★ 단점**: **`httpOnly` 쿠키가 오리진에 묶여 있어 분리하는 순간 인증 설계가 영향받는다.**
  서브도메인으로 나누면 쿠키 도메인 범위를 넓혀야 하고, 그 순간 *"사용자 사이트의 XSS가
  관리자 쿠키에 닿는가"* 를 다시 따져야 한다. **`ADR-001`을 다시 여는 결정**이다.

## 권고

**A를 유지하고 004를 끝낸다.** 이 결정은 **되돌릴 수 있는 시점이 뒤에도 있다** —
지금 정하지 않아도 004가 막히지 않는다. B가 필요해지는 방아쇠를 적어 둔다.

**방아쇠**: ① 관리자 기능이 별도 팀·별도 배포 주기를 갖게 될 때
② 관리자 화면이 사용자 번들 크기에 실제로 영향을 줄 때
③ 관리자 접근을 네트워크 수준(사내망·IP 제한)으로 막아야 할 때 ← **가장 현실적인 방아쇠**

## 남은 리스크

1. **경로 보호를 프론트에서만 하면 소용없다.** 004 `FR-011`이 같은 원칙을 적었고
   001 `SecurityConfig`가 `/api/admin/**`를 이미 막는다. **화면 분리는 보안 장치가 아니다.**
2. 004가 발견한 것 — **`GET /api/categories`가 현재 코드에서 401이 난다**
   (`.anyRequest().authenticated()`). `AC-32`(비인증 분류 조회)가 지금 거짓이다.
   **A/B 어느 쪽을 골라도 이건 별개로 고쳐야 한다.**
