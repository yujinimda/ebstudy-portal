- **날짜**: 2026-07-29

## 맥락

4번 기술 계획의 001 범위에서 정해야 할 항목이었다(`STATUS.md` 누적 표). 배경 조건이 이미 셋 있었다:

1. **6.7에서 사람이 마이그레이션 SQL을 직접 쓴다**(`process.md` 4.7, constitution 원칙 VI).
   즉 **스키마는 ORM이 만들지 않는다.** ORM에게 남는 일은 *"이미 있는 테이블을 자바 객체로
   읽고 쓰는 것"* 뿐이다.
2. **`ADR-003`이 PostgreSQL을 확정**해 물리 설계를 쓸 수 있게 됐다.
3. **001에는 복잡한 조회가 없다.** 목록·검색·페이징이 없고 전부 단건 조회와 삽입이다
   (`contracts/auth-api.md` 엔드포인트 8개 전부).

그리고 조사 중에 **우리 규칙이 이미 한쪽을 전제하고 있다는 것**이 드러났다. 그것이 이 결정의 축이 됐다.

## 검토한 대안

### A. Spring Data JPA (Hibernate) — **채택**

- **장점**
  - **`ddl-auto=validate`를 쓸 수 있다.** 이것이 JPA/Hibernate 기능이며 아래 "결정적 근거" 참조
  - Spring Boot 표준 조합이라 자료·예제가 압도적으로 많다. **막혔을 때 찾을 것이 있는지가
    학습 단계에서 실질 비용**이다
  - `ADR-002`가 고른 자동증가 숫자 기본키를 `@Id @GeneratedValue`로 그대로 받는다 —
    `data-model.md` 전역 규칙이 *"자바/스프링 생태계가 이 방식을 전제로 한다"* 고 이미 적어뒀다
  - Testcontainers · Flyway와의 조합이 1급이다(`test-strategy.md` 5.1)
- **단점**: 아래 "그래서 포기한 것" 참조

### B. MyBatis

- **장점**
  - **모든 SQL이 눈에 보인다.** 개발자가 쓴 SQL이 그대로 실행되고 자동 생성이 없다
  - **이것은 약한 근거가 아니다.** `ADR-003`에서 `username` 대소문자 무시를 MySQL 콜레이션이
    아니라 **`LOWER()` 함수 유니크 인덱스**로 고른 이유가 *"규칙이 스키마에 보이게"* 였다.
    **MyBatis를 고르는 것은 그 취향의 자연스러운 연장**이며, 같은 논리가 여기서도 성립할 수 있었다
  - 자바 백엔드 학습 목표(SQL을 직접 쓴다)와 정면으로 맞는다. 6.7에서 DDL을 손으로 쓰기로 한
    판단과 같은 방향이다
  - 국내 실무 점유율이 높다 — `ADR-001`에서 *"회사에서 JWT가 기본"* 이 Claude 추천을 이긴
    선례가 있고, `ADR-003`에서도 MySQL 대안에 같은 장치를 걸어뒀다
- **기각 이유**
  - **`ddl-auto`에 대응하는 기능이 없다.** MyBatis는 매퍼 XML/인터페이스와 실제 스키마가
    어긋나도 **그 SQL을 실행하는 순간까지 모른다.** 부팅은 정상적으로 끝난다
  - 따라서 MyBatis를 고르면 **constitution 원칙 VI를 개정하고 그 안전망을 포기**해야 한다.
    거버넌스 1항에 따라 `process.md` 4.7을 먼저 고쳐야 하는 규모의 변경이다
  - **그 취향(SQL이 보인다)을 이긴 것은 안전망의 구체성**이다 — 아래 결정적 근거 참조

### C. Spring Data JDBC

- **장점**: 배울 것이 JPA보다 훨씬 적다(영속성 컨텍스트·지연 로딩이 없다). SQL에 가깝고
  객체 매핑의 편의는 일부 얻는다. **"JPA는 무겁고 MyBatis는 손이 많이 간다"의 중간**이다
- **기각 이유**
  - **`ddl-auto`가 없다.** A안의 결정적 근거가 성립하지 않는다
  - 실무 사례·한국어 자료가 JPA/MyBatis에 비해 현저히 적다. **막혔을 때 찾을 것이 적은 것은
    학습 단계에서 실질 비용**이며, C안의 최대 장점(배울 것이 적다)을 상당 부분 상쇄한다

### D. JPA + 보조 조회 도구(QueryDSL·JOOQ 등)를 **지금 함께** 도입

- **장점**: 나중에 복잡한 조회가 필요해질 때 도구가 이미 있다. 도입 시점에 코드를 두 번
  손대지 않는다
- **기각 이유**
  - **001에 복잡한 조회가 없다.** 목록·검색·페이징이 하나도 없고 전부 단건 조회·삽입이다.
    **쓰지 않을 도구를 지금 넣으면 배울 것만 늘어난다**(YAGNI)
  - 보조 도구의 값은 *"JPA만으로 불편한가"* 가 실측된 뒤에 판단해야 한다. 지금 고르면
    추측으로 고르는 것이고, `process.md` 결정 26이 게이트에 대해 정한 논리
    (*"게이트는 실제로 무엇을 잡아내는지로 판단해야 한다. 추측으로 정하면 틀린다"*)와 같다
  - → **방아쇠를 박아 미룬다**(아래 "미룬 것" 절)

## ★ 결정적 근거 — 우리 규칙이 이미 JPA를 전제하고 있었다

`constitution` 원칙 VI와 `process.md` 4.7이 **`ddl-auto=validate`를 규칙으로 박아뒀다**:

> `ddl-auto=validate`로 둔다. 테이블을 만들지는 않지만 **"엔티티와 실제 스키마가 어긋났다"를
> 앱 부팅 때 잡아준다.** 공짜 안전망. — `process.md` 4.7

**`ddl-auto`는 JPA/Hibernate 설정이다.** 즉 이 규칙은 ORM을 정하기 전에 이미 쓰였는데
**한쪽을 전제한 상태로 쓰여 있었다.**

**이 안전망이 특히 중요한 이유는 6.7이다.** 마이그레이션 SQL을 사람이 손으로 쓰기로 했으므로
*"손으로 쓴 스키마와 자바 엔티티가 어긋나는 것"* 은 가능성이 아니라 **실제로 일어날 종류의
실수**다. `validate`는 그것을 **앱 부팅 시점**에 잡는다 — 런타임에 쿼리가 터지는 것보다
훨씬 이르고, 이르다는 것 자체가 값이다.

```
6.7  사람이 V1__create_user.sql 을 쓴다        ← 오타가 여기서 들어온다
 7   엔티티 클래스를 쓴다
     ↓
     JPA + validate  →  부팅 실패. "user 테이블에 name 컬럼이 없다"     ← 즉시
     MyBatis         →  부팅 성공. 가입 API를 호출하는 순간 터진다        ← 나중
```

**정직하게 적어둔다 — 이 근거는 순환에 가깝다.** 규칙이 JPA를 전제했기 때문에 JPA가 유리해진 것이고,
규칙을 먼저 정한 것 자체가 순서상의 실수다(ORM보다 4.7이 먼저 쓰였다). 그러나
**규칙을 되돌리는 비용과 규칙을 따르는 비용을 비교하면 결론은 바뀌지 않는다** —
안전망을 포기하는 쪽이 더 비싸다.

## 오간 대화

> **Claude**: ORM을 정해야 합니다. 4지선다입니다 —
> A. Spring Data JPA(추천) / B. MyBatis / C. Spring Data JDBC /
> D. JPA + 보조 조회 도구를 지금 함께
> **그리고 조사하다 발견한 것이 있습니다: `constitution` 원칙 VI와 4.7이 이미
> `ddl-auto=validate`를 규칙으로 박아뒀고, 그건 JPA 기능입니다.**
> MyBatis를 고르면 원칙 VI를 개정하고 그 안전망을 포기해야 합니다.

> **사용자**: JPA로 하고 복잡한 조회만 다른 걸로 하는 거

**해석**: 사용자가 고른 것은 **"JPA 채택 + 복잡한 조회는 다른 도구"** 다.
그중 **JPA 채택은 즉시 확정**했고, **"다른 도구"는 지금 고르지 않고 미뤘다** —
001에 복잡한 조회가 하나도 없어서 무엇이 불편한지 실측할 대상이 없기 때문이다.
즉 **A + D의 절반**이고, D의 나머지 절반(지금 도입)은 방아쇠로 옮겼다.

**정직한 기록**: 사용자는 **추천안을 골랐고 독자적인 근거를 제시하지 않았다.**
`ADR-003`과 같은 위임 구조이며 `process.md` 5.5의 **판단 위임 표기 대상**이다.
*(사용자가 판단을 Claude에 위임)*

다만 `ADR-003`과 다른 점이 하나 있다 — **사용자가 제시된 선택지를 그대로 고르지 않고
"JPA + 복잡한 조회만 다른 것"으로 쪼개서 답했다.** A~D 중 하나가 아니라
**A와 D를 가른 답**이며, 목록을 그대로 받지 않은 첫 사례에 해당한다.

## 그래서 포기한 것

| 포기한 것 | 내용 |
|---|---|
| **SQL이 눈에 보이는 것** | JPA가 SQL을 자동 생성하므로 내가 쓴 코드와 실제로 도는 SQL이 다르다. **이것이 학습 목표(SQL을 직접 다룬다)와 정면으로 부딪히는 지점**이라 완화 두 가지를 규칙으로 둔다 — ① `show-sql`을 상시 켜서 생성된 SQL을 항상 본다 ② **통합 테스트가 실제 DB에 실제 SQL을 날리므로**(`test-strategy.md` 1장) 생성된 SQL이 **실물로 검증**된다. 목(mock)으로 발랐으면 ②가 불가능했다 — **1장의 통합 중심 전략이 여기서 값을 한다** |
| **학습 곡선의 얕음** | 영속성 컨텍스트 · 지연 로딩 · N+1 · flush 시점을 알아야 한다. C안(Spring Data JDBC)이면 이 층이 대부분 없었다 |
| **보조 도구를 지금 갖는 것** | D안을 절반만 받았으므로 002에서 복잡한 조회를 만들 때 **도구를 그때 도입하는 비용**을 낸다. 대신 001에서 쓰지 않을 도구를 배우지 않는다 |

## 미룬 것 — 복잡한 조회 보조 도구 (방아쇠 있음)

**QueryDSL · JOOQ · MyBatis(부분 도입) 중 무엇을 쓸지는 지금 정하지 않는다.**

| | |
|---|---|
| **방아쇠** | **002 자유게시판의 목록 + 검색 + 페이징을 만드는 시점** |
| 왜 그 시점인가 | 그때 처음으로 **JPA만으로 불편한지가 실측**된다. 001에는 대상이 없다 |
| 그때 정할 것 | 도구를 넣을 것인가 / 넣는다면 무엇인가 / 그 결정은 다시 ADR 대상인가 |

**방아쇠를 적는 이유는 `process.md` 6.2와 같다** — *"적지 않으면 「나중에」가 「영원히」가 된다."*

## 남은 리스크

1. **JPA를 "SQL을 안 써도 되는 도구"로 이해하면 사고가 난다.** 이것이 가장 큰 리스크다.
   자동 생성된 SQL이 N+1(한 번 조회하면 될 것을 행 수만큼 조회)을 만들어도 **코드는 정상으로
   보이고 테스트도 통과한다.** 001은 단건 조회뿐이라 발생하지 않지만 **002 목록 조회에서
   즉시 만난다.**
   → 완화: `show-sql` 상시 + 002 진입 시 이 리스크를 다시 읽는다.
2. **`ddl-auto=validate`가 함수 유니크 인덱스 일치를 검증하지 않는다.**
   `ADR-003` 리스크 1과 같은 항목이다. 엔티티에 `unique = true`만 걸어두고
   실제 인덱스가 `LOWER(username)`이면 **둘이 어긋난 채로 부팅이 성공한다.**
   → **이 ADR이 근거로 삼은 안전망에 구멍이 하나 있다는 뜻이므로 정직하게 적어둔다.**
   메워주는 것은 `test-strategy.md` 5.2의 **동시 가입 경합 테스트에 포함하는
   대소문자 다른 아이디(`Kim` vs `kim`) 경합**이며, **그것이 이 인덱스를 확인하는 유일한
   장치**다(`research.md` 9).
3. **엔티티가 스키마의 두 번째 정의가 된다.** 진짜 스키마는 6.7의 SQL 파일이고 엔티티는
   그것의 자바 표현인데, **두 곳에 같은 것을 적으므로 갈라질 수 있다.**
   `validate`가 컬럼 수준에서는 이것을 막지만 리스크 2의 범위는 막지 못한다.
