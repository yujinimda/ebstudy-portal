# ADR-001 인증 방식 — JWT (Access + Refresh)

- **상태**: 채택
- **날짜**: 2026-07-27
- **관련**: 001 인증 스토리 / constitution 보안 요구사항
- **되돌리기 비용**: **최상** — 인증을 바꾸면 전 API가 영향받고, 이미 저장된 비밀번호는
  해시 알고리즘을 바꿔도 재해싱이 불가능해 전원 재설정이 필요하다

---

## 맥락

원 요구사항이 인증을 **두 벌**로 나눠놨다:

| | 방식 | 저장 | 만료 |
|---|---|---|---|
| 사용자 화면 | Access-token | LocalStorage | **없음** |
| 관리자 화면 | 세션 | 쿠키 | 30분 |

세 가지가 문제였다:

1. **만료 없는 토큰** — 한 번 탈취되면 영구히 유효하고 폐기 수단이 없다
2. **LocalStorage 저장** — JS로 읽히므로 XSS 한 번에 토큰이 유출된다
3. **인증이 두 벌** — 보안 로직이 두 개면 취약점 표면도 두 배고, 한쪽을 고칠 때
   다른 쪽을 잊는다. 원 요구사항이 나눈 것은 SPA/MPA를 나눈 결과이고 보안 판단이 아니었다

1과 2는 constitution 보안 요구사항이 이미 금지하므로 선택의 여지가 없었다.
남은 결정은 **"세션이냐 JWT냐"** 와 **"JWT라면 어떤 형태냐"** 였다.

## 검토한 대안

### A. 세션으로 통일 (Claude 최초 권고)

- 서버가 로그인 상태를 저장하고 브라우저엔 세션 ID 쿠키만 준다
- **장점**: 로그아웃이 즉시 동작(저장된 세션 삭제). `httpOnly`가 기본이라
  constitution 보안 요구사항을 자연히 만족. Spring Security 기본값이라 구현량이 적다.
  학습 순서상으로도 JWT가 스프링 시큐리티 필터 체인 위에 얹는 것이므로 세션이 먼저다
- **단점**: 서버가 여러 대면 공유 저장소(Redis) 필요. 네이티브 앱 클라이언트에는 번거롭다
- **기각 이유**: 아래 "내 판단" 참조

### B. JWT, Access 토큰만

- **장점**: 완전 무상태. 구현이 가장 단순
- **단점**: **로그아웃이 원리적으로 불가능**하다. 프론트에서 토큰을 버려도 서버 입장에서
  그 토큰은 만료까지 유효하다. 계정 탈취 신고가 들어와도 끊을 방법이 없다
- **기각 이유**: 실서비스에서 로그아웃 불가는 선택지가 아니다.
  만료를 길게 하면 탈취 위험이 커지고, 짧게 하면 사용자가 계속 재로그인해야 한다

### C. JWT, Access(짧게) + Refresh(길게, 서버 저장) — **채택**

| | 수명 | 서버 저장 | 상태 |
|---|---|---|---|
| Access | 짧게 (15분~1시간) | ❌ | 무상태 |
| Refresh | 길게 (7~30일) | ✅ | 상태 있음 |

- 로그아웃 = 서버에서 Refresh를 삭제 → 재발급 차단 → 최대 Access 수명만큼 뒤 완전 차단
- **실무 표준.** 순수 무상태를 포기하는 대신 로그아웃·강제 차단을 얻는다

## 오간 대화

> **사용자**: 근데 세션을 지금 진짜 하는 곳이 있어?

Claude 답변 요지: 많다. Spring Security 기본이 세션이고, Django·Rails·Laravel도 그렇다.
브라우저 웹 앱은 대체로 `httpOnly` 쿠키 인증이다. OWASP는 브라우저의 LocalStorage 토큰 저장을
권장하지 않아서, 요즘 권고는 "JWT를 쓰더라도 쿠키에 담아라"이고 그러면 저장 방식이 세션과 같아진다.
"JWT가 요즘"이라는 인상은 **튜토리얼 편향**이다 — 세션은 프레임워크가 알아서 해주니 가르칠
내용이 없고, JWT는 직접 만들어야 해서 강의 재료가 된다.
실제 갈림길은 "요즘/옛날"이 아니라 **"누가 클라이언트냐"** 다.

> **Claude 질문**: 나중에 네이티브 앱을 붙일 계획이 있나요?
> (이것이 유일하게 권고를 바꿀 수 있는 사실이었다)

**→ 답을 받지 못했다.** 사용자가 다른 근거(회사 표준)로 결정했기 때문에 이 질문은 미해결로 남았다.
앱 계획이 있다면 C가 더 확실히 맞고, 없다면 A도 타당했다. 즉 이 결정은
**앱 여부와 무관하게 성립**하지만, 근거의 한 축이 비어 있다는 점을 기록해 둔다.

> **사용자**: 클라이언트가 "앱을 포함면"이라는 게 무슨 말이야?

Claude 답변 요지: 클라이언트 = 서버에 요청을 보내는 쪽. 쿠키는 **브라우저의 기능**이라
자동으로 저장·부착되지만 네이티브 앱에는 그 장치가 없어 직접 관리해야 한다.
그리고 안전한 저장소가 환경마다 뒤집힌다 — 브라우저는 `httpOnly` 쿠키(JS 접근 불가),
앱은 OS 저장소(iOS Keychain / Android Keystore).

> **사용자**: 일단 음... 일단 JWT로 시작하는 게 그렇게 안 좋나?
> 그럼 이번만 세션으로 해볼까?

Claude 답변 요지: "안 좋다"고 한 것이 아니다. JWT로 시작하면 감당할 것은
① 로그아웃을 직접 구현 ② 브라우저에 안전하게 둘 곳이 없음 ③ 필터 체인을 모른 채
커스텀 필터를 복붙하게 됨 ④ 비용을 내는데 이 프로젝트에서 그 이점(무상태 확장·앱 지원)을 안 씀.
그리고 세션이 영구 선택이 아니다 — 나중에 JWT로 전환하는 것 자체가 좋은 학습이 되고
ADR supersede·expand-contract를 실제로 써보는 기회가 된다.

> **사용자**: 아니야. 그냥 **JWT**로 가자. 나 회사에서 JWT가 기본이야.

> **사용자**: 무상태가 뭐야? 일단 표준인 걸 하고 싶어.

→ 무상태 개념은 `specs/learning/2026-07-27-stateless-jwt-session.md` 에 별도 기록.
"표준인 것"을 원한다는 판단에 따라 C 채택.

## 그래서 포기한 것

| 포기한 것 | 내용 |
|---|---|
| **완전 무상태** | Refresh를 서버에 저장하므로 JWT의 "서버가 상태를 안 가진다"는 장점이 절반 사라진다. 남는 차이는 조회 빈도뿐 — 세션은 매 요청, 이 방식은 재발급 시에만 |
| **구현 단순성** | 세션이면 Spring Security 기본 설정으로 끝난다. JWT는 토큰 발급·검증·Refresh 회전·무효화를 직접 만들어야 하고, 001의 작업량이 늘어난다 |
| **학습 순서** | 필터 체인을 이해하기 전에 커스텀 필터를 다루게 된다. 이 위험은 learning 노트로 보완한다 |
| **즉시 차단** | 로그아웃 후에도 Access 토큰 수명(최대 1시간)만큼은 유효하다. 세션이면 즉시 끊긴다 |

## 남은 리스크

1. **초기 관리자 비밀번호 변경 강제 기능이 없다.** 001 범위에서 회원정보 수정을 제외했기
   때문이다. 환경변수로 시딩한 초기 비밀번호가 계속 쓰일 수 있다.
   → 회원정보 수정 스토리에서 처리한다.
2. **Access 토큰 수명 동안의 차단 지연.** 즉시 차단이 필요한 요구가 생기면
   Access 토큰 블랙리스트가 필요해지고, 그때 이 ADR을 대체하는 새 ADR을 쓴다.
3. **네이티브 앱 계획 미확인.** 위 "오간 대화" 참조. 결정 자체는 앱 여부와 무관하게
   성립하지만 근거의 한 축이 비어 있다.

## 파생 결정 (같은 세션에서 함께 정함)

| | 결정 | 근거 |
|---|---|---|
| 저장 위치 | `httpOnly` 쿠키 | constitution 보안 요구사항이 LocalStorage를 금지 |
| 만료 | Access·Refresh 모두 필수 | constitution 보안 요구사항 |
| 사용자/관리자 | **하나의 체계**, 권한은 role로 구분 | 인증을 두 벌 만들면 취약점 표면이 두 배 |
| 비밀번호 해싱 | bcrypt 또는 argon2 | constitution. 원 요구사항의 MySQL `SHA2()`는 빠른 해시라 금지 |
| 비밀번호 길이 | 최소 8자, **최대 64자** | 최소는 constitution. 상한 12자는 완화 — 해시는 입력 길이와 무관하게 같은 길이로 저장되므로 짧은 상한은 얻는 것이 없고 패스프레이즈만 막는다 |
| 관리자 계정 생성 | 앱 부팅 시 **환경변수 기반 시딩**(없을 때만 생성) | 마이그레이션에 `INSERT`를 넣으면 bcrypt 해시가 git에 커밋된다. 레포가 public이라 constitution 원칙 VII와 충돌 |

Access·Refresh의 **구체적 수명 값**은 4번 plan에서 정한다(실무 범위: Access 15분~1시간,
Refresh 7~30일).
