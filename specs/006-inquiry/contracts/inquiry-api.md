# API 계약 — 006 문의게시판

> `/speckit-plan` Phase 1 산출물. **AC와 1:1로 대응시킨 계약**이며,
> 7번에서 코덱스가 **이 문서와 `spec.md`만 보고** 테스트를 작성한다(구현 코드를 보지 않는다).

**공통 오류 형식**: RFC 9457 Problem Details + `code`/`traceId` 확장 — **001이 만든 공통
생성기를 그대로 쓴다.** 006이 추가하는 것은 **`code` 값뿐**이다.

```json
HTTP 4xx/5xx
Content-Type: application/problem+json
{
  "type": "/errors/<범주>",
  "title": "...",
  "status": 403,
  "detail": "사람이 읽는 메시지",
  "instance": "/api/inquiries/12/unlock",
  "code": "INQUIRY_PASSWORD_INVALID",
  "traceId": "a3f9c2"
}
```

**오류 코드 접두사는 `INQUIRY_`** 다. 게시판 4종의 공통 체계가 2단계에서 정해지면 그쪽을
따른다 — **문자열만 바뀌고 이 표의 구조는 유지된다**(spec Assumptions 8).

**인증**: 001의 `httpOnly` 쿠키를 그대로 쓴다. 006은 **새 자격증명을 만들지 않는다.**
단 하나의 예외가 **열람 통과**이며, 그것은 자격증명이 아니라 **글 하나에 대한 단기 열람
상태**다(`FR-025`) — 보관 방식은 **`ADR-026`에서 사람이 확정**한다.

## 엔드포인트 한눈에 — **권한을 여기서 못박는다**

| # | 메서드 · 경로 | 인증 | 권한 | 주요 AC |
|---|---|---|---|---|
| 1 | `GET /api/inquiries` | **불필요** | 누구나. **단 `mine=true`는 인증 필요** | `AC-1`~`AC-15` |
| 2 | `GET /api/inquiries/{id}` | **선택** | 누구나 요청 가능. **비밀글 본문은 작성자·`ADMIN`·통과자만** | `AC-28`~`AC-32`·`AC-38`·`AC-41` |
| 3 | `POST /api/inquiries/{id}/unlock` | **불필요** | 누구나(비로그인 포함) | `AC-29`·`AC-34`·`AC-35`·`AC-37`·`AC-42`·`AC-50` |
| 4 | `POST /api/inquiries` | **필요** | `USER` 또는 `ADMIN` | `AC-16`~`AC-18`·`AC-22`~`AC-25` |
| 5 | `PUT /api/inquiries/{id}` | **필요** | **작성자 본인만**(미답변). `ADMIN` 도 남의 글은 불가 | `AC-18`~`AC-20`·`AC-26`·`AC-33`·`AC-49`·`AC-51`② |
| 6 | `DELETE /api/inquiries/{id}` | **필요** | **작성자 본인(미답변) 또는 `ADMIN`(제한 없음)** | `AC-19`·`AC-21`·`AC-33`·`AC-51`① |
| 7 | `POST /api/admin/inquiries/{id}/answer` | **필요** | **`ADMIN`** | `AC-43`~`AC-46` |
| 8 | `PUT /api/admin/inquiries/{id}/answer` | **필요** | **`ADMIN`** | `AC-47`① |
| — | `DELETE .../answer` | — | **존재하지 않는다** | `AC-47`② |

> **7·8을 `/api/admin/**` 아래에 두는 이유**: 001 `SecurityConfig`가 이미 그 경로에
> **인증 + `ADMIN` 게이트**를 걸어 두었다(`001 AC-21`·`AC-22`). 새 게이트를 만들면
> **권한 판정이 두 곳**이 되고, 두 곳은 언젠가 갈라진다.
>
> **반대로 목록·상세는 관리자도 1·2번을 그대로 쓴다.** 관리자 화면(004)이 보는 데이터가
> 사용자 화면과 같고, 경로를 나누면 **같은 규칙을 두 벌 유지**하게 된다.
> 응답 차이(비밀글 본문·검색 범위)는 **경로가 아니라 요청자의 권한**이 만든다.

## 1. `GET /api/inquiries` — 목록

**인증**: 불필요 (`FR-001` — `001 FR-021`의 이행)

### 요청 파라미터

| 파라미터 | 기본값 | 허용 | 위반 시 | AC |
|---|---|---|---|---|
| `from` · `to` (등록일시) | **최근 1개월** | **최대 1년**(002 표기와 같다 — 아래 정정) · `from ≤ to` | 400 `BOARD_SEARCH_PERIOD_TOO_LONG` / `BOARD_SEARCH_PERIOD_INVALID`(뒤집힌 경우) | `AC-2`·`AC-3` |
| `keyword` | 없음 | 제목·내용·등록자 부분 일치. **앞뒤 공백 제거, 공백뿐이면 조건에서 뺀다** | — | `AC-4`~`AC-6` |
| `size` (개씩 보기) | **10** | `10·20·30·40·50` | 400 `BOARD_PAGE_SIZE_NOT_ALLOWED` | `AC-7` |
| `sort` (정렬 기준) | **등록일시** | 등록일시 · 제목 · 조회수 | 400 `BOARD_SORT_NOT_ALLOWED` (**`분류`도 여기로**) | `AC-8`·`AC-9` |
| `direction` | **내림차순** | 내림차순 · 오름차순 | 400 `BOARD_SORT_NOT_ALLOWED` | `AC-8` |
| `page` | **`0`** | **0 이상**(0 기반) | 400 `BOARD_PAGE_INVALID`. **범위를 넘은 페이지는 400이 아니라 200 + 빈 목록**(002 `AC-13`) | Edge Cases |
| `mine` (나의 문의내역) | `false` | `true`면 **인증 필요** | **401 `AUTH_REQUIRED`** (조용히 무시하지 않는다) | `AC-13`·`AC-14` |

> **파라미터 이름은 이 표에서 확정하지 않는다.** 게시판 4종의 **공통 계약**(2단계)이 정하며,
> 006이 먼저 정하면 4종이 갈라진다. **이 표가 규정하는 것은 기본값·허용 범위·위반 시 응답**이다.

> ⚠️ **통합 단계 정정 (2026-07-31) — 002 기준으로 통일했다.** 원문과 달라진 것 3가지.
>
> | 항목 | 006 원문 | 002 계약 = 확정 | 왜 006이 틀렸나 |
> |---|---|---|---|
> | `page` | `1`, **1 이상**, 0·음수는 400 | **`0`, 0 이상**(0 기반) | 002는 `page=0`이 **첫 페이지**다. 006 규칙이면 공통 훅이 보낸 첫 요청이 **전부 400**이 된다 |
> | 범위 초과 페이지 | Edge Cases가 400으로 읽히게 적혀 있었다 | **200 + 빈 목록**(`AC-13`) | *"보는 사이 남이 글을 지우면 정상 사용 중에 발생한다"* — 002가 이미 근거를 적었다 |
> | 기간 상한 | **365일** | **1년** | 윤년이 낀 구간에서 **366일**이 되어 같은 조건이 게시판마다 통과/거부로 갈린다 |
>
> 오류 코드도 `INQUIRY_*` → **`BOARD_*` / `POST_*`** 로 바꿨다. 같은 실패에 게시판마다
> 다른 `code`를 주면 **공통 화면이 분기할 수 없다.**

### 응답

| 응답 | 조건 | `code` | AC |
|---|---|---|---|
| **200** | 목록 + 전체 건수. **결과가 0건이어도 200이고 빈 목록** | — | `AC-1`·`AC-2`·`AC-4` |
| **200** | 마지막 페이지 너머 요청 → 빈 목록 | — | Edge Cases |
| 400 | 위 표의 위반 | 위 표 | `AC-3`·`AC-7`·`AC-9` |
| **401** | `mine=true` 인데 미인증 | `AUTH_REQUIRED` | `AC-14` |

**행 하나에 담기는 것 — 화이트리스트다**

```
번호(전체 건수 기준 역순) · 제목 · 등록자 이름 · 등록일시 · 조회수
· 답변 상태(미답변/답변완료) · 비밀글 여부 · new 표시
```

**★ 이 목록에 없는 것은 응답에 담지 않는다.** 특히 **본문 내용과 답변 내용**(`AC-15`·`FR-011`).
비밀글도 **제목과 등록자는 그대로 보인다**(`AC-22` — 가리면 제목 검색이 깨진다).

**계약 주의**

- **번호는 전체 건수 기준 역순**이다. 25건·10개씩이면 **2페이지 첫 행이 15**다(`AC-10`).
  페이지 안의 행 번호를 쓰면 2페이지 첫 글도 1번이 되어 글을 특정할 수 없다.
- **`new` 기준 일수는 설정값**이고 기본 7일이다(`AC-11`). **코드에 박으면 안 된다** —
  바꿔서 결과가 달라지는 것까지가 계약이다.
- **`mine`은 다른 조건과 AND**다(`AC-13`). *"내 글 전부"* 도 *"검색어에 걸린 전부"* 도 아니다.

### ★ 검색 범위가 요청자에 따라 달라진다 (`FR-004`)

| 요청자 | 검색 대상 |
|---|---|
| 비로그인 · 다른 사용자 | 모든 글의 **제목·등록자** + **공개글의 내용** + **자기 비밀글의 내용** |
| 작성자 본인 | 위 + **자기 비밀글의 내용** |
| `ADMIN` | **제한 없음** |

**이것은 공통 규칙(검색 범위 = 제목·내용·등록자)에서 의도적으로 이탈한 것이다.**
그대로 두면 **결과의 유무가 내용을 한 글자씩 알려주어** `환불계좌` → `환불계좌 1` →
`환불계좌 12` 로 좁혀가며 **비밀번호를 한 번도 맞히지 않고 내용을 복원**할 수 있다(`AC-5`).

## 2. `GET /api/inquiries/{id}` — 상세

**인증**: 선택. **응답 내용이 요청자에 따라 달라진다.**

| 응답 | 조건 | `code` | AC |
|---|---|---|---|
| **200** | 공개글 | — | `AC-42` |
| **200** | 비밀글 + **작성자 본인** | — | `AC-30` |
| **200** | 비밀글 + **`ADMIN`** | — | `AC-31`·`AC-36`② |
| **200** | 비밀글 + **유효한 열람 통과 보유** | — | `AC-37`① |
| **403** | 비밀글 + 위 셋 중 아무것도 아님. **공개 항목만 반환** | `INQUIRY_PASSWORD_REQUIRED` | `AC-28`·`AC-32`·`AC-41` |
| **404** | 없는 글 · 삭제된 글 | `POST_NOT_FOUND` | `AC-38`① |

**200이 반환하는 것**: 목록의 항목 + **본문 내용** + **답변**(있으면 내용·답변자 이름·답변일시).
답변이 없으면 **답변 영역이 비어 있다는 사실**을 응답이 말한다 — 문구
(`"아직 등록된 답변이 없습니다."`)는 **화면이 그린다**(`AC-48`).

**403이 반환하는 것**: **목록에 이미 공개된 항목만** —
번호 · 제목 · 등록자 · 등록일시 · 조회수 · 답변 **상태**.
**본문 내용과 답변 내용은 어떤 필드에도 없다.**

> **왜 403에 무언가를 주는가**: 비밀번호 입력 화면이 *"어떤 글의 비밀번호를 넣는지"* 를
> 보여줘야 한다. 그 항목들은 **목록에서 이미 보이므로 새로 새는 정보가 없다**(판단 15).

**계약 주의**

- **`GET`은 열람 통과를 만들지 않는다.** 통과를 만드는 것은 3번뿐이다.
- **`GET`은 비밀글의 조회수를 올리지 않는다** — 403으로 끝난 요청은 열람이 아니다(`AC-42`).
  200으로 본문을 반환할 때만 1 증가한다.
- **차단(`AC-34`) 중에도 이 엔드포인트는 작성자·`ADMIN` 에게 200이다**(`AC-36`).
  **차단은 3번 경로에만 걸린다.**

## 3. `POST /api/inquiries/{id}/unlock` — 비밀번호로 열람

**인증**: 불필요. **비로그인 사용자도 통과할 수 있어야 한다**(`AC-29`의 Given).

```json
{ "password": "1234" }
```

| 응답 | 조건 | `code` | AC |
|---|---|---|---|
| **200** | 정확한 비밀번호. **2번의 200과 같은 본문** + 열람 통과 성립 + **조회수 +1** | — | `AC-29`·`AC-37`·`AC-42`·`AC-50` |
| **400** | 형식 위반(4자리 아님 · 숫자 아님) | `INQUIRY_SECRET_PASSWORD_FORMAT_INVALID` | `AC-24` |
| **403** | 비밀번호 불일치. **남은 시도 횟수를 함께** 준다 | `INQUIRY_PASSWORD_INVALID` | `AC-38`②·`AC-39` |
| **429** | 글 단위 또는 클라이언트 단위 임계 초과 | `INQUIRY_PASSWORD_TOO_MANY_ATTEMPTS` | `AC-34`·`AC-35` |
| **404** | 없는 글 · 열람 대기 중 작성자가 삭제 | `POST_NOT_FOUND` | `AC-38`①·Edge Cases |
| **400** | 비밀글이 아닌 글에 호출 | `INQUIRY_NOT_SECRET` | — |

### ★ 이 엔드포인트의 규칙 5개 — 하나라도 어기면 비밀글이 비밀이 아니다

| | 규칙 | 어기면 |
|---|---|---|
| 1 | **성립하는 통과는 `{id}` 하나에만 적용된다** | A를 뚫으면 B·C가 함께 열린다(`AC-37`②) |
| 2 | **통과에는 만료가 있다** | 한 번 연 사람이 영구히 연다(`FR-025`) |
| 3 | **통과는 열람만 준다** | 4자리를 맞히면 남의 글을 지울 수 있게 되고, **1만 번이면 게시판이 지워진다**(`AC-33`) |
| 4 | **실패는 401이 아니라 403이다** | 401은 이 프로젝트에서 **로그인 자격증명 경로**라 화면이 재발급·로그인 이동으로 반응한다 → **비밀번호 한 번 틀렸다고 로그아웃**된다(`AC-39`) |
| 5 | **실패 카운트를 두 축으로 센다** | 글 축만 세면 **글을 돌아가며 우회**하고, 클라이언트 축만 세면 **여러 곳에서 한 글을 노리는 시도**를 못 막는다(`AC-34`·`AC-35`) |

**점진적 지연과 차단** (`FR-023`·`FR-024` · 값은 가정이며 7번에서 실측):
실패가 쌓일수록 응답이 늦어지고, **글 단위 10회 / 클라이언트 단위 30회**(1분 창)를 넘으면
**429 + 10분 차단**. **차단 상태에서는 지연 없이 즉시 429**를 준다 — 차단 중에도 기다리게 하면
**방어 장치가 스레드를 붙잡는 서비스 거부 수단**이 된다(001이 같은 함정을 처리했다).

**차단은 작성자와 `ADMIN` 에게 영향을 주지 않는다**(`AC-36`). 001이 계정 잠금을 기각한 이유는
*"아이디만 아는 공격자가 주인을 쫓아낼 수 있다"* 였는데, **여기서는 주인과 관리자가 이 경로를
쓰지 않아 피해자가 없다.** 같은 규칙을 다르게 적용하는 것이 아니라 **막았을 때 누가 피해를
보는지가 다르다.**

**비밀번호는 앞뒤 공백을 제거하지 않는다.** 숫자 4자리이므로 공백이 섞였다면
**형식 위반으로 거부하는 것이 맞다**(검색어와 반대다).

## 4. `POST /api/inquiries` — 등록

**인증**: 필요 (`FR-012`)

```json
{ "title": "결제 오류 문의", "content": "...", "secret": true, "password": "1234" }
```

| 응답 | 조건 | `code` | AC |
|---|---|---|---|
| **201** | 성공. 등록자는 요청자, 상태는 **미답변** | — | `AC-16` |
| **401** | 미인증 | `AUTH_REQUIRED` | `AC-17` |
| 400 | 제목 빈 값 | `POST_TITLE_REQUIRED` | `AC-18`① |
| 400 | 제목 **100자 이상** | `POST_TITLE_LENGTH_INVALID` | `AC-18`② |
| 400 | 내용 빈 값 | `POST_CONTENT_REQUIRED` | `AC-18`③ |
| 400 | 내용 **4000자 이상** | `POST_CONTENT_LENGTH_INVALID` | `AC-18`④ |
| 400 | `secret=true` 인데 비밀번호 없음 | `INQUIRY_SECRET_PASSWORD_REQUIRED` | `AC-23` |
| 400 | 비밀번호 형식 위반 | `INQUIRY_SECRET_PASSWORD_FORMAT_INVALID` | `AC-24` |

**계약 주의**

- **위 400들은 화면을 거치지 않은 직접 호출에도 동일**하다. 화면 검증은 편의일 뿐
  **서버가 방어선**이다(`FR-013` — `001 FR-002`와 같은 원칙).
- 길이는 **문자 수**로 센다. 이모지·한글을 바이트로 세면 훨씬 일찍 막힌다.
- **비밀번호는 문자열로 다룬다.** `0000` 이 유효하고 앞자리 0이 잘리면 안 된다(`AC-50`).
- **`secret=false` 인데 비밀번호를 보내면 무시하고 저장하지 않는다**(Edge Cases).
  쓰이지 않는 잠금 값을 남기면 `AC-26`이 막으려던 상태가 그대로 생긴다.
- **저장은 되돌릴 수 없는 느린 해시 + 글마다 다른 소금값**이다(`AC-25`).
  같은 `1234` 두 건의 **저장값이 서로 달라야** 한다 — 같으면 *"비밀번호가 같은 글"* 을
  묶을 수 있고, 값의 종류가 1만뿐이라 그 충돌이 자주 일어난다.

## 5. `PUT /api/inquiries/{id}` — 수정

**인증**: 필요. **작성자 본인만**(`FR-014`)

| 응답 | 조건 | `code` | AC |
|---|---|---|---|
| **200** | 성공(작성자 + 미답변) | — | `AC-26`·`AC-49` |
| 400 | 4번과 **동일한 검증 전부** | 4번과 동일 | `AC-18` |
| **401** | 미인증 | `AUTH_REQUIRED` | — |
| **403** | 남의 글 · **비밀번호를 맞힌 제3자** · **`ADMIN` 의 남의 글 수정** | `AUTH_FORBIDDEN` | `AC-19`·`AC-33`·`AC-51`② |
| **409** | **답변이 등록된 글** | `INQUIRY_ALREADY_ANSWERED` | `AC-20` |
| **404** | 없는 글 | `POST_NOT_FOUND` | — |

**★ 비밀번호 칸의 3상태 — 여기가 이 엔드포인트에서 가장 틀리기 쉽다**

| 요청 | 결과 | 근거 |
|---|---|---|
| `secret=true` + 비밀번호 **새 값** | 새 값으로 교체 | — |
| `secret=true` + 비밀번호 **비어 있음** | **기존 비밀번호 유지** | **`AC-49`.** "삭제"로 해석하면 `AC-23`이 금지한 상태가 **수정 경로로 우회 생성**된다 |
| `secret=false` | 공개글이 되고 **저장된 비밀번호를 지운다** | **`AC-26`.** 남겨두면 나중에 비밀글로 되돌릴 때 **작성자가 잊은 옛 비밀번호가 되살아난다** |

**409 판정은 저장 시점에 다시 한다**(Edge Cases). 수정 화면을 열 때 미답변이었다는 사실은
**권한의 근거가 되지 않는다** — 그 사이에 관리자가 답변할 수 있다.

## 6. `DELETE /api/inquiries/{id}` — 삭제

**인증**: 필요. **작성자 본인(미답변) 또는 `ADMIN`(제한 없음)** (`FR-014`·`FR-015`)

| 응답 | 조건 | `code` | AC |
|---|---|---|---|
| **204** | 작성자 + 미답변 | — | — |
| **204** | **`ADMIN`** — **답변 여부와 무관** | — | `AC-51`① |
| **403** | 남의 글(일반 사용자) · 비밀번호를 맞힌 제3자 | `AUTH_FORBIDDEN` | `AC-19`·`AC-33` |
| **409** | **작성자**인데 답변이 등록된 글 | `INQUIRY_ALREADY_ANSWERED` | `AC-21` |
| **404** | 없는 글 | `POST_NOT_FOUND` | — |

> **★ 관리자와 작성자의 규칙이 다른 유일한 자리다.** 운영자는 부적절한 글을 내릴 수 있어야
> 하고(`AC-51`①), **`FR-015`의 미답변 제한은 작성자에게만** 적용된다.
> 반대로 **수정은 관리자에게도 주지 않는다**(`AC-51`②) — 관리자가 질문 문구를 바꿀 수 있으면
> **문답 기록의 신뢰가 사라진다.**
>
> *(이 비대칭은 스펙의 Edge Cases와 판단 16에만 있고 `FR-014`에는 없어 **문서가 스스로와
> 어긋나 있었다.** 4번 계획이 `FR-014` 문구를 고치고 `AC-51`을 신설했다.)*

**글이 지워지면 답변도 함께 지워진다**(답변을 별도 테이블로 둘 경우 `ON DELETE CASCADE`).
문의 없는 답변은 의미가 없고, 남으면 고아 행이 그대로 장애가 된다.

## 7. `POST /api/admin/inquiries/{id}/answer` — 답변 등록

**인증**: 필요 + **`ADMIN`**(`FR-030`)

```json
{ "content": "확인 결과 ..." }
```

| 응답 | 조건 | `code` | AC |
|---|---|---|---|
| **201** | 성공. 상태가 **답변완료**로 바뀐다 | — | `AC-43` |
| **403** | `USER` 권한 | `AUTH_FORBIDDEN` | `AC-44` |
| **409** | **이미 답변이 있음** | `INQUIRY_ANSWER_ALREADY_EXISTS` | `AC-45` |
| 400 | 내용 빈 값 | `INQUIRY_ANSWER_CONTENT_REQUIRED` | `AC-46`① |
| 400 | 내용 **4000자 이상** | `INQUIRY_ANSWER_CONTENT_LENGTH_INVALID` | `AC-46`② |
| **404** | 없는 글 | `POST_NOT_FOUND` | — |

**계약 주의**

- **409 판정을 코드로만 하면 안 된다.** 관리자 둘이 동시에 누르면 *"답변이 있나?"* 검사를
  **둘 다 통과**하고 **나중 쓰기가 앞을 조용히 덮어쓴다.** → **DB 유일 제약이 판정한다**
  (001이 아이디 중복을 DB에 맡긴 것과 같은 판단. 스키마 형태는 **`ADR-027`**).
- **답변 등록은 문의의 조회수를 올리지 않는다.**
- **관리자가 자기 문의에 자기가 답하는 것을 막지 않는다**(Edge Cases). 막을 근거가 없다.
- 상태가 답변완료로 바뀌는 순간 **작성자의 수정·삭제가 409로 닫힌다**(`AC-20`·`AC-21`).

**인증**: 필요 + **`ADMIN`**

| 응답 | 조건 | `code` | AC |
|---|---|---|---|
| **200** | 내용이 바뀌고 **상태는 답변완료 그대로** | — | `AC-47`① |

## 답변 삭제 — **엔드포인트를 만들지 않는다**

`DELETE /api/admin/inquiries/{id}/answer` 는 **404 또는 405**로 응답한다(`AC-47`②).

> **왜 없는가**: 답변을 지우면 상태가 **미답변으로 되돌아가고, 그 순간 작성자의 수정·삭제
> 권한이 되살아난다**(`FR-015`). 관리자가 오타를 지우려다 **질문이 통째로 바뀔 수 있는 문**을
> 여는 것이다. 오타는 8번으로 고치고, 문의 자체를 없애야 하면 6번을 쓴다.
> **상태가 답변완료 → 미답변으로 가는 경로가 이 계약에 존재하지 않는다.**

## ★ 이 계약에서 가장 깨지기 쉬운 부분

### 1. **비밀글의 본문과 답변이 실리면 안 되는 자리가 넷이다**

**셋을 막고 하나를 놓치면 막은 셋이 전부 무의미해진다.** 그리고 넷은 서로 다른 코드에서
만들어지기 쉽다 — 목록은 목록 쿼리가, 검색은 검색 조건이, 403 응답은 예외 핸들러가,
답변은 답변 매퍼가 만든다.

| # | 자리 | 새면 | AC |
|---|---|---|---|
| 1 | **목록 응답** | 개발자 도구로 전 비밀글 본문을 읽는다. **화면이 안 그리는 것과 서버가 안 보내는 것은 다르다** | `AC-15` |
| 2 | **검색 결과** | 결과의 유무로 내용을 **한 글자씩 복원**한다. 비밀번호를 한 번도 맞히지 않는다 | `AC-5` |
| 3 | **권한 없는 상세(403)** | 화면이 가리기만 하면 그대로 읽힌다 | `AC-28`·`AC-32` |
| 4 | **답변 내용** | **답변은 질문을 인용하므로 본문보다 더 많이 말한다.** 본문만 가리면 가린 의미가 없다 | `AC-41` |

**대응**: **응답 필드를 고르는 자리를 하나로 둔다.** 001이 오류 응답을 **공통 생성기 1개 +
어댑터 3개**로 묶은 것과 같은 구조다. 그리고 **네 응답을 같은 화이트리스트로 검사하는
테스트를 따로** 둔다 — 각각 통과해도 넷이 서로 다를 수 있다.

**검사는 화이트리스트로 한다.** *"본문 문자열이 응답에 없는지"* 를 보면 **본문이 우연히
짧거나 비어 있는 테스트 데이터에서 통과**한다. **허용된 필드만 있는지**를 본다
(001 `AC-28`이 금지 문자열 목록을 기각한 것과 같은 이유).

### 2. **404와 403을 반대로 주기 쉽다** — 그리고 이것은 원칙의 예외다

| 요청 | 응답 |
|---|---|
| 없는 글 · 삭제된 글 | **404 `POST_NOT_FOUND`** |
| 존재하는 비밀글 + 권한 없음 | **403 `INQUIRY_PASSWORD_REQUIRED`** |
| 존재하는 비밀글 + 비밀번호 틀림 | **403 `INQUIRY_PASSWORD_INVALID`** |

**constitution 원칙 IV는 *"남의 비공개 리소스 요청은 403이 아니라 404"* 를 요구한다.**
006은 이것을 **의도적으로 벗어난다.** 근거는 *"그 규칙의 목적은 존재 여부를 숨기는 것인데,
**문의글의 존재는 목록에서 이미 공개된다**"* 이고, 숨겨서 얻는 것이 0인 반면
**삭제된 글에 접근한 사용자가 원인 모른 채 차단에 걸리는** 손실은 실재한다.
→ **`plan.md`의 Complexity Tracking · **`ADR-028`**.** **사람이 예외를 인정하기 전까지는
미결이다.**

### 3. **열람 통과가 다른 글로 번진다**

구현하기 쉬운 쪽(*"이 사용자는 비밀글을 볼 수 있다"*)이 **틀린 쪽**이다.
통과 키에 **반드시 글 식별자를 포함**한다. `AC-37`②가 이것만 본다 —
A를 통과한 뒤 B가 여전히 403인지.

### 4. **조회수를 상세 진입부에서 올린다**

자연스럽게 쓰면 그렇게 된다. 그러면 **무차별 대입 1만 번이 조회수 1만으로 찍혀** 수치가
의미를 잃는다. **본문을 반환하기로 결정한 뒤에** 올린다(`AC-42`).

### 5. **`ADMIN` 을 "전부 할 수 있는 사람"으로 구현한다**

관리자에게 주는 것은 **열람 · 답변 · 삭제**이고 **남의 글 내용 수정은 주지 않는다**(`AC-51`②).
권한 검사를 `isAdmin || isOwner` 하나로 뭉치면 **수정까지 열린다.**

## 프론트 계약 (화면이 책임지는 것)

| | 요구 | AC |
|---|---|---|
| 비밀번호 입력 화면 | 상세 요청이 403 `INQUIRY_PASSWORD_REQUIRED` 면 **403이 함께 준 공개 항목으로 "어떤 글인지"를 보여주고** 입력을 받는다. **본문을 받아두고 가리는 방식을 쓰지 않는다** | `AC-28`·`AC-32` |
| 비밀글 등록 안내 | 비밀글 체크를 켜면 **제목과 등록자가 목록에 공개된다**는 안내를 표시한다 | `AC-27` |
| 남은 시도 횟수 | 403 `INQUIRY_PASSWORD_INVALID` 가 준 남은 횟수를 보여준다. 429면 **다시 시도할 수 있는 시점**을 안내한다 | `AC-34` |
| **403을 로그인으로 오해하지 않는다** | 비밀번호 오류는 **401이 아니다.** 화면의 401 처리(재발급·로그인 이동)가 이 응답에 발동하면 **비밀번호 한 번 틀렸다고 로그아웃**된다 | `AC-39` |
| 답변 없음 문구 | `"아직 등록된 답변이 없습니다."` | `AC-48` |
| 검색 조건 유지 | 상세→목록, 등록/수정 취소→목록에서 **직전 검색어·기간·정렬·개씩 보기·페이지**를 유지한다. **구현 방식은 공통 프론트(5단계)가 정한다** | `AC-12` |
| 확인 대화 | 등록/수정 취소 · 삭제 · 답변 등록 앞에 확인을 둔다(공통 규칙 1.2 · 6.5) | — |
