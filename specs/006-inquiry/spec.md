**작성일**: 2026-07-31

> 프레임워크·라이브러리·DB 종류는 이 문서에 등장하지 않는다.

## 개요

문의게시판은 사용자가 운영자에게 질문을 남기고 **관리자만 답변**하는 게시판이다.
다른 게시판 3종과 목록·상세·등록의 뼈대를 공유하지만 **이 스토리에만 있는 것이 셋**이다.

| | 이 스토리에만 있는 것 |
|---|---|
| **비밀글 + 4자리 비밀번호** | 열람을 비밀번호로 막는다. **보안 판단이 가장 많이 필요한 곳** |
| **관리자 답변** | 답변 유무가 사용자의 수정·삭제 권한을 좌우한다 |
| **나의 문의내역 필터** | 로그인한 사람만 쓸 수 있는 목록 필터 |

**포함**: 목록(검색·정렬·페이징·나의 문의내역) · 상세 · 등록/수정/삭제 · 비밀글 보호 ·
관리자 답변

**제외**: 분류(카테고리) · 첨부파일 · 댓글 — 이 게시판에는 없다

### 이 스토리가 가장 위험한 이유 — 4자리는 1만 가지다

비밀글 비밀번호는 **4자리**다. 숫자 4자리면 경우의 수가 **10,000**이고,
초당 20회만 시도해도 **10분이 채 걸리지 않는다.** 즉 **무차별 대입이 이론이 아니라 현실적으로
가능한 수준**이다. 001이 로그인에 점진적 지연(`001 AC-29`)을 넣은 것과 같은 이유로,
**시도 제한이 없으면 비밀글은 비밀이 아니다.**

그래서 이 스펙은 비밀번호를 "저장 방식"의 문제로만 다루지 않는다.
**해시로 저장하는 것(`FR-018`)은 DB가 유출됐을 때의 최소 조치일 뿐**이고 —
4자리는 느린 해시를 써도 오프라인에서 1만 번이면 전부 시도된다 —
**실제 방어선은 온라인 시도 제한(`FR-023`·`FR-024`)과 서버 권한 검증(`FR-019`~`FR-022`)이다.**
이 한계를 감추지 않고 문서에 남긴다.

## 001에서 이관된 AC — 이 스토리의 특별 임무

`001 spec.md`의 **`AC-25`**(*"인증 없이 문의게시판 목록 조회"*, `001 FR-021`)는
**006에서 검증하기로 미뤄둔 항목**이다. 001에는 문의게시판 리소스가 없어 검증할 수 없었고,
스텁을 만드는 것은 기각됐다(`test-strategy.md` 5.3).

- **이관 결과**: 이 문서의 **`AC-1`** 이 그 AC다. 본문을 옮겨 담았고 `001 FR-021`을 검증한다.
- **커버리지**: `test-strategy.md` 5.3 규칙 2에 따라 **001의 분모(36개)에서 제외되어 있고
  006의 분모(51개)에 들어간다.** 006에서 `AC-1`이 빠지면 `001 FR-021`은 **프로젝트 전체에서
  아무도 검증하지 않는 요구사항**이 된다.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 문의 목록을 본다 (Priority: P1) 🎯 MVP

누구나 문의 목록을 보고, 로그인한 사람은 자기 문의만 골라 본다.

**Why this priority**: 목록이 없으면 상세도 등록도 진입로가 없다. 그리고 **로그인 없이
열리는 유일한 게시판 경로**여서 `001 FR-021`의 검증 지점이기도 하다.

**Independent Test**: 로그아웃 상태로 목록을 요청해 200과 목록을 받는다 →
검색·정렬·개씩 보기·페이징이 반영되는지 확인 → 로그인해 `나의 문의내역`을 켜면 자기 글만 나온다.

**Acceptance Scenarios**:

- **AC-1** 인증 없이 문의게시판 목록을 조회한다 — ★ **`001 AC-25` 이관분**
  - **Given** 로그인하지 않은 상태이고 문의글이 1건 이상 등록되어 있고
  - **When** 문의게시판 목록 조회를 요청하면
  - **Then** 200이고 목록이 반환된다. `AUTH_REQUIRED` 로 거부되지 않는다
  - *근거*: `001 FR-021`. 문의게시판은 **로그인 전에 둘러볼 수 있어야** 사람들이 이미 답변된
    문의를 먼저 찾아보고 중복 문의를 줄인다. 001에는 이 리소스가 없어 검증을 006으로 이관했다
    (`test-strategy.md` 5.3) (001 FR-021)

- **AC-2** 기간을 지정하지 않으면 최근 1달이다
  - **Given** 60일 전 문의 1건과 3일 전 문의 1건이 있고
  - **When** 기간 조건 없이 목록을 요청하면
  - **Then** 3일 전 문의만 포함되고 60일 전 문의는 포함되지 않는다 (FR-002)

- **AC-3** 1년을 넘는 기간은 거부한다
  - **Given** 목록 조회를 준비했고
  - **When** 기간을 `from` ~ `to` 로 **366일** 지정해 요청하면
  - **Then** 400이고 `code=BOARD_SEARCH_PERIOD_TOO_LONG`
  - *근거*: 상한이 없으면 전체 기간 스캔 요청을 반복해 응답을 지연시킬 수 있다 (FR-002)

- **AC-4** 검색어는 제목·내용·등록자에 부분 일치한다
  - **Given** 제목에 `배송`이 든 글, 내용에 `배송`이 든 **공개글**, 등록자 이름이 `배송현`인 글이
    각각 있고 — 셋 다 비밀글이 아니고
  - **When** 검색어 `배송` 으로 목록을 요청하면
  - **Then** 세 건이 모두 포함된다 (FR-003)

- **AC-5** 비밀글의 **내용**은 제3자의 검색에 걸리지 않는다 ★
  - **Given** 다른 사람이 쓴 비밀글의 **내용**에만 `환불계좌` 라는 문자열이 있고 제목·등록자에는 없고
  - **When** 로그인하지 않은 상태(또는 작성자가 아닌 다른 사용자)로 검색어 `환불계좌` 로
    목록을 요청하면
  - **Then** 그 글이 결과에 **포함되지 않는다**
  - *근거*: 내용을 검색 대상에 두면 **검색 결과의 유무가 내용을 한 글자씩 알려준다.**
    `환불계좌` → `환불계좌 1` → `환불계좌 12` 로 좁혀가면 **비밀번호를 한 번도 맞히지 않고
    내용을 복원**할 수 있다. 비밀글을 만든 이유가 그 자리에서 무너진다 (FR-004)

- **AC-6** 본인과 관리자에게는 자기(또는 모든) 비밀글의 내용이 검색된다
  - **Given** `AC-5`와 같은 비밀글이 있고
  - **When** **그 글의 작성자**로 로그인해 검색어 `환불계좌` 로 요청하면
  - **Then** 그 글이 결과에 포함된다. **`ADMIN` 권한으로 요청해도 포함된다**
  - *근거*: 본인과 관리자는 어차피 본문을 볼 수 있으므로 검색에서 빼면 기능만 불편해지고
    막아지는 것이 없다 (FR-004)

- **AC-7** 개씩 보기는 기본 10이고 허용 값 밖은 거부한다
  - **Given** 문의글이 25건 있고
  - **When** ① 개씩 보기를 지정하지 않으면 **10건**이 반환되고 ② `30`으로 지정하면 25건 전부가
    반환되며 ③ `1000`으로 지정하면
  - **Then** ③은 400이고 `code=BOARD_PAGE_SIZE_NOT_ALLOWED` (허용: 10·20·30·40·50)
  - *근거*: 상한이 없으면 한 번의 요청으로 전체 데이터를 긁어갈 수 있다 (FR-005)

- **AC-8** 정렬은 기본 등록일시 내림차순이고 지정하면 바뀐다
  - **Given** 등록일시와 조회수가 서로 다른 문의글 3건이 있고
  - **When** ① 정렬을 지정하지 않고 요청하면 ② 정렬 기준 `조회수` · 방향 `오름차순`으로 요청하면
  - **Then** ①은 등록일시 내림차순, ②는 조회수 오름차순으로 반환된다 (FR-006)

- **AC-9** 정렬 기준으로 `분류`를 요청하면 거부한다
  - **Given** 목록 조회를 준비했고
  - **When** 정렬 기준을 `분류`(카테고리)로 지정해 요청하면
  - **Then** 400이고 `code=BOARD_SORT_NOT_ALLOWED`
  - *근거*: 문의게시판에는 분류가 없다. 조용히 무시하면 사용자는 정렬이 적용된 줄 알고
    잘못된 순서를 신뢰한다 (FR-006)

- **AC-10** 글 번호는 전체 건수 기준 역순이다
  - **Given** 문의글이 25건 있고 개씩 보기는 10이고
  - **When** **2페이지**를 요청하면
  - **Then** 첫 행의 번호가 **15**다(행 번호 1이 아니다). 1페이지 첫 행은 25다 (FR-007)

- **AC-11** `new` 표시는 기준 일수 안의 글에만 붙는다
  - **Given** 기준 일수가 7일이고, 3일 전 등록된 글과 10일 전 등록된 글이 있고
  - **When** 목록을 요청하면
  - **Then** 3일 전 글만 `new` 로 표시되고, **기준 일수를 3일로 바꾸면 어느 글에도 붙지 않는다**
  - *근거*: 기준을 코드에 박으면 게시판마다 다르게 두려 할 때 배포가 필요하다 (FR-008)

- **AC-12** 상세를 보고 돌아오면 검색 조건이 남아 있다
  - **Given** 검색어·기간·정렬·페이지를 지정해 목록을 조회한 상태이고
  - **When** 어떤 글의 상세로 들어갔다가 `목록` 으로 돌아오면
  - **Then** **직전과 동일한 검색어·기간·정렬·페이지**의 목록이 보인다.
    등록/수정을 취소하고 돌아올 때도 같다 (FR-009)

- **AC-13** `나의 문의내역` 은 다른 조건과 AND로 걸린다
  - **Given** 로그인한 사용자에게 검색어 `배송`이 포함된 자기 글 1건이 있고, 같은 검색어가
    포함된 **다른 사람의 글**도 1건 있고
  - **When** `나의 문의내역만 보기`를 켜고 검색어 `배송` 으로 요청하면
  - **Then** **자기 글 1건만** 반환된다(둘 다 아니고, 자기 글 전부도 아니다) (FR-010)

- **AC-14** 로그인하지 않고 `나의 문의내역`을 요청하면 거부한다
  - **Given** 로그인하지 않은 상태이고
  - **When** `나의 문의내역만 보기`를 켠 채 목록을 요청하면
  - **Then** 401이고 `code=AUTH_REQUIRED`
  - *근거*: 조건을 조용히 무시하고 전체 목록을 주면, 사용자는 **자기 글만 본다고 믿으면서
    전체를 보게 된다.** 401을 주면 화면이 로그인으로 보낸 뒤 `001 AC-24`(원래 목적지 복귀)로
    필터가 적용된 목록에 돌아올 수 있다 (FR-010)

- **AC-15** 목록 응답에 비밀글의 내용이 들어 있지 않다
  - **Given** 다른 사람이 쓴 비밀글이 있고 로그인하지 않은 상태이고
  - **When** 목록을 요청해 **응답 본문 전체**를 확인하면
  - **Then** 번호·제목·등록자·등록일시·조회수·답변 상태·비밀글 여부는 있고,
    **본문 내용과 관리자 답변 내용은 어떤 필드에도 들어 있지 않다**
  - *근거*: 화면이 안 그리는 것과 서버가 안 보내는 것은 다르다. 응답에 실려 있으면
    개발자 도구로 그냥 읽힌다 (FR-011)

### User Story 2 - 문의를 남기고 고치고 지운다 (Priority: P1)

로그인한 사용자가 문의를 등록하고, **아직 답변이 달리지 않았으면** 고치거나 지운다.

**Why this priority**: 목록에 보여줄 데이터를 만드는 단계다. US1과 함께 있어야
"문의게시판"이 성립한다.

**Independent Test**: 로그인해 문의를 등록하고 목록에서 확인 → 본인 글 수정·삭제 성공 →
관리자가 답변을 단 뒤 같은 수정을 시도하면 거부되는 것 확인.

**Acceptance Scenarios**:

- **AC-16** 로그인한 사용자가 문의를 등록한다
  - **Given** `USER` 권한으로 로그인했고
  - **When** 제목과 내용을 담아 문의 등록을 요청하면
  - **Then** 201이고 글이 생성되며 등록자는 그 사용자, 상태는 **미답변**이다 (FR-012)

- **AC-17** 로그인하지 않고 등록을 시도하면 거부한다
  - **Given** 로그인하지 않은 상태이고
  - **When** 문의 등록을 **직접** 요청하면
  - **Then** 401이고 `code=AUTH_REQUIRED`
  - *참고*: 화면은 `001 AC-24`에 따라 로그인 후 등록 화면으로 복귀시킨다 (FR-012)

- **AC-18** 제목·내용의 필수와 길이를 서버가 막는다
  - **Given** 로그인한 상태이고 **화면을 거치지 않고 직접 요청을 보낼 수 있고**
  - **When** ① 제목이 빈 값 ② 제목이 100자 ③ 내용이 빈 값 ④ 내용이 4000자 로 각각 요청하면
  - **Then** ①③은 400이고 `code=POST_TITLE_REQUIRED` / `POST_CONTENT_REQUIRED`,
    ②④는 400이고 `code=POST_TITLE_LENGTH_INVALID` / `POST_CONTENT_LENGTH_INVALID`
    (허용: 제목 100자 **미만**, 내용 4000자 **미만**). **수정 요청도 동일하다**
  - *근거*: 화면 검증만 있으면 직접 호출로 전부 우회된다(`001 FR-002`와 같은 원칙) (FR-013)

- **AC-19** 남의 글은 수정·삭제할 수 없다
  - **Given** 사용자 A의 미답변 문의가 있고 사용자 B로 로그인했고 **화면에는 수정 버튼이
    보이지 않고**
  - **When** B가 그 글의 수정(또는 삭제)을 **직접** 요청하면
  - **Then** 403이고 `code=AUTH_FORBIDDEN`. 글은 변경되지 않는다
  - *근거*: 버튼을 숨기는 것은 권한 검증이 아니다(`001 FR-019`·`001 AC-26`) (FR-014)

- **AC-20** 답변이 달린 글은 수정할 수 없다
  - **Given** 본인이 쓴 문의에 관리자 답변이 등록되어 상태가 **답변완료**이고
  - **When** 그 글의 수정을 요청하면
  - **Then** 409이고 `code=INQUIRY_ALREADY_ANSWERED`. 내용은 변경되지 않는다
  - *근거*: 답변 뒤에 질문을 바꾸면 **답변이 대답하지 않은 질문에 붙은 것처럼 남는다.**
    다른 사용자가 그 문답을 참고하면 잘못된 정보를 얻는다 (FR-015)

- **AC-21** 답변이 달린 글은 삭제할 수 없다
  - **Given** 본인이 쓴 문의가 답변완료 상태이고
  - **When** 그 글의 삭제를 요청하면
  - **Then** 409이고 `code=INQUIRY_ALREADY_ANSWERED`. 글과 답변이 모두 남는다
  - *근거*: 답변은 운영 기록이다. 질문자가 지우면 관리자가 무엇에 답했는지 사라진다 (FR-015)

- **AC-22** 비밀글로 등록하면 목록에 자물쇠와 **제목**이 보인다
  - **Given** 로그인했고
  - **When** 비밀글로 체크하고 제목 `결제 오류 문의`, 비밀번호 `1234` 로 등록한 뒤
    **로그아웃하고** 목록을 조회하면
  - **Then** 그 글이 목록에 나타나고 **제목 `결제 오류 문의`와 등록자 이름이 그대로 보이며**
    비밀글 표시(자물쇠)가 함께 붙는다 (FR-016)

- **AC-23** 비밀글인데 비밀번호가 없으면 거부한다
  - **Given** 로그인했고
  - **When** 비밀글로 지정하면서 비밀번호를 **비운 채** 등록을 직접 요청하면
  - **Then** 400이고 `code=INQUIRY_SECRET_PASSWORD_REQUIRED`. 글이 생성되지 않는다
  - *근거*: 비밀번호 없는 비밀글이 생기면 **아무도 열 수 없거나 아무나 열리는** 둘 중 하나가
    되고, 어느 쪽인지 코드를 봐야 알 수 있다 (FR-017)

- **AC-24** 비밀번호 형식이 어긋나면 거부한다
  - **Given** 로그인했고
  - **When** 비밀번호를 ① `123`(3자리) ② `12345`(5자리) ③ `12a4`(숫자 아닌 문자 포함)로
    각각 직접 요청하면
  - **Then** 셋 다 400이고 `code=INQUIRY_SECRET_PASSWORD_FORMAT_INVALID`
    (허용: **숫자 정확히 4자리** — Assumptions 3) (FR-017)

- **AC-25** 저장된 비밀번호는 평문이 아니고, 같은 값이라도 저장값이 다르다
  - **Given** 비밀번호를 **똑같이 `1234`** 로 지정한 비밀글 두 건을 등록했고
  - **When** 저장된 데이터를 조회하면
  - **Then** ① 두 저장값 어디에도 `1234` 라는 문자열이 없고 ② **두 저장값이 서로 다르다**
  - *근거*: ②가 없으면(글마다 다른 소금값이 없으면) 저장값 비교만으로 *"이 두 글은 비밀번호가
    같다"* 를 알 수 있고, 한 글의 비밀번호를 알아내면 같은 값을 쓴 모든 글이 함께 열린다.
    4자리는 값의 종류가 1만뿐이라 이 충돌이 **자주** 일어난다 (FR-018)

- **AC-26** 수정에서 비밀글을 해제하면 공개된다
  - **Given** 본인의 미답변 비밀글이 있고
  - **When** 비밀글 체크를 해제해 수정한 뒤 **로그아웃하고** 그 글의 상세를 요청하면
  - **Then** 200이고 **비밀번호를 묻지 않고 본문이 반환된다.** 저장되어 있던 비밀번호는 남지 않는다
  - *근거*: 비밀번호를 남겨두면 "공개글인데 잠금 값이 붙어 있는" 상태가 되고,
    나중에 비밀글로 되돌릴 때 **작성자가 잊은 옛 비밀번호가 되살아난다** (FR-016)

- **AC-27** 비밀글 등록 화면이 제목 공개를 알린다
  - **Given** 문의 등록 화면이고
  - **When** 비밀글 체크박스를 켜면
  - **Then** **제목과 등록자 이름은 목록에서 누구에게나 보인다**는 안내가 표시된다
  - *근거*: "비밀글"이라는 이름 때문에 사용자는 제목도 가려진다고 믿는다.
    그 오해 상태에서 제목에 주문번호·연락처·증상을 적는다. **기능을 바꾸지 않고 오해를 없애는
    가장 싼 방법이 안내다** (FR-028)

- **AC-49** 비밀글을 수정하면서 비밀번호를 비워 보내면 기존 비밀번호가 유지된다 ★
  — *4번 계획 신설*
  - **Given** 비밀번호가 `1234` 인 본인의 미답변 비밀글이 있고
  - **When** 비밀글 체크는 **켠 채** 제목만 바꾸고 **비밀번호 칸을 비워** 수정을 요청하면
  - **Then** 200이고, 이후 그 글은 **여전히 `1234` 로 열리며** 빈 비밀번호·다른 값으로는
    열리지 않는다. **비밀번호가 없는 비밀글이 만들어지지 않는다**
  - *근거*: Edge Cases에 규칙만 있고 검증하는 AC가 없었다. 빈 값을 *"비밀번호 삭제"* 로 해석하면
    `AC-23`이 금지한 상태(비밀번호 없는 비밀글)가 **수정 경로로 우회 생성**된다. 그 글은
    **아무도 열 수 없거나 아무나 열리고**, 어느 쪽인지는 비교 코드가 `null` 을 어떻게 다루는지에
    달린다 — 그것은 요구사항이 아니라 사고다 (FR-016)

- **AC-50** 비밀번호 `0000` 이 유효하고 앞자리 0이 보존된다 — *4번 계획 신설*
  - **Given** 로그인했고
  - **When** 비밀번호 `0000` 으로 비밀글을 등록한 뒤, 로그아웃하고 `0000` 으로 열람을 요청하면
  - **Then** 등록은 201이고 열람은 200이다. **`0` 이나 `000` 으로는 열리지 않는다**
  - *근거*: Edge Cases에 규칙만 있고 검증하는 AC가 없었다. 4자리를 **숫자로 다루면**
    `0000` 이 `0` 이 되어 ① 4자리 형식 검증에 스스로 걸리거나 ② `0`·`00`·`000` 과
    **같은 값이 되어 경우의 수가 1만보다 줄어든다.** 값의 공간이 조용히 좁아지는 것이라
    시도 제한 설계의 전제(`SC-003`)가 함께 흔들린다. **문자열로 다룬다** (FR-017)

- **AC-51** 관리자는 남의 글을 삭제할 수 있고 수정할 수는 없다 — *4번 계획 신설*
  - **Given** 사용자 A가 쓴 문의가 있고(답변 유무와 무관) `ADMIN` 으로 로그인했고
  - **When** ① 그 글의 **삭제**를 요청하고 ② 그 글의 **수정**을 요청하면
  - **Then** ①은 성공하고(204) ②는 403 `code=AUTH_FORBIDDEN` 이며 내용이 변경되지 않는다
  - *근거*: 운영자는 부적절한 글을 내릴 수 있어야 하지만 **질문 문구를 바꿀 수 있으면
    문답 기록의 신뢰가 사라진다**(판단 16). 이 비대칭이 Edge Cases와 판단 표에만 있고
    `FR-014`에는 *"작성자 본인만"* 으로 적혀 **문서가 스스로와 어긋나 있었다** —
    계약이 삭제 권한을 어느 쪽으로 쓰든 한쪽 문장을 위반하는 상태였다.
    `FR-014`의 문구를 함께 정정했다 (FR-014)

### User Story 3 - 비밀글을 지킨다 (Priority: P1) ★ 보안 핵심

비밀글의 내용은 **작성자 · 관리자 · 비밀번호를 맞힌 사람**에게만 보이고,
**무차별 대입으로는 뚫리지 않는다.**

**Why this priority**: 이 게시판의 존재 이유다. 뚫리면 사용자가 문의에 남긴 개인정보가
그대로 노출된다. US1·US2보다 뒤에 두는 것은 검증 순서일 뿐 우선순위가 낮아서가 아니다.

**Independent Test**: 제3자로 비밀글 상세를 요청해 본문이 오지 않는 것 확인 →
비밀번호를 반복해 틀려 지연·차단이 걸리는 것 확인 → 작성자·관리자는 비밀번호 없이 열리는 것 확인.

**Acceptance Scenarios**:

- **AC-28** 제3자의 비밀글 상세 요청에는 본문이 오지 않는다
  - **Given** 다른 사람이 쓴 비밀글이 있고 로그인하지 않은 상태이고
  - **When** 그 글의 상세를 요청하면
  - **Then** 403이고 `code=INQUIRY_PASSWORD_REQUIRED`. 응답에는 **목록에 이미 공개된 항목**
    (번호·제목·등록자·등록일시·조회수·답변 상태)만 들어 있고 **본문 내용과 답변 내용은 없다**
  - *근거*: 공개 항목을 함께 주는 이유는 비밀번호 입력 화면에 *"어떤 글의 비밀번호를 넣는지"*
    를 보여주기 위해서다. 그 항목들은 목록에서 이미 보이므로 새로 새는 정보가 없다 (FR-019)

- **AC-29** 올바른 비밀번호를 넣으면 본문이 열린다
  - **Given** `AC-28`의 비밀글이고 그 비밀번호가 `1234` 이고
  - **When** 비밀번호 `1234` 로 열람을 요청하면
  - **Then** 200이고 **본문 내용과 관리자 답변(있다면)이 반환된다** (FR-019)

- **AC-30** 작성자에게는 비밀번호를 묻지 않는다
  - **Given** 자기가 쓴 비밀글이 있고 그 계정으로 로그인했고
  - **When** 그 글의 상세를 요청하면
  - **Then** 200이고 **비밀번호를 한 번도 입력하지 않은 채** 본문이 반환된다
  - *근거*: 자기 글을 보려고 자기가 정한 4자리를 매번 기억해야 하면, 사용자는
    **모든 글에 `1111`을 쓰기 시작한다.** 편의가 아니라 **비밀번호를 약하게 만들지 않기 위한
    조치**다 (FR-020)

- **AC-31** 관리자에게도 비밀번호를 묻지 않는다
  - **Given** 다른 사람의 비밀글이 있고 `ADMIN` 권한으로 로그인했고
  - **When** 그 글의 상세를 요청하면
  - **Then** 200이고 비밀번호 없이 본문이 반환된다
  - *근거*: 관리자는 답변을 써야 하는데 **비밀번호를 알 방법이 없다.** 물으면 답변 기능이
    성립하지 않는다 (FR-020)

- **AC-32** 화면을 거치지 않은 직접 호출도 서버가 막는다
  - **Given** 다른 사람의 비밀글이 있고, 화면에서는 비밀번호 입력 창이 뜨는 상태이고
  - **When** 화면을 거치지 않고 상세 조회를 **직접** 요청하면
  - **Then** `AC-28`과 동일하게 403이고 본문이 반환되지 않는다
  - *근거*: 화면이 본문을 받아두고 가리기만 하면 개발자 도구로 그대로 읽힌다.
    비밀글 판정은 **서버가** 한다(`001 FR-019`와 같은 원칙) (FR-021)

- **AC-33** 비밀번호를 맞혀도 수정·삭제는 할 수 없다 ★
  - **Given** 다른 사람의 미답변 비밀글이고 그 비밀번호를 정확히 알고 있고
  - **When** 비밀번호로 열람에 성공한 뒤 같은 글의 **수정 또는 삭제**를 요청하면
  - **Then** 403이고 `code=AUTH_FORBIDDEN`. 글은 변경되지 않는다
  - *근거*: 비밀번호는 **읽기 통로**일 뿐이다. 4자리를 맞히면 남의 글을 지울 수 있다면,
    1만 번 시도로 **게시판을 삭제할 수 있다.** 수정·삭제의 기준은 소유자 확인 하나뿐이다
    (`001 FR-019`) (FR-022)

- **AC-34** 비밀번호를 반복해 틀리면 응답이 점점 늦어지고 결국 거부된다
  - **Given** 다른 사람의 비밀글이 있고
  - **When** 틀린 비밀번호로 같은 글에 연속으로 시도하면
  - **Then** 실패가 쌓일수록 응답까지 걸리는 시간이 길어지고, 기준을 넘으면 429와
    `code=INQUIRY_PASSWORD_TOO_MANY_ATTEMPTS` 를 반환한다.
    **지연 시간이 지난 뒤 올바른 비밀번호로는 정상 열람된다**
  - *근거*: 4자리는 1만 가지뿐이다. 제한이 없으면 자동화로 **10분 안에 전부 시도**된다.
    001의 `AC-29`와 같은 방식이며 이유도 같다 (FR-023)

- **AC-35** 글을 바꿔가며 시도해도 막힌다
  - **Given** 비밀글이 5건 있고
  - **When** **같은 클라이언트**가 다섯 글을 번갈아 가며 틀린 비밀번호를 반복 시도하면
  - **Then** 글별 임계에 닿기 전에도 **클라이언트 단위 임계**에서 429와
    `code=INQUIRY_PASSWORD_TOO_MANY_ATTEMPTS` 를 반환한다
  - *근거*: 제한을 **글 단위로만** 걸면 글을 돌아가며 시도해 그대로 우회된다.
    반대로 클라이언트 단위로만 걸면 여러 곳에서 한 글을 노리는 공격을 못 막는다.
    **두 축을 모두 세야 한다** (FR-023)

- **AC-36** 글 단위 차단이 걸려도 작성자와 관리자는 영향을 받지 않는다
  - **Given** 어떤 비밀글에 실패가 누적되어 비밀번호 경로가 일시 차단된 상태이고
  - **When** ① **그 글의 작성자**가 로그인해 상세를 요청하고 ② `ADMIN` 이 상세를 요청하면
  - **Then** 둘 다 200이고 본문이 정상 반환된다. 차단은 **비밀번호 입력 경로에만** 적용된다
  - *근거*: 001은 계정 잠금을 기각했다 — 아이디만 아는 공격자가 **주인을 쫓아낼 수 있기**
    때문이다. 여기서 글 단위 차단을 채택할 수 있는 이유는 **주인(작성자)과 관리자가 그 경로를
    쓰지 않기 때문**이다. 차단으로 불편해지는 사람은 *작성자가 비밀번호를 알려준 제3자* 뿐이고,
    그 통로는 부수적이다. **같은 규칙을 다르게 적용하는 것이 아니라, 막았을 때 누가 피해를
    보는지가 다르다** (FR-024)

- **AC-37** 한 번 열면 그 글은 다시 묻지 않고, 다른 글은 여전히 묻는다
  - **Given** 비밀글 A와 B가 있고 A의 비밀번호를 맞혀 열람에 성공했고
  - **When** ① A의 상세를 다시 요청하고 ② B의 상세를 요청하면
  - **Then** ①은 비밀번호 없이 200이고, ②는 403 `INQUIRY_PASSWORD_REQUIRED` 다.
    ①의 통과는 **정해진 유효 시간이 지나면 만료**되어 다시 비밀번호를 묻는다
  - *근거*: 새로고침·뒤로가기마다 4자리를 다시 치게 하면 사용자는 **기억하기 쉬운 값**을
    고른다. 통과를 재사용하되 **글 단위로 좁히고 시간으로 끊는 것**이 균형점이다.
    A의 통과가 B에 번지면 한 글만 뚫려도 전부 열린다 (FR-025)

- **AC-38** 없는 글과 틀린 비밀번호를 구분해 응답한다 ★
  - **Given** ① 존재하지 않는(또는 삭제된) 글 번호와 ② 존재하는 비밀글이 있고
  - **When** ①의 상세를 요청하고, ②에 틀린 비밀번호로 열람을 요청하면
  - **Then** ①은 404 `code=POST_NOT_FOUND`, ②는 403 `code=INQUIRY_PASSWORD_INVALID` 로
    **서로 다르게** 응답한다
  - *근거*: 001은 *"실패는 전부 같은 얼굴"*(`001 AC-2`·`AC-3`·`AC-32`)이었지만
    **여기는 계정 열거가 아니다.** 001이 응답을 통일한 이유는 **아이디의 존재 여부가 다른
    어디에도 공개되지 않는 정보**여서 응답이 유일한 누출 경로였기 때문이다.
    반면 **문의글의 존재는 목록에서 이미 공개된다**(`AC-22` — 비밀글도 번호·제목·등록자가 보인다).
    **이미 공개된 사실을 응답에서만 숨기는 것은 방어가 아니라 사용성 손실**이고,
    실제 피해는 이쪽이 크다 — 오래된 링크로 삭제된 글에 들어간 사람이 *"비밀번호가 틀렸다"* 를
    보고 계속 시도하다 `AC-34`의 차단에 걸리고, **원인을 영원히 알 수 없다** (FR-026)

- **AC-39** 비밀번호 오류가 로그인 상태를 흔들지 않는다
  - **Given** `USER` 로 로그인한 상태이고 다른 사람의 비밀글이 있고
  - **When** 틀린 비밀번호로 열람을 요청하면
  - **Then** 응답은 **401이 아니다**(403이다). 그 직후 인증이 필요한 다른 요청이 정상 동작하고
    로그인 화면으로 튕기지 않는다
  - *근거*: 이 프로젝트에서 401은 **로그인 자격증명 문제**(`AUTH_REQUIRED`·
    `AUTH_INVALID_CREDENTIALS`)로 이미 쓰이고, 화면은 401을 받으면 재발급이나 로그인 이동을
    한다(`001 FR-016`·`FR-020`). 글 비밀번호 오류에 401을 쓰면 **비밀번호를 한 번 틀렸다고
    로그아웃되는** 동작이 된다 (FR-027)

- **AC-40** 비밀번호가 기록에 남지 않는다
  - **Given** 비밀글 등록 · 열람 성공 · 열람 실패 · 차단 발동을 모두 수행했고
  - **When** 그 요청들이 남긴 **기록 전체**를 확인하면
  - **Then** **입력한 비밀번호 원문도, 저장된 해시값도** 어떤 형태로도 나타나지 않는다
  - *근거*: constitution 원칙 V. 실패 경로가 특히 위험하다 — 디버깅용으로
    *"입력값: 0000, 기대값: ..."* 을 남기기 쉽고, 그 로그 한 줄이 곧 비밀글 전체의 열쇠다.
    001의 `AC-36`과 같은 취지 (FR-029)

- **AC-41** 비밀글의 답변도 본문과 똑같이 보호된다
  - **Given** 다른 사람의 비밀글에 관리자 답변이 등록되어 있고 로그인하지 않은 상태이고
  - **When** 그 글의 상세를 요청하면
  - **Then** 403이고 **답변 내용이 응답에 포함되지 않는다.** 답변 **유무**(답변완료 표기)만 보인다
  - *근거*: 답변은 질문을 인용하기 마련이라 **본문보다 더 많이 말한다.**
    본문만 가리고 답변을 열어두면 가린 의미가 없다 (FR-035)

- **AC-42** 조회수는 열람에 성공했을 때만 오른다
  - **Given** 비밀글의 현재 조회수가 5이고
  - **When** ① 틀린 비밀번호로 3번 시도한 뒤 조회수를 확인하고 ② 올바른 비밀번호로 열람한 뒤
    조회수를 확인하면
  - **Then** ①은 여전히 5이고 ②는 6이다. 공개글은 상세를 열 때마다 1씩 오른다
  - *근거*: 실패한 시도로 조회수가 오르면 **무차별 대입 1만 번이 조회수 1만으로 찍혀**
    그 수치가 의미를 잃는다 (FR-036)

### User Story 4 - 관리자가 답변한다 (Priority: P2)

관리자가 문의에 답변을 등록하면 상태가 **답변완료**로 바뀐다.

**Why this priority**: US1·US2가 있어야 답변할 대상이 존재한다. 다만 답변 유무가
US2의 수정·삭제 권한을 좌우하므로 같은 스토리 안에서 완결한다.

**Independent Test**: `ADMIN` 으로 미답변 문의에 답변을 등록 → 목록·상세에 답변완료가 뜨고
작성자의 수정이 거부되는지 확인 → `USER` 로 같은 요청을 하면 403인지 확인.

**Acceptance Scenarios**:

- **AC-43** 관리자가 답변을 등록하면 답변완료가 된다
  - **Given** `ADMIN` 으로 로그인했고 미답변 문의가 있고
  - **When** 그 문의에 답변 내용을 담아 답변 등록을 요청하면
  - **Then** 200(또는 201)이고 상태가 **답변완료**로 바뀌며, 이후 상세·목록 조회에서
    답변 내용과 답변자 이름·답변일시가 함께 반환된다 (FR-030, FR-033)

- **AC-44** 일반 사용자는 답변할 수 없다
  - **Given** `USER` 권한으로 로그인했고 미답변 문의가 있고 **화면에 답변 입력창이 없고**
  - **When** 답변 등록을 **직접** 요청하면
  - **Then** 403이고 `code=AUTH_FORBIDDEN`. 상태는 미답변 그대로다
  - *근거*: `001 AC-26`. 화면에서 감춘 기능도 서버가 막는다 (FR-030)

- **AC-45** 답변은 문의당 하나다
  - **Given** 이미 답변이 등록된 문의가 있고 `ADMIN` 으로 로그인했고
  - **When** 같은 문의에 답변 등록을 **다시** 요청하면
  - **Then** 409이고 `code=INQUIRY_ANSWER_ALREADY_EXISTS`. 기존 답변은 그대로다
  - *근거*: 상태가 `미답변`/`답변완료` 둘뿐이므로 답변이 여러 개면 **어느 것이 그 상태를
    대표하는지 정의할 수 없다.** 내용을 고치려면 수정을 쓴다(`AC-47`) (FR-031)

- **AC-46** 답변 내용의 필수와 길이를 서버가 막는다
  - **Given** `ADMIN` 으로 로그인했고
  - **When** ① 답변 내용을 빈 값으로 ② 4000자로 직접 요청하면
  - **Then** ①은 400 `code=INQUIRY_ANSWER_CONTENT_REQUIRED`,
    ②는 400 `code=INQUIRY_ANSWER_CONTENT_LENGTH_INVALID` (허용: 4000자 미만).
    상태는 미답변 그대로다 (FR-032)

- **AC-47** 답변은 고칠 수 있고 지울 수는 없다
  - **Given** 답변이 등록된 문의가 있고 `ADMIN` 으로 로그인했고
  - **When** ① 답변 수정을 요청하고 ② 답변 **삭제**를 요청하면
  - **Then** ①은 200이고 내용이 바뀌며 상태는 **답변완료 그대로**다.
    ②는 제공되지 않는 동작으로 거부된다(404 또는 405). **상태가 미답변으로 되돌아가는 경로가
    존재하지 않는다**
  - *근거*: 답변을 지우면 상태가 미답변으로 돌아가고, 그 순간 **작성자의 수정·삭제 권한이
    되살아난다**(`FR-015`). 관리자가 오타를 지우려다 질문이 통째로 바뀔 수 있는 문을 연다.
    오타는 수정으로 고친다. 문의 자체를 없애야 하면 **글 삭제**를 쓴다 (FR-034)

- **AC-48** 답변이 없으면 없다고 보여준다
  - **Given** 미답변 문의가 있고
  - **When** 그 글의 상세를 조회하면
  - **Then** 답변 영역에 `"아직 등록된 답변이 없습니다."` 가 표시되고,
    목록에서도 그 글은 **미답변**으로 표기된다 (FR-033)

### Edge Cases

**경계값**

- **기간 검색의 양 끝**: `from`과 `to`가 같은 날이면 그 하루가 조회된다. `from`이 `to`보다
  뒤면 400으로 거부한다(조용히 뒤바꾸지 않는다 — 사용자가 잘못 입력한 것을 서버가 추측하면
  결과가 왜 그런지 설명할 수 없다). 정확히 365일은 통과하고 366일은 거부한다.
- **제목 99자 / 100자**: 99자는 통과, 100자는 거부(**미만**). 내용 3999자 / 4000자도 같다.
  길이는 **문자 수**로 센다 — 이모지·한글이 바이트로 세면 훨씬 일찍 막힌다.
- **빈 목록**: 검색 결과가 0건이어도 200이고 빈 목록이다. 404가 아니다.
- **마지막 페이지 너머**: 25건인데 5페이지를 요청하면 200이고 빈 목록이다.
- **비밀번호 `0000`**: 유효한 값이다. 앞자리 0이 잘려 3자리로 취급되면 안 된다(문자열로 다룬다).
  → **`AC-50`이 검증한다**(4번 계획 신설).

**동시성**

- **수정 화면을 열어둔 사이 답변이 달린다**: 사용자가 수정 화면에 들어간 뒤, 저장 전에
  관리자가 답변을 등록할 수 있다. **저장 시점에 서버가 상태를 다시 확인하고** 409
  `INQUIRY_ALREADY_ANSWERED` 로 거부한다. 화면을 열 때 미답변이었다는 사실은 권한의 근거가
  되지 않는다.
- **관리자 둘이 동시에 답변**: 하나만 성공하고 다른 하나는 `AC-45`와 같이 409다.
- **조회수 동시 증가**: 같은 글을 동시에 열면 증가가 유실될 수 있다. 조회수는 **정확한 회계가
  아니라 인기 지표**이므로 유실을 허용한다. 대신 **감소하거나 뒤로 가지는 않는다.**
- **삭제와 열람의 경합**: 비밀번호 입력 화면에 머무는 사이 작성자가 글을 삭제하면,
  열람 요청은 404 `POST_NOT_FOUND` 다(`AC-38`의 ①과 같은 응답).
- **차단 카운터의 경합**: 여러 요청이 동시에 실패하면 카운터가 임계를 **넘겨서** 증가할 수
  있다. 넘겨 세는 쪽(더 빨리 막히는 쪽)은 안전하므로 허용한다. **덜 세는 것은 허용하지 않는다.**

**빈 값 · 잘못된 값**

- **검색어가 공백뿐**: 빈 검색어와 같게 취급해 조건에서 뺀다. 공백을 그대로 부분 일치에 넣으면
  거의 모든 글이 걸려 검색이 무의미해진다.
- **검색어 앞뒤 공백**: 제거한 뒤 검색한다. 다만 **비밀번호는 제거하지 않는다** —
  숫자 4자리라 공백이 포함되면 형식 위반으로 거부하는 것이 맞다.
- **비밀글 체크 없이 비밀번호만 보냄**: 비밀번호를 무시하고 공개글로 등록한다.
  저장하지 않는다(`AC-26`과 같은 이유 — 쓰이지 않는 잠금 값을 남기지 않는다).
- **비밀글 수정 시 비밀번호를 비워서 보냄**: 기존 비밀번호를 유지한다. 비밀번호를 바꾸려면
  새 값을 넣는다. *(비워서 보낸 것을 "삭제"로 해석하면 `AC-23`이 금지한 상태가 만들어진다.)*
  → **`AC-49`가 검증한다**(4번 계획 신설).
- **존재하지 않는 정렬 필드**: 400으로 거부한다(`BOARD_SORT_NOT_ALLOWED`).
- **페이지 번호가 음수**: 400으로 거부한다(`BOARD_PAGE_INVALID`).
  *(통합 단계 정정 2026-07-31 — 원문은 **"0 또는 음수"** 를 거부했으나 **002 계약은 0 기반**이라
  `page=0`이 첫 페이지다. 006 규칙을 그대로 두면 공통 목록 훅의 첫 요청이 전부 400이 된다.)*
- **마지막 페이지를 넘어선 페이지 번호**: **400이 아니라 200 + 빈 목록**이다(002 `AC-13` 상속).

**권한 경계**

- **관리자 자신이 쓴 문의**: `ADMIN` 계정도 문의를 등록할 수 있다. 그 글의 수정·삭제는
  **소유자 규칙**을 따르고(`FR-014`), 답변은 **권한 규칙**을 따른다. 두 축이 독립이다.
- **관리자가 자기 문의에 자기가 답변**: 막지 않는다. 막을 근거가 없고, 운영자가 공지성 문답을
  만드는 정당한 사용이 될 수 있다.
- **비밀글의 작성자가 탈퇴하면**: 001에 회원 탈퇴가 없으므로 이번 스토리에서 다루지 않는다.
  → Out of Scope.
- **`ADMIN` 이 남의 글을 수정**: 허용하지 않는다. 관리자에게 주는 것은 **열람·답변·삭제**이고
  **내용 수정은 주지 않는다** — 관리자가 사용자의 질문 문구를 바꿀 수 있으면 문답 기록의
  신뢰가 사라진다. → **`AC-51` ②가 검증한다**(4번 계획 신설).
- **`ADMIN` 의 글 삭제**: 답변 여부와 무관하게 허용한다(운영상 부적절한 글을 내려야 한다).
  `FR-015`의 미답변 제한은 **작성자에게만** 적용된다. → **`AC-51` ①이 검증한다.**
- **비밀번호를 아는 제3자**: 열람만 가능하다(`AC-33`). 수정·삭제·답변 어느 것도 얻지 못한다.

**한계 — 정직하게 남긴다**

- **DB가 통째로 유출되면 4자리는 지킬 수 없다.** 느린 해시를 써도 값의 종류가 1만이라
  오프라인에서 전부 시도할 수 있다. `FR-018`이 막는 것은 *"유출 즉시 평문"* 까지이고,
  그 이상은 4자리라는 조건 자체의 한계다. → **`ADR-025`**.
- **분산 시도**(주소를 바꿔가며)는 애플리케이션에서 막을 수 없다. `001`이 같은 판단을 했고

  **비밀글 여부**, **비밀번호(되돌릴 수 없는 형태 + 글별 소금값)**, 답변 상태.
  분류·첨부·댓글을 갖지 않는다.
- **답변(Answer)**: 관리자가 문의에 붙이는 응답. 대상 문의(**1:1**), 내용, 답변자, 답변일시.
  삭제하지 않는다(`FR-034`).
- **비밀번호 시도 기록(Password Attempt)**: 무차별 대입 방어의 근거. **글 단위**와
  **클라이언트 단위** 두 축의 실패 횟수와 마지막 실패 시각, 차단 해제 시각.
- **열람 통과(Read Grant)**: 비밀번호를 통과한 상태. 대상 글, 요청자, 만료 시각.
  **글 하나에만 적용된다**(`FR-025`).

> 구체적인 데이터 구조·관계·제약은 **3.5 DB 논리 설계**에서 사람이 확정한다
> (constitution 원칙 III). 특히 **답변을 문의 테이블의 컬럼으로 둘지 별도 테이블로 둘지**,
> **시도 기록과 열람 통과를 어디에 보관할지**는 되돌리기 비용이 큰 결정이다 → **`ADR-026`·`ADR-027`**.

## Success Criteria *(mandatory)*

- **SC-001**: 로그인하지 않은 사람도 문의 목록을 볼 수 있다 — **인증 때문에 막히는 목록 조회
  경로가 0건**이다.
- **SC-002**: 비밀글의 내용은 **작성자·관리자·비밀번호를 맞힌 사람 외에는 어떤 경로로도
  얻을 수 없다** — 목록 응답·상세 응답·검색 결과 어디에서도 새지 않는다.
- **SC-003**: 자동화된 무차별 대입으로 **비밀번호 1만 가지를 모두 시도하는 데 걸리는 시간이
  현실적으로 불가능한 수준**까지 늘어난다.
- **SC-004**: 비밀글에 대한 시도 제한이 **작성자와 관리자의 열람을 한 번도 막지 않는다** —
  차단으로 인한 정당한 사용자의 접근 실패 **0건**.
- **SC-005**: 사용자는 **삭제된 글에 접근한 것인지 비밀번호를 틀린 것인지 응답만 보고
  구분할 수 있다.**
- **SC-006**: 답변이 달린 문의의 질문 내용은 **어떤 경로로도 변경되지 않는다** — 문답 기록의
  정합이 100% 유지된다.
- **SC-007**: 화면을 거치지 않고 직접 요청해도 모든 검증과 권한 규칙이 동일하게 적용된다 —
  **화면 검증 우회로 통과하는 경로가 0건**이다.
- **SC-008**: 저장된 데이터와 로그가 전부 노출되어도 **비밀번호 원문이 그 자리에서 읽히지
  않는다.** *(단 4자리라는 조건상 오프라인 전수조사는 막지 못한다 — Edge Cases의 "한계" 참조)*
- **SC-009**: 로그인한 사용자는 `나의 문의내역`으로 자기 문의를 **3번 이내의 조작**으로 찾는다.

## Assumptions

요구사항에 정의가 없거나 불명확해 합리적 기본값을 택한 항목이다. 4번 계획에서 확정되거나
뒤집힐 수 있다.

1. **비밀번호를 쓰는 사람** — 작성자는 로그인 상태에서 비밀번호 없이 보므로(`FR-020`),
   비밀번호를 실제로 입력하는 사람은 **작성자가 그 값을 알려준 제3자**이거나
   **다른 기기·비로그인 상태의 작성자**라고 가정한다. 이 가정이 `FR-024`(글 단위 차단)를
   허용하는 근거다 — 차단으로 불편해지는 사람의 범위가 좁다.
2. **비밀번호 시도 임계값** — 글 단위 **10회**, 클라이언트 단위 **30회**를 초기값으로
   가정한다(1분 창 기준). 차단 시간은 **10분**. 4번 계획에서 확정한다.
   AC는 *"반복하면 지연되고 임계를 넘으면 429"* 라는 **동작**만 규정하므로 값이 바뀌어도
   AC는 유지된다(001 Assumptions 1과 같은 방식).
3. **비밀번호 문자 집합** — **숫자 4자리**로 가정한다. "4자리 잠금 비밀번호"는 통상 PIN
   입력을 뜻하고 화면도 4칸 입력이다. → 판단 5 · **`ADR-025`**.
4. **열람 통과 유효 시간** — **30분**으로 가정한다. 001의 사용자 Access 수명과 같은 크기이며,
   한 번 열어본 글을 그 방문 동안 다시 묻지 않는다는 목적에 맞는다.
5. **답변자 표시** — 답변에 **관리자 이름과 답변일시**를 함께 보여준다고 가정한다.
   공지사항 상세가 등록한 관리자 이름을 보여주므로 일관된다.
6. **조회수 중복 카운트** — 공통 규칙에 따라 **단순 증가**로 가정한다(같은 사람의 재조회를
   구분하지 않는다). 비밀글은 열람 성공 시에만 오른다(`FR-036`).
7. **관리자의 수정 불가** — 관리자에게 열람·답변·삭제를 주고 **사용자 글의 내용 수정은
   주지 않는다**고 가정한다.
8. **오류 코드 접두사** — 이 문서는 `INQUIRY_` 를 썼다. 게시판 4종의 공통 코드 체계가
   공통 기반 단계에서 정해지면 그쪽을 따른다(코드 문자열이 바뀌어도 AC의 구조는 유지된다).
9. **문의당 첨부·댓글 없음** — 요구사항 표에 따라 제공하지 않는다.

## 판단한 것 — 사람 검증 필요

기획 입력에 근거가 없어 Claude가 정한 것들이다. **뒤집히면 AC가 바뀐다.**
번호 옆 ★는 **보안 판단**이라 특히 확인이 필요한 항목이다.

| # | 판단 | 왜 그렇게 정했나 | 뒤집으면 |
|---|---|---|---|
| 1 ★ | **없는 글(404)과 틀린 비밀번호(403)를 구분한다** | 001의 *"실패는 전부 같은 얼굴"* 은 **계정 열거** 방어였고, 아이디 존재 여부는 어디에도 공개되지 않는 정보였다. 반면 **문의글의 존재는 목록에서 이미 공개**된다. 이미 공개된 사실을 숨기면 방어는 늘지 않고, 삭제된 글에 접근한 사용자가 원인을 모른 채 차단에 걸린다 | `AC-38` 폐기, 두 응답을 404로 통일. `FR-026` 삭제 |
| 2 ★ | **비밀번호 오류에 403을 쓴다(401 아님)** | 401은 이 프로젝트에서 로그인 자격증명 문제로 이미 쓰이고 화면이 재발급·로그인 이동으로 반응한다. 401을 쓰면 비밀번호 한 번 틀렸다고 로그아웃된다 | `AC-39` 재작성 |
| 3 ★ | **비밀글의 내용을 제3자 검색 대상에서 제외한다** | 검색 결과의 유무로 내용을 한 글자씩 좁혀 **비밀번호 없이 내용을 복원**할 수 있다. 공통 규칙 1.1(검색 범위 제목·내용·등록자)에서 의도적으로 이탈한 것이다 | `AC-5`·`AC-6` 폐기, `FR-004` 삭제. **이탈을 되돌리면 취약점이 생긴다** |
| 4 ★ | **글 단위 실패 임계 초과 시 비밀번호 경로를 일시 차단한다** | 001은 계정 잠금을 기각했다(주인이 쫓겨난다). 여기서는 **주인과 관리자가 그 경로를 쓰지 않아** 피해자가 사실상 없다. 지연만으로는 1만 가지를 못 막는다 | `AC-36` 폐기, 지연만 유지. 그러면 SC-003이 위태롭다 |
| 5 ★ | **비밀번호를 숫자 4자리로 확정한다** | "4자리 잠금 비밀번호"는 PIN 관례이고 화면도 4칸이다 | **영숫자 4자리로 바꾸면 경우의 수가 1만 → 약 168만으로 168배**가 된다. 방어가 크게 좋아지므로 **검토를 권한다.** 이미 데이터가 쌓이면 되돌리기 어렵다 → **`ADR-025`** |
| 6 ★ | **비밀번호 통과를 서버가 관리하고 글 단위·시간 제한으로 재사용한다** | 새로고침마다 재입력을 요구하면 사용자가 `1111` 같은 값을 고른다. 반대로 통과가 다른 글에 번지면 하나만 뚫려도 전부 열린다 | `AC-37` 재작성. 인증 체계(stateless)와의 관계는 **`ADR-026`** |
| 7 ★ | **관리자는 비밀번호 없이 비밀글을 본다** | 관리자가 비밀번호를 알 방법이 없어, 물으면 답변 기능 자체가 성립하지 않는다 | 성립 가능한 대안이 보이지 않는다. *(선택지가 하나에 가까운 항목)* |
| 8 ★ | **비밀번호로는 열람만 얻는다(수정·삭제 없음)** | 4자리를 맞혀 삭제가 되면 1만 번 시도로 게시판을 지울 수 있다 | 되돌릴 이유가 없다고 판단한다 |
| 9 | **틀린 비밀번호 응답에 남은 시도 횟수를 포함한다** | 사용자가 차단 직전임을 알 수 있다. 공격자가 얻는 정보는 *"제한이 있다"* 뿐인데 그것은 429로 어차피 드러난다 | 포함하지 않기로 하면 `AC-34`의 Then에서 그 부분만 뺀다 |
| 10 | **답변은 1건, 수정 가능, 삭제 없음** | 상태가 둘뿐이라 답변이 여럿이면 상태를 정의할 수 없고, 삭제하면 상태가 되돌아가 작성자의 수정 권한이 되살아난다 | `AC-45`·`AC-47` 재작성. 스키마가 바뀐다 → **`ADR-027`** |
| 11 | **조회수는 단순 증가, 비밀글은 열람 성공 시에만** | 중복 방지 규칙이 정의되어 있지 않다. 실패 시도로 오르면 무차별 대입이 조회수로 찍혀 수치가 의미를 잃는다 | `AC-42` 일부 재작성 |
| 12 | **정렬 기준에서 분류를 빼고, 요청하면 400** | 이 게시판에 분류가 없다. 조용히 무시하면 사용자가 잘못된 순서를 신뢰한다 | `AC-9` 폐기 |
| 13 | **비로그인 `나의 문의내역` 요청은 401(무시 아님)** | 무시하면 사용자가 자기 글만 본다고 믿으면서 전체를 본다. 401이면 화면이 `001 AC-24`로 필터가 적용된 목록에 복귀시킬 수 있다 | `AC-14` 폐기 |
| 14 | **비밀글의 제목·등록자 노출을 유지하고, 등록 화면에 안내를 넣는다** | 제목을 가리면 목록 검색(제목 대상)이 깨지고, 사용자가 자기 글을 목록에서 못 찾는다. **기능을 바꾸지 않고 오해만 없애는 쪽**을 골랐다 | 제목 마스킹으로 바꾸면 `AC-22`·`AC-27`·`FR-003` 재작성 |
| 15 | **권한 없는 상세 요청에도 공개 항목은 반환한다** | 비밀번호 입력 화면에 *"어떤 글인지"* 를 보여줘야 한다. 그 항목들은 목록에서 이미 보이므로 새로 새는 것이 없다 | 아무것도 반환하지 않기로 하면 `AC-28` 재작성 |
| 16 | **관리자는 남의 글을 수정할 수 없다(삭제는 가능)** | 관리자가 질문 문구를 바꿀 수 있으면 문답 기록의 신뢰가 사라진다. 부적절한 글은 삭제로 처리한다 | Edge Cases 권한 경계 항목 재작성 |
| 17 | **`new` 기준 일수를 설정값으로 둔다** | 게시판마다 다르게 둘 수 있어야 한다는 공통 규칙을 따랐다 | `AC-11`의 후반부 삭제 |
| 18 | **오류 코드 접두사를 `INQUIRY_` 로 쓴다** | 게시판 공통 체계가 아직 없다. 공통이 정해지면 그쪽을 따른다 | 코드 문자열만 일괄 치환. AC 구조는 유지 |

<details>
<summary>번호 부여 전 원문 (근거는 ADR로 옮겨졌다)</summary>

> **번호를 붙이지 않는다.** ADR 번호는 프로젝트 전역 연속이라 병렬 작성 중에 확정하면
> 충돌한다. 통합 단계에서 번호를 부여한다. 아래는 **무엇을 · 왜 결정해야 하는지**만 적는다.

1. **비밀글 비밀번호의 저장 방식**
   - 결정할 것: 어떤 느린 해시를 쓰고 파라미터를 어떻게 두는가. 사용자 계정 비밀번호와
     **같은 설정을 공유할 것인가 따로 둘 것인가**.
   - 왜 결정해야 하나: `ADR-005`(Argon2id)는 **8~64자 계정 비밀번호**를 전제로 파라미터를
     잡는다. 여기는 **4자리**라 위협 모델이 다르다 — 오프라인 전수조사가 1만 번이면 끝나므로
     파라미터를 강하게 잡을 실익과, 열람 요청마다 그 비용을 치르는 부담을 함께 봐야 한다.
   - 되돌리기 비용: **최상.** 저장된 해시는 알고리즘을 바꿔도 재계산할 수 없어
     **모든 비밀글 작성자에게 비밀번호를 다시 받아야 한다.**

2. **비밀번호 시도 제한의 저장 위치와 카운팅 단위**
   - 결정할 것: 실패 횟수를 **어디에** 보관하는가(프로세스 메모리 / DB / 외부 캐시).
     "클라이언트"를 무엇으로 식별하는가(로그인 사용자 / 요청 출처 / 그 조합).
   - 왜 결정해야 하나: 메모리에 두면 **서버를 늘리는 순간 제한이 무력화**되고 재시작으로
     초기화된다. DB에 두면 실패 요청마다 쓰기가 생긴다. 배포 형태가 정해져야 답이 나온다.
   - 되돌리기 비용: 중~상. 인프라 결정(001이 *"분산 공격은 인프라 몫"* 으로 남긴 지점)과 묶인다.

3. **비밀번호 통과 상태를 어떻게 들고 있을 것인가**
   - 결정할 것: 서버 보관(세션형) vs **서명된 단기 값**을 클라이언트에 주는 방식.
   - 왜 결정해야 하나: `ADR-001`이 인증을 **stateless JWT**로 정했다. 여기서 서버 보관 상태를
     들이면 그 전제가 부분적으로 깨진다. 반대로 클라이언트에 주면 **위조 방지와 만료**를
     직접 설계해야 한다. `FR-021`(서버가 검증)을 어느 쪽이든 만족시켜야 한다.
   - 되돌리기 비용: 중. 다만 인증 구조 전체와 맞물린다.

4. **`FR-026` — constitution 원칙 IV의 "비공개 리소스는 404"에 대한 예외 인정**
   - 결정할 것: 문의 비밀글에서 **404 위장을 하지 않는 것**을 정식 예외로 인정할 것인가.
   - 왜 결정해야 하나: **거버넌스 3항이 "원칙을 벗어나려면 ADR로 남긴다"고 규정한다.**
     예외를 문서 없이 두면 다음 게시판에서 같은 판단을 다시 하게 되고, 반대로 결정하면
     프로젝트 안에 서로 다른 두 규칙이 생긴다.
   - 되돌리기 비용: 낮음(코드), 그러나 **규범 문제**라 기록이 필요하다.

5. **비밀글 내용의 검색 제외**
   - 결정할 것: 검색을 어떻게 구현하면서 **요청자에 따라 대상 범위를 다르게** 할 것인가.
   - 왜 결정해야 하나: 나중에 전문 검색 색인을 도입하면 **색인에 비밀글 내용이 들어가는 순간
     이 규칙이 조용히 깨진다.** 지금 결정을 남겨야 그때 걸린다.
   - 되돌리기 비용: 중. 조회 구조와 색인 설계에 영향.

6. **비밀번호의 문자 집합과 자릿수**
   - 결정할 것: 숫자 4자리(1만 가지)를 유지할 것인가, **영숫자 4자리**(약 168만 가지)로
     넓힐 것인가.
   - 왜 결정해야 하나: **경우의 수가 168배 차이**이고, 이것이 시도 제한 설계의 여유를 결정한다.
   - 되돌리기 비용: **최상.** 이미 저장된 비밀번호는 해시라 새 규칙으로 옮길 수 없다.

7. **답변의 카디널리티와 저장 형태**
   - 결정할 것: 답변을 문의 테이블의 컬럼으로 둘 것인가 **별도 테이블 1:1**로 둘 것인가.
     `FR-031`(답변 1건)을 나중에 다건으로 바꿀 여지를 남길 것인가.
   - 왜 결정해야 하나: 컬럼으로 두면 단순하지만 다건으로 확장할 때 마이그레이션이 크다.
     별도 테이블은 확장이 쉬운 대신 항상 조인이 붙는다. **`process.md` 4.7의 정규화 원칙**
     (한 테이블이 두 개념을 겸하지 않는다)과 대조해야 한다.
   - 되돌리기 비용: **최상(스키마).**

## 의존

### 001에서 이미 끝난 것 — 다시 만들지 않는다

| 무엇 | 근거 |
|---|---|
| 로그인·로그아웃·자격증명 재발급, `httpOnly` 쿠키 | `001 FR-010`~`FR-016` |
| `USER` / `ADMIN` 권한과 **서버 권한 검증** | `001 FR-017`~`FR-019` |
| 미인증 401 / 권한 부족 403의 코드와 형식 | `001 AC-21`·`AC-22` |
| 로그인 후 **원래 목적지 복귀**와 그 목적지 검증 | `001 FR-020`·`FR-035` — 미로그인 등록 시도(`AC-17`)와 `나의 문의내역`(`AC-14`) 흐름이 여기에 얹힌다 |
| 공통 오류 형식 + `code` + 추적 식별자, 5xx 내부 정보 비노출 | `001 FR-024`·`FR-025` — 006은 코드 값만 추가한다 |
| 비밀·자격증명의 로그 비노출 원칙 | `001 FR-026` — `FR-029`가 같은 원칙을 글 비밀번호로 확장한다 |
| 429 응답 형식 | `001 FR-031` — `FR-023`·`FR-024`가 재사용한다 |
| 관리자 진입점 분리 | `001 FR-032`~`FR-034` — 답변 기능이 그 뒤에 놓인다 |

**006이 001에 갚는 것**: `001 AC-25`(= 이 문서 `AC-1`). 이것을 검증하지 않으면
`001 FR-021`은 프로젝트 전체에서 미검증으로 남는다.

### 다른 스토리·단계가 정할 것 — 006이 정하지 않는다

| 무엇 | 어디서 |
|---|---|
| 목록의 검색·정렬·페이징 **공통 계약**(파라미터 이름, 응답 형태, 기간 파라미터 표기) | 공통 백엔드 기반(2단계) · 프론트 공통(5단계) |
| 페이징 UI(`<<` `<` 1~10 `>` `>>`)와 검색 조건 유지의 구현 방식 | 프론트 공통(5단계) — `FR-009`는 **동작**만 규정한다 |
| `new` 기준 일수를 **어디에** 두는가(설정 항목의 위치·형식) | 공통 기반(2단계) — `FR-008`은 "바꿀 수 있어야 한다"만 규정한다 |
| 게시판 공통 **오류 코드 접두사 체계** | 공통 기반(2단계) → Assumptions 8 |
| 문의 테이블·답변 저장 형태·비밀번호 해시 컬럼·시도 기록 저장소의 **스키마와 마이그레이션** | 데이터 모델(1단계) · 6.7 — **사람이 확정한다**(원칙 III) |
| 메인 페이지의 문의 영역(최신 5개 · 답변완료 표기 · 자물쇠 · `더보기+` · `나의 문의내역` 링크) | 메인 페이지 담당 — 006은 그 영역이 쓰는 **목록 계약과 필터**를 제공한다 |
| 관리자 화면 골격(좌측 메뉴 · 목록/상세 레이아웃) | 004 관리자 화면 — 006은 답변의 **동작과 권한**만 정한다 |
| 분산 시도(주소를 바꿔가며) 방어 | 인프라 계층 — `001`이 같은 경계를 그었다 |

## Out of Scope

분류(카테고리) · 첨부파일 · 댓글 · 답변 삭제 · 답변 다건 · 문의 카테고리별 통계 ·
문의 알림(메일·푸시) · 비밀번호 찾기(잊은 4자리의 복구) · 작성자 탈퇴 시의 글 처리
(001에 탈퇴가 없다) · 문의 이관/병합 · 첨부 없는 대신의 이미지 붙여넣기.

> **비밀번호 찾기를 넣지 않는 이유**: 4자리를 잊은 사람은 **로그인하면 비밀번호 없이 볼 수
> 있다**(`FR-020`). 즉 작성자에게는 복구가 필요한 상황이 원리적으로 생기지 않는다.
> 제3자에게 알려준 값을 잊은 경우는 작성자가 다시 알려주면 된다.
