## Summary

**만들 것**: 로그인 없이도 볼 수 있는 문의 목록과, **4자리 비밀번호로 열람을 막는 비밀글**,
그리고 **관리자만 다는 답변**. 답변 유무가 작성자의 수정·삭제 권한을 좌우한다.

**기술 접근**: 목록·등록·수정·삭제는 게시판 공통 골격을 그대로 쓴다. 006 고유의 무게는
**세 곳에 몰려 있다.**

| | 어디 | 왜 무거운가 |
|---|---|---|
| 1 | **비밀글 응답 필드 판정** | 본문이 새지 않아야 할 자리가 **넷**이다(목록 · 검색 · 권한 없는 상세 · 답변). 한 곳만 새면 나머지 셋이 무의미해진다 |
| 2 | **시도 제한과 열람 통과** | 4자리는 1만 가지다. **저장 방식이 아니라 온라인 시도 제한이 실제 방어선**이고, 그 상태를 어디에 두느냐가 인프라 결정과 묶인다 |
| 3 | **답변의 카디널리티** | 답변 1건이 상태(`미답변`/`답변완료`)를 정의하고, 그 상태가 **권한**을 정의한다. 스키마 결정이 곧 권한 결정이다 |

**이 스토리를 관통하는 설계 축**: **비밀글의 본문과 답변이 응답에 실리는 자리는 하나여야 한다.**
001이 *"실패는 전부 같은 얼굴"* 을 한 자리(공통 Problem Details 생성기)로 강제한 것과 같은
구조다. 목록·검색·상세가 각자 필드를 고르면 **셋 중 하나는 반드시 어긋난다.**

## Constitution Check

*GATE: Phase 0 이전 통과 필수.*

**현행 constitution 기준**(버전은 `.specify/memory/constitution.md` 하단 참조 — 이 문서에
버전을 박지 않는다).

- [x] **I. 테스트 우선** — 7번 레인에서 코덱스가 스펙·계약만 보고 테스트를 먼저 쓴다.
      **응답·오류코드·권한·경계값을 전부 통합으로 내렸다**(아래 배정 표). E2E는 **1개**다.

      **AC 하나당 최소 하나**를 배정했고 묶음 성격의 AC(`AC-18`·`AC-24`·`AC-47`·`AC-51`처럼
      ①②③을 가진 것)는 **분기마다 따로** 잡았다. 줄 커버리지 숫자 게이트 없음.

      않으므로 아무도 세지 않는다."** 상세는 아래 [스펙에 되돌린 것](#이-계획이-스펙에-되돌린-것).
- [x] **III. 사람이 하는 결정** — **되돌리기 비용이 최상인 3건을 이 계획이 확정하지 않았다**
      (답변 저장 형태 · 비밀번호 해시 설정 · 문자 집합). 대안과 근거만 제시하고 사람에게
      넘긴다. 마이그레이션 SQL은 1단계에서 사람이 쓴다.
- [ ] **IV. 에러 누수 차단** — ⚠️ **위반 1건.** *"남의 비공개 리소스 요청은 403이 아니라
      404로 응답한다"* 를 **의도적으로 벗어난다**(`FR-019`·`FR-026`). 근거와 기각한 대안은
      **Complexity Tracking**에 적었고 **`ADR-028`**로 올린다.
      나머지(전역 핸들러 단일화 · 4xx/5xx 2분류 · RFC 9457 + `code`/`traceId`)는 001의 생성기와
      어댑터를 **그대로 재사용**하며 006은 **`code` 값만 추가**한다.
- [x] **V. 관측 가능성** — 001의 `traceId` 필터·JSON 로깅을 그대로 쓴다.
      **`FR-029`가 마스킹 대상을 넓힌다** — 계정 비밀번호에 더해 **글 비밀번호 원문과 해시**.
      **`AC-40`이 로그를 직접 캡처해 검사**한다(001 `AC-36`과 같은 방식).
- [x] **VI. 되돌릴 수 있는 스키마** — Flyway 버전 파일, 앱이 DDL을 실행하지 않음, `validate`.
      **006은 마이그레이션 파일을 추가하지 않는다** — 1단계가 일괄 작성한다.
      신규 테이블 생성뿐이라 파괴적 변경이 없어 expand-contract가 발동하지 않는다.
      → ⚠️ **`validate`가 검증하지 못하는 것이 이 스토리에 있다**(아래 위험 표 10번).
- [x] **VII. 시크릿** — 새 키는 임계값·수명뿐이다(`INQUIRY_*`). `.env.example`에 이름만.
      **비밀글 비밀번호는 시크릿이 아니라 사용자 데이터**이므로 환경변수와 무관하다.
- [x] **VIII. 도구가 강제하는 게이트** — 001이 만든 CI 잡(`build`/`test`/`e2e`/`coverage-report`)에
      얹는다. **새 잡을 만들지 않는다.** 사람 게이트를 늘리지 않는다.
- [x] **보안 요구사항** — 되돌릴 수 없는 느린 해시(`FR-018`), 권한은 서버 검증(`FR-019`~`FR-022`),
      `httpOnly` 쿠키(001 그대로).
      → **"비밀번호 최소 8자"는 계정 비밀번호 규칙이고 글 비밀번호에 적용되지 않는다.**
      근거는 001이 티켓 식별 값에 SHA-256을 쓴 것과 **같은 형태의 판정**이다 —
      보안 요구사항의 근거는 *"사람이 만든 로그인 자격증명"* 이고, 글 비밀번호는 **계정을
      열지 않는다.** 다만 **1만 가지라는 사실은 남으므로** 스펙이 그 자리를 시도 제한
      (`FR-023`·`FR-024`)으로 메웠다. **이 판정 자체를 **`ADR-025`**이 다시 묻는다.**

**결과: 위반 1건.** Complexity Tracking에 기록했다.

### 이 계획이 스펙에 되돌린 것

계획을 쓰다 **스펙 쪽의 빈틈 3개**가 드러났다. 001에서 5번 게이트가 잡은 것과 같은 종류다.

| | 무엇 | 왜 문제인가 | 처리 |
|---|---|---|---|
| 1 | **`FR-014`가 문서와 어긋나 있었다** | `FR-014`는 수정·삭제를 묶어 *"작성자 본인만"* 이라 적었는데, Edge Cases와 판단 16은 **관리자 삭제를 허용**한다. **계약이 어느 쪽으로 쓰든 한쪽 문장을 위반**하는 상태였다 | `FR-014` 문구 정정 + **`AC-51` 신설** |
| 2 | **빈 비밀번호로 수정하면 어떻게 되는지 아무도 세지 않았다** | Edge Cases에 규칙만 있었다. 빈 값을 "삭제"로 해석하면 **`AC-23`이 금지한 상태가 수정 경로로 우회 생성**된다 | **`AC-49` 신설** |
| 3 | **`0000`이 유효한지 아무도 세지 않았다** | 숫자로 다루면 `0000`=`0`=`00`이 되어 **값의 공간이 1만보다 줄어든다.** `SC-003`의 전제가 조용히 흔들린다 | **`AC-50` 신설** |

> **셋 다 "스펙에 적혀 있었지만 AC가 없었다"** 는 같은 모양이다.
> 001의 5번 게이트가 *"엣지 케이스로 검증한다는 판정은 실제로는 테스트가 배정되지 않는다는
> 뜻이었다"* 를 잡은 것과 동일하며, **그 교훈이 실제로 재사용된 첫 사례**다.

### 개념 나누기 — 도구 1·2·3 적용

| 질문 | 답 | 결과 |
|---|---|---|
| 문의와 답변은 같은 개념인가? | **아니다.** 하나는 사용자의 질문, 하나는 운영자의 응답이고 **작성자·작성 시점·권한이 전부 다르다** | ★ 별 테이블 후보 (**`ADR-027`**) |

| 한 컬럼에 값이 여러 개 들어가는가? | 없다. 분류·첨부·댓글이 없어 다중 값 자체가 없다 | 도구 3 통과 |

| 비밀글 여부 | `BOOLEAN` | NOT NULL | **`false`** | `FR-016`. **기본값이 없으면 `NULL`이 들어와 "비밀글인지 알 수 없는 글"** 이 생긴다 |
| 비밀번호 해시 | `VARCHAR` (길이 제한 없음) | **NULL 허용** | 아래 CHECK | `FR-018`. **길이를 박지 않는다** — 해시 문자열이 파라미터를 자기 안에 담아 길이가 변한다(`ADR-005`가 겪은 함정) |
| 조회수 | `BIGINT` | NOT NULL | **`0`** + `CHECK >= 0` | `FR-036` |
| 등록일시 | `TIMESTAMPTZ` | NOT NULL | `now()` | data-model 1절 |
| 수정일시 | `TIMESTAMPTZ` | NOT NULL | `now()` | 수정 여부 표시는 없지만 **운영에서 없으면 항상 아쉬운 컬럼**이다 ★사람 확인 |

**★ 이 테이블의 핵심 제약 — CHECK 하나가 AC 셋을 DB에서 못박는다**

```
CHECK ( (비밀글여부 = false AND 비밀번호해시 IS NULL)
     OR (비밀글여부 = true  AND 비밀번호해시 IS NOT NULL) )
```

| 이 CHECK가 막는 것 | 관련 AC |
|---|---|
| 비밀번호 없는 비밀글이 생기는 것 | **`AC-23`** (등록) · **`AC-49`** (빈 값 수정) |
| 공개글에 잠금 값이 남는 것 | **`AC-26`** (비밀글 해제) · Edge Cases(체크 없이 비밀번호만 보냄) |

**코드로만 막으면 경로 세 개(등록·수정·해제)를 각각 지켜야 하고, 하나만 빠뜨려도 조용히
어긋난 행이 생긴다.** 001이 아이디 중복을 DB 유니크에 맡긴 것과 **같은 종류의 판단**이다.

### 테이블: 답변(answer) ★ — **별도 테이블 vs 문의의 컬럼** (**`ADR-027`** · 사람 확정)

| | 별도 테이블 1:1 **(권고)** | 문의 테이블의 컬럼 3개 |
|---|---|---|
| 정규화 | ✅ `process.md` 4.7 — 한 테이블이 두 개념을 겸하지 않는다 | ❌ 질문과 응답이 한 행에 섞인다 |
| **NULL** | ✅ 답변이 없으면 **행이 없다** | ❌ 미답변 글에서 **3컬럼이 항상 NULL** — data-model 리뷰 체크리스트가 *"항상 비어 있는 컬럼은 테이블을 잘못 나눈 신호"* 라고 적은 그 모양 |
| **`FR-031`(1건)** | ✅ **`inquiry_id`에 UNIQUE** → DB가 보장. `AC-45`의 동시 등록 경합이 **DB에서 판정**된다 | △ 컬럼이 하나뿐이라 자연히 1건이지만, **경합 시 나중 쓰기가 앞을 덮어쓴다**(409가 아니라 조용한 손실) |
| 대가 | 목록의 답변 상태 표기에 **조인/EXISTS**가 붙는다 | 조인이 없다 |
| 다건 확장 | 쉽다(UNIQUE 제거) | 마이그레이션이 크다 |

**권고는 별도 테이블**이고 결정적인 이유는 **세 번째 줄**이다 — `AC-45`(답변은 문의당 하나)를
**코드로 막으면 관리자 둘이 동시에 누를 때 깨진다.** 001이 *"코드로 막으면 동시 요청에서
깨진다"* 며 아이디 중복을 DB에 맡긴 판단과 같다. **다만 스키마는 되돌리기 비용 최상이라
사람이 확정한다.**

| 컬럼(논리) | 타입 | NULL | 제약 | 근거 |
|---|---|---|---|---|
| 기본키 | `BIGINT ... IDENTITY` | NOT NULL | PK | 전역 규칙 |
| 문의 참조 | `BIGINT` | NOT NULL | **FK → 문의, `ON DELETE CASCADE`** + **UNIQUE** | `FR-031` 1:1. **CASCADE인 이유**: 문의 없는 답변은 의미가 없고, 남으면 고아 행이 그대로 장애가 된다(001 티켓과 같은 근거) |
| 내용 | `VARCHAR(3999)` | NOT NULL | — | `FR-032` |
| 답변자 참조 | `BIGINT` | NOT NULL | FK → 유저 | Assumptions 5 (답변자 이름 표시) |
| 답변일시 | `TIMESTAMPTZ` | NOT NULL | `now()` | Assumptions 5 |
| 수정일시 | `TIMESTAMPTZ` | NOT NULL | `now()` | `FR-034`(수정은 있고 삭제는 없다) |

### 인덱스 — **조회 패턴에서 도출한다**

먼저 **AC가 요구하는 조회를 전부 적고**, 그다음 각 조회가 인덱스를 필요로 하는지 본다.
*(인덱스를 먼저 나열하고 이유를 붙이면 "있으면 좋을 것 같아서"가 섞인다.)*

| # | 조회 패턴 | 근거 AC | 인덱스 |
|---|---|---|---|
| P1 | `등록일시 BETWEEN ? AND ?` → **등록일시 내림차순** → 페이지 잘라내기 | `AC-2`·`AC-7`·`AC-8`·`AC-10` | **`ix_inquiry_created_at`** |
| P2 | 같은 조건의 **전체 건수** (글 번호가 전체 건수 기준 역순이라 매 요청에 필요) | `AC-10` | P1과 같은 인덱스 |
| P3 | `작성자 = 나` + 기간 → 등록일시 내림차순 | `AC-13` | **`ix_inquiry_author_created`(작성자, 등록일시)** |
| P4 | 제목·내용·등록자 **부분 일치** | `AC-4`·`AC-5`·`AC-6` | **인덱스 없음** (아래 ★) |
| P5 | 기본키 단건 조회 | `AC-28`~`AC-31` | PK |
| P6 | 문의 하나의 답변 조회 · 목록의 답변 상태 | `AC-43`·`AC-48` | **`uk_answer_inquiry`(UNIQUE)** — 유일 제약이 곧 조회 인덱스다 |
| P7 | 글 단위 / 클라이언트 단위 실패 횟수 조회·증가 | `AC-34`·`AC-35` | **테이블이 아님**(아래) |

**★ P3의 인덱스가 FK 인덱스 역할을 겸한다.** PostgreSQL은 **FK 컬럼에 인덱스를 자동으로
만들지 않는다**(`data-model.md` 5.5의 4번이 001에서 잡은 함정). 선두 컬럼이 작성자이므로
*"이 사람의 글"* 조회와 FK 무결성 검사 양쪽에 쓰인다 — **인덱스를 따로 만들지 않는다.**

**★ P4에 인덱스를 만들지 않는 이유를 적어둔다** (적어두지 않으면 *"빠뜨린 것"* 과 구분되지 않는다):
`%검색어%` 형태의 부분 일치는 **B-tree 인덱스를 탈 수 없다.** 앞이 열려 있어 정렬 순서로
좁힐 수 없기 때문이다. 지금 만들면 **쓰이지 않는 인덱스를 쓰기 비용만 내고 유지**하게 된다.
→ **방아쇠: 목록 응답이 체감되게 느려지는 시점.** 그때 `pg_trgm` + GIN 인덱스를 검토하며,
**그 순간이 `FR-004`(비밀글 내용 검색 제외)가 조용히 깨지는 지점**이다 → **`ADR-029`.**

**만들지 않기로 판정한 인덱스**

| | 왜 |
|---|---|
| 제목 · 조회수 (정렬 대상) | 정렬 3종 × 방향 2 = 6조합에 전부 인덱스를 두면 **쓰기가 6배 비싸진다.** 기본 정렬(등록일시)만 인덱스로 받치고 나머지는 **기간 필터로 이미 좁혀진 집합**을 정렬한다 |
| 비밀글 여부 | 값이 2종이라 선택도가 낮다. 그리고 *"비밀글만 조회"* 하는 기능이 없다 |
| 답변 상태 | **컬럼이 아니다**(답변 행의 존재 여부로 판정한다). P6의 UNIQUE가 그 판정을 받친다 |

**인덱스 이름은 `data-model.md` 5.5의 규칙**(`uk_`/`ix_`/`fk_`/`ck_`)을 따르고, 실제 이름은
**1단계에서 사람이** 붙인다.

### 테이블이 아닌 상태 2종 ★

| | 무엇 | 사라지면 | 후보 |
|---|---|---|---|
| **시도 기록** | 글 단위·클라이언트 단위 실패 횟수와 차단 해제 시각 | 카운터가 0으로 돌아간다. **공격자가 재시작을 유발할 수 없으므로** 허용 가능 | **서버 메모리**(001과 같은 판정) / DB / 외부 캐시 → **`ADR-026`** |
| **열람 통과** | 어떤 요청자가 어떤 글을 통과했는가 + 만료 | 사용자가 비밀번호를 다시 친다. **무해** | 서버 보관 / **서명된 단기 쿠키** → **`ADR-026`** |

**★ 열람 통과에는 스펙이 답하지 않은 질문이 하나 더 있다 — "요청자"를 무엇으로 식별하나.**
`AC-29`의 Given이 **로그인하지 않은 상태**이므로 **로그인 사용자로 좁힐 수 없다.**
실재하는 선택지를 빠뜨리지 않기 위해 셋을 적는다(원칙 III):

| | 방식 | 대가 |
|---|---|---|
| 1 | 서버가 **열람 전용 식별 쿠키**를 발급하고 그 키로 통과 목록을 서버에 보관 | `ADR-001`의 stateless 전제가 부분적으로 깨진다. 서버 2대가 되면 공유가 필요하다 |
| 2 | **글 id + 만료를 서명한 단기 쿠키**를 글마다 발급 | stateless가 유지된다. 대신 **위조 방지·만료를 직접 설계**해야 하고, 여러 글을 열면 쿠키가 늘어난다 |
| 3 | 통과 글 목록을 **하나의 서명된 쿠키**에 담는다 | 쿠키가 하나다. 대신 **목록이 길어지면 쿠키 크기 한계**에 닿고, 무효화가 어렵다 |

**어느 쪽이든 `FR-021`(판정은 서버가 한다)과 `FR-025`(글 단위 · 만료)를 만족해야 한다.**
→ **`ADR-026`에서 사람이 확정한다.**

**클라이언트 식별은 001의 결론을 그대로 쓴다** — `/api/*` rewrite 때문에 백엔드가 보는
원격 주소가 **프록시 하나**다. `X-Forwarded-For`의 **클라이언트 홉**을 쓰고 **신뢰할 프록시를
명시**한다. 하지 않으면 `AC-35`의 클라이언트 단위 제한이 **전원을 한 키로 묶어 방어가 아니라
장애**가 된다(001 `AC-30`이 겪은 것과 같은 함정).

## E2E 예산

**006이 요구하는 것: 1개.**

| | 내용 | 왜 이것만 E2E인가 |
|---|---|---|
| `inquiry-secret.spec.ts` | 목록의 **자물쇠 글 클릭 → 비밀번호 입력 화면 → 통과 → 본문 표시** (`AC-28`·`AC-29` 병행) | **비밀번호 입력 화면은 006에만 있는 화면**이고, 통합 테스트는 *"서버가 본문을 안 준다"* 까지만 본다. **화면이 403을 받고 입력 화면을 띄우는지, 통과 뒤 본문을 그리는지**는 브라우저가 있어야 의미가 있다. `test-strategy.md` 4.1이 남긴 예외 규칙(*"전부 API로 우회하면 화면이 깨져도 실패하는 테스트가 하나도 없다"*)이 그대로 적용되는 자리다 |

**깎을 수 있는가 — 판단**

| 후보 | 판단 |
|---|---|
| `AC-12`(검색 조건 유지) | **깎았다.** 게시판 4종의 **공통 규칙**이라 006에서 E2E로 잡으면 002·003·005가 같은 것을 네 번 산다. **공통 프론트(5단계)의 몫**으로 넘기고 006은 단위로 받는다 |
| 등록→목록 확인 정상 흐름 | **깎았다.** 다른 게시판과 동일한 골격이고 통합으로 전부 덮인다 |
| 관리자 답변 흐름 | **깎았다.** 화면 골격이 004이고 006이 정하는 것은 **동작과 권한**이라 통합이 맞다 |
| 비밀글 열람 흐름 | **남긴다.** 위 근거 |
| **0개로 줄이기** | **권고하지 않는다.** 대가는 *"화면이 본문을 받아놓고 가리기만 하는 구현"* 이 **어떤 테스트에도 걸리지 않는 것**이다 — `FR-021`이 명시적으로 금지한 실수인데 서버 쪽 통합만으로는 화면 구현을 못 본다 |

**⚠️ 프로젝트 전체 예산 경고.** `test-strategy.md` 4장의 **5~10개는 프로젝트 전체 기준**이고
**001이 이미 7개**를 쓴다. 006이 1개를 쓰면 **8개**이고, **002·003·004·005·메인·공통 프론트가
남은 2개를 나눠 써야 한다.** 006이 더 깎아서 해결되는 문제가 아니다(1 → 0은 위 대가를 받는다).
→ **해소는 001의 7개를 깎는 쪽**이며, 그것은 `STATUS.md` 18번에 **보류(관찰)** 로 이미 열려
있는 항목이다. **006은 예산을 1개만 청구하고, 초과 판정은 6번 태스크 분해에서 프로젝트
전체를 놓고 한다.**

## 위험과 대응

| 위험 | 왜 위험한가 | 대응 |

| **★ 비밀글 본문이 새는 자리가 넷이다** | 목록(`AC-15`) · 검색(`AC-5`) · 권한 없는 상세(`AC-28`) · 답변(`AC-41`). **셋을 막고 하나를 놓치면 막은 셋이 전부 무의미**하다. 그리고 각각 다른 코드에서 만들어지기 쉽다 | **응답 필드를 고르는 자리를 하나로 두고** 넷이 공유한다(001의 공통 Problem Details 생성기와 같은 구조). **네 응답을 같은 화이트리스트로 검사하는 테스트를 따로** 둔다 |

## Complexity Tracking

> **Constitution Check 위반 1건.** 001은 0건이었다 — 늘어난 것을 감추지 않는다.

| Violation | Why Needed | Simpler Alternative Rejected Because |
|-----------|------------|-------------------------------------|
| **원칙 IV** — *"남의 비공개 리소스 요청은 403이 아니라 404로 응답한다"* 를 벗어난다. 006은 **권한 없는 비밀글 요청에 403**(`FR-019`)을, **없는 글에 404**(`FR-026`)를 준다 | 그 규칙의 **목적은 존재 여부를 숨기는 것**인데, **문의글의 존재는 목록에서 이미 공개된다**(`AC-22` — 비밀글도 번호·제목·등록자가 보인다). **이미 공개된 사실을 응답에서만 숨기면 방어는 늘지 않고 사용성만 잃는다.** 게다가 삭제된 글에 오래된 링크로 들어간 사용자가 *"비밀번호가 틀렸다"* 를 보고 반복 시도하다 **`FR-024`의 차단에 걸려 원인을 영원히 알 수 없게** 된다 | **대안 1 — 둘 다 404로 통일**: 목록이 이미 존재를 알려주므로 **숨겨지는 정보가 0**인데, 위의 사용성 손실만 그대로 받는다. **대안 2 — 둘 다 403으로 통일**: 삭제된 글에 대해 *"비밀번호를 넣으면 열릴 수 있다"* 는 잘못된 기대를 만들고, 열리지 않는 이유를 끝내 알 수 없다. → **`ADR-028`로 올려 사람이 예외를 인정한다**(거버넌스 3항) |
