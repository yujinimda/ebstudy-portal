# API 계약 — 005 갤러리

> `/speckit-plan` Phase 1 산출물. **AC와 1:1로 대응시킨 계약**이며,
> 7번에서 코덱스가 **이 문서와 `spec.md`만 보고** 테스트를 작성한다(구현 코드를 보지 않는다).

**공통 오류 형식**: RFC 9457 Problem Details + `code`/`traceId` 확장 — **001이 만든 생성기를
그대로 쓴다.** 005는 형식을 새로 정하지 않고 **코드만 추가**한다.

```json
HTTP 4xx/5xx
Content-Type: application/problem+json
{
  "type": "/errors/validation",
  "title": "Validation Failed",
  "status": 400,
  "detail": "1MB를 넘는 이미지가 있습니다",
  "instance": "/api/gallery/posts",
  "code": "GALLERY_IMAGE_SIZE_EXCEEDED",
  "traceId": "a3f9c2",
  "errors": [
    { "field": "images[2]", "filename": "IMG_0042.jpg", "reason": "1,412,336 bytes" }
  ]
}
```

**인증**: 001 그대로 — 자격증명은 `httpOnly` 쿠키, 권한 판정은 서버(`ADR-001` · 001 `FR-019`).
005는 **인증 메커니즘을 건드리지 않는다.**

**목록·상세 조회는 인증이 필요 없다**(요구사항 1.3). 등록·수정·삭제는 필요하다.

## 0. 이 계약을 관통하는 규칙 3개 — 먼저 읽는다

### 규칙 1. **이미지 주소는 서버가 응답에 담아 준다. 클라이언트가 조립하지 않는다.**

목록·상세 응답에 `thumbnailUrl` · `images[].url`이 **완성된 형태**로 담긴다.
클라이언트가 `/api/gallery/images/{id}` 같은 규칙으로 **주소를 만들어 쓰지 않는다.**

**왜 이것이 규칙인가**: 주소 형태와 캐시 정책은 **`ADR-019`이 아직 정하지 않았다.**
클라이언트가 주소를 조립하면 **그 결정이 프론트 코드에 박히고**, 나중에
*"내용에 따라 변하는 불변 주소"* 를 고르면 **프론트를 전부 고쳐야** 한다.
서버가 주는 값을 그대로 쓰면 **어느 선택지가 이겨도 계약이 깨지지 않는다.**

### 규칙 2. **썸네일은 저장된 값이 아니라 계산된 값이다.**

응답의 `thumbnailUrl`은 **표시 순서가 가장 작은 이미지**를 그때 계산한 결과다.
어디에도 *"썸네일 식별자"* 를 저장하지 않는다 → `AC-32`(첫 장 삭제)에서
**끊긴 참조가 생길 자리 자체가 없다**(`plan.md` 데이터 모델 1절).

### 규칙 3. **등록·수정 요청의 `images` 배열은 "최종 상태"다. 델타가 아니다.**

수정 후 그 글에 남을 이미지 전부를 **원하는 순서 그대로** 담는다.
**배열에 없는 기존 이미지는 삭제된다.** 배열의 **순서가 곧 표시 순서**다.

> **★ 이 한 줄이 이 계약에서 가장 자주 오해되는 지점이다.**
> *"보낸 것을 추가한다"* 로 읽으면 삭제가 일어나지 않고(`AC-32`·`AC-34` 실패),
> *"보낸 것만 남긴다"* 를 놓치면 안 보낸 것이 남는다. **`AC-34`가 이 해석을 직접 시험한다** —
> 배열을 비워 보내면 `GALLERY_IMAGE_REQUIRED`로 거부되고 **기존 3장이 그대로 남아야** 한다.

## 1. `GET /api/gallery/posts` — 목록 (카드형)

**인증**: 불필요

**쿼리 파라미터**: **002가 정한 공통 목록 규칙을 그대로 쓴다** — 기간(`from`·`to`) · 분류 ·
검색어와 범위 · 개씩 보기 · 정렬 기준·방향 · 페이지. **갤러리 전용 파라미터를 만들지 않는다**(`FR-004`).
파라미터 이름과 기본값의 **원천은 002의 계약**이고 여기에 복제하지 않는다 — 복제하면 갈라진다.

**응답 200** — 페이지 구조(전체 건수 · 페이지 정보 · 글 번호)는 002 공통. **갤러리 고유 필드만** 적는다.

```json
{
  "items": [
    {
      "id": 128,
      "number": 57,
      "categoryName": "풍경",
      "title": "가을 산행",
      "excerpt": "이번 주말에 다녀온 ...",
      "thumbnailUrl": "/api/gallery/images/9f2c.../thumb",
      "extraImageCount": 4,
      "viewCount": 12,
      "authorName": "홍길동",
      "createdAt": "2026-07-30T10:11:12+09:00",
      "new": true
    }
  ]
}
```

| 응답 | 조건 | `code` | AC |
|---|---|---|---|
| **200** | 카드 목록. `thumbnailUrl`이 **첫 번째 이미지의 축소본** | — | `AC-1`·`AC-4` |
| 200 | 이미지 5장인 글의 `extraImageCount`가 **4** | — | `AC-2` |
| 200 | 이미지 1장인 글에 **`extraImageCount` 필드가 없다** | — | `AC-3` |
| 200 | 공통 목록 규칙 11종이 002와 동일하게 동작 | — | `AC-6` *(묶음 — 규칙마다 테스트 따로)* |

**계약 주의**

- **`extraImageCount`는 0일 때 필드를 담지 않는다.** `0`을 담지 않는 이유:
  `+0`을 숨길지 말지를 **화면마다 다시 판단하게 되고**, 갤러리 카드 · 관리 목록 · **메인 페이지**
  **세 곳에서 각각 틀릴 수 있다.** 계약이 한 번 정하면 세 화면이 자동으로 같아진다(`AC-3`의 근거를
  계약 수준으로 올린 것).
- **`thumbnailUrl`은 축소본을 가리킨다.** 원본 주소를 담으면 `AC-4`가 깨지는데,
  **주소가 다르다는 것만 보는 테스트는 통과해 버린다** → `AC-4`는 그 주소를 실제로 받아
  **원본보다 작은지**까지 본다.
- **N+1 금지**: 카드 50장에 대해 이미지를 글마다 따로 조회하지 않는다
  (`plan.md` 데이터 모델 2절 Q1·Q2).

## 2. `GET /api/gallery/posts/{postId}` — 상세

**인증**: 불필요

**응답 200**

```json
{
  "id": 128,
  "categoryName": "풍경",
  "title": "가을 산행",
  "content": "...",
  "authorName": "홍길동",
  "viewCount": 13,
  "createdAt": "2026-07-30T10:11:12+09:00",
  "images": [
    { "imageId": 501, "url": "/api/gallery/images/9f2c...", "width": 1600, "height": 1200 },
    { "imageId": 502, "url": "/api/gallery/images/a71d...", "width": 1200, "height": 1600 }
  ]
}
```

| 응답 | 조건 | `code` | AC |
|---|---|---|---|
| **200** | `images`가 **저장된 순서 그대로**. 배열의 첫 항목이 목록 썸네일과 **같은 이미지** | — | `AC-7` |
| 200 | 조회할 때마다 `viewCount` **증가**. 같은 사람이 다시 열어도 증가 | — | `AC-15` |
| **404** | 없는 글 / 삭제된 글 | `POST_NOT_FOUND` | `AC-16` |

**계약 주의**

- **`images` 배열의 순서가 진실이다.** 응답에 `order`(순서 번호) 필드를 담지 않는다 —
  담으면 **배열 순서와 순서 필드가 어긋날 수 있고**, 그때 무엇이 맞는지를 또 정해야 한다.
  **정보를 두 곳에 두지 않는다.**
- **대체 텍스트를 서버가 만들지 않는다.** `AC-13`의 `"<제목> 이미지 2/3"` 은 **화면 문구**이고,
  프론트가 이미 가진 값(제목 · 배열 인덱스 · 길이)으로 만들 수 있다.
  서버가 문자열을 만들면 **문구를 바꿀 때 서버를 배포해야 한다.**
- **`canEdit` 같은 권한 힌트를 담더라도 그것은 화면 편의일 뿐이다.**
  수정·삭제의 판정은 **서버가 요청 시점에** 한다(`AC-39` · 001 `FR-019`).

## 3. `POST /api/gallery/posts` — 글 등록

**인증**: **필요**(로그인 사용자). 미인증 직접 호출은 **401 `AUTH_REQUIRED`**

**요청**: `multipart/form-data` — 파트 2종

| 파트 | 개수 | 내용 |
|---|---|---|
| `payload` | 1 | `application/json`. 아래 구조 |
| `files` | 0~20 | 이미지 바이트. **보낸 순서가 `fileIndex` 0, 1, 2 …** |

```json
// payload
{
  "categoryId": 3,
  "title": "가을 산행",
  "content": "...",
  "images": [
    { "source": "new", "fileIndex": 1 },
    { "source": "new", "fileIndex": 0 }
  ]
}
```

> **`images` 배열의 순서가 표시 순서다**(규칙 3). 위 예시는 **두 번째로 올린 파일이 첫 장**이며,
> 따라서 **그것이 썸네일**이 된다. 순서 번호를 따로 보내지 않는다.

| 응답 | 조건 | `code` | AC |
|---|---|---|---|
| **201** | 성공. 이미지가 **배열 순서대로 저장**되고 첫 항목이 썸네일 | — | `AC-17` |
| 400 | 이미지 **21개 이상** | `GALLERY_IMAGE_COUNT_EXCEEDED` | `AC-18`·`AC-23` |
| 400 | 이미지 **한 장이라도 1MB 초과**. **전부 저장되지 않는다** | `GALLERY_IMAGE_SIZE_EXCEEDED` | `AC-19`·`AC-23` |
| 400 | 허용 외 형식(`jpg`·`gif`·`png` 외) | `GALLERY_IMAGE_TYPE_INVALID` | `AC-20`·`AC-23` |
| 400 | **확장자만 이미지**(내용이 이미지가 아님) — **같은 코드** | `GALLERY_IMAGE_TYPE_INVALID` | `AC-21` |
| 400 | 이미지 **0개** | `GALLERY_IMAGE_REQUIRED` | `AC-22`·`AC-23` |
| 400 | `images`가 참조하지 않는 `files` 파트가 있다 / 없는 `fileIndex` 참조 / **중복 참조** | `GALLERY_IMAGE_REFERENCE_INVALID` | — *(계약 신설 — 아래 주의)* |
| 400 | 픽셀 수 상한 초과 | `GALLERY_IMAGE_PIXEL_EXCEEDED` | — **(상한 값 미확정 — `plan.md` 미해결 4)** |
| **413** | **요청 전체 크기 초과** | `GALLERY_REQUEST_TOO_LARGE` | `AC-24` |
| 400 | 제목·내용·분류 위반 | **002가 정한 코드** | `AC-28` *(묶음)* |
| **401** | 미인증 직접 호출 | `AUTH_REQUIRED` | `AC-29` |

**계약 주의**

- **`AC-23`(직접 호출 우회)** — 위 400들은 **화면을 거치지 않은 요청에도 동일**하다.
  화면 검증은 편의일 뿐 **서버가 방어선**이다(`FR-017`). **파일 업로드는 화면에서 막기 쉬워
  서버 검증을 생략하기 특히 쉽다.**
- **형식은 확장자가 아니라 내용으로 판정한다**(`FR-018`). 저장하는 `Content-Type`도
  **판정 결과**이지 업로드가 알려준 값이 아니다 — 그 값을 그대로 믿으면 6번 엔드포인트가
  **틀린 형식으로 응답**하게 된다.
- **크기 경계**: **정확히 `1,048,576` 바이트는 허용**, 그보다 1바이트라도 크면 거부.
  *(Claude 판단 — `1MB`의 정의가 스펙에 없다. `plan.md` "스펙으로 되돌릴 것" 2)*
- **오류 응답의 `errors[]`에 어느 파일인지 담는다** — `SC-005`(*"어느 파일이 왜 거부됐는지"*)가
  이것 없이는 성립하지 않는다. `field`는 `images[n]`, `filename`은 **원본 파일명**.
  **원본 파일명은 사용자 입력이므로** 화면이 그대로 그릴 때 이스케이프해야 하고,
  **로그에 쓸 때는 개행·제어문자를 제거**한다(`plan.md` 원칙 V).
- **저장 파일명은 업로드 파일명이 아니다**(`FR-027`). 이름이 같은 두 장이 서로를 덮어쓰지 않고
  **각각 별개로 저장**된다 → `AC-26`.
- **촬영 위치 등 메타데이터를 제거한 뒤 저장한다**(`FR-026`) → `AC-25`.
  검증은 **저장된 파일을 다시 읽어** 확인한다 — 응답만 봐서는 알 수 없다.
- **전부 아니면 전무**(`FR-023`) — 한 장이 걸리면 **글도 만들어지지 않고 다른 장도 남지 않는다.**

## 4. `PUT /api/gallery/posts/{postId}` — 글 수정 ★

**인증**: **필요 + 작성자 본인**. 남의 글이면 **403 `AUTH_FORBIDDEN`**

**요청**: 3번과 같은 `multipart/form-data`. 차이는 `images` 항목이 **두 종류**라는 것뿐이다.

```json
{
  "categoryId": 3,
  "title": "가을 산행 (수정)",
  "content": "...",
  "images": [
    { "source": "existing", "imageId": 503 },
    { "source": "new",      "fileIndex": 0 },
    { "source": "existing", "imageId": 501 }
  ]
}
```

**이 요청이 뜻하는 것**: 최종 이미지는 3장이고 순서는 `503` → 새 파일 → `501` 이다.
**언급되지 않은 기존 이미지 `502`는 삭제된다.** 썸네일은 `503`이 된다.

| 응답 | 조건 | `code` | AC |
|---|---|---|---|
| **200** | 순서 변경 반영. **목록 썸네일이 새 첫 장으로 바뀐다** | — | `AC-31` |
| 200 | **첫 장을 뺀** 배열 → 남은 것 중 첫 항목이 썸네일. 상세 캐러셀 첫 화면도 동일 | — | `AC-32` ★ |
| 200 | **가운데만 뺀** 배열 → 썸네일 그대로 | — | `AC-33` |
| 200 | 목록 재조회 시 **새 썸네일의 축소본**이 나온다(옛 축소본이 계속 보이지 않는다) | — | `AC-36` ★ |
| 400 | `images`가 **빈 배열**. **기존 이미지는 그대로 남는다** | `GALLERY_IMAGE_REQUIRED` | `AC-34` |
| 400 | 규칙 위반이 하나라도 있으면 **순서·구성이 수정 전 그대로** | (해당 코드) | `AC-35` |
| 400 | **`imageId`가 이 글의 이미지가 아니다** / 없는 id / **중복 참조** | `GALLERY_IMAGE_REFERENCE_INVALID` | — *(계약 신설 — ★ 아래)* |
| 400 | 개수·크기·형식·픽셀 위반 | 3번과 **같은 코드** | `AC-18`~`AC-21` |
| **413** | 요청 전체 크기 초과 | `GALLERY_REQUEST_TOO_LARGE` | `AC-24` |
| **401** | 미인증 | `AUTH_REQUIRED` | `AC-29` |
| **403** | 남의 글 (화면에 버튼이 없어도 동일) | `AUTH_FORBIDDEN` | `AC-37`·`AC-39` |
| **404** | 없는 글 | `POST_NOT_FOUND` | `AC-16` |

**★ 계약 주의 — `imageId` 소속 검증**

`imageId`를 받는 순간 **다른 글의 이미지 식별자를 넣을 수 있게 된다.**
소유자 검증을 **글에 대해서만** 하면 통과하고, 그러면 **남의 글 이미지가 내 글로 옮겨 온다.**

> **스펙에 이 경우의 AC가 없다.** `AC-37`(남의 글 수정 403)은 **글**의 소유를 보고
> **이미지**의 소속은 보지 않는다. → `plan.md`의 *"스펙으로 되돌릴 것" 1*로 올렸고,
> **AC가 신설될 때까지 이 계약 항목이 유일한 방어 근거**다.

**★ 계약 주의 — 순서 재배치의 중간 상태**

`(글, 표시 순서)` 유니크를 그냥 걸면 **재배치 도중 위반**한다(`A=0,B=1` 을 `B=0,A=1` 로 바꾸는 순간).
**커밋 시점에만 검사하는 유니크**(`DEFERRABLE INITIALLY DEFERRED`)를 권고한다 —
`plan.md` 데이터 모델 3절. **최종 상태만 검사한다는 점이 `AC-35`(전부 아니면 전무)와 같은 성질**이다.

**★ 계약 주의 — 수정은 저장 시 일괄 반영된다**

화면에서 이미지를 지워도 **저장 전에는 서버에 아무 일도 일어나지 않는다**(스펙 판단 14).
그래서 **개별 삭제·순서 변경 엔드포인트를 두지 않는다.** 두면 취소가 성립하지 않고
`FR-023`(원자성)이 깨진다.

## 5. `DELETE /api/gallery/posts/{postId}` — 글 삭제

**인증**: **필요 + 작성자 본인**

| 응답 | 조건 | `code` | AC |
|---|---|---|---|
| **200** | 삭제. **그 글의 이미지도 함께 제공 중단** | — | `AC-41` |
| **403** | 남의 글 (화면에 버튼이 없어도 동일) | `AUTH_FORBIDDEN` | `AC-38`·`AC-39` |
| **401** | 미인증 | `AUTH_REQUIRED` | — |
| **404** | 없는 글 | `POST_NOT_FOUND` | `AC-16` |

- **삭제 확인 대화**(`"정말로 삭제 하시겠습니까"`)는 **화면의 책임**이다 → `AC-40`.
  **서버는 확인 여부를 알 수 없다** — 확인 없이 온 요청과 구분할 방법이 없으므로,
  이것을 서버 계약으로 만들려는 시도(예: `confirmed=true` 파라미터)는 **검증이 아니라 장식**이다.
- 삭제 후 **이미지 주소로 직접 요청하면 404**여야 한다(6번). 파일 실체를 언제 지우는지는
  **`ADR-019`**이지만, **제공이 즉시 중단되는 것은 이 계약이 확정**한다.

## 6. `GET /api/gallery/images/{key}` — 이미지 제공 (원본 · 축소본)

**인증**: 불필요(글이 공개이므로). **주소 형태는 **`ADR-019`**이 정한다** — 클라이언트는
1·2번 응답이 준 주소를 그대로 쓴다(규칙 1).

| 응답 | 조건 | 헤더 | AC |
|---|---|---|---|
| **200** | 이미지 바이트 | 아래 표 전부 | `AC-8` |
| **200** | 축소본 요청이면 **원본보다 작은 바이트** | — | `AC-4` |
| **304** | 검증 헤더가 일치하는 조건부 요청 | — | `AC-5` |
| **404** | 없는 키 / **삭제된 글의 이미지** | `GALLERY_IMAGE_NOT_FOUND` | `AC-41` |

**응답 헤더 — 전부 명시한다**

| 헤더 | 값 | 왜 |
|---|---|---|
| `Content-Type` | **저장 시 판정한 형식**(`image/jpeg`·`image/png`·`image/gif`) | 업로드가 알려준 값을 믿지 않는다(`FR-018`) |
| `Content-Disposition` | **`inline`** (또는 생략) | **★ `attachment`면 갤러리가 성립하지 않는다.** 002는 *"이미지라도 다운로드로 처리"* 이고 **갤러리는 정반대**다(`FR-035`·`AC-8`). **공통 첨부 처리를 재사용하면 그대로 끌려온다** |
| **`X-Content-Type-Options`** | **`nosniff`** | **★ 인라인 표시를 고른 대가.** 002는 다운로드라 브라우저가 내용을 해석하지 않지만, 갤러리는 **렌더링을 시킨다.** 없으면 브라우저가 내용을 스니핑해 **이미지로 저장된 파일이 다른 것으로 해석**될 수 있다 |
| `Cache-Control` · 검증 헤더 | **`ADR-019`** | `AC-5`가 요구하는 것은 *"본문이 다시 전송되지 않는다"* 이며, 우리가 지킬 수 있는 것은 **헤더 계약**이다 — 조건부 요청에 **304** |

> **★ `AC-5`와 `AC-36`이 여기서 부딪힌다.**
> 캐시를 길게 걸수록 전송량은 줄지만(`AC-5`), 첫 장을 지운 뒤 *"목록에서 안 없어진다"* 가
> 오래 간다(`AC-36`). **주소가 내용에 따라 변하면 둘 다 성립한다** — 옛 주소가 조회되지 않기
> 때문이다. 그 대신 **목록 응답 자체는 캐시하지 않아야** 새 주소가 전달된다.
> → **`ADR-019`이 이 짝을 함께 결정해야 한다.** 한쪽만 정하면 다른 쪽이 조용히 깨진다.

- **키는 추측 가능하면 안 된다** — 순번이면 주소 하나로 전부 열거된다(`plan.md` 데이터 모델 5절).
- **애니메이션 GIF의 축소본은 첫 프레임**이다(스펙 판단 15).

## ★ 이 계약에서 가장 깨지기 쉬운 부분

001의 계약이 *"실패 응답 3경로가 같아야 한다"* 를 꼽았듯, 005에도 **한 곳만 틀려도
요구사항이 통째로 무너지는 지점**이 있다. 순서대로 위험이 크다.

### 1. **수정 요청을 델타로 읽는 것** (규칙 3)

*"보낸 것을 추가"* 로 구현하면 **삭제가 영원히 일어나지 않는다.**
`AC-32`·`AC-34`가 잡지만 **원인을 찾는 데 오래 걸린다** — 등록은 정상 동작하기 때문이다.
→ 계약 첫 절에 못박았고, **`AC-34`(빈 배열)가 이 해석을 직접 시험**한다.

### 2. **`imageId`의 소속을 검증하지 않는 것**

소유자 검증을 **글에 대해서만** 하고 이미지에 대해 하지 않으면 **남의 글 이미지를 가져올 수 있다.**
**스펙에 이 AC가 없다** — 계약이 유일한 방어 근거다(4번 참조).

### 3. **썸네일을 저장하는 것**

`gallery_post.thumbnail_image_id` 같은 컬럼을 두는 순간 `AC-32`가 **끊긴 참조**를 만들고,
`AC-31`(순서 변경)마다 갱신을 잊을 자리가 생긴다. **갱신을 빠뜨려도 상세는 멀쩡하고 목록만
조용히 틀린다** — 발견이 늦는 종류다. → **저장하지 않는다**(규칙 2).

### 4. **검증 순서와 20MB**

개수·전체 크기를 **파일을 전부 받은 뒤** 판정하면, 거부할 요청에 **20MB의 시간과 대역**을 쓴다.
→ **개수는 파트 헤더 단계에서, 전체 크기는 수신 중에** 판정한다.
**그러면서도 `AC-24`대로 판별 가능한 응답을 보내야 한다** — 그냥 끊으면 원칙 IV 위반이다.

### 5. **요청 크기 상한을 누가 자르는가**

배포 환경의 프록시에 **우리보다 낮은 상한**이 있으면 요청이 우리 앱에 도달하지 않고,
`GALLERY_REQUEST_TOO_LARGE` 대신 **프록시의 기본 오류 화면**이 나간다.
**테스트에서는 통과하고 배포에서만 깨진다** — 로컬 Compose에는 프록시가 없어서 드러나지 않는다.
→ **앱 상한을 프록시 상한보다 낮게.** 값은 `plan.md` 미해결 2.

### 6. **파일 저장과 DB 커밋이 원자적이지 않다**

`FR-023`은 원자성을, `SC-008`은 *"주인 없는 파일 0건"* 을 요구하는데 **파일 저장소는
트랜잭션에 참여하지 않는다.**
→ **① 검증 전부 → ② 파일 쓰기 → ③ DB 커밋**, ③ 실패 시 ②를 **보상 삭제**하고
**보상 삭제 실패는 반드시 로그**로 남긴다. **순서를 바꾸면 안 된다** — DB를 먼저 커밋하면
*"글은 있는데 그림이 없다"* 가 되고 그건 **사용자에게 보이는 고장**이다.

### 7. **002의 첨부 규칙이 그대로 끌려오는 것**

002는 *"이미지 파일이라도 다운로드로 처리(인라인 표시 금지)"* 이고 **갤러리는 정반대**다.
공통 첨부 처리를 재사용하면서 `Content-Disposition: attachment`가 따라오면
**갤러리가 성립하지 않는다**(`AC-8`). 그리고 인라인으로 바꾸는 순간 **`nosniff`가 필수**가 된다 —
002에는 없던 요구다(6번 헤더 표).

### 8. **`AC-5`와 `AC-36`을 각각만 만족시키는 것**

한쪽만 만족시키기는 쉽다. **캐시를 길게 걸면 `AC-5`가 통과하고 `AC-36`이 깨지며,
캐시를 끄면 반대**다. **두 테스트를 모두 두는 것이 유일한 방어**이고, 근본 해법은
**주소를 내용에 따라 변하게** 두는 것이다(**`ADR-019`**).

> 그건 우리가 무엇을 어떻게 검사하는지를 노출한다 — 001이 *"실패는 전부 같은 얼굴"* 로 정한 것과
> 같은 성질의 판단이다.
