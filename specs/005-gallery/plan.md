## Summary

**만들 것**: 이미지가 본문인 게시판. 목록은 카드(썸네일 + `+N`), 상세는 캐러셀,
등록·수정은 이미지 최대 20개를 **순서까지** 다룬다.

**기술 접근**: **썸네일을 저장하지 않는다.** `썸네일 = 이미지 순서의 첫 번째`라는 규칙을
**계산으로만 성립**시키고 어느 테이블에도 `thumbnail_id`를 두지 않는다. 이미지 목록은
**델타가 아니라 최종 상태**로 받아 한 트랜잭션에서 통째로 재배치한다.

**이 스토리를 관통하는 설계 축**: **"첫 번째"라는 규칙이 스스로 성립해야 한다.**
썸네일을 별도 컬럼·별도 참조로 저장하는 순간 `AC-32`(첫 장 삭제)가 **끊긴 참조**를 만들고,
그 상태는 화면에서 *"목록에 없는 그림이 계속 뜬다"* 로 나타난다. 저장하지 않으면
그 버그가 **원리적으로 발생할 수 없다.** 아래 모든 결정(스키마 · 계약 · 캐시)이 이 축을 따른다.

**두 번째 축**: **글 하나가 20MB다.** 그래서 *"검증을 언제 하는가"*, *"파일 저장과 DB 커밋 중
무엇이 먼저인가"*, *"요청 상한을 누가 자르는가"* 가 기능 문제가 아니라 **이 스토리의 주요 위험**이다.

> 이어 붙이고 3.5 절차(codex 크로스 검증)를 거쳐야 확정된다.
> **컬럼 타입·인덱스·제약은 물리 설계**이므로 여기 적는 것이 맞다(`process.md` 4.7).

### 0. 먼저 — 글 테이블의 형태는 005가 정하지 않는다

게시판 4종의 글을 **공통 1테이블 + 게시판 구분 컬럼**으로 둘지 **게시판별 테이블**로 둘지는
`data-model.md` 도구 1의 판단이고 **002의 몫**이다. 005는 소비자다.

**005가 어느 쪽에도 요구하는 것 3가지**

| | 요구 | 없으면 |
|---|---|---|
| 1 | 글에 **숫자 기본키**가 있다(`ADR-002`) | 이미지가 글을 참조할 수 없다 |
| 2 | **갤러리 글만 골라 페이지 단위로** 조회할 수 있다 | `AC-6`의 목록 규칙이 성립하지 않는다 |
| 3 | 글 삭제가 **이미지 삭제로 이어진다**(FK 또는 명시적 삭제) | `AC-41`이 깨지고 고아 행이 남는다 |

**두 형태에서 무엇이 달라지는가** — 이 표가 002에 넘기는 입력이다.

| | 공통 1테이블 | 게시판별 테이블 |
|---|---|---|
| 이미지 FK | `post(id)` | `gallery_post(id)` |
| **무결성** | ⚠️ **자유게시판 글에도 이미지를 붙일 수 있다.** DB가 막지 못하고 **코드가 지켜야 한다** | ✅ **타입이 곧 제약**이다 |
| 목록 조회 | 구분 컬럼 조건이 매 쿼리에 붙는다 → **구분 컬럼이 선두인 복합 인덱스**가 필요 | 조건이 없다 |

> **005의 의견**(결정권 없음): 무결성 차이가 실질적이다. 다만 공통 테이블을 고르더라도
> **이미지 테이블은 갤러리 전용**이므로 005의 설계는 FK 대상만 바뀐다.

### 1. 테이블: 갤러리 이미지 — **005가 새로 만드는 유일한 테이블**

**왜 별 테이블인가** (도구 1·2·3):
글 하나가 이미지를 **0~20개** 가지고(도구 2 → 1:N, FK는 N쪽),
이미지 하나는 글 하나에 속한다. 한 컬럼에 파일 목록을 몰아넣으면 **그중 하나만 지우거나
순서를 바꾸는 것이 불가능**해진다(도구 3) — 그리고 `AC-32`·`AC-33`이 정확히 그 동작이다.

| 컬럼(논리) | 타입 | NULL | 제약·기본값 | 근거 |
|---|---|---|---|---|
| 기본키 | `BIGINT GENERATED ALWAYS AS IDENTITY` | NOT NULL | PK | `ADR-002` · data-model 1절 |
| 글 참조 | `BIGINT` | NOT NULL | **FK → 글, `ON DELETE CASCADE`** | `AC-41`·`FR-025`. 삭제 규칙을 지금 정한다 — 나중에 `ALTER`로 고치지 않는다(001의 4절과 같은 판단) |
| **표시 순서** | `INTEGER` | NOT NULL | **`UNIQUE (글 참조, 표시 순서) DEFERRABLE INITIALLY DEFERRED`** + `CHECK (>= 0)` | ★ 아래 3절. **`ADR-020`가 이 컬럼의 의미를 정한다** |
| 저장 키 | `VARCHAR` | NOT NULL | **UNIQUE** | `FR-027`. **사용자 파일명이 아니다.** 추측 불가능한 값이어야 한다 — 아래 5절 |
| 원본 파일명 | `VARCHAR(255)` | NOT NULL | — | 기록·표시용. **경로로 쓰지 않는다** |
| 형식 | `VARCHAR` | NOT NULL | **`CHECK (image/jpeg · image/png · image/gif)`** | `FR-014`. **`ENUM`을 쓰지 않는다**(data-model 5.6과 같은 판단 — `CHECK`는 마이그레이션으로 자연히 바뀌고 제약이 SQL에 보인다). **저장 시 판정한 값**이지 업로드 헤더가 아니다(`FR-018`) |
| 바이트 크기 | `INTEGER` | NOT NULL | **`CHECK (> 0 AND <= 1048576)`** | `FR-015`. **DB에도 둔다** — `FR-017`(서버 검증)의 마지막 방어선. 001이 `username` 길이를 DB에도 건 것과 같은 이유 |
| 가로·세로 픽셀 | `INTEGER` ×2 | NOT NULL | — | 축소본 생성과 **픽셀 상한 판정**(미해결 4)에 필요. 판정 결과를 다시 계산하지 않으려면 저장해야 한다 |
| **축소본 키** | `VARCHAR` | **`ADR-019`에 달림** | UNIQUE | **업로드 시 생성**이면 `NOT NULL`, **첫 요청 시 생성**이면 `NULL` 허용, **매 요청 생성**이면 **컬럼 자체가 없다.** 세 선택지가 스키마를 다르게 만든다 — 이것이 후보 2를 ADR로 올린 이유다 |
| 생성 시각 | `TIMESTAMPTZ` | NOT NULL | `now()` | data-model 1절 |

**썸네일 컬럼이 없다는 것이 이 설계의 핵심이다.**
`gallery_post.thumbnail_image_id` 같은 컬럼을 두면 `AC-32`(첫 장 삭제)에서 **끊긴 참조**가 생기고,
`AC-31`(순서 변경)마다 그 컬럼을 함께 갱신해야 하며, **갱신을 빠뜨리면 목록만 조용히 틀린다.**
저장하지 않고 `min(표시 순서)`로 계산하면 **틀릴 자리가 없다.**

**이미지 1~20개 제약은 DB가 지키지 못한다** — 정직하게 적어둔다.
행 개수에는 `CHECK`를 걸 수 없다. `FR-016`(≤20)과 `FR-019`(≥1)는 **애플리케이션이 트랜잭션
안에서** 지키고 **통합 테스트가 검증**한다(`AC-18`·`AC-22`·`AC-34`).
**비정규화 카운트 컬럼 + `CHECK`는 기각한다** — 카운트를 갱신하는 코드가 또 하나의 틀릴 자리이고,
지금은 목록의 `+N`을 집계로 얻을 수 있다. **방아쇠: 목록 집계가 실측으로 문제가 되는 시점.**

### 2. 인덱스 — **조회 패턴에서 도출한다**

먼저 005가 실제로 던지는 질의를 전부 적는다. 인덱스는 그 다음이다.

| # | 언제 | 질의 | AC |
|---|---|---|---|
| Q1 | 목록 카드의 썸네일 | 글 N건에 대해 **글마다 표시 순서가 가장 작은 이미지 1개** | `AC-1`·`AC-4`·`AC-44` |
| Q2 | 목록 카드의 `+N` | 글 N건에 대해 **글별 이미지 개수** | `AC-2`·`AC-3`·`AC-44` |
| Q3 | 상세 캐러셀 | 글 1건의 **이미지 전부를 표시 순서로** | `AC-7` |
| Q4 | 이미지 제공 | **저장 키로 이미지 1건** (+ 소속 글이 살아 있는지) | `AC-8`·`AC-41` |
| Q5 | 수정 저장 | 글 1건의 이미지 전부를 잠그고 재배치 | `AC-31`~`AC-35` |
| Q6 | 글 삭제 | 글 1건의 이미지 전부 삭제(CASCADE) | `AC-41` |

**도출 결과 — 인덱스는 2개면 충분하다.**

| # | 인덱스 | 무엇을 태우나 | 도출 |
|---|---|---|---|
| 1 | **`(글 참조, 표시 순서)` 복합 유니크** | **Q1·Q2·Q3·Q5·Q6 전부** | 3절의 유니크 제약이 만드는 인덱스가 **그대로 조회 인덱스**다. 선두 컬럼이 글 참조이므로 *"이 글의 이미지"* 가 전부 이 인덱스를 탄다 |
| 2 | **`저장 키` 유니크** | Q4 | 이미지 제공은 **키로 단건**이다. 없으면 이미지 한 장 볼 때마다 전 테이블 스캔이다 |

**★ FK 인덱스를 따로 만들지 않는다 — 그리고 그것이 이번 도출의 핵심이다.**
`data-model.md` 5.5의 4번은 *"PostgreSQL은 FK 컬럼에 인덱스를 자동으로 만들지 않으므로
`ON DELETE CASCADE`가 전체 스캔이 된다"* 고 규칙화했다. 그 규칙을 기계적으로 적용하면
`ix_gallery_image_post_id`를 만들게 되는데, **1번 복합 인덱스의 선두 컬럼이 이미 글 참조**라
**완전히 중복**이다. 중복 인덱스는 쓰이지 않으면서 **모든 INSERT/UPDATE/DELETE를 느리게 하고
용량을 먹는다** — 그리고 글 하나에 이미지가 20행씩 들어오는 테이블이다.
→ **규칙은 "FK 컬럼이 어떤 인덱스의 선두에 있는가"로 읽어야 한다.**

**필요 없다고 판정한 인덱스** (적어두지 않으면 나중에 *빠뜨린 것* 과 구분되지 않는다):

| | 왜 필요 없나 |
|---|---|
| 형식 | 값이 3종이라 선택도가 낮고, *"png만 조회"* 같은 요구가 없다 |
| 바이트 크기 · 픽셀 | 범위로 찾는 기능이 없다. 저장은 **판정 결과 보존**이 목적이다 |
| 생성 시각 | 이미지를 시각으로 찾는 기능이 없다. **방아쇠: **`ADR-019`**가 *"표시 후 일괄 정리"* 로 결정되면** 정리 배치가 시각으로 훑으므로 그때 필요해진다 |
| 축소본 키 | 축소본 주소로 찾는다면 필요하다 — **`ADR-019`**가 정해진 뒤 판단. 원본 키와 같은 이름공간을 쓰면 2번 인덱스로 덮인다 |

**★ Q1·Q2가 N+1이 되기 쉽다.**
목록 10~50건에 대해 글마다 이미지를 따로 조회하면 **한 화면에 쿼리 50개**다.
`글 참조 IN (...)` 한 번으로 묶고, 개수는 같은 조건의 집계 하나로 얻는다.
**JPA를 쓰면 기본이 N+1이므로 이것이 `ADR-004`가 경고한 그 함정**이다 —
`local`·`test` 프로필의 SQL 로깅으로 확인한다.

### 3. ★ 표시 순서의 유니크 제약과 "중간 상태" — 이 스키마에서 가장 틀리기 쉬운 곳

`AC-35`는 *"순서가 중복되거나 비면 첫 번째를 결정할 수 없다"* 를 근거로 원자성을 요구한다.
그 규칙을 DB로 강제하려면 `(글 참조, 표시 순서)`에 유니크가 필요하다. **그런데 그냥 걸면
순서 변경이 실패한다.**

```
현재: A=0, B=1, C=2      목표: C=0, A=1, B=2
C를 0으로 UPDATE → 이 순간 A도 0이다 → 유니크 위반 → 롤백
```

**중간 상태가 규칙을 위반한다.** 최종 상태는 멀쩡한데 도중에 걸린다.

| 방법 | 판단 |
|---|---|
| **`DEFERRABLE INITIALLY DEFERRED` 유니크** *(권고)* | **커밋 시점에만 검사**한다. 중간 상태를 허용하면서 **최종 상태의 정합성은 DB가 보장**한다. `AC-35`(전부 아니면 전무)와 성질이 정확히 같다 |
| 전부 삭제 후 재삽입 | 기존 이미지 행의 기본키가 바뀐다 → **이미 배포된 이미지 주소가 전부 무효**가 되고 `AC-5`(캐시 재사용)와 정면 충돌한다. **기각** |
| 임시 음수 값으로 밀어냈다 되돌리기 | 동작하지만 **UPDATE가 두 배**이고, 중간에 실패하면 음수가 남는다. `DEFERRABLE`이 있는 DB에서 손으로 흉내 내는 것이다. **기각** |
| 유니크를 걸지 않고 코드로 | 위반 상태가 **실제로 저장 가능**해진다. `AC-35`가 막으려는 상태를 DB가 허용한다. **기각** |

> **이것이 `ADR-020`(순서 표현 방식)와 묶인다.** *"간격을 둔 정수"* 나 *"소수"* 를 고르면
> 사이 삽입 때 재배치가 줄어드는 대신 **값이 조밀해지면 결국 재배치가 필요**하고,
> *"연속 정수"* 는 항상 재배치하는 대신 **규칙이 단순하고 `min()`이 곧 썸네일**이다.
> 005는 **한 번에 최대 20개**이고 **수정은 최종 상태를 통째로 받으므로**(계약 4번) 재배치 비용이
> 애초에 작다 → 005의 의견은 **연속 정수**다. **결정은 사람이 한다.**

### 4. 축소본을 별 테이블로 두지 않는 이유

이미지 1건에 축소본이 **정확히 1개**이고(여러 해상도 대응은 Out of Scope), 원본과 **생명주기가
같다**(원본이 지워지면 함께 지워진다). 1:1이고 항상 함께 사는 것은 **같은 행의 컬럼**이다.
→ 도구 1의 *"같은 개념인가"* 에 걸린다. **방아쇠: 해상도가 2종 이상 필요해지는 시점**
(그때는 1:N이 되므로 테이블이 맞다).

### 5. 저장 키는 추측 가능하면 안 된다

`FR-027`은 *"업로드 파일명을 저장 이름으로 쓰지 않는다"* 만 요구하지만, **순번(`1.jpg`, `2.jpg`)으로
바꾸는 것도 그 요구는 충족한다.** 그런데 순번이면 **주소를 하나 알면 전부를 열거**할 수 있다.
갤러리 글은 공개라 목록 자체는 문제가 아니지만, **`AC-41`(삭제된 글의 이미지)** 과 함께 보면
*"주소를 아는 사람에게 계속 공개"* 를 막으려는 요구와 어긋난다.
→ **저장 키는 충분한 난수를 포함한다.** *(Claude 판단 — 사람 검증 필요)*

## E2E 예산 — **005는 1개를 쓴다**

`test-strategy.md` 4장: **프로젝트 전체 5~10개.** 001이 **7개**를 쓴다.

**스펙이 올린 후보는 2개**였다(`AC-12` 키보드 도달 · `AC-27` 즉시 미리보기).
**깎을 수 있는지 판단하라**는 것이 이 절의 몫이다.

| 후보 | 판단 | 근거 |
|---|---|---|
| **`AC-12` 키보드만으로 전 이미지 도달** | ✅ **남긴다** | **대체 수단이 없다.** 인덱스 계산·순환은 단위로 내려갔고 **남은 것은 "초점이 캐러셀에 도달하고 키 입력이 먹는가"** 뿐인데, 그것은 **브라우저가 하는 일**이다. 그리고 이 AC가 거짓이면 결과는 *"보기 불편"* 이 아니라 **"볼 수 없다"** 다(spec 판단 4) — 001의 `AC-7`(스크립트로 쿠키를 못 읽는다)과 같은 급의 항목이다 |
| **`AC-27` 선택 즉시 미리보기** | ❌ **깎는다** | ① *"저장 전에 개별 삭제·추가"* 라는 **상태 전이 부분이 단위로 내려간다** — E2E가 아니면 못 보는 것은 *"파일 선택 직후 그림이 뜬다"* 한 줄이다. ② **005 고유의 위험이 아니다** — 002 첨부에도 같은 화면이 있고, 거기서 만들면 005는 재사용이다. ③ 파일 선택은 E2E에서 **가장 잘 깨지는 조작**이라 유지 비용이 높다(4장이 개수를 줄이라는 이유 그 자체). → **9.5 기능 QA로 내리고, 통과한 AC는 원칙 VIII에 따라 승격 대상으로 표기**한다 |

**결론**

```
001: 7개   005: 1개   →  누계 8개 / 예산 5~10개
남은 스토리 002·003·004·006 넷이 나눠 쓸 수 있는 것 = 2개 이하
```

**여전히 부족하다.** 005가 2개에서 1개로 깎아도 **넷에 2개**다.
005의 판단은 이렇다 — **예산 숫자를 지금 고치지 않는다**(추측으로 규칙을 고치는 것은
`process.md` 결정 26이 경고한 것이다). 대신 **관찰 결과 하나를 통합 단계에 넘긴다**:

> **001의 7개 중 4개(`AC-7` 쿠키 · `AC-24` 복귀 · `AC-34` 오픈 리다이렉트 · `AC-4` 재발급 재시도)는
> 인증 고유이고 002~006이 다시 쓰지 않는다.** 반면 **`AC-24`(복귀)는 005의 `AC-29`가 그대로
> 재사용한다** — 005가 E2E를 만들지 않고 넘어갈 수 있는 것이 그 덕이다.
> **게시판 4종이 서로의 E2E를 재사용할 수 있는지가 남은 예산의 실질**이며,
> 그 판단은 **네 스펙이 다 모이는 통합 단계**에서만 할 수 있다.

**1번을 앞으로 당긴 이유를 강조한다.** US1이 스펙상 먼저인 것은 **사용자 가치의 우선순위**이고,
구현 순서는 **검증 가능성의 순서**다. 001도 같은 이유로 US1을 먼저 했다(관리자 계정이
자동 생성되어 가입 없이 검증 가능했기 때문). 005는 **자동으로 생기는 갤러리 글이 없다.**

**2번을 3번보다 먼저 두는 이유**: `AC-4`(축소본)와 `AC-36`(캐시 갱신)은 **목록의 응답 형태를
결정**한다. 목록을 먼저 만들고 나중에 축소본을 얹으면 **주소 설계가 바뀌어 목록을 다시 쓴다.**

## 위험과 대응

| 위험 | 왜 위험한가 | 대응 |
|---|---|---|
| **★ 파일 저장과 DB 커밋이 원자적이지 않다** | `FR-023`은 원자성을, `SC-008`은 *"주인 없는 파일 0건"* 을 요구하는데 **파일 저장소는 트랜잭션에 참여하지 않는다.** DB를 롤백해도 파일은 남는다 | **① 검증을 전부 끝낸 뒤 ② 파일을 쓰고 ③ DB를 커밋**한다. ③이 실패하면 **②를 보상 삭제**하고, **보상 삭제가 실패하면 로그로 남긴다**(원칙 V). **순서를 바꾸면 안 된다** — DB를 먼저 커밋하면 *"글은 있는데 그림이 없다"* 가 되고, 그건 사용자에게 보이는 고장이다(고아 파일은 보이지 않는다). **완전한 0건은 정리 배치가 있어야 성립** → **`ADR-019`** |
| **★ 21장을 20MB 다 받은 뒤에 거부한다** | 개수·전체 크기 검증을 **파일을 전부 수신한 다음**에 하면, 거부할 요청에 **20MB의 대역과 시간**을 쓴다. 악의가 없어도 그렇고, 있으면 그대로 서비스 거부 수단이다 | **개수는 파트 헤더 단계에서, 전체 크기는 수신 중에** 판정하고 **초과 즉시 끊는다.** 그리고 **끊더라도 `AC-24`대로 판별 가능한 응답을 보낸다** — 그냥 끊으면 원칙 IV 위반이다. **어디까지가 프레임워크이고 어디부터 우리 코드인지**를 7번에서 실측한다 |
| **★ 프록시가 먼저 자르면 우리 오류 코드가 나가지 못한다** | 배포 환경의 리버스 프록시에 **우리보다 낮은 본문 상한**이 있으면 요청이 우리 앱에 도달하지 않는다. `AC-24`가 **테스트에서는 통과하고 배포에서 깨지는** 종류다 | **앱 상한을 프록시 상한보다 낮게** 잡는다(그래야 우리가 먼저 판정한다). 값은 배포 환경에 달려 미해결 2. **로컬 Compose에는 프록시가 없어 이 문제가 드러나지 않는다** — 방아쇠는 배포 환경 확정 시점(`process.md` 6.2) |
| **★ 수정 요청을 델타로 오해한다** | 계약은 *"이미지 목록 = 최종 상태"* 인데(계약 4번) 구현이 *"보낸 것을 추가"* 로 읽으면 **삭제가 일어나지 않고**, 반대로 *"보낸 것만 남긴다"* 를 놓치면 **안 보낸 것이 안 지워진다.** 둘 다 `AC-32`·`AC-34`가 잡지만 **원인을 찾는 데 오래 걸린다** | 계약 문서에 **최종 상태임을 첫 줄에** 못박았고, `AC-34`(전부 삭제 시도)가 이 해석을 직접 시험한다 |
| **★ 다른 글의 이미지 식별자를 수정 요청에 섞을 수 있다** | 수정 요청이 *"유지할 이미지 id"* 를 받으므로, **남의 글 이미지 id를 넣으면 내 글로 옮겨 온다.** 소유자 검증은 **글**에 대해 하지 정작 **이미지**에 대해 하지 않기 쉽다 | **모든 이미지 id가 그 글에 속하는지 검증**하고 아니면 거부한다(`GALLERY_IMAGE_REFERENCE_INVALID`). **스펙에 이 AC가 없다** — 계약에서 발견했고 아래 *스펙으로 되돌릴 것* 에 올렸다 |
| **캐시를 길게 걸수록 `AC-36`이 오래 깨진다** | `AC-5`(캐시 재사용)와 `AC-36`(바뀌면 즉시 반영)이 **정면으로 부딪힌다.** 한쪽만 만족하기는 쉽다 | **이미지 주소를 내용에 따라 변하게** 두면 둘 다 성립한다(주소가 바뀌므로 옛 캐시가 조회되지 않는다). 단 **목록 응답 자체는 캐시하지 않아야** 새 주소가 전달된다 → **`ADR-019`** |
| **JPA N+1로 목록이 무너진다** | 카드 50장 × 이미지 조회 = 쿼리 50개 | 글 식별자 묶음 조회 + 집계 1회. `local`·`test` SQL 로깅으로 확인(`ADR-004` 완화책 그대로) |
| **극단적 해상도가 메모리를 먹는다** | 1MB 이하인데 20000×20000이면 **축소본을 만드느라 수 GB**를 쓴다. 크기 상한이 픽셀 상한을 보장하지 않는다 | **픽셀 상한을 둔다.** 값은 처리 방식이 정해져야 알 수 있다 → 미해결 4. **상한 판정은 이미지 전체를 펼치기 전에** 헤더로 한다 |
| **인라인 제공이 새 표면을 만든다** | `FR-035`가 브라우저에게 렌더링을 시킨다. 002는 다운로드라 없던 위험이다 | `nosniff` + 저장 시 판정한 형식으로 `Content-Type` 고정 + 허용 형식 3종 유지(**SVG를 넣지 않는 것이 방어의 큰 부분**이다 — SVG는 스크립트를 담는다) |
| **관리자 경로에 검증이 두 벌 생긴다** | `AC-46`이 잡으려는 것. 관리 등록/수정을 별 컨트롤러로 만들면 **검증을 복사**하게 되고, 한쪽만 고치는 날이 온다 | **검증과 저장을 같은 서비스**로 두고 컨트롤러만 나눈다. `AC-46`이 *"같은 코드가 나오는가"* 로 이것을 시험한다 |
| **002가 축소본 개념 없는 첨부 기반을 준다** | 그러면 005가 그 위에 따로 얹고 **파일 저장 경로가 두 벌**이 된다 | **의존 절에 명시했다.** 002 착수 전에 통합 단계가 전달해야 하는 항목 |

| **갤러리 카테고리** | **004** | 분류가 필수라 **하나도 없으면 등록이 불가능**하다 |
| **관리자 화면 골격** | **004** | US6이 그 위에 얹힌다 |
| **공통 1단계 마이그레이션에 이미지 테이블 포함** | **1단계(사람)** | **005가 시작조차 못 한다** |

**005가 다른 스토리에 넘기는 것**: 없다. 단 **메인 페이지의 갤러리 영역**(최신 3개 · 썸네일 · `+N`)이
`FR-002`·`FR-003`을 그대로 쓴다 — **규칙을 다시 정하지 말고 이 스펙을 참조**해야 한다.

## 스펙으로 되돌릴 것 — 계획이 발견한 빈틈

001의 5번 게이트가 계획 단계에서 AC 3개를 신설했던 것과 같은 종류다.
**여기서 스펙을 고치지 않고 통합 단계에 올린다**(병렬 중 스펙 수정은 충돌한다).

| # | 무엇 | 왜 스펙 결함인가 |
|---|---|---|
| 1 | **수정 요청에 다른 글의 이미지 식별자를 넣는 경우의 AC가 없다** | *"본인 글만 수정"*(`AC-37`)은 **글**의 소유를 보고, **이미지**의 소속은 보지 않는다. 그 틈으로 **남의 글 이미지를 내 글로 가져올 수 있다.** 권한 경계 Edge Case에 이 줄이 없다 → **AC 신설 권고** |
| 2 | **`1MB`의 정의가 없다** | `1,048,576`(2^20)인지 `1,000,000`인지에 따라 **경계 테스트가 갈린다.** Edge Cases는 *"정확히 1MB 허용 / 1MB+1바이트 거부"* 라고만 적었다. 005는 **`1,048,576`으로 읽었다** *(Claude 판단 — 사람 검증 필요)* |
| 3 | **`AC-5`의 "다시 전송되지 않는다"를 서버가 단독으로 보장할 수 없다** | 캐시 재사용은 **브라우저의 동작**이다. 우리가 지킬 수 있는 것은 **헤더 계약**이므로 AC를 *"검증 가능한 캐시 헤더를 제공하고 조건부 요청에 304로 답한다"* 로 조이는 것이 정확하다 |
