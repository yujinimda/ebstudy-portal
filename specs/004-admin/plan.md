**일치**(스펙이 판단한 것을 스키마가 이미 지키고 있다):

| 스펙 | 스키마 | |
|---|---|---|
| `J-3` 사용 중 분류는 삭제하지 않는다 | `fk_posts_categories ... ON DELETE RESTRICT` | ✅ **DB가 판정한다** |

**어긋남 3건** — ⚠️ **착수 전에 어느 쪽을 고칠지 정해야 한다**:

| # | 스펙 | 스키마 | 무엇이 문제인가 |
|---|---|---|---|
| **불일치-1** | `FR-016`·`AC-21` 이름 **1~30자**, 초과는 400 `CATEGORY_NAME_INVALID` | `name VARCHAR(50)` | **31~50자가 DB를 통과한다.** 앱에서 30자로 막으면 동작은 맞지만 **DB의 마지막 방어선이 스펙과 다른 값**이 되고, `data-model.md` 5.6이 *"길이 제약을 DB에도 둔다 — 서버 검증의 마지막 방어선"* 으로 정한 규칙과 어긋난다 |
| **불일치-2** | Edge Cases *"표시 순서가 음수 또는 0 — **허용한다**"* | `ck_categories_sort_order CHECK (sort_order >= 0)` | **음수를 넣으면 DB 제약 위반 → 500이 난다.** 스펙이 허용한 입력이 예상 못한 예외가 되는 것이라 **원칙 IV 위반 경로**다 |
| **불일치-3** | `FR-016` *"1자 이상"* | `ck_categories_name_not_blank CHECK (btrim(name) <> '')` | 스펙대로면 **공백 1자(`" "`)가 유효한 이름**인데 DB가 거부한다. 스펙 쪽이 덜 적힌 것이며 **DB가 맞다** |

**권고**: 불일치-3은 **스펙을 고친다**(이름은 공백만으로 이룰 수 없다 — DB가 옳다).
불일치-1·2는 **사람 결정**이며 → [미해결 항목](#미해결-항목-needs-clarification) 3·4.
어느 쪽으로 가든 **적용된 마이그레이션은 수정하지 않고 새 번호(`V11`)로 고친다**(원칙 VI).

### 0.2 **`ADR-007`·`ADR-008`**는 "정할 것"이 아니라 "뒤집을 것"이 됐다

스펙은 **`ADR-007`**(분류 저장 구조)·**`ADR-008`**(글이 분류를 참조하는 방식)을 **아직 열린 결정**으로 적었다.
**실제로는 둘 다 이미 코드에 있다.**

| ADR 후보 | 스펙의 표기 | 실제 상태 |
|---|---|---|
| 3 저장 구조 | 게시판별 테이블 분리 vs 단일 테이블 + 구분 값 | **단일 테이블 + `board_type`으로 이미 구현·적용됨** (V5) |
| 4 참조 방식 | 참조 vs 등록 시점 이름 복사 | **참조로 이미 구현·적용됨** (`posts.category_id` FK, 이름 복사 컬럼 없음) |

**이것은 결함이 아니라 사실의 갱신이다.** 004 스펙은 002의 바이브 코딩과 **병렬로** 쓰였고,
스펙을 쓰는 쪽에서 그 결과를 볼 수 없었다. 다만 **문서가 사실보다 뒤처진 상태로 남으면
사람이 "아직 안 정했구나"로 읽는다.** 그래서 여기서 갱신한다.

→ 사람에게 남는 질문은 *"무엇으로 할까"* 가 아니라 **"뒤집을 것인가"** 이고,
뒤집는 비용은 **마이그레이션 + 이미 들어간 글 데이터 이관**이다.
번호는 통합 단계가 붙이되, **두 ADR의 본문은 "채택된 결정의 사후 기록"으로 쓴다.**

### 2. 004의 조회 패턴 → 인덱스 역산

**인덱스는 "있으면 좋은 것"이 아니라 조회 패턴의 결과다.** 004가 실제로 던지는 쿼리를 먼저 적는다.

| # | 언제 | 쿼리 | 빈도 |
|---|---|---|---|
| **1** | **모든 목록 화면**(사용자 포함)의 분류 필터·글 등록 선택지 | `board_type = ? AND active = true ORDER BY sort_order, id` | **최다.** 비로그인 방문자 포함 |
| 2 | 관리 화면의 분류 목록 | `board_type = ? ORDER BY sort_order, id` (비활성 포함 — `AC-28`) | 관리자만 |
| 3 | 이름 중복 판정 (`AC-20`) | `board_type = ? AND LOWER(name) = LOWER(?)` | 등록·수정 시 |
| 4 | 단건 조회 (수정·삭제·글 등록 검증) | `id = ? AND board_type = ?` | 건별 |
| 5 | **사용 중 판정**(`AC-22`의 안내 문구용 건수) | `SELECT count(*) FROM posts WHERE category_id = ?` | 삭제 시도 시 |
| 6 | 활성 분류 0개 판정 (`AC-31`) | 1번과 같은 쿼리의 존재 여부 | 글 등록 시 |
| 7 | 사용불가 아이디 목록 (`AC-33`) | `SELECT * FROM reserved_usernames ORDER BY LOWER(username)` | 관리자만 |

**→ 필요한 인덱스와 그것을 만족하는 기존 인덱스**:

| 패턴 | 인덱스 | 상태 | 왜 이 형태인가 |
|---|---|---|---|
| 1·2·6 | `ix_categories_board_type_sort_order (board_type, sort_order, id)` | ✅ V5 | **등가 조건(`board_type`)이 선두**여야 뒤의 정렬까지 인덱스로 받는다. `id`가 뒤에 붙어 **`AC-30`(중복 순서의 결정적 정렬)이 인덱스 차원에서 성립**한다 — 코드의 2차 정렬에 기대지 않는다 |
| 3 | `uk_categories_board_type_name (board_type, LOWER(name))` | ✅ V5 | 유일성과 조회를 겸한다. **판정 쿼리도 `lower()`로 써야 인덱스를 탄다**(`data-model.md` 2절과 같은 함정) |
| 4 | PK + `board_type` 필터 | ✅ | 인덱스 추가 불필요. **`id`만으로 찾지 않는 것이 중요하다** — 다른 게시판의 분류 `id`를 넘기는 우회를 막는다 |
| **5** | `ix_posts_category_id` | ✅ V6 | **없으면 삭제 시도마다 `posts` 전체를 훑는다.** 그리고 이 인덱스는 **FK `RESTRICT` 판정 자체가 쓰는 인덱스**이기도 하다 |
| 7 | `uk_reserved_usernames_username_lower (LOWER(username))` | ✅ V3 | **정렬을 이 인덱스가 그대로 받는다** — `ORDER BY LOWER(username)`이 함수 인덱스와 같은 식이다 |

**만들지 않는 인덱스** (적어두지 않으면 나중에 *빠뜨린 것*과 구분되지 않는다):

| | 왜 필요 없나 |
|---|---|
| `(board_type, active, sort_order)` 또는 `active` 부분 인덱스 | 패턴 1이 `active`로 한 번 더 좁히지만, **게시판당 분류는 수십 개 규모**다. 선두 두 컬럼으로 이미 수십 행까지 좁혀지고 그 뒤 필터는 비용이 없다. 인덱스를 하나 더 깔면 **분류를 활성/비활성으로 바꿀 때마다 인덱스 두 개를 갱신**한다 |
| `categories.name` 단독 | 이름으로 검색하는 화면이 없다. 중복 판정은 항상 `board_type`과 함께 온다 |
| `reserved_usernames`의 추가 인덱스 | 목록이 수십~수백 행이고 화면이 하나다 |

### 3. 관리자 행위 기록 (`FR-012`·`AC-16`) — **설계 2안, 결정은 사람**

## AC → 테스트 레벨 배정

> ⚠️ **이것은 "배정"이지 "커버리지"가 아니다.** *(001의 5번 게이트가 이 혼동을 잡았다.)*
> 커버리지는 **테스트 이름의 AC-ID**로 세며(원칙 II), 이 시점에는 `tasks.md`도 테스트 코드도
> 없다. **실제 커버리지가 확정되는 곳은 6번·7번이고 판정되는 곳은 CI다.**
> 이 표가 말하는 것은 **"배정 없이 남은 AC가 0개"** 하나뿐이다.

`test-strategy.md` 3장 기준을 적용했다. **AC 하나당 최소 하나, 여러 AC를 한 테스트로 뭉치지 않는다.**

| AC | 무엇 | 레벨 | 비고 |
|---|---|---|---|
| AC-1 | 관리 메뉴 + 현재 위치 표시 | **E2E** ⚠️ | 서버가 관여하지 않는다. **프론트 레벨이 있으면 그쪽**(**`ADR-024`**) |
| AC-2 | 관리자 이름 · 로그아웃 노출 | **E2E** ⚠️ | 위와 같음. `AC-1`과 **다른 테스트**로 둔다 |
| AC-3 | 미인증 진입 → 관리자 로그인 | **E2E** | 브라우저가 이동을 수행한다. **004의 핵심 판단 `J-12`를 검증하는 유일한 자리**이며 001의 E2E는 사용자 화면이었다 |
| AC-4 | `USER` 진입 → 같은 처리 | **단위** | **`AC-3`과 목적지가 같고 입력만 다르다.** 가드 판정은 `(인증여부, 권한) → 목적지` 의 순수 함수다. **실제 차단은 001 `AC-22`의 통합이 이미 본다** — 화면 이동은 편의일 뿐이다(스펙 `AC-4` 근거) |

### E2E 예산 — 004는 예산 안에 들어가지 못한다

| | 개수 |
|---|---|
| `test-strategy.md` 4장 상한 (**프로젝트 전체**) | **5~10** |
| 001이 쓰는 것 | **7** |
| 004가 요구하는 것 (위 배정) | **7** |
| 002·003·005·006이 쓸 것 | **미정 (0은 아니다)** |
| **합계** | **14 + α > 10** |

**깎을 수 있는 만큼 이미 깎았다.** 스펙의 초안은 E2E 후보 8개였고 이 계획이 다음을 내렸다:

| 내린 것 | 어디로 | 근거 |
|---|---|---|
| `AC-4` | E2E → **단위** | `AC-3`과 목적지가 같고 입력 하나 차이다. 실제 차단은 001 통합이 본다 |
| `AC-5` | E2E → **단위** | 001 `AC-34`가 이미 브라우저 이동을 E2E로 본다. 004는 판정을 좁힐 뿐이다 |
| `AC-25`·`AC-26`·`AC-28` | E2E → **통합** | *"선택지에 무엇이 있는가"* 는 **API 응답의 내용**이고 화면은 그것을 그린다 |
| `AC-11` | E2E → **통합** + 002 E2E 재사용 | 관리 목록이 같은 엔드포인트를 쓴다는 것이 요점이다 |

**남은 7개는 004 안에서 더 깎을 수 없다.** 전부 **서버가 관여하지 않는 화면 동작**이고
(`AC-1`·`AC-2`·`AC-6`~`AC-9`) 또는 **브라우저가 수행하는 이동**(`AC-3`)이다.
통합 테스트가 볼 수 있는 것이 하나도 없다.

**→ 004 밖에서 둘 중 하나가 필요하다** (미해결 항목 1):

| 안 | 004의 E2E | 대가 |
|---|---|---|
| **A. 프론트 컴포넌트 레벨 신설** (**`ADR-024`**) | **2개** (`AC-3`·`AC-6`) | 테스트 도구·설정이 하나 늘고 `test-strategy.md`를 고쳐야 한다. **`AC-1`·`AC-2`·`AC-7`~`AC-9`가 여기로 간다** |
| **B. E2E 상한 재정** | 7개 유지 | 001의 7개까지 합쳐 14개. **4장이 막으려던 것**(*"100개 쌓이면 그 자체가 짐"*)에 한 걸음 다가간다 |

**계획의 권고는 A다.** 근거는 개수가 아니라 **성질**이다 — `AC-8`(*"취소하면 요청이 가지
않고 입력이 남는다"*)을 E2E로 쓰면 **브라우저를 띄우고 로그인 상태를 주입하고 목록을 열어
등록 화면으로 들어간 다음** 확인창을 취소한다. 검증하려는 것은 **컴포넌트 하나의 분기**인데
비용의 90%가 거기 도달하는 데 쓰인다. **4장이 금지한 "매 테스트 로그인"과 같은 종류의
낭비**이며, 도구가 아니라 **레벨 선택이 틀린 것**이다.

## 구현 순서 — 테스트가 먼저 (원칙 I)

스펙의 우선순위(US1 → US2 → US3 → US4)를 그대로 따르지 **않는다.**
**US3(분류)의 공개 조회 경로가 다른 스토리의 선행 조건**이기 때문이다.

| 순서 | 무엇 | 왜 이 순서 |
|---|---|---|
| **0** | **미해결 항목 1·2·3·4를 사람이 확정** | E2E 레벨과 기록 위치는 **테스트를 쓰기 전에** 정해져야 한다. 불일치-1·2는 **테스트가 기대할 값 자체**를 바꾼다 |
| **1** | **공개 분류 조회 + `SecurityConfig` permitAll** (`AC-32`·`AC-19`·`AC-25`·`AC-30`) | ★ **002·003·005의 목록 화면이 전부 이것을 기다린다.** 비로그인 목록 화면이 필터를 못 그리면 그 게시판들의 화면이 성립하지 않는다. **공통 파일(`SecurityConfig`)을 건드리는 유일한 단계**라 먼저 끝내고 잠근다 |
| 2 | 관리자 분류 CRUD (`AC-17`·`AC-18`·`AC-20`~`AC-24`) | 1의 데이터를 만드는 쪽. **`AC-22`의 FK 위반 → 409 번역을 여기서 세운다** |
| 3 | 비활성 규칙 (`AC-26`·`AC-27`·`AC-29`·`AC-31`) | **글 등록·수정 검증에 얹히는 규칙**이라 002·003·005의 등록 API가 존재해야 검증된다 |
| 4 | 관리자 삭제 예외 (`AC-12`~`AC-16`) | **002의 글·댓글 삭제 계약 위에 얹힌다.** 002가 없으면 검증 대상이 없다 |
| 5 | 사용불가 아이디 (`AC-33`~`AC-35`) | 001 데이터 위에 화면만. **다른 무엇도 기다리지 않는다** → 병목이 아니므로 뒤로 |
| 6 | 관리자 셸 + 화면 6개 (`AC-1`~`AC-11`) | 1~5의 엔드포인트가 있어야 화면이 붙는다 |

**1번을 먼저 하는 이유를 강조한다.** `AC-32`는 004의 AC지만 **004에서 가장 늦게 아쉬워지는
것이 아니라 가장 먼저 아쉬워진다** — 002·003·005의 사용자 목록 화면이 열리는 순간 필요하다.
그리고 그것을 여는 파일이 **모두가 공유하는 `SecurityConfig`** 다.
뒤로 미루면 **다른 레인이 각자 우회로를 만든다**(분류를 하드코딩하거나 목록 화면을 로그인
전용으로 바꾸는 식으로). **우회로는 나중에 지우기 어렵다.**

> **US4(P3)를 5번에 두었지만 순서상 마지막이 아니다.** 우선순위와 구현 순서가 다른 이유는
> **의존 방향이 우선순위와 무관**하기 때문이다. US4는 아무도 기다리지 않으므로 어디에 놓아도
> 남을 막지 않는다.

## 위험과 대응

| 위험 | 왜 위험한가 | 대응 |
|---|---|---|
| **★ 분류 삭제를 "건수 조회 후 삭제"로 구현한다** | `AC-24`가 정확히 이 틈이다. 조회와 삭제 사이에 글이 들어오면 **`AC-22`가 막으려던 손상이 그대로 들어온다.** 그리고 코드로 막으면 001의 동시 가입 경합에서 이미 배운 실수를 반복하는 것이다 | **판정은 DB가 한다** — `fk_posts_categories ON DELETE RESTRICT`(V6)가 이미 있다. 코드는 삭제를 시도하고 **위반을 409 `CATEGORY_IN_USE`로 번역**한다. **건수 조회는 안내 문구용이지 판정용이 아니다.** `AC-24` 테스트는 **초기화 격리**로 실제 커밋을 경합시킨다 |
| **★ `AC-32`가 배포에서만 깨진다** | 지금 `SecurityConfig`가 `.anyRequest().authenticated()`다. **개발자는 대개 로그인 상태로 화면을 보므로 분류 필터가 잘 나온다.** 로그아웃한 방문자에게만 깨지고, 그것이 **첫 방문자**다 | 1번 단계에서 permitAll에 추가하고 **`AC-32` 통합 테스트를 인증 없는 클라이언트로** 돌린다. E2E가 `storageState`를 주입하므로(`test-strategy.md` 4.1) **E2E로는 이 버그가 잡히지 않는다** — 통합이어야 한다 |
| **관리자 예외가 권한이 아닌 조건으로 구현된다** | `AC-14`·`AC-15`가 막는 것. *"관리 화면에서 온 요청이면 허용"* 처럼 구현하면 일반 사용자가 그 조건을 흉내낸다 | **삭제 권한 판정을 한 함수로 모은다** — `요청자.id == 소유자.id \|\| 요청자.role == ADMIN`. 경로·헤더·화면 구분을 **입력으로 받지 않는다.** 8번 코드 리뷰의 명시 항목 |
| **비활성 분류로 "변경"과 "유지"를 서버가 구분하지 못한다** | 수정 요청은 항상 `categoryId`를 함께 보내므로 *"비활성이면 거부"* 로 짜면 **`AC-26`이 깨지고**(제목도 못 고친다), *"항상 허용"* 으로 짜면 **`AC-27`이 깨진다** | **기존 값과 비교해서 판정한다** — 값이 같으면 유지, 다르면 변경. 두 AC를 **짝으로 배정**한 이유가 이것이다 |
| **분류 이름을 고치면 과거 글 표시가 함께 바뀐다** | 참조 방식(**`ADR-008`**)의 결과다. 오타 수정이면 기대 동작이지만, **분류의 의미를 바꾸는 rename이면 과거 글이 엉뚱한 분류로 보인다** | 스펙 Edge Cases가 이미 기대 동작으로 정했다. **화면에서 rename 확인창에 *"이 분류로 등록된 글 N건의 표시도 함께 바뀝니다"* 를 넣는다** — 건수 조회는 이미 `AC-22`용으로 있다 |
| **`AC-31`이 초기 데이터 때문에 검증되지 않는다** | V10이 게시판별 분류를 미리 넣어 두어 **활성 분류 0개 상태가 자연히 오지 않는다.** 테스트가 그 상태를 만들지 않으면 조용히 통과한다 | `AC-31` 통합 테스트가 **그 게시판의 분류를 전부 비활성으로 내린 뒤** 등록을 시도한다. **삭제로 만들 수 없다** — 글이 있으면 `RESTRICT`가 막는다 |
| **오류 코드가 기존 것과 겹치거나 갈라진다** | 004가 9개를 한 번에 추가한다. `CATEGORY_NONE_AVAILABLE`(`AC-31`)과 *"분류는 필수"* 를 같은 코드로 뭉치면 **`AC-31`의 "원인 안내" 요구가 사라진다** | `ErrorCode` enum **한 곳**에만 추가하고 계약 문서의 표를 단일 진실로 삼는다. **필수 누락과 선택지 없음을 다른 코드로 둔다** |
| **004 화면이 002~006의 미완성 규칙을 기다리다 멈춘다** | 관리 등록 화면에 상단 고정(003)·썸네일(005)·비밀글(006) 자리가 필요하다 | 스펙이 이미 *"자리만 비워 둔다"* 로 경계를 그었다. **004는 그 자리에 아무 규칙도 넣지 않는다** — 넣으면 003·005·006과 두 벌이 된다 |
| **관리자 계정이 하나라 `FR-012`의 "누가"가 검증되지 않는다** | 행위자가 항상 같으면 **행위자 식별자를 하드코딩해도 테스트가 통과**한다 | `AC-16` 테스트에서 **`ADMIN` 계정을 하나 더 만들어** 두 관리자의 삭제가 서로 다른 행위자로 기록되는지 본다. 001 Assumptions 2가 *"관리자가 늘어날 것을 전제"* 로 이미 적었다 |

2. **사용 중인 분류의 처리 정책** ★ — `J-3`
