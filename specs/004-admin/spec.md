# 기능 명세: 004 관리자 화면 + 카테고리(분류) 관리

**브랜치 / 디렉터리**: `004-admin`

**작성일**: 2026-07-31

**상태**: 초안. **3번 게이트(스펙 검증) 미통과** — 사람 검증이 필요한 판단이 남아 있다
(→ [판단한 것 목록](#판단한-것-목록--사람-검증-대상)).

**규모**: **AC 35개 · FR 28개**. **AC가 없는 FR 0개.**

**원칙**: `.specify/memory/constitution.md` · 프로세스: `specs/process.md` ·
테스트 레벨 배정: `specs/test-strategy.md` 3장

> **AC 번호 규칙**: 이 명세 **안에서 연속**이며 `AC-1`부터 시작한다. 스토리를 넘어가도
> 리셋하지 않는다. **001의 AC 번호와 겹치지만 문제되지 않는다** — 참조할 때 스토리 번호를
> 함께 쓴다(`004 AC-12`).

> **AC 표기에 대하여**: 001과 같은 이유로 HTTP 상태코드와 오류 코드를 AC에 담는다.
> 이것들은 프레임워크가 아니라 **API 계약**이고, 원칙 II가 요구하는 *검증 가능한 인수기준*이
> 그대로 테스트 이름과 QA 체크리스트가 되기 때문이다.

---

## 개요

관리자가 자기 화면 안에서 **네 게시판을 관리**하고, 모든 게시판 목록이 참조하는
**분류(카테고리)를 스스로 정의**할 수 있게 한다.

**포함**

| | |
|---|---|
| 관리자 셸 | 좌측 메뉴(LNB) · 현재 위치 표시 · 상단 인사말과 로그아웃 · 미인증 진입 처리 |
| 관리 화면 4종 | 공지사항 · 자유게시판 · 갤러리 · 문의게시판의 관리 목록/등록/수정/삭제 **공통 골격** |
| 공통 상호작용 | 등록·수정·삭제 실행 전 **확인 절차** |
| 관리자 삭제 예외 | 관리자는 **남의 글·댓글**을 삭제할 수 있다 |
| **분류 관리** | 게시판별 분류 목록 · 이름/표시 순서/사용 여부 · **사용 중인 분류의 처리** |
| 사용불가 아이디 관리 | 001이 004로 미룬 항목 (→ [의존](#의존)) |

**제외**

- 게시판별 도메인 규칙 — **상단 고정**(003) · **썸네일·캐러셀**(005) · **비밀글·답변**(006) ·
  **첨부 검증**(002). 004는 이들을 **정의하지 않고**, 관리자 화면에 얹힐 자리만 비워 둔다.
- 공통 목록 규칙(기간·검색어·개씩 보기·정렬·페이징·검색조건 유지)의 **정의**. 004는 그것을
  **그대로 쓴다**(→ `FR-008`).
- 관리자 계정 추가·수정·삭제 화면. 관리자 계정은 시스템이 하나만 생성하며(001) 계정을
  늘리는 요구가 아직 없다.
- 회원 목록·회원 검색. 지금 관리자가 회원을 상대로 하는 동작이 없다.
- 통계·대시보드.

**004를 별도 스토리로 두는 이유**: 관리 화면 4종은 게시판마다 다르게 생겼지만
**셸·확인 절차·삭제 권한 예외·분류 참조**는 네 곳에서 똑같이 필요하다. 게시판 스토리마다
각자 만들면 네 벌이 생기고, 그중 하나만 고치는 사고가 난다.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 관리자 셸과 접근 처리 (Priority: P1) 🎯 MVP

관리자가 관리자 경로로 들어와 자기가 어느 메뉴에 있는지 알고, 인증이 끊기면 그 사실을 안다.

**Why this priority**: 관리 화면 4종과 분류 관리가 전부 이 셸 안에 들어간다.
셸이 없으면 나머지를 얹을 자리가 없다.

**Independent Test**: 관리자로 로그인해 관리자 경로에 진입 → 메뉴가 보이고 현재 위치가
표시되는지 확인 → 로그아웃 후 같은 경로로 다시 들어가 관리자 로그인 화면으로 가는지 확인.

**Acceptance Scenarios**:

- **AC-1** 관리자 셸에 관리 메뉴가 있고 현재 위치가 표시된다
  - **Given** `ADMIN` 권한으로 로그인한 상태이고
  - **When** 관리자 경로의 어느 관리 화면에 진입하면
  - **Then** 좌측에 관리 메뉴 목록이 보이고, **진입한 화면에 해당하는 메뉴 하나만**
    현재 위치로 구분되어 표시된다
  - *근거*: 관리 화면은 목록 생김새가 서로 비슷해서, 현재 위치 표시가 없으면
    관리자가 **다른 게시판의 글을 지운다**

- **AC-2** 로그인한 관리자를 알아볼 수 있고 나갈 수 있다
  - **Given** `ADMIN` 권한으로 로그인한 상태이고
  - **When** 어느 관리 화면이든 진입하면
  - **Then** 화면 상단에 **로그인한 관리자의 이름**과 **로그아웃 수단**이 함께 보이고,
    로그아웃하면 이후 관리자 경로 진입이 `AC-3`과 같이 처리된다

- **AC-3** 미인증 상태로 관리자 화면에 들어가면 관리자 로그인으로 간다
  - **Given** 로그인하지 않은 상태이고
  - **When** 관리자 경로의 화면 주소로 직접 진입하면
  - **Then** **관리자 로그인 진입점**으로 이동하고, 관리 데이터가 화면에 그려지지 않는다.
    **사용자 로그인 화면으로 보내지 않는다**
  - *근거*: 001 `FR-032`가 진입점을 분리한 이유가 여기서 무너진다 — 관리자를 사용자
    로그인 화면으로 보내면 로그인 후 사용자 화면으로 튕기고, 관리자는 왜 관리 화면에
    가지 못하는지 알 수 없다 (FR-003)

- **AC-4** `USER` 권한으로 로그인한 상태에서 관리자 화면 진입
  - **Given** `USER` 권한으로 로그인한 상태이고
  - **When** 관리자 경로의 화면 주소로 직접 진입하면
  - **Then** **AC-3과 동일하게** 관리자 로그인 진입점으로 이동하고 관리 데이터가 그려지지
    않는다. 사용자 세션은 유지된다
  - *근거*: 화면 이동은 편의일 뿐이고 실제 차단은 서버가 한다(001 `AC-22`·`AC-26`).
    화면에 *"권한이 없습니다"* 전용 페이지를 따로 만들 이유가 없다 (FR-003)

- **AC-5** 로그인 후 원래 관리 화면으로 돌아오되, 관리자 경로 밖은 무시한다
  - **Given** `AC-3`으로 관리자 로그인 화면에 도착했고 복귀 목적지가 지정되어 있고
  - **When** 관리자 계정으로 로그인을 완료하면
  - **Then** 목적지가 **관리자 경로 하위의 상대 경로**면 그 화면으로 이동하고,
    **외부 주소이거나 관리자 경로 밖**이면 그 목적지를 **무시하고** 관리자 기본 화면으로 이동한다
  - *근거*: 001 `FR-035`(같은 출처의 상대 경로만)를 **한 단계 더 좁힌다**. 관리자 로그인을
    마친 직후 사용자 화면으로 튀는 목적지는 정상 흐름이 아니고, 그런 링크가 성립하면
    관리자를 임의의 우리 화면으로 유도하는 수단이 된다 (FR-004)

- **AC-6** 인증이 끊긴 화면은 빈 목록을 정상처럼 보여주지 않는다
  - **Given** 관리 목록 화면을 열어 둔 채 자격증명이 만료되었고 재발급도 실패하는 상태이고
  - **When** 화면이 목록 데이터를 다시 요청해 401 또는 403을 받으면
  - **Then** 화면은 **목록을 비운 채 정상 화면으로 두지 않고** 재로그인이 필요하다는 상태로
    전환한다
  - *근거*: 실패를 빈 목록으로 그리면 관리자는 *"글이 하나도 없다"* 로 읽는다.
    **오류를 정상처럼 보여주는 것이 가장 위험한 화면 버그다** (FR-005)

### User Story 2 - 관리 화면 4종의 공통 동작 (Priority: P1)

관리자가 네 게시판의 글을 같은 방식으로 등록·수정·삭제하고, **남이 쓴 글과 댓글도**
지울 수 있다.

**Why this priority**: 관리자 화면이 존재하는 이유 자체다. US1 다음으로 완결 가능하다.

**Independent Test**: 관리자로 로그인해 자유게시판 관리에서 **다른 사용자가 쓴 글**을
삭제 → 성공하는지 확인. 같은 요청을 `USER` 계정으로 보내 거부되는지 확인.

**Acceptance Scenarios**:

- **AC-7** 등록은 확인을 거쳐야 진행된다
  - **Given** 관리자가 등록 화면에서 유효한 값을 입력했고
  - **When** 등록을 실행하고 확인 절차에서 **진행**을 선택하면
  - **Then** 등록이 수행되고 목록으로 돌아가며, 등록한 글이 목록에 보인다

- **AC-8** 확인에서 취소하면 아무 일도 일어나지 않는다
  - **Given** 관리자가 등록(또는 수정) 화면에서 값을 입력했고
  - **When** 실행 후 확인 절차에서 **취소**를 선택하면
  - **Then** **서버로 등록·수정 요청이 전송되지 않고**, 데이터가 변하지 않으며,
    **입력하던 값이 그대로 남아 있다**
  - *근거*: 취소했는데 입력이 날아가면 확인 절차가 사용자를 돕는 게 아니라 방해한다 (FR-006)

- **AC-9** 삭제 확인에서 취소하면 대상이 남는다
  - **Given** 관리 목록에 글 `P`가 있고
  - **When** 삭제를 실행하고 확인 절차에서 **취소**를 선택하면
  - **Then** 글 `P`가 그대로 남아 있고 삭제 요청이 서버로 전송되지 않는다

- **AC-10** 확인 절차를 거치지 않은 직접 호출도 서버 규칙이 그대로 적용된다
  - **Given** 화면을 거치지 않고 관리자 기능을 직접 호출할 수 있는 상태이고
  - **When** 확인 절차 없이 등록·수정·삭제를 직접 요청하면
  - **Then** **확인 절차가 있었을 때와 동일한** 입력 검증·권한 검증 결과가 나온다.
    확인 절차의 유무가 결과를 바꾸지 않는다
  - *근거*: 확인창은 **실수 방지 장치**이지 보안 장치가 아니다. 001 `FR-002`·`FR-019`와
    같은 원칙이며, 이 둘을 혼동하면 *"화면에서 확인을 받으니까 서버는 안 봐도 된다"* 로 간다 (FR-007)

- **AC-11** 관리 목록도 사용자 목록과 같은 목록 규칙을 따른다
  - **Given** 관리 목록 화면에 글이 페이지 크기보다 많이 있고
  - **When** 기간·분류·검색어로 검색하고 개씩 보기와 정렬을 바꾼 뒤 상세로 들어갔다가
    목록으로 돌아오면
  - **Then** 사용자 목록과 **동일한 규칙**으로 동작하고(개씩 보기·정렬은 선택 즉시 반영),
    돌아왔을 때 **직전 검색조건이 유지된다**
  - *근거*: 규칙을 관리자용으로 따로 만들면 두 벌이 생기고 한쪽만 고쳐진다 (FR-008)

- **AC-12** 관리자는 **남이 쓴 글**을 삭제할 수 있다 — 소유자 규칙의 예외
  - **Given** 사용자 `U`가 작성한 글 `P`가 있고 `ADMIN` 권한으로 로그인한 상태이고
  - **When** 글 `P`의 삭제를 요청하면
  - **Then** **삭제에 성공한다.** 소유자가 아니라는 이유로 거부되지 않는다
  - *근거*: 일반 규칙은 *"본인 글만 수정·삭제"* 인데 관리자는 여기서 **의도적인 예외**다.
    예외를 AC로 못박지 않으면, 소유자 검증을 구현하는 쪽이 관리자까지 막아 버리고
    **부적절한 게시물을 아무도 내릴 수 없는 서비스**가 된다 (FR-009)

- **AC-13** 관리자는 **남이 쓴 댓글**을 삭제할 수 있다
  - **Given** 사용자 `U`가 작성한 댓글 `C`가 있고 `ADMIN` 권한으로 로그인한 상태이고
  - **When** 댓글 `C`의 삭제를 요청하면
  - **Then** 삭제에 성공한다 (FR-010)

- **AC-14** 일반 사용자는 남의 글을 삭제할 수 없다 — 예외가 새지 않는다
  - **Given** 사용자 `U`가 작성한 글 `P`가 있고 **다른** `USER` 권한 계정으로 로그인한 상태이고
  - **When** 글 `P`의 삭제를 요청하면
  - **Then** 403이고 `code=AUTH_FORBIDDEN`. 글 `P`는 그대로 남아 있다
  - *근거*: `AC-12`가 만든 예외가 **권한이 아니라 다른 조건**으로 구현되면(예: 화면 구분,
    요청 경로 구분) 일반 사용자가 그 경로를 흉내내 남의 글을 지울 수 있다.
    예외의 판정 근거는 **오직 권한**이어야 한다 (FR-011)

- **AC-15** 일반 사용자는 남의 댓글을 삭제할 수 없다
  - **Given** 사용자 `U`가 작성한 댓글 `C`가 있고 **다른** `USER` 권한 계정으로 로그인한 상태이고
  - **When** 댓글 `C`의 삭제를 요청하면
  - **Then** 403이고 `code=AUTH_FORBIDDEN`. 댓글 `C`는 그대로 남아 있다 (FR-011)

- **AC-16** 관리자의 타인 콘텐츠 삭제는 기록으로 남는다
  - **Given** `AC-12`·`AC-13`으로 관리자가 남의 글과 댓글을 삭제했고
  - **When** 그 요청들이 남긴 기록을 확인하면
  - **Then** **누가(관리자 식별자) 무엇을(대상 종류와 식별자) 언제** 삭제했는지 확인할 수 있고,
    001 `AC-36`이 금지한 값(비밀번호·자격증명)은 포함되지 않는다
  - *근거*: 남의 글을 지우는 것은 **되돌릴 수 없고 분쟁이 생기는 동작**이다.
    *"내 글이 사라졌다"* 는 문의에 답할 수 없으면 서비스가 신뢰를 잃는다 (FR-012)

### User Story 3 - 분류(카테고리) 관리 (Priority: P1)

관리자가 게시판별 분류 목록을 직접 만들고, 쓰지 않게 된 분류를 **글을 망가뜨리지 않고**
정리한다.

**Why this priority**: 세 게시판(공지사항·자유게시판·갤러리)의 **목록 필터와 등록 화면이
전부 이 목록을 참조**한다. 이것이 없으면 그 게시판들의 글 등록 자체가 성립하지 않는다.
US1·US2와 같은 P1이지만, 셸 안에 들어가는 화면이므로 US1 뒤에 둔다.

> ⚠️ **이 스토리 전체가 사람 검증 대상이다.** 분류 관리 화면은 요구사항에 형태가 없고,
> 아래 규칙은 *"모든 목록이 관리자가 등록한 분류를 참조한다"* 는 사실 하나에서 역산한
> **Claude 판단**이다. 개별 판단은 [판단한 것 목록](#판단한-것-목록--사람-검증-대상)에 모았다.

**Independent Test**: 자유게시판 분류를 하나 만들고 그 분류로 글을 등록한 뒤,
그 분류를 삭제하려 시도해 거부되는지 확인 → 사용 안 함으로 내리고 새 글 등록 화면에서
사라지는지, **기존 글의 분류 표시는 그대로인지** 확인.

**Acceptance Scenarios**:

- **AC-17** 게시판별로 분류 목록이 분리되어 있다
  - **Given** 자유게시판에 분류 `질문`이 있고 갤러리에는 없고
  - **When** 각 게시판의 분류 목록을 조회하면
  - **Then** 자유게시판 목록에만 `질문`이 포함되고 갤러리 목록에는 포함되지 않는다 (FR-013)

- **AC-18** 문의게시판은 분류 관리 대상이 아니다
  - **Given** 분류 관리 화면에 들어왔고
  - **When** 관리 대상 게시판을 선택하면
  - **Then** 선택지에 **문의게시판이 없다**. 문의게시판을 대상으로 지정한 분류 등록 요청은
    400으로 거부된다
  - *근거*: 문의게시판에는 분류가 없다. 화면에서 고를 수 없게 하는 것만으로는 직접 호출을
    막지 못한다(001 `FR-002`) (FR-013)

- **AC-19** 분류를 등록하면 이름·표시 순서·사용 여부가 저장된다
  - **Given** 관리자로 로그인해 자유게시판 분류 관리 화면에 있고
  - **When** 이름 `공지`, 표시 순서 `1`, 사용 여부 `사용함`으로 등록하면
  - **Then** 201이고 목록에 그 값 그대로 나타나며, 자유게시판 글 등록 화면의 분류 선택지에
    `공지`가 포함된다 (FR-014)

- **AC-20** 같은 게시판 안에서 분류 이름은 중복될 수 없다
  - **Given** 자유게시판에 분류 `질문`이 이미 있고
  - **When** 같은 게시판에 `질문`을 다시 등록하면
  - **Then** 409이고 `code=CATEGORY_NAME_DUPLICATED`.
    **갤러리에 `질문`을 등록하는 것은 성공한다**
  - *근거*: 같은 이름이 두 개 있으면 글쓴이가 어느 것을 고른 건지 알 수 없고, 하나를
    비활성으로 내려도 목록에서 구분되지 않는다. 게시판이 다르면 충돌하지 않는다 (FR-015)

- **AC-21** 분류 이름 검증은 서버가 한다
  - **Given** 분류 등록 요청을 준비했고
  - **When** 이름을 **빈 값**으로 또는 **31자**로 요청하면
  - **Then** 400이고 `code=CATEGORY_NAME_INVALID` (허용: 1자 이상 30자 이하).
    화면을 거치지 않고 직접 요청해도 동일하다 (FR-016)

- **AC-22** **사용 중인 분류는 삭제되지 않는다** ★ 이 스토리의 핵심
  - **Given** 자유게시판 분류 `질문`을 사용하는 글이 **1건 이상** 있고
  - **When** 관리자가 분류 `질문`의 삭제를 요청하면
  - **Then** 409이고 `code=CATEGORY_IN_USE`. 분류가 삭제되지 않고, 그 분류를 쓰는 글의
    **건수와 함께** *"사용 안 함으로 내릴 수 있다"* 는 안내가 전달된다
  - *근거*: 삭제를 허용하면 **이미 쌓인 글이 손상된다** — 글의 분류를 비우면 목록 화면의
    분류 칸이 빈 채로 남고, 분류 필터로는 영원히 찾을 수 없는 글이 생긴다.
    삭제는 되돌릴 수 없고 **비활성은 되돌릴 수 있다.**
    되돌릴 수 없는 쪽을 기본값으로 두지 않는다 (FR-017)

- **AC-23** 쓰이지 않는 분류는 삭제할 수 있다
  - **Given** 자유게시판 분류 `임시`를 사용하는 글이 **0건**이고
  - **When** 관리자가 분류 `임시`의 삭제를 확인 후 요청하면
  - **Then** 삭제에 성공하고 목록에서 사라진다
  - *근거*: 오타로 만든 분류를 영구히 남길 이유가 없다. `AC-22`가 지키려는 것은
    *"분류를 지우지 말자"* 가 아니라 *"쌓인 글을 손상시키지 말자"* 다 (FR-018)

- **AC-24** 삭제 판정과 삭제 사이에 글이 등록되면 삭제되지 않는다 — 동시성
  - **Given** 분류 `임시`를 쓰는 글이 0건이라 관리자 화면이 삭제 가능으로 표시했고
  - **When** 관리자가 삭제를 실행하는 사이에 **다른 요청이 그 분류로 글을 등록**하면
  - **Then** 둘 중 하나만 성립한다 — 삭제가 성공하면 그 글 등록이 거부되고,
    글 등록이 성공하면 삭제가 `AC-22`와 같이 409 `CATEGORY_IN_USE`로 거부된다.
    **분류가 없는 글이 남는 상태는 발생하지 않는다**
  - *근거*: 화면이 본 "0건"은 **과거의 사실**이다. 서버가 삭제 시점에 다시 확인하지 않으면
    `AC-22`가 막으려던 손상이 이 틈으로 그대로 들어온다 (FR-018)

- **AC-25** 사용 안 함으로 내린 분류는 새 글의 선택지에서 사라진다
  - **Given** 자유게시판 분류 `질문`을 사용 여부 `사용 안 함`으로 변경했고
  - **When** 자유게시판 글 등록 화면의 분류 선택지를 확인하면
  - **Then** `질문`이 선택지에 없다 (FR-019)

- **AC-26** 비활성 분류를 가진 글은 분류를 그대로 둔 채 수정할 수 있다
  - **Given** 분류 `질문`으로 등록된 글 `P`가 있고 그 뒤 `질문`이 사용 안 함으로 내려갔고
  - **When** 글 `P`의 제목만 고쳐 저장하면
  - **Then** 수정에 성공하고 글 `P`의 분류는 **여전히 `질문`** 이다.
    수정 화면의 선택지에는 현재 값 `질문`이 **사용 안 함으로 표시된 채** 포함된다
  - *근거*: 비활성 분류를 선택지에서 완전히 빼면 **그 글은 제목 한 글자도 고칠 수 없게 된다**
    (저장할 때 분류가 비어 유효성에 걸린다). 비활성의 의미는 *"새로 고르지 못한다"* 이지
    *"기존 글을 못 만진다"* 가 아니다 (FR-019)

- **AC-27** 비활성 분류로 **바꾸는** 것은 거부된다
  - **Given** 분류 `공지`(사용함)로 등록된 글 `P`가 있고 분류 `질문`은 사용 안 함이고
  - **When** 글 `P`의 분류를 `질문`으로 변경 요청하면
  - **Then** 400이고 `code=CATEGORY_INACTIVE`. 화면을 거치지 않은 직접 호출도 동일하다
  - *근거*: `AC-26`이 *유지*를 허용하므로, 서버가 *변경*과 *유지*를 구분하지 않으면
    비활성 분류가 직접 호출로 다시 쓰이기 시작한다 (FR-020)

- **AC-28** 분류 필터는 사용자 화면과 관리자 화면이 다르다
  - **Given** 자유게시판에 활성 분류 `공지`와 비활성 분류 `질문`이 있고
  - **When** 사용자 목록 화면과 관리자 목록 화면의 분류 필터를 각각 확인하면
  - **Then** **사용자 필터에는 `공지`만** 있고, **관리자 필터에는 `공지`와 `질문`이 모두**
    있으며 `질문`은 사용 안 함으로 구분 표시된다
  - *근거*: 관리자는 **과거 글을 찾아야 하는 사람**이다. 비활성 분류를 필터에서 지우면
    그 분류로 등록된 글을 관리 화면에서 골라낼 방법이 사라진다.
    사용자는 새 분류 체계만 보면 되므로 반대다 (FR-021)

- **AC-29** 비활성 이후에도 기존 글의 분류 표시는 유지된다
  - **Given** 분류 `질문`으로 등록된 글 `P`가 있고 `질문`이 사용 안 함으로 내려갔고
  - **When** 사용자 목록과 상세에서 글 `P`를 보면
  - **Then** 분류 칸에 **`질문`이 그대로 표시된다.** 비어 있거나 다른 값으로 바뀌지 않는다
  - *근거*: 이것이 삭제 대신 비활성을 고른 이유 자체다. 표시가 사라지면 비활성도
    삭제와 같은 손상이 된다 (FR-022)

- **AC-30** 분류 목록의 순서는 결정적이다
  - **Given** 표시 순서가 `1`, `2`, **`2`**(중복)인 분류 세 개가 있고
  - **When** 목록을 여러 번 조회하면
  - **Then** 표시 순서 오름차순으로 정렬되고, **같은 순서끼리의 상대 위치가 매번 동일하다**
  - *근거*: 정렬 2차 기준이 없으면 같은 순서의 분류들이 조회할 때마다 자리를 바꾼다.
    관리자는 자기가 뭘 잘못 눌렀는지 의심하게 된다 (FR-023)

- **AC-31** 활성 분류가 하나도 없으면 글 등록이 거부되고 원인을 알려준다
  - **Given** 자유게시판의 활성 분류가 **0개**이고
  - **When** 자유게시판에 글 등록을 요청하면
  - **Then** 400이고 `code=CATEGORY_NONE_AVAILABLE`. 응답은 **분류를 먼저 등록해야 한다**는
    원인을 담는다
  - *근거*: 분류가 필수인 게시판에서 활성 분류가 0개면 **아무도 글을 쓸 수 없는 상태**가 된다.
    이때 *"분류는 필수입니다"* 라고만 답하면 사용자는 고를 것이 없는데 고르라는 말을 듣는다 (FR-024)

- **AC-32** 분류 조회는 누구나, 분류 변경은 관리자만
  - **Given** 로그인하지 않은 상태이고
  - **When** 활성 분류 목록 **조회**를 요청하면 200이고 목록이 반환되며,
    같은 상태에서 분류 **등록·수정·삭제**를 요청하면
  - **Then** 401이고 `code=AUTH_REQUIRED`
  - *근거*: 사용자 목록 화면의 분류 필터는 **로그인 전에도 그려져야 한다.**
    분류 읽기 경로를 관리자 전용 경로 아래 두면 비로그인 목록 화면이 필터를 못 그린다 (FR-028)

### User Story 4 - 사용불가 아이디 목록 관리 (Priority: P3)

관리자가 가입에 쓸 수 없는 아이디를 화면에서 추가·삭제한다.

**Why this priority**: 001이 **명시적으로 004에 넘긴 항목**이다(001 `FR-028` ·
Out of Scope). 없어도 서비스는 돌지만(초기 목록이 이미 데이터로 들어 있다),
**넘겨받은 곳에서 다루지 않으면 그 약속이 사라진다.** 다만 게시판 운영과 무관하므로 P3다.

> ⚠️ 이 스토리를 004에 넣은 것 자체가 **Claude 판단**이다 — 관리 메뉴 목록에는
> 이 화면이 없다. [판단한 것 목록](#판단한-것-목록--사람-검증-대상) `J-9` 참조.

**Independent Test**: 사용불가 아이디에 `support`를 추가한 뒤 그 아이디로 가입을 시도해
거부되는지 확인 → 삭제 후 다시 시도해 가입되는지 확인.

**Acceptance Scenarios**:

- **AC-33** 사용불가 아이디를 조회하고 추가한다
  - **Given** `ADMIN` 권한으로 로그인한 상태이고 `support`가 목록에 없고
  - **When** 목록을 조회한 뒤 `support`를 추가하면
  - **Then** 201이고 목록에 `support`가 나타난다. 이미 있는 값을 다시 추가하면 409이고
    `code=RESERVED_ID_DUPLICATED` (FR-025)

- **AC-34** 추가·삭제가 가입 검증에 즉시 반영된다
  - **Given** `AC-33`으로 `support`가 목록에 추가되었고
  - **When** 재시작이나 재배포 없이 아이디 `support`로 가입을 요청하면
  - **Then** 001 `AC-13`과 동일하게 400이고 `code=USER_ID_NOT_ALLOWED`.
    그 뒤 목록에서 `support`를 삭제하고 같은 가입을 다시 요청하면 **성공한다**
  - *근거*: 목록을 앱 시작 시점에 한 번만 읽어 캐시하면, 관리자가 화면에서 추가해도
    아무 일도 일어나지 않는다. **화면이 거짓말을 하게 된다** (FR-026)

- **AC-35** 이미 가입한 계정을 나중에 차단하지 않는다
  - **Given** 아이디 `helper`로 가입한 활성 계정이 있고
  - **When** 관리자가 `helper`를 사용불가 목록에 추가하면
  - **Then** 추가는 성공하지만 **기존 계정 `helper`는 그대로 로그인된다.**
    이후 신규 가입만 거부된다
  - *근거*: 사용불가 목록은 **가입 시점의 규칙**이다. 소급 적용하면 관리자의 오타 한 번으로
    실제 사용자가 서비스에서 쫓겨나고, 001에 비밀번호 찾기도 계정 복구 수단도 없어
    되돌릴 방법이 사용자 쪽에 없다 (FR-027)

### Edge Cases

**분류**

- **분류 이름만 바꾼 경우**: 이미 그 분류로 등록된 글의 표시도 **함께 바뀐다**(참조 방식).
  오타 수정이 목적이므로 이것이 기대 동작이다. 반대로 *"등록 당시 이름을 보존"* 하려면
  글에 이름을 복사해 두어야 하고, 그러면 오타를 고쳐도 과거 글에는 남는다. → **`ADR-008`**
- **비활성 분류를 다시 활성화**: 허용한다. 즉시 새 글 선택지에 다시 나타난다.
  비활성이 되돌릴 수 있다는 것이 `AC-22`에서 삭제 대신 비활성을 고른 근거다.
- **표시 순서가 음수 또는 0**: 허용한다. 순서는 상대적 비교에만 쓰이고 값 자체에 의미가 없다.
  범위를 좁히면 맨 앞에 하나 끼워 넣을 때 전체를 다시 매겨야 한다.
- **표시 순서 중복**: 허용한다(`AC-30`). 유일성을 강제하면 중간 삽입마다 전체 재배치가 필요하고,
  그 재배치가 실패하면 순서가 깨진 채 남는다.
- **활성 분류 0개인 게시판의 관리 화면**: 목록은 정상적으로 열리고 글 등록만 막힌다(`AC-31`).
  관리 화면까지 막으면 관리자가 분류를 등록하러 갈 수 없다.
- **두 관리자가 같은 분류를 동시에 수정**: 나중 요청이 이긴다. 분류는 값이 세 개뿐이고
  충돌 감지를 붙이는 비용이 이득보다 크다. *(Claude 판단 — `J-8`)*
- **삭제 확인창이 떠 있는 사이 다른 관리자가 먼저 삭제**: 404로 응답하고 화면은
  *"이미 삭제되었습니다"* 로 안내한 뒤 목록을 갱신한다. 500으로 떨어뜨리지 않는다.

**관리자 셸 · 권한**

- **폼 작성 도중 자격증명 만료**: 저장 요청이 401을 받으면 `AC-6`처럼 재로그인 상태로
  전환하되 **입력값을 지우지 않는다**. 관리자 자격증명 수명이 사용자보다 짧아서
  (001 `FR-033`) 긴 글을 쓰는 도중에 실제로 일어난다.
- **로그아웃 후 뒤로 가기**: 브라우저 캐시로 이전 화면이 잠깐 보일 수 있으나, 화면이
  데이터를 다시 요청하는 순간 `AC-6`으로 전환된다. **캐시된 화면에 남은 값은 이미 노출된
  값이며 새로운 유출이 아니다.**
- **관리자가 자기 자신의 글을 삭제**: 소유자이면서 관리자다. 일반 소유자 규칙으로 성공한다.
- **삭제 대상이 이미 삭제된 글**: 404. 관리자에게도 존재하지 않는 것은 존재하지 않는다.
- **문의게시판 비밀글을 관리 화면에서 여는 경우**: 004 범위 밖이다. 관리자가 비밀번호 없이
  볼 수 있어야 하는지는 **006이 정한다**(→ [의존](#의존)).

**사용불가 아이디**

- **목록에서 마지막 항목까지 전부 삭제**: 허용한다. 목록이 비면 아이디 제한이 없어질 뿐이고
  다른 검증(길이·형식·중복)은 그대로 작동한다.
- **대소문자**: 001이 아이디 대소문자를 구분하지 않으므로(001 Assumptions 2)
  `Support`를 추가해도 `support` 가입이 거부되어야 한다.

## Requirements *(mandatory)*

### Functional Requirements

> 아래 FR은 **004에서 새로 필요한 것만** 적는다. 001이 이미 제공하는 것
> (관리자 전용 경로 차단 · 관리자 로그인 진입점 · 서버 권한 검증 · 오류 응답 형식 ·
> 로그 마스킹)은 **다시 요구하지 않는다.** → [의존](#의존)

**관리자 셸 · 접근**

- **FR-001**: 관리자 화면은 관리 대상 메뉴 목록을 항상 노출하고 **현재 위치를 구분 표시**해야 한다(MUST).
- **FR-002**: 관리자 화면은 로그인한 관리자의 **이름**과 **로그아웃 수단**을 노출해야 한다(MUST).
- **FR-003**: 인증되지 않았거나 `ADMIN` 권한이 아닌 상태로 관리자 화면 경로에 진입하면
  **관리자 로그인 진입점**으로 이동시켜야 한다(MUST). 사용자 로그인 화면으로 보내는 것을
  금지한다(MUST NOT). *(001 `FR-032`가 진입점을 분리한 의도를 화면에서도 유지한다)*
- **FR-004**: `FR-003`의 복귀 목적지는 **관리자 경로 하위의 상대 경로만** 허용해야 한다(MUST).
  그 밖의 값은 무시하고 관리자 기본 화면으로 이동한다(MUST). *(001 `FR-035`를 004에서 더 좁힌 것)*
- **FR-005**: 관리 화면이 데이터 요청에서 401 또는 403을 받으면 **정상 화면으로 유지하지 않고**
  재인증이 필요한 상태로 전환해야 한다(MUST). 빈 결과로 표시하는 것을 금지한다(MUST NOT).

**공통 상호작용 — 확인 절차**

- **FR-006**: 관리 화면의 등록·수정·삭제는 실행 전 **확인 절차**를 거쳐야 한다(MUST).
  확인에서 취소하면 서버로 요청을 보내지 않아야 하며(MUST NOT), 입력값을 폐기해서는 안 된다(MUST NOT).
- **FR-007**: 확인 절차는 **실수 방지 장치**이며 입력 검증·권한 검증을 대체하지 않는다.
  확인 절차의 유무가 서버 처리 결과를 바꾸어서는 안 된다(MUST NOT). *(001 `FR-002`·`FR-019`와 같은 원칙)*
- **FR-008**: 관리 목록은 사용자 목록과 **같은 목록 규칙**(기간·분류·검색어·개씩 보기·정렬·
  페이징·검색조건 유지)을 사용해야 한다(MUST). 004는 이 규칙을 다시 정의하지 않는다.

**관리자의 타인 콘텐츠 삭제 — 소유자 규칙의 예외**

- **FR-009**: `ADMIN` 권한은 **소유자가 아닌 글**을 삭제할 수 있어야 한다(MUST).
- **FR-010**: `ADMIN` 권한은 **소유자가 아닌 댓글**을 삭제할 수 있어야 한다(MUST).
- **FR-011**: `FR-009`·`FR-010`의 예외는 **오직 권한으로만** 판정해야 한다(MUST).
  요청 경로·화면 구분 등 권한 외의 조건으로 이 예외를 여는 것을 금지한다(MUST NOT) —
  그런 조건은 일반 사용자가 흉내낼 수 있다.
- **FR-012**: 관리자가 타인의 글·댓글을 삭제하면 **행위자·대상·시각**을 확인할 수 있는 기록을
  남겨야 한다(MUST). 되돌릴 수 없는 동작이고 사후에 설명할 수 있어야 한다.

**분류(카테고리) 관리** *(전 항목 Claude 판단 — 사람 검증 필요)*

- **FR-013**: 시스템은 **게시판별로 분리된** 분류 목록을 관리(조회·등록·수정·삭제)할 수
  있어야 한다(MUST). 분류를 쓰지 않는 게시판(문의)을 대상으로 하는 분류를 허용해서는 안 된다(MUST NOT).
- **FR-014**: 분류는 **이름 · 표시 순서 · 사용 여부**를 가져야 한다(MUST).
- **FR-015**: 같은 게시판 안에서 **분류 이름 중복을 거부**해야 한다(MUST).
  게시판이 다르면 같은 이름을 허용한다.
- **FR-016**: 분류 이름을 **1자 이상 30자 이하**로 서버에서 검증해야 한다(MUST).
- **FR-017**: **그 분류를 사용하는 글이 1건 이상이면 삭제를 거부해야 한다(MUST NOT 삭제).**
  대신 사용 여부를 '사용 안 함'으로 내릴 수 있어야 한다(MUST).
  *(삭제는 되돌릴 수 없고 이미 쌓인 글을 손상시킨다. 비활성은 되돌릴 수 있다)*
- **FR-018**: 사용하는 글이 0건인 분류는 삭제할 수 있어야 한다(MUST).
  삭제 시점에 **서버가 사용 여부를 다시 확인**해야 하며(MUST), 확인과 삭제 사이에 그 분류를
  쓰는 글이 생기면 **분류 없는 글이 남지 않도록** 둘 중 하나만 성립시켜야 한다(MUST).
- **FR-019**: 비활성 분류를 **새 글의 선택지로 제공하는 것을 금지한다(MUST NOT).**
  다만 이미 그 분류를 가진 글은 **분류를 유지한 채 수정할 수 있어야 한다**(MUST).
- **FR-020**: 글의 분류를 **비활성 분류로 변경**하는 요청을 거부해야 한다(MUST).
  서버가 *변경*과 *유지*를 구분해야 한다(MUST).
- **FR-021**: 사용자 화면의 분류 필터에는 **활성 분류만** 제공해야 하고(MUST NOT 비활성),
  관리자 화면의 분류 필터에는 **비활성 분류도 포함**해야 한다(MUST).
  *(관리자는 과거 글을 찾아야 하는 사람이다)*
- **FR-022**: 분류가 비활성이 되어도 **이미 등록된 글의 분류 표시는 유지**되어야 한다(MUST).
- **FR-023**: 분류 목록은 **표시 순서 오름차순**으로 제공해야 하며(MUST), 순서가 같은 항목의
  상대 위치가 조회할 때마다 달라지는 것을 금지한다(MUST NOT).
- **FR-024**: 분류가 필수인 게시판에 **활성 분류가 0개**이면 글 등록을 거부하고(MUST),
  응답에 **분류를 먼저 등록해야 한다는 원인**을 담아야 한다(MUST).
- **FR-028**: **활성 분류 목록 조회는 인증을 요구하지 않아야 한다**(MUST NOT 인증 요구).
  분류의 등록·수정·삭제는 관리자 전용 경로에 두어야 한다(MUST).
  *(비로그인 사용자의 목록 화면도 분류 필터를 그려야 한다. 001의 `/api/admin/**` 차단 아래에
  읽기 경로를 두면 그 화면이 성립하지 않는다)*

**사용불가 아이디 목록 관리** *(001 `FR-028`이 004로 넘긴 항목)*

- **FR-025**: 관리자는 사용불가 아이디 목록을 **조회·추가·삭제**할 수 있어야 한다(MUST).
  이미 있는 값의 중복 추가를 거부해야 한다(MUST).
- **FR-026**: 추가·삭제는 **재시작이나 재배포 없이 즉시** 가입 검증에 반영되어야 한다(MUST).
- **FR-027**: 사용불가 목록 추가는 **이미 존재하는 계정에 소급 적용해서는 안 된다**(MUST NOT).
  신규 가입에만 적용한다. *(001에 계정 복구 수단이 없어 소급 차단이 영구 차단이 된다)*

### Key Entities

- **분류(Category)**: 게시판별 글 묶음. **대상 게시판 · 이름 · 표시 순서 · 사용 여부**.
  같은 게시판 안에서 이름이 고유하다. 글이 이것을 참조한다.
- **글의 분류 참조**: 글 하나가 분류 하나를 가리킨다(문의게시판 제외).
  **분류가 사라지면 글이 손상되므로 참조가 끊기지 않아야 한다**(`FR-017`).
- **사용불가 아이디(Reserved Identifier)**: 001에서 이미 데이터로 존재한다.
  004는 **화면만 얹는다.**

> 구체적인 데이터 구조·관계·제약은 **3.5 DB 논리 설계**에서 사람이 확정한다
> (constitution 원칙 III). 특히 [ADR 후보](#adr-후보) 3·4가 여기에 걸린다.

## Success Criteria *(mandatory)*

- **SC-001**: 관리자는 어느 관리 화면에 있는지 **화면을 보고 즉시** 알 수 있다.
- **SC-002**: 관리자가 실수로 삭제를 눌러도 **확인 단계에서 되돌릴 수 있다** — 확인 없이
  데이터가 바뀌는 경로가 **0건**이다.
- **SC-003**: 부적절한 게시물·댓글은 작성자가 아니어도 **관리자가 내릴 수 있다.**
- **SC-004**: 관리자 예외가 일반 사용자에게 새는 경로가 **0건**이다.
- **SC-005**: 분류를 정리해도 **이미 등록된 글이 손상되지 않는다** — 분류 표시가 비거나
  달라진 글이 **0건**이다.
- **SC-006**: 관리자는 새 분류를 만들어 **1분 이내**에 그 분류로 글을 등록할 수 있다.
- **SC-007**: *"내 글이 왜 사라졌나"* 라는 문의에 대해 **누가 언제 지웠는지 답할 수 있다.**
- **SC-008**: 인증이 끊긴 관리 화면이 **정상 화면처럼 보이는 경우가 0건**이다.

## Assumptions

원 요구사항에 없거나 불명확해 합리적 기본값을 택한 항목이다. 4번 계획에서 확정되거나 뒤집힐 수 있다.

1. **관리 메뉴 구성**: 게시판 관리 4종 + **분류 관리** + **사용불가 아이디 관리** = 6개.
   뒤의 두 개는 요구사항의 메뉴 목록에 없다(→ `J-1`·`J-9`).
2. **관리자 계정은 하나**다(001). 따라서 *"어느 관리자가 지웠나"* 는 당장 한 명을 가리키지만,
   `FR-012`는 관리자가 늘어날 것을 전제로 행위자를 기록한다.
3. **분류 이름 길이 30자.** 목록의 분류 칸에 들어가야 하고, 그보다 길면 이름이 아니라 설명이다.
4. **분류에 설명·색상·아이콘을 두지 않는다.** 목록 화면이 이름만 표시한다.
5. **관리자 화면은 데스크톱 우선**이며 모바일 대응을 004 범위로 보지 않는다.
   관리 작업은 넓은 화면에서 이루어진다.
6. **관리 목록의 기본값은 사용자 목록과 같다**(개씩 보기 10 · 등록일시 내림차순).
   `FR-008`이 규칙을 공유하므로 기본값도 공유한다.
7. **관리자 화면은 별도 앱이 아니라 같은 프론트 앱의 경로 분리**다(001에서 확정된 구조).
   물리 분리 여부는 → [**`ADR-022`**](#adr-후보).
8. **분류 관리 화면은 게시판을 먼저 고르고 그 게시판의 목록을 편집**하는 형태다.
   세 게시판의 분류를 한 화면에 섞으면 어느 게시판 것인지 매번 확인해야 한다.
