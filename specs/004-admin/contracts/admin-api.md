### 004가 추가하는 오류 코드 — **9개. 이 표가 단일 진실이다**

| `code` | 상태 | `detail`(고정 문구) | AC |
|---|---|---|---|
| `CATEGORY_BOARD_NOT_SUPPORTED` | 400 | 이 게시판은 분류를 사용하지 않습니다 | `AC-18` |
| `CATEGORY_NAME_INVALID` | 400 | 분류 이름은 1자 이상 30자 이하여야 합니다 | `AC-21` |
| `CATEGORY_NAME_DUPLICATED` | **409** | 같은 게시판에 이미 있는 분류 이름입니다 | `AC-20` |
| `CATEGORY_IN_USE` | **409** | 이 분류를 사용하는 글이 있어 삭제할 수 없습니다 | `AC-22`·`AC-24` |
| `CATEGORY_INACTIVE` | 400 | 사용하지 않는 분류로는 변경할 수 없습니다 | `AC-27` |
| `CATEGORY_NONE_AVAILABLE` | 400 | 이 게시판에 사용할 수 있는 분류가 없습니다. 분류를 먼저 등록해 주세요 | `AC-31` |
| `CATEGORY_NOT_FOUND` | 404 | 분류를 찾을 수 없습니다 | Edge Cases |
| `RESERVED_ID_DUPLICATED` | **409** | 이미 등록된 아이디입니다 | `AC-33` |
| `RESERVED_ID_NOT_FOUND` | 404 | 등록되지 않은 아이디입니다 | `AC-34` |

> **`CATEGORY_NAME_INVALID`의 문구에 숫자가 들어 있다.** 스펙은 30자인데 **DB는
> `VARCHAR(50)`이다**(`plan.md` 불일치-1). **착수 전에 확정되지 않으면 이 문구가 거짓말이 된다.**
>
> **`CATEGORY_NONE_AVAILABLE`을 `CATEGORY_REQUIRED`(분류 필수)와 합치지 않는다.**
> 합치면 *"고를 것이 없는데 고르라"* 는 응답이 되고 **`AC-31`의 "원인 안내" 요구가 사라진다.**

## 1. `GET /api/categories?boardType=FREE` — 분류 목록 (공개)

**인증**: **불필요** ★ (`FR-028`)

**왜 공개인가**: 비로그인 방문자의 목록 화면도 분류 필터를 그려야 한다. 이 경로를
`/api/admin/**` 아래 두면 **첫 방문자의 화면이 성립하지 않는다.**

```json
200 OK
{
  "boardType": "FREE",
  "categories": [
    { "id": 4, "name": "자유", "sortOrder": 1 },
    { "id": 5, "name": "질문", "sortOrder": 2 }
  ]
}
```

| 응답 | 조건 | `code` | AC |
|---|---|---|---|
| **200** | **활성 분류만**, `sortOrder` 오름차순 · 같으면 `id` 오름차순 | — | `AC-19`·`AC-25`·`AC-30`·`AC-32` |
| 200 | 활성 분류가 0개면 **빈 배열**(오류가 아니다) | — | `AC-31`의 선행 상태 |
| 400 | `boardType`이 `INQUIRY` 또는 알 수 없는 값 | `CATEGORY_BOARD_NOT_SUPPORTED` | `AC-18` |

**계약 주의**

- **★ 이 엔드포인트는 "활성만"을 인자로 받지 않는다.** `?includeInactive=true` 같은 파라미터를
  두면 **비인증 요청이 비활성 분류를 볼 수 있는 경로가 생긴다.** 활성 필터는 **하드코딩**이며,
  비활성을 보는 유일한 경로는 2번(`ADMIN`)이다 → 깨지기 쉬운 부분 7번
- 응답에 **`active` 필드를 넣지 않는다.** 전부 활성이므로 항상 `true`이고, 필드가 있으면
  *"false도 올 수 있나"* 로 읽힌다
- **`sortOrder`를 응답에 담는 이유**: 관리 화면과 응답 형태를 맞춰 프론트 타입을 하나로 쓴다.
  화면이 다시 정렬하지는 않는다 — **정렬은 서버가 끝낸다**(`AC-30`)

## 2. `GET /api/admin/categories?boardType=FREE` — 분류 목록 (관리자)

**인증**: 필요 + **`ADMIN`**

```json
200 OK
{
  "boardType": "FREE",
  "categories": [
    { "id": 4, "name": "자유", "sortOrder": 1, "active": true,  "usedPostCount": 12 },
    { "id": 5, "name": "질문", "sortOrder": 2, "active": false, "usedPostCount": 0 }
  ]
}
```

| 응답 | 조건 | `code` | AC |
|---|---|---|---|
| **200** | **활성 + 비활성 전부.** 정렬은 1번과 동일 | — | `AC-17`·`AC-28` |
| 400 | `boardType`이 `INQUIRY` 또는 알 수 없는 값 | `CATEGORY_BOARD_NOT_SUPPORTED` | `AC-18` |
| **401** | 미인증 | `AUTH_REQUIRED` | `AC-32` |
| 403 | `USER` 권한 | `AUTH_FORBIDDEN` | 001 `AC-22` |

**계약 주의**

- **`AC-28`은 1번과 2번의 응답을 비교해야 성립한다.** 각각 200이어도 내용이 같으면 거짓이다.
  **비교 테스트를 따로 둔다**(001의 `AC-2`·`AC-3` 비교와 같은 패턴)
- **`usedPostCount`는 표시용이고 판정용이 아니다** *(Claude 판단 — `plan.md` `J-16`)*.
  관리자가 삭제를 누르기 전에 알 수 있게 하려는 값이며, **삭제 가능 여부의 판정은
  5번에서 DB가 한다**(`AC-24`). **이 값이 0이어도 삭제가 409일 수 있다**
- `active: false`인 항목은 화면에서 **사용 안 함으로 구분 표시**된다(`AC-28`)

## 3. `POST /api/admin/categories` — 분류 등록

**인증**: 필요 + **`ADMIN`**

```json
{ "boardType": "FREE", "name": "공지", "sortOrder": 1, "active": true }
```

| 응답 | 조건 | `code` | AC |
|---|---|---|---|
| **201** | 성공. 본문에 생성된 분류 | — | `AC-19` |
| 400 | `boardType`이 `INQUIRY` | `CATEGORY_BOARD_NOT_SUPPORTED` | `AC-18` |
| 400 | 이름이 빈 값·공백만·31자 이상 | `CATEGORY_NAME_INVALID` | `AC-21` |
| **409** | 같은 게시판에 같은 이름 (**대소문자 무시**) | `CATEGORY_NAME_DUPLICATED` | `AC-20` |
| **401** | 미인증 | `AUTH_REQUIRED` | `AC-32` |

**계약 주의**

- **`AC-20`은 "다른 게시판이면 성공한다"까지가 계약이다.** `FREE`에 `질문`이 있어도
  `GALLERY`에 `질문`은 **201**이다. 유일성 범위가 `(boardType, LOWER(name))`이기 때문이다
- **중복 판정은 DB 유니크 인덱스가 한다.** 애플리케이션의 사전 조회는 **친절한 메시지를
  만들기 위한 것**이고, 동시 등록 경합에서 판정하는 것은 `uk_categories_board_type_name`이다
  → **유니크 위반을 409 `CATEGORY_NAME_DUPLICATED`로 번역**한다(500으로 새면 001 `AC-28` 위반)
- **`AC-18`을 애플리케이션이 400으로 막아야 한다.** DB의 `ck_categories_board_type`까지
  내려가면 **예상 못한 예외 → 500**이 된다. **DB 제약은 마지막 방어선이지 응답 생성기가 아니다**
- `sortOrder` 생략 시 기본값 **0**(V5의 `DEFAULT 0`). 음수 허용 여부는 **미확정**
  (`plan.md` 불일치-2)
- `active` 생략 시 **`true`**

## 4. `PATCH /api/admin/categories/{id}` — 분류 수정 (이름 · 순서 · 사용 여부)

**인증**: 필요 + **`ADMIN`**

```json
{ "name": "공지사항", "sortOrder": 2, "active": false }
```

| 응답 | 조건 | `code` | AC |
|---|---|---|---|
| **200** | 성공 (**세 필드 모두 부분 수정 가능**) | — | `AC-25`·`AC-30` |
| 400 | 이름 규칙 위반 | `CATEGORY_NAME_INVALID` | `AC-21` |
| **409** | 같은 게시판에 같은 이름 (자기 자신 제외) | `CATEGORY_NAME_DUPLICATED` | `AC-20` |
| 404 | 없는 분류 | `CATEGORY_NOT_FOUND` | Edge Cases |
| **401** | 미인증 | `AUTH_REQUIRED` | `AC-32` |

**계약 주의**

- **`boardType`은 바꿀 수 없다.** 요청에 담겨도 무시한다 —
  엔티티가 `updatable = false`이고, 바꾸면 **그 분류를 쓰던 글의 분류가 통째로 어긋난다**
- **`active: false`가 `AC-22`가 안내한 "사용 안 함으로 내리기"의 실행 경로**다.
  이 요청은 **그 분류를 쓰는 글이 몇 건이든 성공한다** — 그것이 비활성을 고른 이유다
- **`active: true`로 되돌리는 것도 허용한다**(Edge Cases). 즉시 1번 응답에 다시 나타난다
- **동시 수정은 나중 요청이 이긴다** *(`J-8`)*. **버전 필드도 `If-Match`도 두지 않는다.**
  값이 세 개뿐이라 충돌 감지 비용이 이득보다 크다는 판단이며, **뒤집으면 이 계약과
  스키마(버전 컬럼)가 함께 바뀐다**

## 5. `DELETE /api/admin/categories/{id}` — 분류 삭제

**인증**: 필요 + **`ADMIN`**

| 응답 | 조건 | `code` | AC |
|---|---|---|---|
| **204** | 그 분류를 쓰는 글이 **0건**. 삭제됨 | — | `AC-23` |
| **409** | **그 분류를 쓰는 글이 1건 이상** | `CATEGORY_IN_USE` | `AC-22`·`AC-24` |
| 404 | 이미 삭제됨 / 없는 분류 | `CATEGORY_NOT_FOUND` | Edge Cases |
| **401** | 미인증 | `AUTH_REQUIRED` | `AC-32` |

**409 응답 본문** — `AC-22`가 *"건수와 함께 안내"* 를 요구한다:

```json
409 Conflict
Content-Type: application/problem+json
{
  "type": "/errors/conflict",
  "title": "Conflict",
  "status": 409,
  "detail": "이 분류를 사용하는 글이 있어 삭제할 수 없습니다",
  "instance": "/api/admin/categories/5",
  "code": "CATEGORY_IN_USE",
  "traceId": "b71e04",
  "usedPostCount": 12
}
```

- **`usedPostCount`는 Problem Details 확장 필드**다. 001이 `code`·`traceId`를 확장한 것과
  같은 방식이며 **RFC 9457이 허용한다**
- **원칙 IV와 충돌하지 않는다.** 건수는 내부 구조 정보가 아니라 **관리자에게 필요한 값**이고,
  이 엔드포인트는 `ADMIN` 전용이다. 001 `AC-28`의 화이트리스트 검증은 **5xx만 대상**이다
- 화면은 이 응답을 받아 *"사용 안 함으로 내릴 수 있다"* 를 함께 안내하고
  **4번(`active: false`)으로 유도**한다

### ★ 이 엔드포인트에서 가장 틀리기 쉬운 한 줄

**`count(*)`를 조회해 0이면 삭제하는 방식으로 구현하면 안 된다.**

```
잘못된 구현                       AC-24가 뚫는 곳
─────────────────────────────    ────────────────────────
1. SELECT count(*) ... = 0       ← 여기와
2. (다른 요청이 그 분류로 글 등록)      ↕ 여기 사이
3. DELETE FROM categories        ← 성공해 버린다
```

**판정은 DB가 한다** — `fk_posts_categories ... ON DELETE RESTRICT`(V6)가 이미 있다.
구현은 **삭제를 시도하고, 무결성 위반을 409 `CATEGORY_IN_USE`로 번역**한다.
`count(*)`는 **409 본문의 `usedPostCount`를 만들기 위해서만** 쓴다.

> **001의 동시 가입 경합과 같은 판단이다** — `data-model.md`가 *"코드로 막으면 동시 요청에서
> 깨진다"* 며 유일성을 DB에 맡긴 그 판단을, 여기서는 **참조 무결성**에 적용한다.

## 7. `POST /api/admin/reserved-usernames` — 추가

**인증**: 필요 + **`ADMIN`**

```json
{ "username": "support" }
```

| 응답 | 조건 | `code` | AC |
|---|---|---|---|
| **201** | 성공 | — | `AC-33` |
| **409** | 이미 있는 값 (**대소문자 무시**) | `RESERVED_ID_DUPLICATED` | `AC-33` |
| **401** | 미인증 | `AUTH_REQUIRED` | 001 `AC-21` |

**계약 주의**

- **`AC-34` — 재시작 없이 즉시 반영된다.** 001의 `ReservedUsernameRepository.existsIgnoringCase`가
  **가입마다 DB를 조회**하고 캐시가 없으므로 **이미 성립한다.**
  → **캐시를 도입하지 않는 것이 계약이다.** 붙이는 순간 `AC-34`가 깨지고,
  **화면이 거짓말을 하게 된다**
- **`AC-35` — 소급 적용하지 않는다.** `helper`로 가입한 계정이 있어도 이 요청은 **201**이고,
  **그 계정은 계속 로그인된다.** 이 엔드포인트는 기존 계정을 조회하지도 손대지도 않는다
- **길이 제한을 아이디와 같게 두지 않는다.** `reserved_usernames.username`은 `VARCHAR(255)`이며,
  12자 이상을 금지어로 넣는 것 자체는 무의미하지 않다(가입의 길이 검증이 먼저 거른다)

## 9. 기존 엔드포인트 위에 얹는 계약 — 004는 경로를 새로 만들지 않는다

### 9.1 삭제 권한 — `DELETE /api/posts/{id}` · `DELETE /api/comments/{id}`

**경로와 응답 형식은 002의 계약이다.** 004는 **권한 판정 규칙 하나**만 얹는다.

```
삭제 허용 = (요청자.id == 대상.author_id)  OR  (요청자.role == ADMIN)
```

| 응답 | 조건 | `code` | AC |
|---|---|---|---|
| 204 | 소유자 본인 | — | 002 |
| **204** | **`ADMIN`이 남의 글·댓글 삭제** | — | `AC-12`·`AC-13` |
| **403** | `USER`가 남의 글·댓글 삭제 | `AUTH_FORBIDDEN` | `AC-14`·`AC-15` |
| 404 | 이미 삭제됨 | — | Edge Cases |

**★ 판정 입력에 권한 외의 것을 받지 않는다** (`FR-011`, MUST NOT)

- **요청 경로로 판정하지 않는다** — *"`/api/admin/`으로 오면 허용"* 은 일반 사용자가
  그 경로를 호출해 흉내낼 수 있다(001 `FR-002`)
- **화면 구분·헤더·쿼리 파라미터로 판정하지 않는다** — 전부 클라이언트가 만드는 값이다
- **`AC-12`와 `AC-14`를 반드시 두 테스트로 나눈다.** 한 테스트에서 둘을 보면
  *"예외가 새는가"* 쪽이 조용히 빠진다

**`AC-16` — 이 두 요청 중 `ADMIN`이 남의 것을 지운 경우 기록을 남긴다**

| 담는 것 | 담지 않는 것 |
|---|---|
| 행위자 식별자 · 대상 종류(`POST`/`COMMENT`) · 대상 식별자 · 시각 · `traceId` | **비밀번호·자격증명 원문/해시**(001 `AC-36`) · 글 본문 |

**기록의 형태(로그 vs 이력 테이블)는 미확정**이다 → `plan.md` **`ADR-023`**.
**형태가 무엇이든 위 네 항목은 계약이다.**

### 9.2 글 등록·수정의 분류 검증

**경로는 002·003·005의 계약이다.** 004는 **분류에 관한 규칙**만 얹는다.

| 응답 | 조건 | `code` | AC |
|---|---|---|---|
| 400 | 그 게시판에 **활성 분류가 0개** | `CATEGORY_NONE_AVAILABLE` | `AC-31` |
| 400 | **비활성 분류로 변경** 시도 | `CATEGORY_INACTIVE` | `AC-27` |
| 200 | **비활성 분류를 유지한 채** 다른 필드 수정 | — | `AC-26` |
| 400 | 다른 게시판의 분류 `id` | `CATEGORY_NOT_FOUND` 또는 002의 검증 코드 | — |

**★ 서버가 *변경*과 *유지*를 구분해야 한다** (`FR-020`)

```
요청의 categoryId == 저장된 categoryId  →  유지  →  비활성이어도 허용   (AC-26)
요청의 categoryId != 저장된 categoryId  →  변경  →  비활성이면 400      (AC-27)
```

- ***"비활성이면 무조건 거부"* 로 짜면 `AC-26`이 깨진다** — 그 글은 제목 한 글자도 고칠 수 없다
- ***"항상 허용"* 으로 짜면 `AC-27`이 깨진다** — 비활성 분류가 직접 호출로 다시 쓰이기 시작한다
- 등록(신규)에는 *유지*가 없으므로 **비활성은 항상 거부**다

**수정 화면의 분류 선택지는 어떻게 만드는가** — `AC-26` 후반부

> **공개 목록(1번)에 파라미터를 추가하지 않는다.** 대신 **글 상세 응답이 자기 분류를
> 담고 있으므로**(`AC-29`가 이미 요구한다 — 비활성이어도 이름이 그대로 와야 한다)
> 화면이 **공개 목록 + 현재 값**을 합쳐 선택지를 만든다.
> 현재 값이 비활성이면 **사용 안 함으로 표시된 채** 목록에 포함된다.
>
> 이렇게 하면 **비활성 분류를 노출하는 공개 경로가 생기지 않는다** —
> 보이는 것은 **이미 그 글에 붙어 있어 어차피 공개된 하나**뿐이다.

### 9.3 관리 목록 — 사용자 목록과 **같은 엔드포인트**

`FR-008`·`AC-11`. **관리자 전용 목록 API를 만들지 않는다** *(Claude 판단 — `plan.md` `J-17`)*.

| | 계약 |
|---|---|
| 경로·파라미터 | 002가 정의한 목록 계약 그대로 (기간·분류·검색어·개씩 보기·정렬·페이징) |
| 기본값 | 사용자 목록과 동일 (개씩 보기 10 · 등록일시 내림차순) |
| **비활성 분류로 필터링** | **허용한다** *(`J-18`)*. 막으면 `AC-28`의 관리자 필터가 자기 결과를 부르지 못한다. 그 글들은 어차피 공개이므로 새는 정보가 없다 |
| 검색조건 유지 | 프론트 상태. **관리 화면이 사용자 목록과 같은 훅을 쓰는지**는 8번 코드 리뷰 항목 |

**엔드포인트를 나누지 않는 이유**: 나누면 **같은 목록 규칙이 두 벌**이 되고,
`FR-008`이 막으려던 것이 정확히 그것이다. **`AC-28`이 요구하는 차이는 목록 API가 아니라
분류 목록 API(1번 vs 2번)에 있다.**

## 10. 모든 요청에 걸리는 계약

| | 요구 | AC |
|---|---|---|
| **확인 절차와 무관하다** | 위 8개 엔드포인트와 9.1·9.2의 규칙은 **화면의 확인 절차를 거쳤는지와 무관하게 동일하게 동작**한다. 확인창 없이 직접 호출해도 **같은 입력 검증·같은 권한 판정·같은 상태코드**가 나온다 | **`AC-10`** |
| 오류 형식 | 001과 동일한 Problem Details + `code`·`traceId`. **004는 새 형식을 만들지 않는다** | 001 `AC-27` |
| 5xx 비노출 | 004가 추가하는 경로에서도 **제약조건명·인덱스명·SQL 조각이 새지 않는다.** ★ 004에서 가장 새기 쉬운 곳이 **`fk_posts_categories` 위반**이다 → 5번 절 | 001 `AC-28` |
| 로그 | 004의 기록(`AC-16`)에도 비밀번호·자격증명을 남기지 않는다 | 001 `AC-36` |

**`AC-10`이 계약 문서에 있어야 하는 이유**: 확인 절차는 `FR-006`으로 **화면 요구**이고,
`AC-10`은 **그 화면 요구가 서버 계약을 바꾸지 않는다**를 말한다. 계약 쪽에 적지 않으면
*"관리 화면에서만 쓰는 API니까 화면이 이미 확인했다"* 로 읽혀 **서버 검증이 느슨해진다** —
001 `FR-002`·`FR-019`가 막으려던 것과 같은 사고다.

**테스트 방법**: 8개 엔드포인트 중 **상태를 바꾸는 5개**(3·4·5·7·8)에 대해
**화면을 거치지 않은 직접 요청**을 보내고, 화면 경로와 **같은 응답**이 나오는지 본다.

## ★ 이 계약의 가장 깨지기 쉬운 부분

> 001 계약의 같은 절과 같은 목적이다 — **각각 통과해도 전체가 틀릴 수 있는 곳**을 적는다.

### 1. `GET /api/categories`가 **지금 코드에서 401을 낸다** ★ 최우선

현재 `SecurityConfig`는 permitAll 목록에 없는 모든 경로에 `.anyRequest().authenticated()`를
건다. 004가 이 경로를 명시적으로 열지 않으면 **`AC-32`가 거짓이고,
비로그인 방문자의 목록 화면이 분류 필터를 그리지 못한다.**

**이 버그가 특히 위험한 이유는 개발 중에 보이지 않는다는 것이다.**

| | |
|---|---|
| 개발자 | 대개 로그인 상태로 화면을 본다 → **잘 나온다** |
| E2E | `storageState`로 로그인 상태를 주입한다(`test-strategy.md` 4.1) → **잡히지 않는다** |
| **실제 첫 방문자** | **깨진다** |

→ **`AC-32`는 반드시 통합 테스트로, 인증 쿠키 없는 클라이언트로** 검증한다.

**여는 방법의 함정 2개**

- `/api/categories` 를 열되 **`/api/admin/categories`가 그 규칙에 걸리지 않게** 한다.
  경로가 다르므로 접두사로는 겹치지 않지만, `**` 패턴을 넓게 쓰면 겹칠 수 있다
- **읽기만 연다.** `GET`만 permitAll이고 나머지 메서드는 열지 않는다

### 2. 분류 삭제를 코드가 판정한다 (`AC-24`)

5번 절의 *"가장 틀리기 쉬운 한 줄"*. **`count(*)` → `DELETE` 순서로 짜면 그 사이가 뚫린다.**
판정은 `ON DELETE RESTRICT`가 하고 코드는 **위반을 409로 번역**만 한다.

**번역하지 않으면 두 번 틀린다** — ① 500이 나가고 ② 001 `AC-28`이 금지한 **제약조건명**이
그 경로로 노출된다(`fk_posts_categories`).

### 3. 관리자 예외가 권한이 아닌 조건으로 열린다 (`AC-14`·`AC-15`)

9.1의 MUST NOT. **`AC-12`가 통과해도 `AC-14`가 통과하지 않으면 서비스가 뚫린 것**이고,
**둘 다 통과해도 판정 입력에 경로가 섞여 있으면 나중에 뚫린다.**
→ 테스트로 완전히 막을 수 없는 부분이 남으므로 **8번 코드 리뷰의 명시 항목**으로 올린다.

### 4. *변경*과 *유지*를 구분하지 못한다 (`AC-26`·`AC-27`)

9.2. **두 AC가 서로를 반증한다** — 한쪽만 보고 짜면 반드시 다른 쪽이 깨진다.
**짝으로 배정한 이유**가 이것이고, 한 테스트로 뭉치면 이 성질이 사라진다.

### 5. 1번과 2번이 같은 리포지토리 메서드를 파라미터로 갈라 쓴다

*"활성만 볼지"* 를 **인자로 받는 순간** 그 인자가 어디서 오는지가 문제가 된다.
쿼리스트링에서 오면 **비인증 요청이 비활성 분류를 본다.**

→ **공개 엔드포인트는 활성 필터를 하드코딩한다.**
`CategoryRepository`에 이미 두 메서드가 **따로** 있다
(`findByBoardTypeAndActiveTrueOrderBy...` / `findByBoardTypeOrderBy...`) —
**하나로 합치지 않는 것이 계약이다.**

### 6. `AC-31`이 초기 데이터 때문에 조용히 통과한다

V10이 게시판별 초기 분류를 넣어 두어 **활성 분류 0개 상태가 자연히 오지 않는다.**
테스트가 그 상태를 만들지 않으면 `CATEGORY_NONE_AVAILABLE` 경로가 **한 번도 실행되지 않은 채**
초록이 된다.

→ 테스트는 **그 게시판의 분류를 전부 `active: false`로 내린 뒤** 등록을 시도한다.
**삭제로 만들 수 없다** — 글이 있으면 `RESTRICT`가 막는다(2번과 같은 이유).

### 7. 사용불가 아이디에 캐시가 붙는다 (`AC-34`)

지금은 가입마다 DB를 조회하므로 성립한다. **성능을 이유로 캐시를 붙이는 순간
`AC-34`가 깨지고, 그 깨짐은 관리자 화면에서 보이지 않는다** — 추가는 성공하고
목록에도 나타나는데 가입만 계속 통과한다. **화면이 거짓말을 하는 상태**다.

## 프론트 계약 (화면이 책임지는 것)

| | 요구 | AC |
|---|---|---|
| 관리 메뉴 · 현재 위치 | 관리 화면 어디서든 메뉴가 보이고 **현재 화면 하나만** 구분 표시 | `AC-1` |
| 관리자 식별 · 로그아웃 | 상단에 로그인한 관리자의 **이름**과 로그아웃 수단 | `AC-2` |
| **진입 처리** | 미인증·`USER` 상태로 관리자 경로 진입 → **관리자 로그인 진입점**으로. **사용자 로그인으로 보내지 않는다** | `AC-3`·`AC-4` |
| **복귀 목적지** | **관리자 경로 하위의 상대 경로만** 허용. 그 밖은 무시하고 관리자 기본 화면으로 | `AC-5` |
| **401/403 처리** | 데이터 요청이 401·403이면 **빈 목록을 정상처럼 그리지 않고** 재인증 상태로 전환. **입력값은 지우지 않는다** | `AC-6` |
| **확인 절차** | 등록·수정·삭제 실행 전 확인. **취소 시 요청을 보내지 않고 입력값을 유지** | `AC-7`·`AC-8`·`AC-9` |

> **`AC-5`의 목적지 판정은 순수 함수로 떼어내 단위 테스트로 변형을 훑는다** —
> 001 `AC-34`의 판정 함수를 **한 단계 더 좁힌 것**이다.
> 001이 막은 것(절대 URL · `//다른도메인` · 역슬래시 · URL 인코딩 변형)에 더해
> **004는 "같은 출처의 상대 경로지만 관리자 경로 밖"** 을 막는다.
> 예: `/mypage` 는 001의 판정을 통과하지만 **004에서는 무시되고 관리자 기본 화면으로 간다.**
>
> **004의 판정 함수가 001의 것을 대체하지 않는다** — 001의 판정을 통과한 값에
> **접두사 조건 하나를 더 얹는다.** 대체하면 001이 막은 변형을 다시 구현하게 되고,
> 두 벌이 되는 순간 한쪽만 고쳐진다.

> **`AC-6`이 프론트 계약인 것은 `FR-019`(서버 권한 검증)의 예외가 아니다.**
> 서버는 이미 401·403으로 **올바르게 막았다.** 남은 문제는 **그 응답을 화면이 어떻게
> 그리느냐**이고, 그것은 브라우저 쪽 책임이다 — 001 `AC-34`가 프론트 계약인 것과 같은 논리.
