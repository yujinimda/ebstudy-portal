### 7번 "역할 역전"이 왜 중요한가

테스트 레인은 **코덱스가 스펙만 보고 테스트를 먼저 작성 → 클코가 통과시킨다.**
이것이 곧 **TDD**(테스트 먼저 → 실패 확인 → 구현)이며,
사람이 혼자 TDD 할 때 가장 잘 무너지는 지점("귀찮으니 구현 먼저, 테스트는 나중")이
**작성자가 물리적으로 분리되어 원리적으로 막혀 있다.** 유지한다.

## 4. 확정 규칙

### 4.1 기록 — ADR

**무엇을 ADR로 남기나 — 되돌리기 비용 기준.**
> "나중에 맘 바꾸면 여러 파일 / DB / 이미 쌓인 데이터를 손대야 하는가?" → YES면 ADR

| ADR 대상 | ADR 아님 |
|---|---|
| ORM 선택 (JPA vs MyBatis) | 폴더를 `domain/` vs `feature/` |
| 사용자 테이블 스키마 설계 | 로거 라이브러리 선택 |
| 세션 vs JWT | 변수명 규칙 |
| 에러 응답 포맷 | 라이브러리 마이너 버전 |
| 비밀번호 해싱 알고리즘 | |

**언제, 누가 쓰나 — 결정 직후. Claude 초안 + 사람이 2칸 직접.**

사후에 몰아 쓰면 이미 결과를 아는 상태라 "이게 맞아서 이걸 골랐다"로 정리된다.
실제로 흔들렸던 지점·버린 대안·몰라서 찍은 부분이 지워지는 것을 **사후 합리화**라 하고,
문서가 6개월 뒤 쓸모없어지는 주된 원인이다.

```
## 맥락                ← Claude
## 검토한 대안          ← Claude
## 오간 대화            ← 사람의 프롬프트 원문 + Claude의 질문, 편집 없이 그대로
## 내 판단             ← ★ 사람이 직접
## 몰랐던 지점          ← ★ 사람이 직접
## 그래서 포기한 것      ← Claude
```

`오간 대화` 칸을 원문 그대로 보존하는 이유: 요약하면 그 순간의 불확실성이 사라진다.
"무엇을 묻지 못했는가"도 기록의 일부다.

### 4.2 기록 — learning 노트

**트리거: 사람이 "이게 뭐야"를 물어서 Claude가 개념을 설명한 매 지점.**

```
## 물리 맥락 (어떤 작업 중에 나왔나)
## 설명 + 예제         ← Claude
## ★ 내 말로 다시       ← 사람. 이걸 못 쓰면 아직 이해하지 못한 것
## 아직 모르는 것       ← 사람
```

`내 말로 다시` 칸의 목적: **이해했다는 착각을 걸러내는 가장 싼 장치.**
Claude의 설명만 저장하면 학습이 아니라 스크랩이다.

### 4.3 기록 — 회고

**스토리 PR 머지마다 5줄.** `retrospective.md`에 누적.

```
## US2 (머지 YYYY-MM-DD)
- 병목:    어느 단계에서 시간이 갔나
- 놓침:    게이트가 잡지 못한 것
- 바꿀 것: 프로세스 수정 사항 → 즉시 process.md 반영
- 배운 것: 이번에 처음 알게 된 것
```

프로젝트 끝에 한 번 쓰지 않는 이유: 초반 스토리의 병목은 그때 이미 기억에서 사라지고,
프로세스 개선이 **이번 프로젝트에 반영되지 못한다.**

공유용 정리 글은 이 재료로 나중에 재구성한다. 없는 것을 만들 수는 없지만 있는 것을 엮는 것은 쉽다.

### 4.4 테스트 전략

**밀집도: API 통합 테스트 중심 (Testing Trophy).**

```
단위        ███        복잡한 계산·검증 로직만
슬라이스     █          거의 안 씀
통합        ████████   ★ 주력
E2E         ██         5~10개
```

전통적 피라미드(단위 多)를 쓰지 않는 이유: 단위 테스트를 많이 쓰면 의존성을 전부 목(mock)으로
발라야 하고, 그러면 **리팩터링마다 테스트가 깨지는데 정작 진짜 버그는 안 잡힌다.**
목은 상상한 대로만 응답하기 때문이다. 실제 버그는 실제 DB와 붙는 경계에서 나온다.

| 레벨 | 무엇 | 속도 | 잡는 버그 |
|---|---|---|---|
| 단위 | 스프링 없이 순수 객체 | ms | 비즈니스 규칙 |
| 슬라이스 | 스프링 일부 (`@WebMvcTest`, `@DataJpaTest`) | 초 | 요청 검증, 쿼리 오류 |
| **통합** | 앱 전체 + **실제 DB** | 수 초 | 트랜잭션, 권한, 실제 SQL |
| E2E | 브라우저 | 수십 초 | 프론트-백 연결 |

**E2E(Playwright) 규칙 — 느림은 대부분 사용 방식 문제다.**

1. **개수를 줄인다** (효과 압도적). E2E는 "여러 시스템이 붙어서 도나"만 검증.
   에러 케이스·권한·경계값은 전부 API 통합 테스트로 내린다. **총 5~10개.**
2. **로그인 재사용 (`storageState`)** — 매 테스트마다 로그인 화면을 클릭하지 않는다.
   한 번 로그인해 쿠키/토큰을 저장하고 주입. 보통 이것만으로 절반 이상 빨라진다.
3. **사전 데이터는 UI가 아니라 API로 만든다** — `request.post()`로 꽂고, 검증만 UI로.
4. **`waitForTimeout` 금지** — `sleep`이 느림의 주범.
   `expect(...).toBeVisible()` 등 web-first assertion을 쓴다(조건 충족 즉시 진행).
5. **로컬에서는 전체를 돌리지 않는다** — 태그로 일부만(`@smoke`), 전체는 CI에서.

### 4.5 QA

| | 시점 | 무엇 | 주체 |
|---|---|---|---|
| **9.5 기능 QA** | 머지 **전**, PR 프리뷰 | 이번 스토리가 AC를 만족하나 | 사람 |
| **9.7 승격** | 9.5 통과 직후, 같은 PR | 통과한 AC를 자동 테스트로 변환 | AI |
| **10.5 회귀 QA** | 머지 **후** | 기존 스토리가 안 깨졌나 | **CI (사람 0분)** |

**회귀를 사람이 반복하지 않는 이유:** 스토리 3개일 때 10분, 8개면 40분, 15개면 건너뛰게 된다.
건너뛴 순간부터 회귀 QA는 있으나 마나다. 한 번 사람이 확인해 통과한 항목은 기계에 넘기고,
사람은 항상 **"이번에 새로 생긴 것"** 만 본다. 그러면 스토리가 20개가 돼도 사람의 QA 시간은 일정하다.

**승격 시 갈라야 한다** (AC 전부를 브라우저 E2E로 만들면 그 자체가 짐이 된다):
- 사람이 돌아다녀야 의미 있는 흐름 → E2E
- 응답·권한·경계값 → API 통합 테스트

**QA 체크리스트는 새로 만들지 않는다.** 스펙의 AC를 그대로 실행한다.
즉흥으로 훑으면 매번 다른 것을 보게 되고, 그러면 **회귀 확인이 원리적으로 불가능**하다
(무엇을 확인했는지 기록이 없으므로 다음에 비교할 대상이 없다).

### 4.6 인수기준(AC) 형식

전체 체인의 시작점이다.

```
2번 spec의 AC ──┬─→ 7번 코덱스가 이것을 보고 테스트 작성
                ├─→ 9.5 기능 QA 체크리스트
                └─→ 9.7 자동 테스트로 승격 → 10.5 회귀
```

**형식: Given / When / Then + AC-ID**

```markdown
### AC-3 빈 검색어 검색
 Given 로그인한 사용자가 있고
  When GET /api/posts?q= 를 요청하면
  Then 400이고 code=SEARCH_QUERY_REQUIRED

### AC-4 남의 비밀 게시글 조회
 Given 다른 사용자의 비밀 게시글이 있고
  When GET /api/posts/{id} 를 요청하면
  Then 404이고 존재 여부를 노출하지 않는다
```

- **사전조건(Given)을 강제하는 것이 핵심.** 칸이 없으면 생략되고, 코덱스가 "로그인 상태"를
  임의로 짐작해서 테스트를 쓴다.
- **AC-ID가 문서들을 묶는 실이다.** QA 기록에 `AC-3 FAIL`이라고 쓰면
  그것이 곧 테스트 이름이고 태스크 번호로 역추적된다.

### 4.7 DB

**논리 설계 vs 물리 설계**
- 논리 설계 — 엔티티, 관계, 어디를 쪼개나. DBMS·ORM 무관. → **3.5, 사람이 직접**
- 물리 설계 — 컬럼 타입, 인덱스, 제약조건, 네이밍. DBMS 의존. → **4번 plan 이후**

**DB 설계를 사람이 하는 이유:** 스키마는 이 프로젝트에서 **되돌리기 비용이 가장 높은 결정**이다.
코드는 틀리면 다시 쓰면 되지만, 스키마는 이미 운영 데이터가 들어있는 상태에서 바꿔야 한다.
컬럼 하나 쪼개는 일이 마이그레이션 + 데이터 이관 + 무중단 배포 순서 고민으로 번진다.

**정규화 원칙:** 한 컬럼에 여러 값을 밀어넣거나(콤마 구분 문자열 등), 한 테이블이 두 개념을
겸하면 나중에 "그중 하나만 조회/수정/삭제"가 불가능해진다. 그때 코드에서 문자열을 파싱해
때우기 시작하고 거기서 무너진다. → **별도 테이블 또는 하위 엔티티로 분리한다.**

**마이그레이션: Flyway. SQL은 사람이 직접 작성, Claude가 리뷰.**

```
db/migration/
  V1__create_user.sql
  V2__create_post.sql
  V3__add_index_to_post.sql
```

- **`spring.jpa.hibernate.ddl-auto=update` 금지.** 이유 3개:
  (1) 하이버네이트가 어떤 DDL을 실행할지 알 수 없다
  (2) 컬럼 타입 변경·삭제 시 **데이터를 날린다**
  (3) **롤백 개념이 없다**
- **`ddl-auto=validate`로 둔다.** 테이블을 만들지는 않지만
  "엔티티와 실제 스키마가 어긋났다"를 앱 부팅 때 잡아준다. 공짜 안전망.
- **이미 적용된 마이그레이션 파일은 절대 수정하지 않는다.** 잘못됐으면 다음 번호를 추가해 고친다.
  (수정하면 내 로컬은 새 V3, 프로덕션은 옛 V3 상태로 영구히 갈라진다.)

**작성 시점: 6.7 — 병렬 구현 진입 전에 일괄.**
스키마는 모든 레인이 공유하는 지점이다. 레인들이 각자 추가하면 V 번호가 충돌하고,
테이블이 없으면 전 레인이 사람을 기다린다. 먼저 다 쓰고 머지한 뒤 7번을 시작한다.

### 4.8 에러 처리

**전역 예외 핸들러(`@RestControllerAdvice`) 하나로 모든 예외를 받는다.**

**핵심은 예외를 두 종류로 가르는 것:**

| | 예 | 응답 | 메시지 |
|---|---|---|---|
| **의도한 실패** | 검증 실패, 권한 없음, 없는 리소스 | 4xx | 사용자에게 보여줘도 됨 |
| **예상 못한 실패** | NPE, DB 다운, SQL 오류 | 5xx | **절대 노출 금지** |

두 번째 부류는 클라이언트에 `"일시적 오류가 발생했습니다"` + **추적 ID**만 주고,
원본 예외와 스택트레이스는 **로그에만** 남긴다.

**왜 — 정보 누수 차단.** 스프링 기본 동작에 맡기면 이런 것이 그대로 나간다:

```
SQLIntegrityConstraintViolationException:
Duplicate entry 'kim@example.com' for key 'user.uk_user_email'
```

공격자가 얻는 것: 테이블명, 인덱스명, DB 종류, **그리고 "이 이메일은 이미 가입돼 있다".**
마지막을 반복하면 가입자 명단을 뽑을 수 있다 (**계정 열거**, account enumeration — 실제 취약점).

**응답 포맷: RFC 9457 Problem Details + `code`/`traceId` 확장**

스프링 6에 `ProblemDetail` 클래스로 내장되어 추가 의존성이 없고, 표준이라 외부 연동에서
설명 비용이 없다. 여기에 프론트 분기용 `code`와 추적용 `traceId`를 확장 필드로 추가한다.

```json
HTTP 400
Content-Type: application/problem+json
{
  "type": "/errors/validation",
  "title": "Validation Failed",
  "status": 400,
  "detail": "이메일 형식이 아닙니다",
  "instance": "/api/users",
  "code": "USER_EMAIL_INVALID",
  "traceId": "a3f9c2",
  "errors": [{ "field": "email", "reason": "형식 오류" }]
}
```

### 4.9 로깅

**목적지: stdout + JSON. 파일을 앱이 만들지 않는다 (12-Factor).**

```
prod   → stdout, JSON 1줄
         {"ts":"...","level":"ERROR","traceId":"a3f9c2",
          "path":"/api/users","msg":"...","stack":"..."}
local  → 콘솔 텍스트 (사람이 읽는 용)

보관·검색·삭제 = 배포 플랫폼 책임
```

JSON으로 쓰는 이유: 로그 1줄 = 레코드 1개로 구조화되어
`traceId=a3f9c2 전부`, `500만`, `1초 넘는 응답` 같은 질의가 가능해진다.

**원칙 2개 (논쟁 없이 확정):**

1. **마스킹** — 비밀번호·토큰·주민번호·카드번호는 **로그에도 남기지 않는다.**
   응답에서 숨겨도 로그에 평문으로 쌓이면 똑같이 유출이다.
   사고의 상당수가 "DB는 안전했는데 로그가 털렸다"이다.
2. **traceId (MDC)** — 요청 진입 시 ID를 생성해 그 요청의 모든 로그에 자동으로 박는다.
   없으면 동시 요청 10개의 로그가 뒤섞여 **한 요청의 흐름을 재구성할 수 없다.**
   4.8의 `traceId`와 같은 값이다.

### 4.10 시크릿

```
로컬 개발    .env 파일           → .gitignore (절대 커밋하지 않음)
             .env.example        → 커밋 (키 이름만, 값은 빈칸)
배포 환경    플랫폼 환경변수 UI   → 파일 없음
자바         application.yml에 ${DB_PASSWORD} 로 참조 (하드코딩 금지)
프론트       NEXT_PUBLIC_ 은 브라우저에 노출됨 — 백엔드 시크릿 금지
```

**방어선: GitHub Secret Scanning + Push Protection 켜기 + CI에 gitleaks.**

- GitHub 기본 기능은 알려진 형식의 키(AWS·Stripe 등)가 커밋에 섞이면 **push 자체를 거부**한다.
- 다만 **DB 비밀번호는 못 잡는다.** `Study1234!` 같은 임의 문자열은 패턴이 없다.
  → gitleaks가 엔트로피 기반으로 보완한다. 무료·자가호스팅이라 레포 공개/비공개에 무관.

**반드시 알아야 할 것:** git에 시크릿을 한 번 커밋하면 **지우는 커밋을 올려도 히스토리에 영구히
남는다.** 되돌릴 방법이 없다. 유일한 대응은 **그 키를 폐기하고 새로 발급(rotate)** 하는 것이다.
이 프로젝트에서 유일하게 복구 불가능한 실수이므로 방어선을 미리 깐다.

### 4.11 배포 · 롤백

**핵심 비대칭: 코드는 되돌리기 쉽고, DB는 어렵다.**
배포에 마이그레이션이 섞여 있으면 코드를 되돌려도 **DB는 이미 새 스키마**다.
옛 코드가 없는 컬럼을 찾다가 부팅조차 안 될 수 있다. 롤백 버튼을 눌러도 안 돌아가는 상황이 이것.

**규칙 3개:**

1. **15분 룰** — 15분 안에 못 고칠 것 같으면 **먼저 되돌리고** 원인은 나중에 찾는다.
   프로덕션이 죽은 상태에서 디버깅하지 않는다.
2. **파괴적 스키마 변경은 2회 이상 배포로 분할** (expand-contract):
   ```
   배포 1: 새 컬럼 추가          (옛 코드도 동작 → 롤백 안전)
   배포 2: 둘 다 쓰기 시작        (롤백 안전)
   배포 3: 읽기를 새 컬럼으로     (롤백 안전)
   배포 4: 옛 컬럼 삭제           (여기서만 되돌리기 어려움)
   ```
3. **판정 기준**
   | 즉시 롤백 | 롤백 안 함 |
   |---|---|
   | 5xx 급증 | 사소한 UI 버그 |
   | 핵심 기능 불가 | → 다음 배포에서 수정 |
   | 데이터를 잘못 쓰는 버그 | |

**한계: 데이터 오염은 롤백으로 고쳐지지 않는다.** 잘못된 값이 이미 DB에 쓰였으면
코드를 되돌려도 그 데이터는 남는다. 별도 복구 작업이다.
그래서 "데이터를 잘못 쓰는 버그"가 가장 위험한 종류다.

## 5. 게이트 규칙

| 게이트 | 판정자 | 종료 조건 |
|---|---|---|
| 1 설계 승인 | 사람 | 승인 전 코드 작성 금지 |
| 3 스펙 검증 | grill-me | `NEEDS CLARIFICATION` 0개 |
| 3.5 DB 설계 | codex | APPROVED |
| 5 계획 검증 | codex | APPROVED |
| 6.5 tasks 정합성 | codex | APPROVED |
| 8 코드 리뷰 | codex-review (read-only) | APPROVED |
| 9 CI | GitHub Actions | 전부 그린 — **실패 시 머지 버튼 물리 차단** |
| 9.5 기능 QA | 사람 | 전 AC PASS |
| 10.5 회귀 | GitHub Actions | 그린 |

**공통 규칙**
- 판정 `APPROVED`가 종료 조건. `BLOCKED`만 수정한다.
- **핑퐁 2회 컷.** 2회 안에 수렴하지 않으면 사람이 판단한다.
- 예외: 소규모·저위험 태스크(설정, 문구, 스타일 단순 수정)는 8번 리뷰 스킵 가능.
  전 태스크 리뷰는 병목이다.
- 디자인 레인은 8번에 사람이 개입 (Orca 요소 피커로 화면 확인 후 피드백).

**실패 시 루프백**
- 구현 버그 → 해당 레인 7번으로
- 설계 문제 → plan 수정 후 6번부터 재분해

**브랜치 · PR**
- 기획(2~6): `spec/NNN-이름` 브랜치 → **게이트 통과 시 클코가 즉시 머지** (사람 확인 대기 없음)
- 개발: PR 생성 = 9번 통과 후 / PR 머지 = 10번. 둘 다 클코가 `gh` CLI로 수행

**PR 승인자를 두지 않는다** (승인 필요 인원 = 0명)

1. GitHub에서는 **자기 PR을 자기가 승인할 수 없다.** 1인 개발에서 1명 이상으로 두면
   영구히 머지가 불가능해진다.
2. 사람 게이트는 PR 승인이 아니라 **3번 grill-me**(기획 산출물)와
   **9.5 기능 QA**(구현)에 있다. grill-me는 사람이 직접 질문에 답하는 단계이므로
   스펙을 읽지 않고 통과할 수 없다.
   → PR 승인 칸은 이 둘과 중복이다. **게이트를 없앤 것이 아니라 위치를 옮긴 것.**

**main 브랜치 보호 (실제 설정)**

| 항목 | 값 |
|---|---|
| 직접 push | 금지 (PR 필수) |
| 승인 필요 인원 | 0명 |
| force push | 금지 |
| 브랜치 삭제 | 금지 |
| 필수 상태 체크 | CI 구성 후 추가 → 9번 게이트 완성 |
| `enforce_admins` | **false** |

`enforce_admins = false` 이유: 1인 레포에서 규칙에 잠기면 풀어줄 사람이 없어 탈출구를 남긴다.
GitHub이 "보호 규칙을 우회합니다" 경고를 띄우므로 **실수로는 우회되지 않는다**(의도적 행동이어야 함).
익숙해지면 `true`로 올린다.
- 머지 단위는 레인 브랜치가 아니라 **스토리 PR** (레인은 작업공간 단위, 머지는 스토리 단위)
- 레인 D(테스트)의 테스트는 해당 스토리 PR에 포함되어 머지 게이트 역할.
  D 단독 머지는 통합 스위트뿐.
- 머지마다 최신 main 기준 rebase 후 테스트 재확인

## 7. 이 프로세스가 정해진 근거

> 사용자 요구: "프롬프트 + 나의 의견 + 트레이드오프를 전부 남기겠다. AI의 질문도."
> 아래는 이 프로세스를 설계한 2026-07-27 세션의 결정 이력이다.

### 7.1 출발점

사용자가 이미 0~11단계 프로세스를 갖고 있었고, 첫 질문이 이것이었다:

> "작업 후에 이 작업방식은 어떻게 되어있는건지에 대한 최종 산출물과 함께 테스트 + QA가
> 있어야하지않나.."

이 직감이 맞았다. 원안은 **"만드는 것"은 촘촘한데 "확인하는 것"과 "남기는 것"이 비어 있었다.**
빠진 것 3종:

1. 테스트 **전략을 정하는** 단계가 없음 (7번은 실행만)
2. QA가 "데모 시나리오 확인" 한 줄뿐
3. 학습·결정 산출물 슬롯이 없음 — 사용자 요구의 핵심인데 자리가 없었음

### 7.3 정직한 기록 — 결정의 질에 대하여

**대부분의 결정은 Claude 추천을 사용자가 그대로 채택했다.** 사용자가 백엔드 실무 경험이
없어 판단 근거 자체가 없는 상태였기 때문이다. 세션 중반 사용자가 이를 직접 말했다:

> "난 지금 선택을 할때 어떻게 해야할지 모르겠어 실무가 어떤 방식으로 이루어지는지 모르니까
> 실무가 git을 써? 아닐꺼라 생각하는데"

이 시점에 **진행 방식을 바꿨다.** 3지선다를 던지고 "당신 근거로 답해달라"고 하는 것은
경험이 없는 영역에서는 작동하지 않는다. 이후 방식:

1. 실무가 실제로 어떻게 하는지 먼저 알려준다 (판단 재료 공급)
2. Claude가 정하고 이유를 설명한다
3. **"이 이유가 납득되나요, 걸리는 데가 있나요?"** — 사람은 근거를 *검증*하는 역할

사람이 근거를 만들어내는 게 아니라 검증하는 쪽으로 역할을 바꾼 것이다.
아는 것이 쌓이면 자연히 이견이 생기고, 그때부터 사람이 결정한다.

**사용자가 실제로 주도한 지점** (= 이미 판단 근거가 있던 영역):
- 테스트+QA가 빠졌다는 최초 지적 (프로세스 전체의 출발점)
- Playwright가 느려서 싫다 → E2E 개수 제한 + 효율화 규칙
- DB 설계는 손으로 하겠다 / slug는 별도 테이블로 → 3.5 단계 신설
- 로그백 보관, 글로벌 예외 핸들러의 정보 누수 → 4.9, 4.8
- 프롬프트·판단·트레이드오프를 산출물로 남기겠다 → 이 문서와 4.1~4.3 전체

이 목록이 **다음 프로젝트에서 사용자가 스스로 결정할 수 있는 범위의 기준선**이다.
회고(10.7)에서 이 범위가 넓어지는지 추적한다.

## 8. 대상 프로젝트

**게시판 포털.** 게시판 4종(공지사항 · 자유게시판 · 갤러리 · 문의) ×
사용자 화면(SPA) + 관리자 화면(MPA), 화면 정의 24개.

> **요구사항 원천에 대하여**
> 요구사항은 제3자 소유의 비공개 기획 문서(28p)에서 도출했다.
> 문서 자체도, 출처를 특정할 수 있는 정보(조직명 · 파일명 · 작성자 · 페이지 번호)도
> 이 레포에 남기지 않는다. 아래는 **기술 요구사항만 재작성**한 것이다.
> 원본 문서는 `.gitignore`로 제외한다.

### 8.1 스토리 분해 — 수직 슬라이스 (vertical slice)

```
001  인증           가입 · 로그인 · 권한
002  자유게시판      ★ 목록 · 상세 · 등록 · 댓글 · 첨부 · 권한까지 끝까지
       └ 여기서 공통 구조가 나온다: 페이징 · 검색 · 파일 · 권한
003  공지사항        위 구조 재사용 + 상단고정
004  관리자 화면 + 카테고리 관리
005  갤러리          + 이미지 다수 · 캐러셀
006  문의게시판      + 비밀글 · 답변
```

**왜 자유게시판을 두 번째에 두나 — 가장 어렵기 때문이다.**

기획서 순서대로 공지사항(가장 단순)부터 하면 파일 업로드·댓글·본인 권한 검증을
**003에서 처음 만난다.** 그때 001·002를 다시 뜯어야 한다.
실무에서 이를 **"어려운 것 먼저(riskiest first)"** 라 하고, 이유는 하나다 —
**재설계 비용이 뒤로 갈수록 커진다.**

반대로 자유게시판을 먼저 끝내면 거기서 만든 페이징·검색·파일·권한이 나머지 3개 게시판에
그대로 쓰인다. 그러면 **"확장 가능하게 만들었다"가 생각이 아니라 실제로 검증된다.**

기각한 대안:
- **기획서 순서 그대로** — 문서와 1:1 대응은 되지만 위의 재설계 비용을 그대로 받는다
- **레이어별(전체 DB → 전체 API → 전체 화면)** — 마지막까지 동작하는 것이 없어
  9.5 기능 QA·데모 게이트가 성립하지 않는다. 이 프로세스와 부딪힌다

### 8.2 기획서를 그대로 따르면 안 되는 곳

실서비스 전제이므로 스펙 단계에서 상향한다. **둘 다 ADR 대상**이다
(이미 저장된 비밀번호는 해시를 바꿔도 재해싱이 불가능해 전원 재설정이 필요 → 되돌리기 비용 최상).

| 원 요구사항 | 문제 | 대응 |
|---|---|---|
| 관리자 비밀번호를 MySQL `SHA2()`로 저장 | SHA2는 **빠른** 해시 → GPU로 초당 수십억 시도. DB 유출 시 사실상 평문. 게다가 `WHERE pw = SHA2('평문')` 형태면 **평문이 SQL 쿼리 로그에 남아** 4.9 마스킹 원칙과 충돌 | **bcrypt 또는 argon2** (스프링 시큐리티 기본이 bcrypt) |
| Access-token 만료 없음 + LocalStorage | 만료가 없으면 **한 번 탈취되면 영구 유효**하고 폐기 수단이 없다. LocalStorage는 JS로 읽혀 XSS 한 번에 유출 | 짧은 수명 토큰 + 갱신, 저장은 `httpOnly` 쿠키 |
| 비밀번호 4자리 이상 12자리 미만 | 실무 최소 8자 | 스펙 단계에서 상향 검토 |

### 8.3 기획서 누락 · 모순 — 2번 스펙 단계에서 채울 것
