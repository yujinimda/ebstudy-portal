## 개요

게시판 포털의 두 번째 스토리이자 **게시판 4종 중 가장 복잡한 것**이다.
댓글과 첨부를 **둘 다** 가진 유일한 게시판이고, 목록의 검색·정렬·페이징 규칙 전부를 쓴다.

**이 스토리가 짊어지는 것 — 002는 자기 화면만 만드는 스토리가 아니다.**

`process.md` 8.1이 자유게시판을 두 번째에 둔 이유가 *"여기서 공통 구조가 나온다"* 였다.
그 약속을 스펙 층위에서 지키는 방법은 하나뿐이다 — **게시판 4종 공통 목록 규칙을
002의 AC로 확정하고, 003 · 005 · 006은 그것을 참조만 하게 하는 것.**

| 공통 규칙 | 002에서 확정하는 AC |
|---|---|
| 기간 검색 기본 1달 · **최대 1년** | `AC-2` `AC-3` `AC-4` |
| 개씩 보기 10/20/30/40/50 | `AC-5` `AC-6` |
| 정렬 기준·방향 · **정렬 결정성** | `AC-7` `AC-8` `AC-9` `AC-10` |
| 개씩 보기·정렬 **즉시 적용** | `AC-11` |
| 페이징 블록 | `AC-12` `AC-13` |
| **글 번호 = 결과 총건수 기준 역순** | `AC-14` |
| 검색어 부분 일치 · 와일드카드 이스케이프 | `AC-15` `AC-16` `AC-17` |
| 분류 필터 | `AC-18` |
| `new` 7일 · 게시판별 설정 | `AC-19` `AC-20` |
| **검색조건 유지** | `AC-23` `AC-24` |

**여기서 빠뜨리면 네 곳에서 빠진다.** 003이 002를 참조할 때 참조 대상이 없으면 003이 다시
발명하고, 005·006이 또 발명해서 **같은 목록이 네 가지 방식으로 동작**하게 된다.

**포함**: 목록(검색·정렬·페이징) · 상세(조회수·첨부 다운로드) · 등록/수정(첨부 5개) ·
삭제 · 댓글(등록·조회·삭제) · 소유자 기반 권한

**제외**: 관리자용 자유게시판 관리 화면과 **관리자의 타인 글 삭제**(→ 004) ·
카테고리(분류) 관리 화면(→ 004) · 메인 페이지의 자유게시판 영역(→ 별도) ·
댓글 수정 · 대댓글 · 좋아요 · 신고 · 임시저장

> **AC 표기에 대하여**: 001과 같은 규약을 따른다. AC에 HTTP 상태코드와 오류 코드를 적는다 —
> 상태코드와 `code`는 프레임워크가 아니라 **API 계약**이므로 구현 세부가 아니고,
> constitution 원칙 II가 요구하는 **검증 가능성**이 그것 없이는 성립하지 않는다.
> 프레임워크·라이브러리·DB 종류는 이 문서에 등장하지 않는다.

> **AC 번호**: 이 스펙 안에서 `AC-1`부터 연속이다. 001의 번호와 겹치지만
> 문서가 다르므로 혼동되지 않는다(참조할 때 `002 AC-14` 처럼 스토리를 함께 적는다).

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 목록에서 글을 찾는다 (Priority: P1) 🎯 MVP

누구나(로그인하지 않아도) 자유게시판 목록을 열어 기간·분류·검색어로 좁히고,
정렬과 개씩 보기를 바꾸고, 페이지를 넘겨 원하는 글을 찾는다.

**Why this priority**: 게시판에서 가장 많이 열리는 화면이고, **여기서 정한 규칙이 003·005·006에
그대로 복사된다.** 글이 하나도 없어도 화면은 성립하므로 다른 스토리 없이 독립 검증이 가능하다.

**Independent Test**: 글을 API로 여러 건 넣고 목록을 호출해 기본값 · 검색 · 정렬 · 페이징 ·
글 번호 · `new`가 규칙대로 나오는지 확인. 로그인 없이 전부 검증된다.

**Acceptance Scenarios**:

> 원칙 II. `AC-N` ID + `Given` 필수.

- **AC-1** 아무 조건 없이 목록을 연다 — 기본값이 적용된다
  - **Given** 최근 1달 안에 등록된 글이 12건, 1달보다 이전에 등록된 글이 3건 있고
  - **When** 검색 조건 없이 목록을 요청하면
  - **Then** 200이고 **최근 1달치 12건 중 10건**이 **등록일시 내림차순**으로 반환되며,
    응답에 **결과 총건수 12**와 **적용된 조건(기간 from/to · 개씩보기 10 · 정렬 등록일시 · 방향 내림차순)** 이 담긴다
  - *근거*: 기본값을 응답에 되돌려주지 않으면 화면이 기본값을 따로 알고 있어야 하고,
    서버와 화면 두 곳에 기본값이 생겨 언젠가 어긋난다

- **AC-2** 기간으로 좁힌다
  - **Given** `2026-03-01`·`2026-05-15`·`2026-07-20`에 등록된 글이 각각 1건 있고
  - **When** `from=2026-05-01`, `to=2026-06-30`으로 목록을 요청하면
  - **Then** 200이고 **`2026-05-15` 글 1건만** 반환된다. 경계일(`from` 당일 00:00:00 ·
    `to` 당일 23:59:59.999)에 등록된 글은 **포함된다**
  - *근거*: `to` 를 당일 00:00으로 해석하면 사용자가 "오늘까지"로 검색했을 때
    **오늘 쓴 글이 안 나온다.** 날짜만 받아 시각으로 확장하는 지점을 AC로 못박는다

- **AC-3** 기간이 1년을 넘으면 거부한다
  - **Given** 목록 요청을 준비했고
  - **When** `from`과 `to`의 간격이 **1년을 초과**하도록 요청하면
  - **Then** 400이고 `code=BOARD_SEARCH_PERIOD_TOO_LONG`. 목록은 반환되지 않는다
  - *근거*: 기간 제한은 화면 편의가 아니라 **조회 범위의 상한**이다. 제한이 없으면
    검색어 1자 + 전 기간 조회 하나로 전체 테이블을 훑는 요청을 누구나 만들 수 있다.
    화면에서 달력을 제한하는 것은 검증이 아니다(001 `FR-002`와 같은 원칙)

- **AC-4** 시작일이 종료일보다 뒤면 거부한다
  - **Given** 목록 요청을 준비했고
  - **When** `from=2026-07-31`, `to=2026-07-01`로 요청하면
  - **Then** 400이고 `code=BOARD_SEARCH_PERIOD_INVALID`
  - *근거*: 빈 목록으로 응답하면 사용자는 "글이 없다"고 읽는다. 조건이 잘못된 것과
    결과가 없는 것은 다른 사건이다

- **AC-5** 개씩 보기를 바꾼다
  - **Given** 조건에 맞는 글이 35건 있고
  - **When** `size=30`으로 1페이지를 요청하면
  - **Then** 200이고 **30건**이 반환되고 총건수는 35, 총 페이지 수는 2다

- **AC-6** 허용되지 않은 개씩 보기 값은 거부한다
  - **Given** 목록 요청을 준비했고
  - **When** `size=1000`(또는 `size=7`)으로 요청하면
  - **Then** 400이고 `code=BOARD_PAGE_SIZE_NOT_ALLOWED` (허용: 10 · 20 · 30 · 40 · 50)
  - *근거*: 임의 값을 허용하면 `size=1000000` 한 번으로 서버 메모리와 응답 크기가 터진다.
    **가장 가까운 허용값으로 깎지(clamp) 않는 이유**는 사용자가 요청한 것과 다른 결과를
    받고도 알 수 없기 때문이다 — 조용히 다르게 동작하는 것보다 거부가 낫다

- **AC-7** 정렬 기준을 바꾼다
  - **Given** 조회수가 각각 5 · 100 · 30인 글 3건이 있고
  - **When** `sort=조회수`, `order=내림차순`으로 요청하면
  - **Then** 200이고 `100 → 30 → 5` 순으로 반환된다

- **AC-8** 정렬 방향을 바꾼다
  - **Given** 등록일시가 다른 글 3건이 있고
  - **When** `sort=등록일시`, `order=오름차순`으로 요청하면
  - **Then** 200이고 **가장 오래된 글이 첫 행**이다

- **AC-9** 허용되지 않은 정렬 기준·방향은 거부한다
  - **Given** 목록 요청을 준비했고
  - **When** `sort=등록자` 또는 `sort` 에 임의 문자열을 넣어 요청하면
  - **Then** 400이고 `code=BOARD_SORT_NOT_ALLOWED`
    (허용 기준: 등록일시 · 분류 · 제목 · 조회수 / 허용 방향: 내림차순 · 오름차순)
  - *근거*: 정렬 기준을 클라이언트가 자유롭게 지정하면 **정렬 대상 지정이 그대로 질의에
    실려 들어간다.** 허용 목록 방식이 아니면 이 경로를 막을 방법이 없다

- **AC-10** 정렬 값이 같아도 순서가 결정적이다 — **페이징이 깨지지 않는다**
  - **Given** **조회수가 모두 0으로 같은** 글이 25건 있고
  - **When** `sort=조회수`, `size=10`으로 **1 · 2 · 3페이지를 차례로** 요청하면
  - **Then** 세 페이지에 나온 글의 합집합이 **25건이고 중복이 0건**이다.
    같은 요청을 반복해도 각 페이지의 결과가 **동일하다**
  - *근거*: **이것이 없으면 정렬 기능이 페이징을 망가뜨린다.** 정렬 값이 동률일 때
    반환 순서는 보장되지 않으므로, 1페이지에 나온 글이 2페이지에 또 나오고 어떤 글은
    아예 안 보인다. 조회수 정렬은 **동률이 기본값(0)** 이라 이 상황이 예외가 아니라 일상이다.
    → 모든 정렬에 **결정적인 2차 정렬 기준**이 붙어야 한다 (FR-006)

- **AC-11** 개씩 보기·정렬은 검색 버튼 없이 즉시 반영된다
  - **Given** 목록 화면에서 검색어를 입력해 검색한 결과를 보고 있고
  - **When** 정렬 기준 또는 개씩 보기를 선택만 하면(검색 버튼을 누르지 않는다)
  - **Then** **입력해 둔 검색어·기간·분류를 그대로 유지한 채** 목록이 즉시 다시 조회된다
  - *레벨*: 화면 상호작용이므로 **E2E**. `test-strategy.md` 3장 레벨 배정 기준

- **AC-12** 페이징은 10개 묶음으로 이동한다
  - **Given** 조건에 맞는 글이 250건이고 `size=10`이라 총 25페이지이고
  - **When** 목록을 요청하면
  - **Then** 응답에 **총건수 · 총페이지 수 · 현재 페이지**가 포함되어 화면이
    `<<` `<` `1~10` `>` `>>` 를 구성할 수 있고, 11페이지를 요청하면 다음 묶음(`11~20`)이 구성된다
  - *근거*: 묶음 계산을 화면이 하려면 총페이지 수가 필요하다. 응답에 총건수만 있고
    개씩보기를 화면이 따로 기억하면 두 값이 어긋날 때 페이징이 잘못 그려진다

- **AC-13** 마지막 페이지를 넘어선 요청
  - **Given** 조건에 맞는 글이 5건이고 `size=10`이라 총 1페이지이고
  - **When** `page=99`를 요청하면
  - **Then** **200이고 빈 목록**과 총건수 5가 반환된다(400이 아니다)
  - *근거*: 페이지를 보는 사이에 다른 사람이 글을 지우면 **정상적인 사용 중에** 이 상황이
    생긴다. 오류로 처리하면 사용자는 자기가 뭘 잘못했다고 읽는다

- **AC-14** 글 번호는 **결과 총건수 기준 역순**이다 — 행 번호가 아니다
  - **Given** 조건에 맞는 글이 25건이고 `size=10`이고
  - **When** **2페이지**를 요청하면
  - **Then** 첫 행의 번호가 **15**, 마지막 행이 **6**이다.
    (1페이지는 25~16, 3페이지는 5~1)
  - *근거*: 페이지마다 1부터 다시 시작하면 사용자가 "몇 번째 글"을 지목할 수 없다.
    **번호는 글에 고정된 값이 아니라 현재 결과 집합에서의 표시용 순번**이다 —
    검색 조건이나 정렬을 바꾸면 같은 글에 다른 번호가 붙는다 (판단 3)

- **AC-15** 검색어는 제목 · 내용 · 등록자에 부분 일치한다
  - **Given** 제목에만 `여행`이 든 글 A, 내용에만 든 글 B, 등록자 이름에만 든 글 C,
    어디에도 없는 글 D가 있고
  - **When** 검색어 `여행`으로 요청하면
  - **Then** 200이고 **A · B · C 3건**이 반환되고 D는 반환되지 않는다

- **AC-16** 검색어의 와일드카드 문자는 글자 그대로 취급한다
  - **Given** 제목이 `할인 50%`인 글 1건과 그 문자가 없는 글 9건이 있고
  - **When** 검색어 `%`로 요청하면
  - **Then** **`할인 50%` 1건만** 반환된다(10건 전부가 아니다).
    `_` 로 요청해도 같은 원리로 그 글자를 포함한 글만 반환된다
  - *근거*: 부분 일치 검색에서 `%`·`_`는 **아무 문자에나 일치하는 특수 문자**다.
    그대로 넘기면 사용자가 `%` 한 글자를 입력하는 것으로 **기간 제한 안의 전체 조회**가
    되어 `AC-3`으로 세운 상한이 새 나간다

- **AC-17** 검색어를 비우면 검색어 조건이 없는 것으로 본다
  - **Given** 조건에 맞는 글이 12건 있고
  - **When** 검색어를 빈 문자열 또는 공백만으로 요청하면
  - **Then** 200이고 **검색어 조건 없이** 12건 기준의 목록이 반환된다(400이 아니다)
  - *근거*: 검색어는 선택 항목이다. 화면에서 검색어를 지우고 검색 버튼을 누르는 것은
    **"조건을 해제한다"** 는 정상 동작이다

- **AC-18** 분류로 좁히고, `전체 분류`는 좁히지 않는다
  - **Given** 자유게시판 분류 `공지`·`잡담`이 있고 각각 글이 3건·4건 있고
  - **When** 분류 `잡담`으로 요청하면 **4건**이 반환되고,
    분류를 `전체 분류`(미지정)로 요청하면 **7건**이 반환된다
  - **Then** 위와 같다. 존재하지 않는 분류 식별자로 요청하면
    400이고 `code=BOARD_CATEGORY_NOT_FOUND`

- **AC-19** `new` 표시는 등록 후 7일 이내다 — 경계를 포함한다
  - **Given** 등록된 지 **6일 23시간 된 글 A**, **7일 1분 된 글 B**가 있고 임계값이 7일이고
  - **When** 목록을 요청하면
  - **Then** A는 `new=true`, B는 `new=false` 로 **서버가 판정한 값**이 응답에 담긴다
  - *근거*: 화면이 등록일시를 보고 계산하게 두면 **브라우저 시계**에 의존하고,
    임계값이 서버 설정이라 값이 두 곳에 흩어진다 (판단 5)

- **AC-20** `new` 임계값은 게시판별로 다르게 설정할 수 있다
  - **Given** 자유게시판의 `new` 임계값을 **3일**로 설정했고 등록된 지 5일 된 글이 있고
  - **When** 목록을 요청하면
  - **Then** 그 글은 `new=false` 다. **코드를 고치지 않고** 설정만 바꿔서 동작이 달라진다
  - *근거*: 요구사항이 *"게시판별로 다를 수 있게 설정 가능"* 을 명시했다. 상수로 박으면
    003·005·006이 각자 상수를 복사하고 나중에 한 곳만 고치게 된다

- **AC-21** 목록 행에 댓글 수와 첨부 여부가 함께 나온다
  - **Given** 댓글 3개·첨부 2개인 글 A, 댓글 0개·첨부 0개인 글 B가 있고
  - **When** 목록을 요청하면
  - **Then** A는 `댓글수=3` · `첨부있음=true`, B는 `댓글수=0` · `첨부있음=false` 다

- **AC-22** 목록의 댓글 수 집계가 **목록 크기에 비례해 질의를 늘리지 않는다**
  - **Given** 댓글이 달린 글이 50건 있고
  - **When** 같은 조건으로 `size=10`과 `size=50`으로 각각 목록을 요청하며
    **그 요청이 데이터베이스에 보낸 질의 수를 센다면**
  - **Then** 두 요청의 질의 수가 **같다**(목록 건수에 비례해 증가하지 않는다)
  - *근거*: **이 자리가 N+1이 실제로 발생하는 지점이다.** 글 목록 1회 + 각 글의 댓글 수
    N회가 되면 10건일 때 11회, 50건일 때 51회가 되고, **개씩 보기 50이 정상 기능이므로
    사용자가 그 상태를 정상적으로 만들 수 있다.** 성능 요구를 SC(측정 지표)가 아니라
    **AC로 쓰는 이유**는, 응답 시간(ms)으로 쓰면 실행 환경에 따라 흔들려 게이트가 되지
    못하지만 **질의 수는 결정적이라 통합 테스트에서 정확히 셀 수 있기** 때문이다.
    (첨부 여부도 같은 자리다 — 함께 검증한다) (FR-014)

- **AC-23** 상세를 보고 목록으로 돌아오면 검색조건이 유지된다
  - **Given** 검색어 `여행` · 분류 `잡담` · `size=30` · 조회수 내림차순 · **3페이지**를 보고 있고
  - **When** 어떤 글의 상세로 들어갔다가 `목록` 으로 돌아오면
  - **Then** **검색어 · 기간 · 분류 · 개씩보기 · 정렬 기준 · 정렬 방향 · 페이지 번호가
    전부 그대로**인 목록이 보인다
  - *근거*: 조건이 초기화되면 사용자는 3페이지까지 다시 찾아 들어가야 한다.
    게시판에서 가장 흔한 불만이 이것이다

- **AC-24** 글 등록을 취소하고 목록으로 돌아와도 검색조건이 유지된다
  - **Given** `AC-23`과 같은 조건의 목록에서 `글 등록`으로 들어갔고
  - **When** `"작성을 취소하시겠습니까?"` 확인 후 취소하면
  - **Then** 목록으로 돌아가고 **조건이 `AC-23`과 동일하게 유지**된다.
    글 수정 화면에서 취소한 경우도 같다

- **AC-25** 검색 결과가 없다
  - **Given** 어떤 조건에도 맞지 않는 검색어로 요청하고
  - **When** 목록을 요청하면
  - **Then** 200이고 **빈 목록 · 총건수 0 · 총페이지 0**이 반환된다(404가 아니다)

- **AC-26** 로그인하지 않아도 목록을 볼 수 있다
  - **Given** 로그인하지 않은 상태이고
  - **When** 목록을 요청하면
  - **Then** 200이고 목록이 반환된다. `글 등록` 동작만 로그인을 요구한다

### User Story 2 - 글을 읽고 첨부를 받는다 (Priority: P1)

누구나 글 상세를 열어 내용을 읽고 첨부파일을 내려받는다. 조회수가 오른다.

**Why this priority**: 목록만으로는 아무것도 읽을 수 없다. US1과 함께 **읽기 전용 서비스가
완결**되며, 여기까지가 로그인 없이 동작하는 범위다.

**Independent Test**: 글과 첨부를 API로 넣고 상세를 호출해 필드 · 조회수 증가 ·
첨부 응답 헤더를 확인. 로그인 없이 검증된다.

**Acceptance Scenarios**:

- **AC-27** 상세를 연다
  - **Given** 분류 `잡담`, 제목·내용·등록자·등록일시가 있는 글이 존재하고
  - **When** 그 글의 상세를 요청하면
  - **Then** 200이고 **분류 · 제목 · 등록일시 · 등록자 이름 · 조회수 · 내용 ·
    첨부 목록(원본 파일명 · 크기) · 댓글 목록**이 반환된다.
    **작성자의 아이디·비밀번호 등 계정 정보는 포함되지 않는다**
  - *근거*: 목록과 상세가 등록자를 **이름**으로만 보여주므로 아이디를 함께 내보내면
    화면에 쓰이지도 않는 계정 식별자가 전 사용자에게 노출된다(001 `FR-011`이 막은
    계정 열거의 우회로가 된다)

- **AC-28** 상세를 열면 조회수가 오른다
  - **Given** 조회수가 7인 글이 있고
  - **When** 상세를 한 번 요청하면
  - **Then** 응답의 조회수가 8이고, 다시 조회하면 9다
    (같은 사람이 다시 열어도 증가한다 — 판단 6)

- **AC-29** 동시에 열어도 조회수가 유실되지 않는다
  - **Given** 조회수가 0인 글이 있고
  - **When** **동시에 100번** 상세를 요청하면
  - **Then** 최종 조회수가 **정확히 100**이다
  - *근거*: "읽어서 +1 해서 쓴다"로 구현하면 두 요청이 같은 값을 읽어 **증가가 덮어써진다**
    (lost update). 조회수는 상세를 열 때마다 발생하므로 **동시 실행이 예외가 아니다**.
    이 AC는 `test-strategy.md` 5.2의 **초기화 방식(실제 커밋 경합)** 으로 검증한다

- **AC-30** 없는 글의 상세
  - **Given** 존재하지 않는 글 식별자이고
  - **When** 상세를 요청하면
  - **Then** 404이고 `code=POST_NOT_FOUND`

- **AC-31** 로그인하지 않아도 상세를 볼 수 있다
  - **Given** 로그인하지 않은 상태이고
  - **When** 상세를 요청하면
  - **Then** 200이고 내용과 댓글 목록이 반환된다. **댓글 입력 수단만 제공되지 않는다**

- **AC-32** 첨부는 **이미지라도 다운로드로 응답한다** — 브라우저에 그려지지 않는다
  - **Given** 글에 `photo.png` 가 첨부되어 있고
  - **When** 그 첨부의 다운로드를 요청하면
  - **Then** 200이고 응답이 **첨부(다운로드) 처리로 지정**되어 브라우저가
    페이지 안에 그리지 않고 파일로 저장한다 (`Content-Disposition: attachment`)
  - *근거*: **이것은 편의 문제가 아니라 보안 요구다.** 사용자가 올린 파일을 우리 도메인에서
    **브라우저가 해석하도록 응답하면 저장형 XSS**가 된다 — 확장자만 `png`이고 내용은 HTML인
    파일을 올려두면, 그것을 연 사람의 브라우저에서 **우리 출처의 스크립트로 실행**된다.
    001이 자격증명을 `httpOnly` 쿠키에 넣어 스크립트로부터 지켰는데(`AC-7`),
    **우리 출처에서 실행되는 스크립트는 쿠키를 읽지 않고도 그 사용자 권한으로 요청을 보낼 수 있어**
    그 방어가 무의미해진다. `zip` 을 허용하는 이 게시판은 특히 위험하다 —
    압축 파일의 내용은 검사할 수단이 사실상 없다(`process.md` 8.3의 *"zip 업로드 보안 검토 필요"*).
    **인라인 표시를 안전하게 하려면 별도 출처(다른 도메인)에서 서빙해야 하고, 그것은
    이 스토리의 범위를 넘는 인프라 결정**이므로 다운로드로 고정한다 (**`ADR-021`**)

- **AC-33** 첨부 응답은 브라우저의 형식 추측을 차단한다
  - **Given** 내용이 HTML인데 확장자만 `.png` 인 파일이 첨부되어 있고
  - **When** 그 첨부를 요청하면
  - **Then** 응답에 **형식 추측 금지 지시**가 포함되어(`X-Content-Type-Options: nosniff`)
    브라우저가 내용을 보고 HTML로 해석하지 않는다
  - *근거*: `AC-32`의 다운로드 지정만으로는 부족하다. 지정이 있어도 **일부 상황에서 브라우저가
    내용을 스니핑해 형식을 다시 판단**하므로 두 지시를 함께 보내야 한 겹이 뚫려도 막힌다

- **AC-34** 다른 글의 첨부 식별자로는 받을 수 없다
  - **Given** 글 A에 첨부 X가, 글 B에 첨부 Y가 있고
  - **When** **글 A의 경로로 첨부 Y**를 요청하면
  - **Then** 404이고 `code=ATTACHMENT_NOT_FOUND`
  - *근거*: 첨부 식별자만 바꿔 넣어 남의 리소스를 꺼내는 것을 막는다. 여기서는 두 글이
    모두 공개라 피해가 작지만, **같은 코드가 006(비밀글)에 복사된다** — 거기서는
    비밀번호를 통과하지 않고 내용을 꺼내는 구멍이 된다. 002에서 규칙을 세운다

- **AC-35** 내려받은 파일 이름은 올린 이름이고, 서버 저장 구조는 드러나지 않는다
  - **Given** `보고서 최종(1).zip` 이라는 한글·공백·괄호가 든 이름으로 업로드했고
  - **When** 그 첨부를 내려받으면
  - **Then** 저장되는 파일 이름이 **`보고서 최종(1).zip`** 이고,
    응답 어디에도 **서버의 저장 경로나 내부 저장 파일명이 노출되지 않는다**
  - *근거*: 저장 파일명을 업로드 파일명 그대로 쓰면 ① 같은 이름이 서로 덮어쓰고
    ② `../` 가 든 이름으로 **의도하지 않은 경로에 쓰기**가 가능해진다.
    그래서 저장 이름과 표시 이름을 분리하는데, 그러면 **표시 이름을 되돌려주는 책임**이 생긴다

### User Story 3 - 글을 쓴다 (Priority: P1)

로그인한 사용자가 분류·제목·내용을 입력하고 파일을 최대 5개 붙여 글을 등록한다.

**Why this priority**: 이것이 없으면 관리자가 데이터를 넣어주지 않는 한 게시판이 비어 있다.
US1·US2와 합쳐 **자유게시판이 서비스로 성립하는 최소 단위**다.

**Independent Test**: 로그인 후 등록을 호출해 성공 응답 → US1 목록과 US2 상세에 나타나는지 확인.
검증 위반 값은 각각 거부되는지 확인.

**Acceptance Scenarios**:

- **AC-36** 정상 등록
  - **Given** `USER` 권한으로 로그인했고 활성 분류 `잡담`이 있고
  - **When** 분류 `잡담`, 제목 `첫 글`, 내용 `안녕하세요`, 첨부 없이 등록을 요청하면
  - **Then** 201이고 글이 생성되며 **등록자는 요청을 보낸 로그인 사용자**이고 조회수는 0이다.
    목록과 상세에서 그 글이 조회된다
  - *근거*: 등록자를 **요청 본문의 값이 아니라 인증 주체에서** 가져와야 한다.
    본문으로 받으면 남의 이름으로 글을 쓸 수 있다

- **AC-37** 로그인하지 않고 등록을 시도한다
  - **Given** 로그인하지 않은 상태이고
  - **When** 글 등록을 요청하면
  - **Then** 401이고 `code=AUTH_REQUIRED`. 화면에서는 로그인 화면으로 이동하고
    **로그인 완료 후 글 등록 화면으로 복귀**하며, 이때 목록의 검색조건도 함께 보존된다
  - *근거*: 001 `FR-020`·`AC-24`(원래 목적지 복귀)와 `FR-035`·`AC-34`(목적지는 같은 출처의
    상대 경로만)를 그대로 따른다. **002가 새 규칙을 만들지 않는다**

- **AC-38** 제목 길이 경계 (100자 미만)
  - **Given** 등록 요청을 준비했고
  - **When** 제목이 **99자**면 통과하고, **100자**면 요청하면
  - **Then** 100자는 400이고 `code=POST_TITLE_LENGTH_INVALID` (허용: 1자 이상 100자 미만)

- **AC-39** 내용 길이 경계 (4000자 미만)
  - **Given** 등록 요청을 준비했고
  - **When** 내용이 **3999자**면 통과하고, **4000자**로 요청하면
  - **Then** 4000자는 400이고 `code=POST_CONTENT_LENGTH_INVALID` (허용: 1자 이상 4000자 미만)

- **AC-40** 필수 항목 누락 · 공백만 입력
  - **Given** 등록 요청을 준비했고
  - **When** 제목을 아예 보내지 않거나 **공백 문자만**(`"   "`) 넣어 요청하면
  - **Then** 400이고 `code=POST_TITLE_REQUIRED`. 내용도 같은 방식으로
    `code=POST_CONTENT_REQUIRED` 다
  - *근거*: 공백만 입력하면 길이 검증은 통과하지만 목록에 **제목 없는 행**이 생긴다.
    "필수"는 "길이 1 이상"이 아니라 "내용이 있다"이다

- **AC-41** 분류를 고르지 않으면 거부한다
  - **Given** 등록 요청을 준비했고
  - **When** 분류를 보내지 않고 요청하면
  - **Then** 400이고 `code=POST_CATEGORY_REQUIRED`

- **AC-42** 사용하지 않는(비활성) 분류로는 등록할 수 없다
  - **Given** 분류 `이벤트`가 **사용 안 함**으로 내려가 있고
  - **When** 그 분류로 등록을 요청하면
  - **Then** 400이고 `code=POST_CATEGORY_NOT_SELECTABLE`.
    **그 분류로 이미 등록된 기존 글은 그대로 조회된다**
  - *근거*: 카테고리는 **삭제하지 않고 비활성으로 내린다**(요구사항 7.2). 비활성의 의미가
    *"새 글에 더는 붙지 않는다"* 인데 서버가 막지 않으면 화면 목록에서 사라졌을 뿐
    직접 호출로 계속 붙는다. **기존 글까지 감추면 안 되는 이유**는 비활성이 삭제가 아니기
    때문이다 (판단 8)

- **AC-43** 다른 게시판의 분류로는 등록할 수 없다
  - **Given** 공지사항 전용 분류 `점검`이 있고
  - **When** 자유게시판 글에 그 분류로 등록을 요청하면
  - **Then** 400이고 `code=POST_CATEGORY_NOT_SELECTABLE`
  - *근거*: 분류가 게시판별로 분리되어 있으므로(요구사항 7.2) 식별자만 알면 넘길 수 있는
    상태를 남기면 자유게시판 목록에 공지사항 분류가 섞여 나온다

- **AC-44** 허용되지 않은 확장자의 첨부
  - **Given** 로그인 상태이고
  - **When** `malware.exe`(또는 `.svg` · `.html` · 확장자 없는 파일)를 첨부해 등록을 요청하면
  - **Then** 400이고 `code=ATTACHMENT_EXTENSION_NOT_ALLOWED` 이며
    **글도 생성되지 않는다** (허용: `jpg` · `gif` · `png` · `zip`)

- **AC-45** 첨부 크기 경계 (개당 2MB까지)
  - **Given** 로그인 상태이고
  - **When** **정확히 2MB인 파일**을 첨부하면 통과하고, **2MB를 1바이트 넘는 파일**을 첨부하면
  - **Then** 초과 파일은 400이고 `code=ATTACHMENT_SIZE_EXCEEDED`
  - *근거*: *"개당 2MB 까지"* 를 **2MB 포함**으로 읽는다. `이하`/`미만`이 갈리면
    사용자가 정확히 2MB 파일에서 실패 이유를 알 수 없다 (판단 9)

- **AC-46** 첨부 개수 초과 (최대 5개)
  - **Given** 로그인 상태이고
  - **When** 파일 **6개**를 첨부해 등록을 요청하면
  - **Then** 400이고 `code=ATTACHMENT_COUNT_EXCEEDED` 이며 글도 생성되지 않는다.
    5개는 정상 등록된다

- **AC-47** 확장자만 바꾼 파일은 통과하지 못한다
  - **Given** 실제 내용이 실행 파일인데 이름만 `image.png` 로 바꾼 파일이 있고
  - **When** 그것을 첨부해 등록을 요청하면
  - **Then** 400이고 `code=ATTACHMENT_CONTENT_MISMATCH`
  - *근거*: 확장자는 **사용자가 자유롭게 정하는 문자열**이라 검증이 아니다.
    파일의 실제 형식(선두 바이트)이 허용 형식과 일치하는지 확인해야 한다.
    ⚠️ **`zip` 은 이 검사로 "zip 형식이다"까지만 확인되고 내부 내용은 알 수 없다.**
    그 한계를 스펙에 남긴다 (**`ADR-021`**)

- **AC-48** 화면 검증을 우회한 직접 호출도 동일하게 차단된다
  - **Given** 화면을 거치지 않고 등록 요청을 직접 보낼 수 있는 상태이고
  - **When** `AC-38` ~ `AC-47`의 위반 값을 담아 직접 요청하면
  - **Then** 각 AC와 **동일한** 상태코드와 `code`로 거부된다
  - *근거*: 001 `AC-19`와 같은 종류다. 파일 검증은 특히 화면에서 하기 쉬워서
    (`accept` 속성 · 크기 확인) **서버 검증을 빼먹기 쉬운 자리**다.
    `test-strategy.md` 3장에 따라 **참조하는 AC마다 따로** 테스트를 만든다

- **AC-49** 첨부 저장이 실패하면 글도 남지 않는다
  - **Given** 첨부 3개를 붙인 등록 요청이고 **세 번째 파일 저장이 실패**하는 상황이고
  - **When** 등록을 요청하면
  - **Then** 오류가 반환되고 **글 · 앞의 두 첨부 기록이 모두 남지 않는다**.
    목록에 그 글이 보이지 않는다
  - *근거*: 글은 저장되고 첨부만 빠지면 사용자는 **첨부가 사라진 것을 모른 채** 글을 올린 것이
    된다. 되돌릴 수 없는 상태다

- **AC-50** 작성 취소
  - **Given** 등록 화면에서 내용을 입력한 상태이고
  - **When** 취소를 누르면
  - **Then** `"작성을 취소하시겠습니까?"` 확인을 거치고, 확인하면 목록으로 이동하며
    **글이 생성되지 않는다.** 취소하지 않으면 작성 화면에 머문다

### User Story 4 - 내 글을 고치고 지운다 (Priority: P2)

작성자 본인만 자기 글을 수정하고 삭제한다. 수정 화면에서 기존 첨부를 받거나 개별 삭제한다.

**Why this priority**: US1~US3이 있어야 검증할 수 있다. 그리고 **소유자 검증이 002의 핵심
보안 요구**다 — 여기서 세운 규칙이 005·006에 복사된다.

**Independent Test**: 사용자 A와 B로 각각 로그인해 A의 글을 A가 고치면 되고 B가 고치면
막히는지 확인.

**Acceptance Scenarios**:

- **AC-51** 본인 글 수정
  - **Given** 사용자 A가 쓴 글이 있고 A로 로그인했고
  - **When** 제목과 내용을 바꿔 수정을 요청하면
  - **Then** 200이고 값이 바뀌며 **등록자와 등록일시는 바뀌지 않는다**.
    관리자 화면 경로에서는 `"정말로 수정 하시겠습니까?"` 확인 후 진행한다

- **AC-52** 남의 글 수정은 서버가 막는다
  - **Given** 사용자 A가 쓴 글이 있고 **사용자 B**로 로그인했고
  - **When** 그 글의 수정을 요청하면
  - **Then** **403**이고 `code=POST_NOT_OWNER`. 글의 내용은 변경되지 않는다
  - *근거 (403인가 404인가 — 의도적 판단)*: constitution 원칙 IV는 *"남의 **비공개** 리소스
    요청은 403이 아니라 404"* 라고 규정한다. **자유게시판의 글은 공개다** — `AC-26`·`AC-31`이
    로그인 없이도 목록과 상세를 볼 수 있게 했으므로 **존재 여부는 이미 모두에게 공개된
    정보**이고, 404로 감출 대상이 없다. 없는 것처럼 응답하면 사용자는 "글이 지워졌나"로
    오해한다. **006 비밀글은 반대다** — 거기서는 존재 자체가 비공개이므로 404가 맞다 (판단 10)

- **AC-53** 화면에 수정 버튼이 없어도 서버가 막는다
  - **Given** 사용자 B로 로그인했고 A의 글 상세에 **수정·삭제 버튼이 보이지 않고**
  - **When** 그 기능을 직접 요청하면
  - **Then** `AC-52`와 동일하게 403 `POST_NOT_OWNER` 다
  - *근거*: 001 `AC-26`과 같은 종류의 AC다. **화면에서 버튼을 숨기는 것은 권한 검증이 아니다**
    (001 `FR-019`). 이 AC가 없으면 "버튼이 안 보인다"를 검증으로 착각한 구현이 통과한다

- **AC-54** 관리자도 남의 글을 수정할 수 없다
  - **Given** `ADMIN` 권한으로 로그인했고 사용자 A가 쓴 글이 있고
  - **When** 그 글의 수정을 요청하면
  - **Then** 403이고 `code=POST_NOT_OWNER`
  - *근거*: 권한 규칙은 *"수정·삭제는 **본인 글만**"* 이고 관리자 예외는 **댓글 삭제에만**
    있다. 관리자가 남의 글 본문을 고칠 수 있으면 작성자가 쓰지 않은 내용이 그의 이름으로
    남는다. 관리자의 **글 삭제(부적절한 글 처리)** 는 관리자 화면 스토리(004)에서 별도
    경로로 다룬다 — 002에 슬쩍 넣지 않는다 (판단 11)

- **AC-55** 수정 화면에서 기존 첨부를 받고 개별로 뺀다
  - **Given** 첨부 3개가 달린 본인 글의 수정 화면이고
  - **When** 기존 첨부 하나를 내려받고, 다른 하나를 삭제 표시한 뒤 저장하면
  - **Then** 200이고 삭제 표시한 첨부만 사라지고 나머지 2개는 유지된다.
    내려받기는 `AC-32`·`AC-33`과 동일하게 다운로드로 응답한다

- **AC-56** 첨부 개수 제한은 **저장 후 최종 상태** 기준이다
  - **Given** 첨부 4개가 달린 본인 글이 있고
  - **When** 그중 2개를 삭제 표시하고 새 파일 3개를 추가해 저장하면 **최종 5개**라 통과하고,
    아무것도 삭제하지 않고 새 파일 2개만 추가하면 **최종 6개**라
  - **Then** 후자는 400이고 `code=ATTACHMENT_COUNT_EXCEEDED` 이며 **아무 변경도 적용되지 않는다**
  - *근거*: "추가하는 파일 수"로 세면 4+2를 막지 못하고, "기존 수"로 세면 정상적인 교체를
    막는다. 제한의 대상은 **저장된 결과**다

- **AC-57** 본인 글 삭제
  - **Given** 사용자 A가 쓴 글이 있고 A로 로그인했고
  - **When** `"정말로 삭제 하시겠습니까"` 확인 후 삭제를 요청하면
  - **Then** 200이고 목록에서 사라지며 상세는 `AC-59`처럼 응답한다

- **AC-58** 남의 글 삭제는 서버가 막는다
  - **Given** 사용자 A의 글이 있고 사용자 B로 로그인했고
  - **When** 삭제를 요청하면
  - **Then** 403이고 `code=POST_NOT_OWNER`. 글은 그대로 남는다

- **AC-59** 삭제된 글의 상세
  - **Given** 삭제된 글의 식별자이고
  - **When** 상세를 요청하면
  - **Then** 404이고 `code=POST_NOT_FOUND` — 존재한 적 없는 글(`AC-30`)과 **응답이 같다**
  - *근거*: 응답이 다르면 "이 번호에 글이 있었다"는 사실이 남는다. 그리고 목록에서
    사라진 글을 삭제/미존재로 구분해 봐야 사용자가 할 수 있는 일이 없다

- **AC-60** 글을 지우면 댓글과 첨부가 남지 않는다
  - **Given** 댓글 3개 · 첨부 2개가 달린 본인 글이 있고
  - **When** 그 글을 삭제하면
  - **Then** 그 글의 **댓글 기록과 첨부 기록이 남지 않는다.**
    다른 글의 댓글·첨부는 영향받지 않는다
  - *근거*: 남으면 어느 글에도 속하지 않는 데이터가 쌓이고, 나중에 같은 식별자가 재사용되면
    **엉뚱한 글에 남의 댓글이 붙는다**

- **AC-61** 두 사람이 같은 글을 동시에 수정한다
  - **Given** 사용자 A가 자기 글의 수정 화면을 연 상태에서, **같은 계정으로 다른 창에서**
    같은 글을 먼저 수정해 저장했고
  - **When** 먼저 연 창에서 저장하면
  - **Then** **나중 요청이 반영되고 데이터가 깨지지 않는다**(내용 일부만 섞인 상태가 되지 않는다).
    첨부 개수 제한 등 모든 검증은 **그 시점의 실제 상태**를 기준으로 다시 판정된다
  - *근거*: 자유게시판 글은 **작성자 본인만 수정**하므로 서로 다른 사람이 경합할 일이 없고
    (`AC-52`·`AC-54`), 같은 사람의 두 창은 드물다. 따라서 **충돌 감지(낙관적 잠금)를 넣지 않고
    나중 저장이 이기게 둔다.** 다만 *"검증을 요청 시점의 실제 상태로 다시 한다"* 는 지켜야
    한다 — 화면이 들고 온 옛 상태(첨부 4개)를 믿고 계산하면 `AC-56`의 상한이 새 나간다 (판단 12)

- **AC-62** 삭제 확인
  - **Given** 상세 화면에서 삭제를 누르고
  - **When** 확인 창에서 취소하면
  - **Then** 삭제되지 않는다. 확인하면 `AC-57`대로 삭제된다

### User Story 5 - 댓글로 이야기한다 (Priority: P2)

로그인한 사용자가 글에 댓글을 단다. 댓글 목록은 누구나 보고, 삭제는 본인 또는 관리자가 한다.

**Why this priority**: 글 없이 댓글이 성립하지 않으므로 US2 다음이다.
**게시판 4종 중 댓글이 있는 것은 자유게시판뿐**이라 다른 스토리로 확산되지 않는다 —
그래서 P2로 내렸다.

**Independent Test**: 글 하나를 API로 넣고 사용자 A·B·관리자로 각각 댓글 등록·삭제를 호출해
허용/거부를 확인.

**Acceptance Scenarios**:

- **AC-63** 댓글 목록은 로그인하지 않아도 보인다
  - **Given** 댓글 2개가 달린 글이 있고 로그인하지 않은 상태이고
  - **When** 상세를 요청하면
  - **Then** 200이고 댓글 2개가 **작성자 이름 · 작성일시 · 내용**과 함께 반환된다.
    **댓글 입력 수단은 제공되지 않는다**

- **AC-64** 로그인하지 않고 댓글을 등록하려 하면 막힌다
  - **Given** 로그인하지 않은 상태이고
  - **When** 댓글 등록을 직접 요청하면
  - **Then** 401이고 `code=AUTH_REQUIRED`. 댓글이 생성되지 않는다
  - *근거*: 입력 폼을 숨기는 것은 검증이 아니다(001 `FR-019`). `AC-63`이 폼을 숨기고
    이 AC가 서버에서 막는다 — **한 쌍이어야 성립한다**

- **AC-65** 댓글 등록
  - **Given** `USER` 권한으로 로그인했고 글이 존재하고
  - **When** 내용 `좋은 글이네요`로 댓글 등록을 요청하면
  - **Then** 201이고 댓글이 생성되며 **작성자는 요청을 보낸 로그인 사용자**다.
    상세를 다시 열면 그 댓글이 **작성일시 오름차순**(오래된 것부터)으로 보인다
  - *근거*: 댓글은 대화의 흐름이라 시간 순으로 읽는다. 목록의 기본 정렬(내림차순)과
    다르므로 명시한다 (판단 13)

- **AC-66** 댓글 내용 검증
  - **Given** 로그인 상태이고
  - **When** 내용을 비우거나 공백만으로 요청하면 400이고 `code=COMMENT_CONTENT_REQUIRED`,
    **1000자를 초과**해 요청하면
  - **Then** 400이고 `code=COMMENT_CONTENT_LENGTH_INVALID` (허용: 1자 이상 1000자 이하)
  - *근거*: 댓글 길이 제한은 요구사항에 없다. **제한이 없으면 상한이 없다**는 뜻이고,
    본문(4000자)보다 긴 댓글이 달릴 수 있다. 본문보다 작은 값으로 정한다 (판단 14)

- **AC-67** 본인 댓글 삭제
  - **Given** 사용자 A가 단 댓글이 있고 A로 로그인했고
  - **When** 그 댓글의 삭제를 요청하면
  - **Then** 200이고 댓글이 사라지며 상세의 댓글 목록에서 빠진다

- **AC-68** 남의 댓글은 일반 사용자가 지울 수 없다 — 서버가 막는다
  - **Given** 사용자 A가 단 댓글이 있고 **사용자 B**로 로그인했고 화면에 삭제 버튼이 보이지 않고
  - **When** 그 댓글의 삭제를 **직접 요청**하면
  - **Then** 403이고 `code=COMMENT_NOT_DELETABLE`. 댓글은 그대로 남는다
  - *근거*: 001 `AC-26`과 같은 종류. 버튼 숨김은 검증이 아니다

- **AC-69** 관리자는 남의 댓글을 지울 수 있다
  - **Given** 사용자 A가 단 댓글이 있고 **`ADMIN` 권한**으로 로그인했고
  - **When** 그 댓글의 삭제를 요청하면
  - **Then** 200이고 댓글이 사라진다
  - *근거*: 권한 규칙에서 **관리자 예외는 댓글 삭제에만** 있다(`AC-54`와 대비된다).
    부적절한 댓글을 작성자만 지울 수 있으면 방치된다

- **AC-70** 지워진 글에는 댓글을 달 수 없다
  - **Given** 상세 화면을 열어 둔 사이에 그 글이 삭제되었고 로그인 상태이고
  - **When** 댓글 등록을 요청하면
  - **Then** 404이고 `code=POST_NOT_FOUND`. **어느 글에도 속하지 않는 댓글이 생기지 않는다**

- **AC-71** 목록의 댓글 수가 실제와 일치한다
  - **Given** 댓글 0개인 글이 목록에 있고
  - **When** 댓글 2개를 등록한 뒤 1개를 삭제하고 목록을 다시 요청하면
  - **Then** 그 글의 댓글 수가 **1**이다
  - *근거*: 댓글 수를 따로 저장해 두는 방식(비정규화)을 고르면 **등록·삭제·글 삭제
    세 경로에서 전부 갱신**해야 하고 한 곳만 빠져도 숫자가 영구히 틀어진다.
    `AC-22`(질의 수 제한)와 이 AC가 **함께 걸려 있어야** 어느 구현을 골라도 안전하다

### Edge Cases

**경계값**

- **정확히 임계값**: 제목 99자/100자 · 내용 3999자/4000자 · 첨부 2MB 정확히 ·
  첨부 5개 정확히 · `new` 7일 정각 · 기간 정확히 1년 — 전부 AC로 고정했다
  (`AC-38` `AC-39` `AC-45` `AC-46` `AC-19` `AC-3`)
- **0바이트 파일**: 크기 상한은 통과하지만 내용이 없다. **거부한다** —
  형식 검증(`AC-47`)이 선두 바이트를 읽을 수 없어 어차피 실패하며,
  통과시키면 목록에 첨부 아이콘만 뜨고 받을 것이 없는 글이 생긴다
- **파일명이 아주 긴 첨부 / 확장자가 여러 개인 파일**(`a.png.exe`): 판정은
  **마지막 확장자**로 하고, 내용 검증(`AC-47`)이 최종 방어선이다
- **총건수가 개씩보기의 정확한 배수**(20건 · `size=10`): 총페이지는 2이고 3페이지는
  `AC-13`대로 빈 목록이다. 3페이지가 되는 구현(off-by-one)을 이 케이스가 잡는다

**동시성**

- **동시 상세 조회 → 조회수 유실**: `AC-29`로 고정. `test-strategy.md` 5.2의
  **초기화 방식**을 쓰는 테스트다(롤백 방식으로는 커밋 경합이 일어나지 않는다)
- **읽는 사이에 글이 삭제됨**: 상세 조회 중 삭제 → `AC-59`(404) ·
  댓글 등록 중 삭제 → `AC-70`(404) · 수정 저장 중 삭제 → 404
- **페이지를 넘기는 사이에 새 글이 등록됨**: 오프셋 방식 페이징의 구조적 한계로
  2페이지에서 **1페이지에 있던 글이 다시 보이거나 한 건이 건너뛰어진다.**
  글이 자주 등록되는 게시판이 아니므로 감수하고, 커서 방식 전환은 **`ADR-012`**로 남긴다
- **같은 글을 두 창에서 동시에 수정**: `AC-61` — 나중 저장이 이기되 검증은 실제 상태로 다시 한다
- **첨부를 삭제하는 동시에 다른 사람이 그 첨부를 내려받는 중**: 내려받기가 실패할 수 있다.
  이미 시작된 다운로드가 끊기는 것은 허용하고, 새 요청은 `AC-34`대로 404다

**빈 값 · 없는 상태**

- **분류가 하나도 등록되지 않은 상태에서 글 등록**: 분류가 필수(`AC-41`)이므로
  **글을 쓸 수 없다.** 004(카테고리 관리)가 나오기 전에는 초기 분류를 데이터로 넣어 둔다
  (001이 사용불가 아이디를 데이터로 넣은 것과 같은 방식)
- **글이 한 건도 없는 게시판**: `AC-25`(빈 목록 200)
- **기본 기간이 1달이라 첫 화면에 아무것도 안 보이는 경우**: 1달 넘게 새 글이 없으면
  기본 조건으로는 빈 목록이 된다. **규칙대로가 맞지만 사용자에게는 "게시판이 비었다"로 보인다**
  → 빈 목록일 때 화면이 *"최근 1개월 내 등록된 글이 없습니다"* 처럼 **적용된 기간을 알려야**
  한다(`AC-1`이 적용된 조건을 응답에 담는 이유)
- **첨부 0개 · 댓글 0개**: 정상. `AC-21`이 `false`/`0`으로 고정

**권한 경계**

- **로그인 후 권한이 바뀐 상태**(`USER` → `ADMIN` 승격 등): 자격증명 안의 권한 정보가
  갱신되기 전까지는 옛 권한으로 판정된다. 001 Edge Cases의 *"로그아웃 후 남은 Access
  자격증명"* 과 같은 성질이며 최대 Access 수명만큼 지연된다
- **작성자 계정이 사라진 글**: 001에 회원 탈퇴가 없으므로 발생하지 않는다.
  탈퇴가 생기면 **글의 등록자 표시와 소유자 판정을 어떻게 할지 다시 정해야 한다**
- **자기 글에 자기가 댓글**: 허용한다. 막을 이유가 없다
- **관리자가 자기 글 수정**: 본인이므로 `AC-51`대로 허용된다.
  `AC-54`가 막는 것은 **남의** 글이다

**보안 경계**

- **첨부 식별자 바꿔치기**: `AC-34`
- **저장형 XSS(파일)**: `AC-32` `AC-33` `AC-47`
- **본문에 스크립트를 넣은 글**: 내용은 **일반 텍스트로 저장하고 화면에서 그대로 렌더하지
  않는다.** 서식 편집기(HTML 저장)를 도입하면 그 순간 정화(sanitize) 규칙이 필요해진다
  → **`ADR-014`**
- **경로 조작 파일명**(`../../etc/passwd`): `AC-35`(저장 이름과 표시 이름 분리)
- **`zip` 안의 내용**: 검사할 수단이 없다. 한계를 명시하고 **`ADR-021`**으로 남긴다

## Requirements *(mandatory)*

### Functional Requirements

> 각 FR에 근거를 한 줄 붙인다. **AC가 없는 FR은 없다** — FR → AC 매핑 표로 확인한다.

**목록 · 검색 · 정렬 · 페이징 (공통 규칙 — 003 · 005 · 006이 참조한다)**

- **FR-001**: 시스템은 자유게시판 글 목록을 **번호 · 분류 · 제목 · 댓글 수 · `new` 여부 ·
  첨부 여부 · 조회수 · 등록일시 · 등록자 이름**으로 제공해야 한다(MUST).
  *근거*: 목록에서 글을 고르는 데 필요한 정보가 이것이고, 여기 없는 값을 화면이 따로
  조회하면 목록 한 번에 요청이 여러 번 붙는다.
- **FR-002**: 목록은 **등록일시 기간 검색**을 제공하고, 기간을 지정하지 않으면 **최근 1개월**을
  적용해야 한다(MUST). 적용된 기간을 응답에 포함해야 한다(MUST).
  *근거*: 기본값이 응답에 없으면 화면이 같은 기본값을 따로 갖게 되고 두 곳이 어긋난다.
- **FR-003**: 시스템은 검색 기간이 **1년을 초과**하는 요청을 거부해야 하며(MUST NOT 허용),
  시작일이 종료일보다 늦은 요청도 거부해야 한다(MUST).
  *근거*: 조회 범위의 상한이 없으면 요청 하나로 전체 테이블을 훑을 수 있다.
- **FR-004**: 개씩 보기는 **10 · 20 · 30 · 40 · 50**만 허용하고 기본값은 10이어야 한다(MUST).
  그 밖의 값은 거부해야 하며 임의 값으로 보정해서는 안 된다(MUST NOT).
  *근거*: 임의 값을 허용하면 한 번의 요청으로 서버 메모리와 응답 크기를 고갈시킬 수 있다.
- **FR-005**: 정렬 기준은 **등록일시(기본) · 분류 · 제목 · 조회수**, 방향은
  **내림차순(기본) · 오름차순**만 허용해야 한다(MUST). 그 밖의 값은 거부해야 한다(MUST).
  *근거*: 정렬 대상을 클라이언트가 자유 문자열로 지정하면 그것이 그대로 질의에 실린다.
- **FR-006**: 모든 정렬은 **결정적**이어야 한다(MUST) — 정렬 값이 같은 행들의 순서가
  요청마다 달라져서는 안 된다(MUST NOT).
  *근거*: 동률에서 순서가 흔들리면 페이지 사이에 **중복과 누락**이 생긴다. 조회수 정렬은
  동률(0)이 기본 상태라 예외가 아니라 일상이다.
- **FR-007**: 개씩 보기와 정렬 변경은 **다른 검색 조건을 유지한 채 즉시 반영**되어야 한다(MUST).
  *근거*: 다시 검색 버튼을 눌러야 하면 사용자는 조건이 초기화된 줄 알고 다시 입력한다.
- **FR-008**: 목록 응답은 **총건수 · 총페이지 수 · 현재 페이지**를 포함해야 한다(MUST).
  범위를 벗어난 페이지 요청에는 **빈 목록과 200**으로 응답해야 한다(MUST).
  *근거*: 페이지 묶음(`<<` `<` 1~10 `>` `>>`)을 그리려면 총페이지가 필요하다.
  범위 초과는 정상 사용 중에 발생하므로 오류가 아니다.
- **FR-009**: 목록의 글 번호는 **결과 총건수 기준 역순 일련번호**여야 한다(MUST).
  페이지마다 1부터 다시 시작해서는 안 된다(MUST NOT).
  *근거*: 페이지마다 1부터면 사용자가 특정 글을 번호로 지목할 수 없다.
- **FR-010**: 검색어는 **제목 · 내용 · 등록자 이름**에 부분 일치해야 하며(MUST),
  검색어에 포함된 **패턴 특수문자를 글자 그대로** 취급해야 한다(MUST).
  검색어가 비었으면 조건 없음으로 처리해야 한다(MUST).
  *근거*: 특수문자를 그대로 넘기면 한 글자 입력으로 전체 조회가 되어 `FR-003`의 상한이 새 나간다.
- **FR-011**: 목록은 **해당 게시판의 분류**로 좁힐 수 있어야 하며, 분류 미지정은
  `전체 분류`로 동작해야 한다(MUST). 존재하지 않는 분류는 거부해야 한다(MUST).
  *근거*: 분류는 게시판별로 분리되어 있으므로 다른 게시판 분류가 섞이면 결과가 뒤섞인다.
- **FR-012**: `new` 표시 여부는 **서버가 판정해 응답에 담아야** 하며(MUST),
  기준 일수는 **게시판별로 설정 가능**해야 한다(MUST). 코드에 상수로 고정해서는 안 된다(MUST NOT).
  *근거*: 화면이 계산하면 브라우저 시계에 의존하고, 상수로 박으면 게시판 4종이 각자
  복사해 한 곳만 고치게 된다.
- **FR-013**: 상세 이동 후 목록 복귀, 등록/수정 취소 후 목록 복귀 시
  **직전 검색조건(기간 · 분류 · 검색어 · 개씩보기 · 정렬 기준 · 정렬 방향 · 페이지)** 이
  유지되어야 한다(MUST).
  *근거*: 초기화되면 사용자가 3페이지까지 다시 찾아 들어가야 한다.
- **FR-014**: 목록 조회가 데이터베이스에 보내는 **질의 수가 목록 건수에 비례해서는
  안 된다**(MUST NOT).
  *근거*: 댓글 수·첨부 여부를 행마다 따로 조회하면 개씩보기 50에서 질의가 51회가 되고,
  **그 상태를 사용자가 정상 기능으로 만들 수 있다.**

**상세 · 조회수**

- **FR-015**: 시스템은 글 상세로 **분류 · 제목 · 등록일시 · 등록자 이름 · 조회수 · 내용 ·
  첨부 목록 · 댓글 목록**을 제공해야 한다(MUST). 작성자의 계정 식별자(아이디)를
  포함해서는 안 된다(MUST NOT).
  *근거*: 화면에 쓰이지 않는 계정 식별자를 내보내면 001이 막은 계정 열거의 우회로가 된다.
- **FR-016**: 상세 조회 시 조회수를 **1 증가**시켜야 하며(MUST), 동시 조회에서
  증가가 유실되어서는 안 된다(MUST NOT).
  *근거*: 중복 방지 규칙은 정해진 바 없어 단순 증가로 둔다(판단 6). 다만 "읽고 더해서 쓰기"로
  구현하면 동시 요청에서 증가가 덮어써지고, 상세 조회는 동시성이 일상이다.
- **FR-017**: 목록 조회 · 상세 조회 · 댓글 목록 조회는 **인증을 요구해서는 안 된다**(MUST NOT).
  *근거*: 요구사항 권한 규칙의 *"목록·상세 조회는 누구나"* 다. 로그인을 요구하면
  검색 엔진과 처음 방문한 사람이 아무것도 볼 수 없다.
- **FR-018**: 존재하지 않거나 삭제된 글·첨부·댓글에 대한 요청은 **404와 동일한 응답**으로
  처리해야 한다(MUST) — 삭제된 것과 존재한 적 없는 것을 구분해서는 안 된다(MUST NOT).
  *근거*: 구분하면 "이 번호에 글이 있었다"가 남고, 구분해 봐야 사용자가 할 수 있는 일이 없다.

**등록 · 수정 · 삭제**

- **FR-019**: 글 등록은 **로그인한 사용자만** 가능해야 하며(MUST), 등록자는 **요청 본문이
  아니라 인증 주체**에서 결정해야 한다(MUST).
  *근거*: 본문으로 받으면 남의 이름으로 글을 쓸 수 있다.
- **FR-020**: 시스템은 제목을 **1자 이상 100자 미만**, 내용을 **1자 이상 4000자 미만**으로
  검증해야 하며(MUST), 공백 문자만으로 이루어진 값을 통과시켜서는 안 된다(MUST NOT).
  *근거*: 공백만은 길이 검증을 통과하지만 목록에 제목 없는 행을 만든다.
- **FR-021**: 글의 분류는 **필수**이며, **해당 게시판에 속하고 사용 중(활성)인 분류**만
  선택할 수 있어야 한다(MUST). 비활성 분류로 새 글을 등록하는 것을 금지하되(MUST NOT),
  이미 그 분류로 등록된 글의 조회를 막아서는 안 된다(MUST NOT).
  *근거*: 카테고리는 삭제 대신 비활성으로 내리므로(요구사항 7.2) 비활성의 의미가
  *"새 글에 더는 붙지 않는다"* 이고, 서버가 막지 않으면 직접 호출로 계속 붙는다.
- **FR-022**: 글의 **수정과 삭제는 작성자 본인만** 가능해야 하며, **서버가 소유자를
  확인**해야 한다(MUST). 화면에서 버튼을 숨기는 것을 검증으로 간주해서는 안 된다(MUST NOT).
  *근거*: 001 `FR-019`·`AC-26`이 그대로 적용된다. 버튼 숨김은 직접 호출로 전부 우회된다.
- **FR-023**: `ADMIN` 권한도 **타인의 글을 수정할 수 없어야** 한다(MUST NOT).
  *근거*: 권한 규칙의 관리자 예외는 **댓글 삭제에만** 있다. 관리자가 남의 본문을 고칠 수
  있으면 작성자가 쓰지 않은 내용이 그의 이름으로 남는다. 관리자의 글 삭제는 004에서 다룬다.
  *(통합 단계 범위 한정 2026-07-31 — **이 MUST NOT은 "사용자가 쓰는 게시판"에만 적용된다.**
  003 `FR-027`은 관리자에게 **다른 관리자가 쓴 공지의 수정**을 허용하며, 그 근거는
  *"공지는 조직의 공식 게시물이고 작성 관리자가 부재하면 오타 하나도 못 고친다"* 이다.
  두 규칙은 모순이 아니라 **게시판의 성격이 다른 것**이지만, 그 경계를 어느 문서도 적지
  않아 `FR-023`이 전역 금지로 읽혔다. 경계 규칙은 **`ADR-017`(관리자 권한 모델)** 이 확정한다.)*
- **FR-024**: 작성 취소 · 삭제 · (관리자 화면의) 등록·수정은 **확인 절차**를 거쳐야 한다(MUST).
  *근거*: 되돌릴 수 없는 동작(삭제)과 입력을 버리는 동작(취소)에 확인이 없으면 오조작이 곧 손실이다.
- **FR-025**: 글과 첨부의 저장은 **전부 성공하거나 전부 실패**해야 한다(MUST).
  일부만 반영된 상태를 남겨서는 안 된다(MUST NOT). 모든 검증은 **요청 시점의 실제 상태**를
  기준으로 판정해야 한다(MUST).
  *근거*: 글만 저장되고 첨부가 빠지면 사용자는 그것을 모른 채 글을 올린 것이 된다.
  화면이 들고 온 옛 상태를 믿고 계산하면 `FR-028`의 상한이 새 나간다.

**첨부**

- **FR-026**: 첨부는 **`jpg` · `gif` · `png` · `zip`** 만 허용해야 하며, 그 밖의 확장자를
  거부해야 한다(MUST). 검증은 **서버에서** 한다(MUST).
  *근거*: 화면의 파일 선택 제한은 직접 호출로 통과된다.
- **FR-027**: 첨부는 **개당 2MB 이하**여야 한다(MUST). 초과를 거부해야 한다(MUST).
  *근거*: 상한이 없으면 저장 공간과 응답 시간이 사용자 손에 달린다.
- **FR-028**: 한 글의 첨부는 **최대 5개**여야 하며, 개수는 **저장 후 최종 상태** 기준으로
  판정해야 한다(MUST).
  *근거*: "추가하는 수"로 세면 기존 4개 + 추가 2개를 막지 못하고, "기존 수"로 세면
  정상적인 교체를 막는다.
- **FR-029**: 시스템은 첨부의 **실제 내용이 허용 형식과 일치하는지** 확인해야 한다(MUST).
  확장자만으로 형식을 판정해서는 안 된다(MUST NOT).
  *근거*: 확장자는 사용자가 정하는 문자열이라 검증이 아니다. 다만 `zip` 은 이 검사로
  "zip 형식이다"까지만 확인되고 내부 내용은 알 수 없다 — 한계를 명시한다.
- **FR-030**: 첨부 응답은 **이미지 형식이라도 다운로드로 처리**해야 하며(MUST),
  브라우저가 페이지 안에 렌더하도록 응답해서는 안 된다(MUST NOT).
  응답에 **형식 추측 금지 지시**를 포함해야 한다(MUST).
  *근거*: 우리 출처에서 사용자 업로드 파일이 해석되면 **저장형 XSS**가 되고,
  우리 출처에서 실행되는 스크립트는 `httpOnly` 쿠키를 읽지 않고도 그 사용자 권한으로
  요청을 보낼 수 있어 001이 세운 방어가 무의미해진다.
- **FR-031**: 첨부 다운로드는 **그 첨부가 요청 경로의 글에 속하는지** 확인해야 한다(MUST).
  *근거*: 식별자만 바꿔 남의 리소스를 꺼내는 경로를 막는다. 같은 코드가 006(비밀글)에
  복사되며 거기서는 비밀번호를 우회하는 구멍이 된다.
- **FR-032**: 시스템은 **저장 파일명과 표시 파일명을 분리**해야 하며(MUST),
  업로드된 이름을 저장 경로에 그대로 사용해서는 안 된다(MUST NOT).
  다운로드 시 **원본 파일명**으로 저장되어야 한다(MUST).
  *근거*: 같은 이름끼리 덮어쓰고, `../` 가 든 이름은 의도하지 않은 경로에 쓴다.
- **FR-033**: 수정 화면에서 **기존 첨부를 내려받고 개별로 삭제**할 수 있어야 한다(MUST).
  *근거*: 개별 삭제가 없으면 파일 하나를 바꾸려고 글을 지웠다 다시 써야 한다.
- **FR-034**: 글이 삭제되면 그 글의 **첨부 기록이 남아서는 안 된다**(MUST NOT).
  *근거*: 어느 글에도 속하지 않는 데이터가 쌓이고, 식별자가 재사용되면 엉뚱한 글에 붙는다.

**댓글**

- **FR-035**: 댓글 목록은 **누구나** 조회할 수 있어야 하며, **작성자 이름 · 작성일시 · 내용**을
  포함해야 한다(MUST).
  *근거*: 상세를 누구나 보는데 댓글만 가리면 글의 절반이 비어 보인다.
- **FR-036**: 댓글 등록은 **로그인한 사용자만** 가능해야 하며(MUST), 작성자는
  **인증 주체**에서 결정해야 한다(MUST).
  *근거*: 입력 폼을 숨기는 것은 검증이 아니다(001 `FR-019`).
- **FR-037**: 댓글 내용은 **필수**이며 **1000자 이하**여야 한다(MUST).
  공백만으로 이루어진 값을 통과시켜서는 안 된다(MUST NOT).
  *근거*: 요구사항에 길이 규정이 없어 상한이 없는 상태였다. 본문(4000자)보다 긴 댓글이
  달릴 수 있으므로 본문보다 작은 값으로 정한다.
- **FR-038**: 댓글 삭제는 **작성자 본인 또는 `ADMIN` 권한**만 가능해야 하며,
  **서버가 확인**해야 한다(MUST).
  *근거*: 부적절한 댓글을 작성자만 지울 수 있으면 방치된다. 글 수정과 달리 여기에만
  관리자 예외가 있다.
- **FR-039**: 글이 삭제되면 그 글의 **댓글이 남아서는 안 된다**(MUST NOT).
  *근거*: `FR-034`와 같다 — 고아 데이터와 식별자 재사용 사고를 막는다.
- **FR-040**: 목록에 표시되는 댓글 수는 **실제 댓글 수와 항상 일치**해야 한다(MUST).
  *근거*: 별도로 세어 저장하는 방식을 고르면 등록·삭제·글 삭제 세 경로를 전부 갱신해야
  하고 한 곳만 빠져도 숫자가 영구히 틀어진다.

**공통 — 001에서 세운 규범의 적용**

- **FR-041**: 002의 **모든 입력 검증과 권한 검증은 서버에서** 이루어져야 한다(MUST).
  화면 검증은 편의이며 대체가 아니다(001 `FR-002`·`FR-019`).
  *근거*: 화면 검증만 있으면 직접 호출로 전부 우회된다.
- **FR-042**: 002의 모든 오류 응답은 **프로젝트 공통 오류 형식**을 따르고
  기계가 판별 가능한 `code`와 추적 식별자를 포함해야 한다(MUST).
  내부 정보(예외 메시지 · 스택 추적 · 데이터 구조 · **파일 저장 경로**)를 노출해서는
  안 된다(MUST NOT) — 001 `FR-024`·`FR-025`.
  *근거*: 첨부를 다루는 002는 **파일 경로가 오류 메시지로 새기 쉬운 새 누출 경로**를 만든다.
- **FR-043**: 로그인이 필요한 동작(글 등록 · 수정 · 삭제 · 댓글 등록·삭제)에 미인증으로
  접근하면 **로그인 후 원래 목적지로 복귀**시켜야 한다(MUST). 복귀 목적지는
  **같은 출처의 상대 경로만** 허용해야 한다(001 `FR-020`·`FR-035`).
  *근거*: 002가 새 규칙을 만들지 않는다. 001이 정한 것을 그대로 쓴다.
- **FR-044**: 목록 조회 파라미터(개씩보기 · 정렬 기준 · 정렬 방향 · 분류)는
  **허용 목록 방식**으로 검증해야 하며, 허용 목록에 없는 값을 무시하거나 보정하지 말고
  **거부**해야 한다(MUST).
  *근거*: 조용히 보정하면 사용자는 요청과 다른 결과를 받고도 알 수 없고,
  검증 누락과 구분되지 않는다.

### Key Entities

- **게시글(Post)**: 자유게시판의 글. 분류 · 제목 · 내용 · 작성자 · 등록일시 · 수정일시 ·
  조회수. 게시판 구분을 가진다(003·005·006과 한 구조를 공유할지는 3.5에서 정한다).
- **첨부(Attachment)**: 게시글에 붙는 파일. 소속 게시글 · **표시 파일명** · **저장 식별자** ·
  크기 · 형식 · 등록일시. **게시글이 사라지면 함께 사라진다**(`FR-034`).
- **댓글(Comment)**: 게시글에 달린 짧은 글. 소속 게시글 · 작성자 · 내용 · 작성일시.
  **게시글이 사라지면 함께 사라진다**(`FR-039`).
- **분류(Category)**: 게시판별 글 분류. 소속 게시판 · 이름 · 표시 순서 · **사용 여부**.
  002는 **읽기만** 하고 관리는 004가 한다.
- **게시판 설정(Board Setting)**: 게시판별로 달라지는 값. 현재는 **`new` 기준 일수**
  하나다(`FR-012`).

> 구체적인 테이블 · 컬럼 · 관계 · 제약은 **3.5 DB 논리 설계에서 사람이 확정**한다
> (constitution 원칙 III). 위 목록은 스펙이 요구하는 **개념**이지 설계가 아니다.
> ⚠️ 특히 *"게시판 4종이 한 테이블인가 네 테이블인가"* 는 되돌리기 비용이 최상이며
> **002가 정하면 안 되는 결정**이다 → **`ADR-006`**.

## Success Criteria *(mandatory)*

- **SC-001**: 사용자는 **로그인 없이** 목록과 상세를 볼 수 있다 — 인증을 요구하는 조회 경로가 **0개**다.
- **SC-002**: 화면을 거치지 않고 직접 요청해도 002의 모든 검증과 권한 규칙이 동일하게 적용된다 —
  **우회로 통과하는 경로가 0건**이다.
- **SC-003**: 개씩 보기를 50으로 올려도 목록 조회의 **질의 수가 10일 때와 같다**.
- **SC-004**: 정렬을 바꾸거나 페이지를 넘길 때 **같은 글이 두 페이지에 나타나거나
  어느 페이지에도 나타나지 않는 일이 0건**이다.
- **SC-005**: 검색 조건을 지정한 사용자는 상세를 보고 돌아오거나 작성을 취소해도
  **조건을 다시 입력하지 않는다**.
- **SC-006**: 업로드된 파일이 **브라우저에서 실행되는 경로가 0건**이다 —
  이미지 확장자를 포함해 모든 첨부가 다운로드로 응답된다.
- **SC-007**: 타인의 글을 수정·삭제하려는 요청은 **100% 서버에서 거부**된다.
- **SC-008**: 삭제된 글에 속했던 **댓글·첨부 기록이 0건** 남는다.
- **SC-009**: 002가 확정한 공통 목록 규칙을 003 · 005 · 006이 **재정의하지 않고 참조**한다 —
  같은 규칙이 서로 다르게 구현된 곳이 **0곳**이다.

## Assumptions

원 요구사항에 없거나 불명확해 합리적 기본값을 택한 항목이다. 3번 게이트에서 확정되거나 뒤집힌다.

1. **글 번호는 표시용 순번이다** — 글에 고정된 번호를 부여하지 않는다. 검색·정렬을 바꾸면
   같은 글에 다른 번호가 붙는다. 고정 번호를 주려면 별도 컬럼이 필요하고 삭제할 때마다
   번호에 구멍이 생긴다.
2. **삭제는 실제 삭제(하드 삭제)** 라고 가정한다. 복구 요구가 없고, 소프트 삭제를 고르면
   모든 조회에 "삭제되지 않은 것만" 조건이 붙어 빠뜨리는 자리가 생긴다.
   → 감사·복구 요구가 생기면 뒤집힌다(**`ADR-010`**).
3. **글 본문은 일반 텍스트**라고 가정한다. 서식 편집기(HTML 저장)는 범위 밖이다
   (**`ADR-014`**).
4. **댓글은 한 단계**다 — 대댓글·댓글 수정이 없다. 요구사항에 화면이 없다.
5. **댓글은 페이징하지 않는다** — 한 글의 댓글을 전부 내려준다. 댓글 수가 수백을 넘는
   게시판이 아니라고 가정한다. 실제로 넘으면 상세 응답이 커지므로 그때 페이징을 넣는다.
6. **등록자 검색은 이름 기준**이다. 목록과 상세가 등록자를 이름으로만 보여주므로
   아이디로 검색하게 하면 화면에 없는 값으로 검색하는 셈이다.
7. **분류 초기 데이터는 마이그레이션으로 제공**한다고 가정한다. 004(카테고리 관리 화면)가
   나오기 전에도 글을 쓸 수 있어야 한다. 001이 사용불가 아이디를 데이터로 넣은 것과 같은 방식이다.
8. **첨부의 총 용량 제한은 두지 않는다** — 개당 2MB × 5개 = 10MB가 사실상의 상한이다.
9. **파일 저장 위치는 이 스펙이 정하지 않는다.** `process.md` 6.2가 002로 미룬 항목이며
   **`ADR-018`**로 넘긴다. 스펙은 *"내려받으면 올린 이름으로 받아진다"* 까지만 규정한다.
10. **조회수는 상세를 열 때마다 증가**한다(중복 방지 없음). 요구사항에 규칙이 없다.
