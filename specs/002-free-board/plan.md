## Summary

**만들 것**: 게시판 4종 중 가장 복잡한 자유게시판. 목록(기간·분류·검색어·정렬·페이징) →
상세(조회수·첨부 다운로드·댓글) → 등록/수정(첨부 5개) → 삭제. 권한은 **소유자 기반**.

**기술 접근**: 001이 세운 것을 하나도 다시 만들지 않는다 — 인증·오류 형식·`traceId`·
로그 마스킹을 그대로 쓰고, 002는 그 위에 **게시판 4종이 공유하는 조회 계층**을 얹는다.

**이 스토리를 관통하는 설계 축 두 개.**

| | 축 | 왜 이것이 축인가 |
|---|---|---|
| 1 | **공통 목록 규칙을 구현체 하나로 만든다** | `SC-009`가 *"같은 규칙이 서로 다르게 구현된 곳 0곳"* 을 요구한다. 검증·정렬·페이징이 게시판마다 한 벌씩 생기면 **네 벌은 반드시 갈라진다.** 001의 *"실패는 전부 같은 얼굴이어야 한다"* 가 응답의 단일화였다면, 002는 **조건 해석의 단일화**다 |
| 2 | **사용자가 올린 파일은 우리 출처에서 절대 해석되지 않는다** | `AC-32`·`AC-33`·`AC-47`. 001이 `httpOnly` 쿠키로 세운 방어선은 **우리 출처에서 스크립트가 돌면 그대로 무력화**된다(쿠키를 읽지 않고도 그 사용자 권한으로 요청을 보낼 수 있다). 002는 파일을 받는 첫 스토리이고 **그 방어선의 새 구멍**을 만든다 |

**가장 깨지기 쉬운 곳**: **정렬 결정성**(`AC-10`)과 **목록 집계의 질의 수**(`AC-22`).
둘 다 *"기능은 정상으로 보이는데 틀린 것"* 이라 눈으로 발견되지 않는다.

## Technical Context

**Language/Version**: **Java 25 LTS**(백엔드) / **TypeScript**(프론트) — `process.md` 6.1

**Primary Dependencies**:
- 백엔드 — **Spring Boot 4.1**, **Spring Data JPA**(`ADR-004`), Flyway, Bean Validation,
  Spring Security(001이 이미 구성). **복잡한 조회 보조 도구(QueryDSL 등)는 아직 없다** —
  `process.md` 6.2가 *"방아쇠: 002의 목록+검색+페이징"* 으로 예고한 결정이며 **`ADR-013`**다
- 프론트 — **Next.js**(사용자·관리자 한 앱, 경로 분리) + `/api/*` rewrite
- 빌드 — Gradle (Kotlin DSL)

**Storage**: **PostgreSQL**(`ADR-003`). 002가 쓰는 테이블 4개 —
`posts` · `comments` · `attachments` · `categories`(읽기만). **첨부 실물 파일은 DB 밖**이며
저장 위치는 **`ADR-018`**이다.

**Testing**: API 통합 중심(Testing Trophy) + Testcontainers 실제 PostgreSQL +
Playwright E2E. 격리는 **롤백 기본, `AC-29`·`AC-61`만 초기화**(`test-strategy.md` 5.2).
**커버리지 게이트 = AC 100%.**

**Target Platform**: 로컬 Docker Compose. **배포 환경은 여전히 미정**이고,
002에서 그 미정이 **처음으로 비용을 만든다** — 첨부 파일이 컨테이너와 함께 사라지는지가
저장 위치 결정(**`ADR-018`**)에 걸려 있다.

**Project Type**: 웹 서비스(자바 백엔드 + Next.js 프론트, 한 레포)

**Performance Goals**: **숫자 목표(ms)를 두지 않는다.** 스펙이 성능 요구를 **질의 수**로
AC화했고(`AC-22`·`SC-003`), 그 이유는 판단 19에 있다 — 시간은 환경에 흔들려 게이트가 되지
못하지만 질의 수는 결정적이다. **이 계획은 그 판단을 그대로 따르며 별도의 ms 목표를
만들지 않는다.**

**Constraints**:
- **첨부는 무조건 다운로드 응답**(`AC-32`). 인라인 미리보기 기능을 만들 수 없다
- **기간 최대 1년**(`AC-3`)이 사실상 이 서비스의 **조회 범위 상한**이다 —
  검색어 최소 길이를 두지 않는 판단(판단 17)이 이 상한에 기대고 있다
- **낙관적 잠금을 넣지 않는다**(판단 12). 대신 **모든 검증을 요청 시점의 실제 상태로 다시** 한다
- 마이그레이션은 **이미 적용된 파일을 수정하지 않는다**(원칙 VI) — 아래 「데이터 모델」 참조

**Scale/Scope**: 화면 4개(목록 · 상세 · 등록 · 수정) · API 엔드포인트 **9개** ·
테이블 4개(신규 3 + 읽기 1) · **AC 71개 전부 002에서 검증**(다른 스토리 이관 0건)

### 이 계획이 test-strategy에 되돌리는 것

계획을 쓰다 **규칙 쪽의 빈틈 2개**가 드러났다. 규칙을 어긴 것이 아니라 규칙이 덜 적혀 있었다.
001의 계획이 constitution에 2건을 되돌린 것과 같은 처리다.

| | 무엇 | 왜 규칙의 빈틈인가 | 제안 |
|---|---|---|---|
| 1 | **자동 테스트를 배정할 레벨이 없는 AC**(`AC-50`·`AC-62` — 확인 대화상자) | `test-strategy.md` 5.3은 *"다른 **스토리**에서 검증되는 AC"* 만 규칙화했다. 이 둘은 **스토리 문제가 아니라 레벨 문제**다 — 서버에 검증할 것이 아예 없고(요청이 발생하지 않는다), E2E는 예산이 없으며, **프론트 컴포넌트 레벨이 전략에 존재하지 않는다.** 규칙이 없으면 *"미배정"* 과 *"잊음"* 이 구분되지 않는다 | ① **프론트 컴포넌트 테스트 레벨을 전략에 추가할지** 판단한다 ② 추가하지 않는다면 **"자동 배정 불가 + 9.5 QA 판정" 표기를 5.3과 같은 급의 규칙**으로 만든다. 표기 없는 미배정은 위반 |
| 2 | **E2E 예산이 스토리 6개를 감당하지 못한다** | 4장이 *"총 5~10개, 프로젝트 전체"* 인데 001이 7개를 썼다. 002가 3개로 깎아도 **10개를 채우고 003·005·006에 0개가 남는다.** 규칙이 그 상태를 *"E2E를 쓰지 마라"* 로 읽히게 하는데, 그것은 4장의 목적(*"100개 쌓이면 짐이 된다"*)이 아니다 | **회고(10.7)에서 예산을 재정한다.** 4장이 이미 *"002~006은 001만큼 쓰지 않을 가능성이 크다 → 6번에서 001의 7개를 깎을 수 있는지 먼저 보고, 그래도 남으면 회고에서 재정"* 으로 열어 뒀다. **002가 그 관찰의 첫 실측치**다 |

> **두 건 모두 이 계획이 임의로 고치지 않는다.** `test-strategy.md`는 전역 문서이고
> 바꿀 때는 ADR로 남긴다(그 문서 머리말). 병렬 작업 중 전역 문서를 고치면 충돌한다.

**Structure Decision**: **`board/common`(4종 공유) + `board/free`(002 전용) 2층으로 가른다.**

- **`SC-009`가 이 구조를 요구한다.** *"공통 규칙이 서로 다르게 구현된 곳 0곳"* 을 지키는
  방법은 **공유 코드가 물리적으로 하나뿐인 것**이다. 문서로 *"003은 002를 참조하라"* 라고
  적는 것은 규칙이 아니라 부탁이다
- 갈라 놓는 대가: **002가 003·005·006의 요구를 모르는 채로 공용 코드를 설계**한다.
  갤러리(이미지 20개)와 문의(분류 없음·비밀글)의 요구가 나중에 공용 코드를 흔들 수 있다
  → 완화: **게시판별로 다른 것은 값(정책)으로 두고 구조를 나누지 않는다**
  (첨부 정책 · `new` 임계값 · 분류 사용 여부)
- ⚠️ 요구사항 9장이 **병렬 경계**를 못박았다 — *"`common/`은 1·2·5 단계에서만 만지고
  이후 아무도 수정하지 않는다."* **002가 그 1·2·5단계의 주인**이므로 공용 코드의
  최종 형태를 002가 확정해야 하고, **003 이후가 고쳐야 하는 상황이 되면 그것이 설계 실패다**

## 데이터 모델

> **인덱스를 "있으면 좋으니까" 만들지 않는다.** 아래 순서로 도출한다 —
> **① 002가 실제로 보내는 조회 패턴을 전부 적고 → ② 각 패턴이 어떤 인덱스를 요구하는지 →
> ③ 그래도 인덱스를 만들지 않기로 한 것과 그 이유.**
> ③을 적지 않으면 나중에 *"빠뜨린 것"* 과 구분되지 않는다(`data-model.md` 5.5의 방식).

### 0. 대조 대상 — 스키마가 이 계획보다 먼저 존재한다

`V5`~`V10`(분류 · 게시글 · 댓글 · 첨부 · 문의답변 · 기본분류)이 **병렬 구현 레인에서 먼저
작성돼 메인에 있다.** 이 절은 그것을 옮겨 적은 것이 아니라 **조회 패턴에서 독립적으로 도출한
뒤 대조한 결과**다. 대조에서 나온 것은 세 종류다 — **일치 / 002가 추가로 요구하는 것 /
002가 판단을 남기는 것**.

### 1. 002가 보내는 조회 패턴 (전수)

### 3. 인덱스 — 조회 패턴에서 도출

| # | 인덱스 | 어느 패턴이 요구하나 | 왜 이 컬럼 순서인가 |
|---|---|---|---|
| 1 | `posts (board_type, created_at DESC, id DESC)` | **Q1(기본 정렬)** · Q2 | **등가 조건(`board_type`)이 앞**에 와야 범위 조건(`created_at`)이 인덱스를 계속 탄다. **`id DESC`가 붙은 것이 `AC-10`의 물리적 실현**이다 — 같은 시각의 글이 여럿일 때 순서가 흔들리면 2페이지에 1페이지 글이 다시 나온다 |
| 2 | `posts (category_id)` | Q1(분류 필터) · **FK 검사** | PostgreSQL은 **자식의 FK 컬럼에 인덱스를 자동으로 만들지 않는다.** 없으면 분류 1건을 바꿀 때마다 `posts` 전체를 훑는다 |
| 3 | `posts (author_id, created_at DESC)` | **FK 검사** · Q12 | 위와 같은 이유. `created_at`을 뒤에 붙인 것은 **006의 "나의 문의내역"** 을 위한 것이며 002는 쓰지 않는다 |
| 4 | `comments (post_id, created_at, id)` | **Q3 · Q7 · Q11** | **한 인덱스가 세 패턴을 덮는다.** ① Q7의 오름차순 정렬이 그대로 인덱스 순서다 ② Q3의 `post_id IN (…)` 집계가 인덱스만으로 끝난다 ③ **Q11의 CASCADE가 도는 방향이 "자식을 찾는 방향"** 이라 이 인덱스가 없으면 글 하나 지울 때마다 `comments` 전체를 훑는다 |
| 5 | `attachments (post_id, sort_order, id)` | **Q4 · Q8 · Q11** | 4번과 같은 짝 |
| 6 | `attachments (stored_path)` **UNIQUE** | 무결성(조회 아님) | 위 컬럼 표 참조 |
| 7 | `categories (board_type, sort_order, id)` | **Q10** | 검색바가 열릴 때마다 부른다. **`active`를 부분 인덱스 조건으로 넣지 않은 이유**: 004 관리 화면이 **비활성 분류도 함께** 본다 |
| 8 | `categories (board_type, LOWER(name))` **UNIQUE** | 무결성 | 같은 게시판에 같은 이름이 둘이면 사용자가 무엇을 고른 것인지 알 수 없다 |
| 9 | `comments (author_id)` · | **FK 검사** | `users` 쪽 변경이 이 인덱스를 요구한다 |

**만들지 않기로 한 인덱스** — 적어두지 않으면 *"빠뜨린 것"* 과 구분되지 않는다.

| | 왜 만들지 않나 | 방아쇠 |
|---|---|---|
| `posts (board_type, view_count)` · `(board_type, title)` · 분류 정렬용 | 정렬 기준 4종 중 **기본(등록일시)만** 받친다. 나머지 3개까지 깔면 **쓰기마다 인덱스 4개를 갱신**하는데, 기본값 아닌 정렬을 얼마나 쓰는지 **모르는 채 지불하는 비용**이다. 정렬은 **인덱스가 없어도 결정적이다**(`ORDER BY … , id`) — `AC-10`은 인덱스가 아니라 **정렬 절**이 지킨다 | 목록 응답이 느려지거나 글이 수만 건을 넘는 시점 |
| 검색어 부분 일치(`LIKE '%키워드%'`) | **B-tree는 앞이 열린 패턴을 타지 못한다.** 그리고 **`AC-3`의 기간 1년 상한이 이미 범위를 유한하게** 만든다 — 판단 17(검색어 최소 길이 제한 없음)이 기대고 있는 것이 정확히 이것이다 | 위와 같은 시점. 그때 `pg_trgm` GIN 인덱스를 검토한다 |
| `users (name)` (등록자 이름 검색) | 위와 같은 이유로 **부분 일치라 어차피 못 탄다.** `data-model.md` 5.5가 *"방아쇠: 004 회원 검색"* 으로 이미 미뤄 뒀다 | 004 |
| `posts (view_count)` 단독 | 조회수 증가는 **PK 단건 UPDATE**(Q6)라 인덱스가 필요 없다. 오히려 **인덱스가 있으면 조회수가 오를 때마다 인덱스도 갱신**되어 상세 조회가 비싸진다 | — |

### 4. 002가 스키마에 **남기지 않는** 것 — 판단

| 무엇 | 결정 | 왜 |
|---|---|---|
| **댓글 수 비정규화 컬럼**(`posts.comment_count`) | **두지 않는다** | `AC-71`이 *"항상 실제와 일치"* 를 요구하는데, 컬럼을 두면 **등록 · 삭제 · 글 삭제 세 경로를 전부 갱신**해야 하고 **한 곳만 빠져도 숫자가 영구히 틀어진다.** `AC-22`(질의 수)는 **Q3 일괄 집계로 이미 달성**되므로 비정규화를 살 이유가 없다. **`AC-22`와 `AC-71`이 함께 걸려 있는 것이 이 판단의 안전장치다** |
| **글 번호 컬럼** | **두지 않는다** | 판단 3 — 번호는 **결과 집합에서의 표시용 순번**이다. 컬럼으로 두면 삭제할 때마다 구멍이 생기고, 정렬을 바꾸면 무의미해진다 |
| **`new` 여부 컬럼** | **두지 않는다** | 시각에 따라 변하는 값이라 저장하면 **매일 갱신하는 작업**이 생긴다. `AC-19`는 조회 시점 계산으로 성립한다 |
| **게시판 설정 테이블**(`new` 임계값) | **두지 않는다 — 환경변수 설정** | `AC-20`은 *"코드를 고치지 않고 설정만 바꿔서"* 를 요구하지 *"화면에서 바꿔서"* 를 요구하지 않는다. `data-model.md`가 자격증명 수명을 *"데이터가 아니라 설정"* 으로 판정한 것과 같다. ▶ **방아쇠: 관리자가 화면에서 바꿔야 한다는 요구가 생기는 시점** |
| **소프트 삭제 컬럼** | **두지 않는다**(Assumptions 2) | 모든 조회에 *"삭제되지 않은 것만"* 이 붙고 **빠뜨리는 자리가 생긴다.** → **`ADR-010`** |

### 5. 대조 결과 — 기존 `V5`~`V10`과의 차이

## AC → 테스트 레벨 배정

`test-strategy.md` 3장의 배정 기준을 적용했다. **AC 하나당 최소 하나, 묶음은 참조마다 따로.**

> ★ **이것은 배정이지 커버리지가 아니다.** 001의 5번 게이트가 *"배정 계획을 커버리지라고
> 주장한 것"* 을 잡았다. 커버리지는 **테스트 이름의 AC-ID로 세는 것**이고 이 시점에는
> `tasks.md`도 테스트 코드도 없다. **실제 커버리지가 확정되는 곳은 6번(태스크 분해)과
> 7번(테스트 작성)이며 판정하는 곳은 CI다.** 이 표가 말하는 것은
> **"어느 AC도 배정 없이 남지 않았는가"** 하나뿐이고, 아래 2건은 **남았다**.

## E2E 예산

**`test-strategy.md` 4장: 총 5~10개, 프로젝트 전체 기준.**

### 002가 **요구하는** 것: 5개

| | AC | 왜 브라우저가 있어야 하나 |
|---|---|---|
| 1 | `AC-11` 즉시 적용 | *"검색 버튼을 누르지 않는다"* 는 **이벤트 처리**다. 서버에서 볼 대상이 없다 |
| 2 | `AC-23` 상세→목록 조건 유지 | 판단 7(조건을 URL에 담는다)의 실제 동작은 **브라우저의 이동과 복귀** |
| 3 | `AC-24` 등록 취소→목록 조건 유지 | 위와 **같은 메커니즘의 다른 진입점**. 규칙상 AC당 테스트 하나라 합칠 수 없다 |
| 4 | `AC-50` 작성 취소 확인 대화상자 | 브라우저 대화상자 |
| 5 | `AC-62` 삭제 확인 대화상자 | 브라우저 대화상자 |

### 깎을 수 있는가 — **판단: 3개로 깎는다**

**깎는 것: `AC-50` · `AC-62`.** 근거 3개.

1. **E2E가 잡으라고 있는 것에 해당하지 않는다.** 4장은 E2E를 *"여러 시스템이 붙어서 도는가"*
   로 규정했다. 확인 대화상자는 **프론트 단독 동작**이고 **요청이 발생하지 않으므로
   붙을 시스템이 없다.**
2. **서버 쪽 절반이 비어 있다.** 두 AC의 *Then*(*"글이 생성되지 않는다"* · *"삭제되지 않는다"*)은
   **요청을 보내지 않았으니 당연히 참**이다. 통합 테스트로 옮길 대상 자체가 없다.
3. **깎아도 요구가 사라지지 않는다.** 두 AC는 **9.5 기능 QA 체크리스트 항목**으로 남고,
   constitution 원칙 VIII(*"사람이 통과시킨 AC는 자동 테스트로 승격"*)에 따라
   **프론트 컴포넌트 테스트 레벨이 생기는 시점에 승격**한다.

**깎지 않는 것과 그 이유**: `AC-11`·`AC-23`·`AC-24`는 **`SC-005`의 본체**이고,
셋 다 *"조건이 유지되는가"* 라는 **게시판에서 가장 흔한 불만**을 검증한다.
그리고 이 셋은 **003·005·006이 그대로 물려받는 규칙**이라 002에서 한 번 확인해 두면
나머지 세 스토리가 E2E를 다시 쓰지 않아도 된다 — **예산 관점에서 가장 남는 3개**다.

### 그래도 예산은 초과한다 — 정직한 기록

| | 개수 |
|---|---|
| 예산 (프로젝트 전체) | **5 ~ 10** |
| 001 사용 | **7** |
| 002 요구 → 깎은 뒤 | 5 → **3** |
| **합계** | **10** — 상한에 정확히 닿는다 |
| **003 · 005 · 006 · 004에 남는 것** | **0개** |

**002 안에서 더 깎는 것은 옳지 않다.** 남은 3개는 전부 *"서버에 검증 대상이 없는데
사용자에게는 핵심인"* 항목이고, 여기서 더 깎으면 **`SC-005`를 확인하는 테스트가 하나도
없어진다.**

**→ 이것은 002의 문제가 아니라 규칙의 문제다.** *"프로젝트 전체 5~10"* 이 **스토리 6개**를
가정하지 않았다. `test-strategy.md` 4장이 이미 *"6번 태스크 분해에서 001의 7개를 깎을 수
있는지 먼저 보고, 그래도 남으면 회고(10.7)에서 예산을 재정한다"* 로 관찰을 열어 뒀고,
**002가 그 관찰의 첫 실측치**다. 두 갈래로 올린다:

| | 안건 | 어디서 |
|---|---|---|
| 1 | **001의 7개를 깎을 수 있는가** — 001은 이미 구현이 끝났으므로 *"실제로 무엇을 잡았나"* 를 볼 수 있다. 추측이 아니라 실측으로 판단할 수 있는 첫 시점이다 | 회고(10.7) |
| 2 | **예산 단위를 바꿀 것인가** — *"프로젝트 전체 N개"* 는 스토리가 늘수록 뒤에 오는 스토리를 0으로 만든다. 다만 **추측으로 규칙을 고치지 않는다**(`process.md` 결정 26) — 안건만 올리고 숫자는 회고에서 정한다 | 회고(10.7) |

## 위험과 대응

| 위험 | 왜 위험한가 | 대응 |
|---|---|---|
| **★ 오류 코드를 하나로 뭉친다** | 조건 검증 실패를 전부 `REQUEST_INVALID` 같은 공통 코드로 던지면 **`AC-3`·`AC-4`·`AC-6`·`AC-9`·`AC-18`이 서로 구분되지 않는다.** 상태코드(400)가 같아서 **테스트를 대충 쓰면 전부 통과**하고, 사용자는 무엇이 잘못됐는지 알 수 없다. **현재 공용 조건 검증 코드가 실제로 그 상태이며 소스에 그 취지의 `TODO`가 남아 있다** | **계약 문서의 `code` 열이 단일 진실**이다(001과 같은 규약). 각 AC의 테스트가 **상태코드가 아니라 `code`를 단언**하게 쓴다 — 그러면 뭉쳐진 구현이 반드시 실패한다 |
| **★ 정렬 2차 기준이 빠진다** | `ORDER BY view_count DESC`만 쓰면 **테스트도 화면도 정상으로 보인다.** 깨지는 것은 *"2페이지에 1페이지 글이 다시 나온다"* 이고 **동률일 때만** 드러나는데, **조회수 정렬은 동률(0)이 기본 상태**라 실제로는 일상이다 | `AC-10`을 **정렬 구현과 같은 단계**(순서 2)에 둔다. 테스트는 **동률 25건 · 3페이지 합집합**으로 쓴다 — 한 페이지만 보는 테스트는 이 결함을 못 잡는다 |
| **★ 목록 집계가 행마다 질의를 보낸다** | 지연 로딩으로 댓글 수를 읽으면 **코드가 자연스러워 보이는데** 질의가 `1 + N`이 된다. `size=50`이 **정상 기능**이라 사용자가 그 상태를 만든다 | `AC-22`가 **질의 수를 센다.** ms가 아니라 개수라 환경에 흔들리지 않는다. **`local`·`test` 프로필의 SQL 로깅**이 개발 중에도 드러나게 한다 |
| **DB 제약이 먼저 걸려 400이 5xx가 된다** | `title VARCHAR(99)` · `CHECK btrim(…) <> ''`가 **서버 검증보다 먼저** 걸리면 사용자는 *"일시적 오류"* 를 본다. **`AC-40`이 특히 위험** — 공백만 입력은 길이 검증을 통과해 DB까지 간다 | **서버 검증이 반드시 앞에** 있게 하고, `AC-38`~`AC-40`의 테스트가 **`code`까지 단언**하게 한다(5xx면 `code`가 `INTERNAL_ERROR`라 즉시 실패). DB 제약은 **마지막 방어선이지 1차 방어선이 아니다** |
| **파일 경로가 오류 메시지로 샌다** | 002는 **파일 시스템을 다루는 첫 스토리**다. 저장 실패·읽기 실패 예외에 **절대 경로가 그대로** 들어 있고, 그것이 `detail`에 실리면 서버 디렉터리 구조가 공개된다(`FR-042`) | ① 5xx는 001 `AC-28`의 **화이트리스트**가 이미 막는다 ② **4xx는 막지 못한다** — 첨부 관련 4xx의 `detail`을 **고정 문구로만** 만들고 예외 메시지를 이어 붙이지 않는다 ③ **`AC-35`가 응답 전체에 `stored_path`가 없는지** 확인한다 |
| **첨부 실물과 DB 행이 어긋난다** | 글 저장은 트랜잭션이지만 **파일 쓰기는 트랜잭션이 아니다.** 롤백되면 **행은 사라지고 파일은 남는다**(고아 파일) | **방향을 고른다** — 고아 파일(디스크 낭비)은 허용하고 **반대 방향(행은 있는데 파일이 없다)은 허용하지 않는다.** 후자는 *"목록에 보이는데 열리지 않는 첨부"* 로 사용자에게 드러난다. `AC-49`가 이 방향을 검증한다 |
| **동시 수정에서 첨부 개수 상한이 샌다** | 낙관적 잠금을 넣지 않기로 했으므로(판단 12), **화면이 들고 온 옛 상태**(첨부 4개)를 믿고 계산하면 실제로는 6개가 된다 | **`AC-56`·`AC-61`이 짝**이다. 개수 판정을 **요청 시점에 DB에서 다시 읽어** 한다. 화면이 보낸 개수를 신뢰하지 않는다 |
| **`AC-29` 조회수 테스트가 가짜 초록이 된다** | 기본 격리가 **롤백**이라 커밋 경합이 일어나지 않는다. 그러면 *"읽고 더해서 쓰기"* 구현도 **테스트를 통과한다** | **`AC-29`·`AC-61`만 초기화 방식**으로 돌린다고 이 문서에 명시했다(`test-strategy.md` 5.2가 *"예외를 쓰는 테스트는 문서에 명시한다"* 를 요구한다) |
| **공용 코드가 003 이후에 흔들린다** | 요구사항 9장이 *"`common/`은 002 이후 아무도 수정하지 않는다"* 로 못박았는데, **002는 갤러리·문의의 요구를 모른 채** 공용 코드를 확정한다 | **게시판별로 다른 것을 전부 값(정책)으로** 뺀다 — 첨부 정책 · `new` 임계값 · 분류 사용 여부 · 검색어 범위. 구조가 아니라 값이면 003이 `common/`을 고치지 않고 값만 준다 |
| **첨부 저장 위치를 안 정한 채 구현이 진행된다** | 인터페이스만 두고 미루면 편해 보이지만, **다운로드 응답 방식(직접 스트리밍 vs 서명 URL 리다이렉트)이 저장 위치에 따라 갈린다.** 후자를 고르면 `AC-32`·`AC-33`의 헤더를 **우리가 못 붙인다** | **`ADR-018`을 순서 5 이전에 확정**한다. 그 전까지는 **로컬 디스크로 진행하되, 다운로드가 반드시 우리 서버를 거치는 형태**를 유지한다 — `AC-32`가 그것을 요구한다 |
