## Content Quality

- [~] **구현 세부가 없다 (언어·프레임워크·API)** — **의도적 예외 2건, 근거 기록됨**
  - AC에 **HTTP 상태코드와 오류 `code`** 를 포함했다. constitution 원칙 II(NON-NEGOTIABLE)가
    검증 가능한 AC를 요구하고 이 AC들이 그대로 테스트·QA 체크리스트가 된다.
    상태코드와 `code`는 프레임워크가 아니라 **API 계약**이다. 001과 같은 처리.
  - **응답 헤더 2종**(`Content-Disposition: attachment` · `X-Content-Type-Options: nosniff`)을
    `AC-32`·`AC-33`에 명시했다. **이것 없이는 그 AC를 검증할 수 없고**, 헤더는 프레임워크가
    아니라 **HTTP 계약**이다. constitution 보안 요구사항이 *"권한은 서버 검증"* 을 직접
    규정한 것과 같은 급의 항목이라 일반화하면 요구가 약해진다.
  - 프레임워크·라이브러리·DB 종류·테이블명은 등장하지 않음을 확인했다.
- [x] **사용자 가치와 비즈니스 요구에 집중** — 각 AC에 *근거* 줄이 붙어 있고,
      *"왜 그렇게 정했는가"* 가 *"무엇을 정했는가"* 보다 길다
- [~] **비기술 이해관계자가 읽을 수 있다** — 상태코드·헤더 표기 때문에 완전한 비기술 문서는
      아니다. 위와 같은 근거. **시나리오 서술 자체는 평서문으로 유지**했다
- [x] **필수 섹션 모두 작성** — User Scenarios(US1~US5) / Requirements(FR-001~044) /
      Success Criteria(SC-001~009) / Edge Cases / Assumptions / Key Entities / Dependencies / Out of Scope

## Requirement Completeness

- [ ] **`[NEEDS CLARIFICATION]` 마커가 남아 있지 않다** — ⚠️ **미충족 (게이트 미실시)**
  - 스펙에 마커 문자열은 없지만, **「판단한 것 — 사람 검증 대상」 20건**이 사실상 같은 역할을 한다.
    스펙 머리말이 *"3번 게이트 미통과. 이 절의 항목이 3번 게이트의 입력이다"* 로 명시하고 있다.
  - **마커 대신 표로 모은 것은 개선이다** — 문서 곳곳에 흩어진 마커보다 한 표가 게이트에서 다루기 쉽다.
    다만 **게이트 종료 조건(미확정 0개)은 아직 충족되지 않았다.**
  - → **3번 게이트 실시가 이 항목의 해소 조건이다.**
- [x] **요구사항이 검증 가능하고 모호하지 않다** — AC 71개 전부 `Given/When/Then + AC-ID`.
      *"잘 동작한다"* 류 문장 0건. **경계값이 양쪽으로 적혀 있다**(99/100 · 3999/4000 ·
      2MB/2MB+1B · 5개/6개 · 6일23시간/7일1분)
- [x] **성공 기준이 측정 가능하다** — SC 9건이 전부 **0건 / 0곳 / 100%** 같은 셀 수 있는 값이다.
      **`SC-003`이 특히 그렇다** — *"질의 수가 10일 때와 같다"* 는 환경에 흔들리지 않는다
- [x] **성공 기준이 기술 중립적이다** — SC-001~009에 프레임워크·DB 용어 없음
- [x] **모든 인수 시나리오가 정의되어 있다** — AC-1 ~ AC-71, 번호 연속·중복 0
- [x] **엣지 케이스가 식별되어 있다** — 4분류(경계값 4 · 동시성 5 · 빈 값 4 · 권한 경계 4) +
      **보안 경계 5**. 보안 경계를 따로 둔 것은 002가 **파일을 받는 첫 스토리**이기 때문이다
- [x] **범위가 명확히 경계 지어져 있다** — Out of Scope 16항목. **각 항목의 행선지**(004 · 별도 ·
      ADR 후보)가 함께 적혀 있어 *"뺀 것"* 과 *"잊은 것"* 이 구분된다
- [x] **의존 관계와 가정이 식별되어 있다** — Assumptions 10건 · 의존을 **세 방향**으로 나눴다
      (001에서 끝난 것 8 / 다른 스토리가 정할 것 6 / **002가 넘겨주는 것 4**).
      **세 번째 칸이 002의 고유 책임**이며 `SC-009`와 짝이다

## 계획(4번)을 쓰면서 발견한 것 — **3번 게이트의 추가 입력**

> 001에서도 같은 일이 있었다 — 4번 계획이 `FR-035`·`AC-34`(오픈 리다이렉트)를 신설했고,
> 5번 게이트가 `AC-35`~`AC-37`을 신설했다. **계획을 쓰면 스펙의 빈틈이 드러난다.**
> 아래는 002에서 같은 방식으로 나온 5건이며, **스펙을 아직 고치지 않았다**
> (3번 게이트가 판단해야 하는 것이지 계획이 임의로 고칠 것이 아니다).

| # | 무엇 | 성격 | 처리 |
|---|---|---|---|
| **1** | **없는 댓글을 삭제하려 할 때의 응답이 없다** | **AC 누락.** `AC-67`~`AC-69`가 전부 *"있는 댓글"* 만 다룬다. `FR-018`이 *"존재하지 않거나 삭제된 글·첨부·**댓글**"* 을 이미 요구하므로 **FR에는 근거가 있고 AC만 없는 상태** — 001의 `FR-024`·`FR-025`가 AC 없이 남았던 것과 **같은 종류** | **`AC-72` 신설을 3번 게이트가 판단**한다. 계약 문서는 `COMMENT_NOT_FOUND`(404)로 임시 확정하고 *"계약이 신설"* 로 표시했다 |
| **2** | **글 번호의 분모가 두 갈래로 읽힌다** | **모호성.** `AC-14`와 판단 3은 **결과 총건수**로 닫았는데, 원 요구사항 문구는 *"전체 게시글 수"* 다. **003·005·006이 물려받는 규칙**이라 한쪽으로 닫혀야 한다 | 3번 게이트에서 확인. 뒤집히면 `AC-14`·`FR-009`를 함께 고친다 |
| **3** | **페이지 번호 상한과 `AC-13`이 충돌할 수 있다** | **규칙 충돌 가능성.** 깊은 페이징을 막으려 `page` 상한을 두면 그 값을 넘는 요청은 400인데, **`AC-13`은 범위 초과에 200 + 빈 목록**을 요구한다. *"어디까지가 `AC-13`이고 어디부터가 거부인가"* 가 정해져 있지 않다 | 3번 게이트. 상한을 두지 않는 쪽이면 `AC-13`이 그대로 유효하다 |
| **4** | **`jpeg` 확장자** | **범위 판단.** 요구사항이 `jpg`만 적었고 `AC-44`가 그것을 따랐다. 실제로는 `.jpeg`로 저장하는 기기가 흔해 **정상 사용자가 막힌다** | 3번 게이트. 허용하려면 `AC-44`·`FR-026`을 먼저 고친다 |
| **5** | **`AC-50`·`AC-62`에 배정할 테스트 레벨이 없다** | **전략의 빈틈**(스펙 결함 아님) | `test-strategy.md` 개정 안건. `plan.md` 미해결 1 |

**태스크 분해(6번) 시 주의**

1. **`AC-48`이 `AC-38`~`AC-47`을 참조하는 묶음 AC다.** **개별 AC마다 직접 호출 테스트가
   생기도록** 주의한다 — 하나로 뭉치면 어느 검증이 빠졌는지 드러나지 않는다.
   001의 `AC-19`와 같은 구조이고, **002는 참조 대상이 10개라 더 크다.**
2. **`AC-29`·`AC-61` 두 건만 초기화 방식**으로 돌린다(`test-strategy.md` 5.2가
   *"예외를 쓰는 테스트는 문서에 명시한다"* 를 요구한다). 롤백으로 돌리면
   **커밋 경합이 일어나지 않아 잘못된 구현도 통과한다.**
3. **`AC-59`와 `AC-30`을 서로 비교하는 테스트**를 따로 만든다. 각각 404여도 `code`·`detail`이
   다를 수 있다(001의 `AC-2`·`AC-3` 처리와 같은 종류).
4. **`AC-32`와 `AC-33`을 한 테스트로 뭉치지 않는다.** 헤더 한 겹이 빠져도 드러나야 한다.
5. **`AC-10`(정렬 결정성)을 정렬 구현과 같은 단계에** 둔다. 뒤로 미루면 이미 깨진 채
   통과한 테스트 위에 2차 정렬 기준을 얹는 일이 된다.

**의도적 예외 3건 (변경 없음)**

Content Quality의 `[~]` 2건과 Feature Readiness의 `[~]` 1건.
AC의 HTTP 상태코드·`code` 표기와 응답 헤더 2종 명시.
constitution 원칙 II(검증 가능한 AC)가 직접 요구하는 사항이므로 일반 명세 지침보다 우선한다.

**미해결로 남은 사항**

- **3번 게이트를 실시하지 않았다.** 요구사항 문서 머리말이 *"정식 스펙 절차(1~6번 게이트)를
  건너뛰고 구현에 바로 들어가기 위해"* 라고 적고 있으므로 **의도된 생략**이지만,
  그 대가가 여기 남는다 — **판단 25건이 아무도 확인하지 않은 채 구현에 들어간다.**
  → `STATUS.md`에 대가를 적는다(요구사항 문서가 요구한 것).
- **E2E 예산이 구조적으로 부족하다.** 001(7) + 002(3) = 10으로 상한에 닿고
  003·004·005·006에 0개가 남는다. **002가 그 관찰의 첫 실측치**이며 회고(10.7)의 안건이다.
