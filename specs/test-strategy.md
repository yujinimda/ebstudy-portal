# 테스트 전략

> **프로세스 3.9.** 프로젝트 전역 문서. **1회 작성하고 모든 스토리가 참조한다.**
> 스토리마다 다시 정하지 않는다 — 스토리별로 다르게 쓰이면 테스트 코드가 두 프로젝트처럼 된다.
> 이 문서를 바꿀 때는 ADR로 남긴다.

**대상 독자**: 테스트를 작성하는 주체(코덱스), 구현하는 주체(클코), 그리고 사람.
**상위 규범**: `.specify/memory/constitution.md` 원칙 I·II. 충돌하면 constitution이 우선한다.

---

## 1. 밀집도 — API 통합 테스트 중심 (Testing Trophy)

```
단위        ███        복잡한 계산·검증 로직만
슬라이스     █          거의 안 쓴다
통합        ████████   ★ 주력
E2E         ██         프로젝트 전체 5~10개
```

| 레벨 | 무엇 | 속도 | 잡는 버그 |
|---|---|---|---|
| 단위 | 프레임워크 없이 순수 객체 | ms | 비즈니스 규칙 (계산·검증) |
| 슬라이스 | 프레임워크 일부만 로드 | 초 | 요청 검증, 쿼리 오류 |
| **통합** | 앱 전체 + **실제 DB** | 수 초 | **트랜잭션 · 권한 · 실제 SQL** |
| E2E | 브라우저 | 수십 초 | 프론트-백 연결 |

**왜 단위 중심(전통적 피라미드)이 아닌가**

단위 테스트를 주력으로 삼으면 주변 의존성을 전부 목(mock)으로 발라야 한다. 그러면
**리팩터링마다 테스트가 깨지는데 정작 진짜 버그는 안 잡힌다.** 목은 상상한 대로만 응답한다.
실제 버그는 **실제 DB와 붙는 경계**에서 나온다.

> **이 근거가 곧 제약이다.** "실제 DB와 붙는다"가 성립하지 않으면 이 전략을 고른 이유가
> 사라진다. → 5장(DB 준비 방식) 참조.

**응답·권한·경계값은 E2E가 아니라 통합 테스트로 내린다.** E2E는 "여러 시스템이 붙어서 도는가"만 본다.

## 2. 역할 역전 TDD (NON-NEGOTIABLE)

constitution 원칙 I.

```
코덱스: 스펙만 보고 테스트 작성  →  실패 확인  →  클코: 통과시킴
```

- 테스트는 **구현보다 먼저** 작성한다.
- **작성자를 분리한다.** 테스트를 쓰는 주체와 통과시키는 주체가 다르다.

**왜 분리하나**: 사람이 혼자 TDD 할 때 가장 잘 무너지는 지점이 *"귀찮으니 구현 먼저,
테스트는 나중"* 이다. 작성자가 물리적으로 분리되면 그것이 **원리적으로 불가능**해진다.

**테스트를 쓰는 주체는 구현 코드를 보지 않는다.** 스펙만 본다. 구현을 보고 쓰면
"구현이 하는 일"을 검증하게 되고, 그건 버그를 잡지 못한다.

## 3. AC와 테스트의 대응

constitution 원칙 II. **AC 하나가 세 곳의 원천이다.**

```
spec.md의 AC ──┬─→ 테스트 작성 (7번)
               ├─→ 기능 QA 체크리스트 (9.5)
               └─→ 자동 테스트로 승격 (9.7)
```

### 규칙

- **테스트 이름에 AC-ID를 넣는다.** QA 기록의 `AC-3 FAIL`이 곧 테스트 이름이 되어
  역추적이 가능해야 한다.
- **AC 하나당 테스트 하나** 이상. 여러 AC를 한 테스트로 뭉치지 않는다.
  뭉치면 **어느 검증이 빠졌는지 드러나지 않는다.**
- 묶음 AC(예: 001의 `AC-19`가 `AC-11`~`AC-18`을 참조)는 **참조하는 AC마다 따로** 테스트를 만든다.

### 레벨 배정 기준

| AC의 성격 | 레벨 |
|---|---|
| 계산·검증 로직이 복잡하다 | 단위 |
| HTTP 요청 → DB → 응답을 확인한다 | **통합** |
| 상태코드·오류코드·권한·경계값 | **통합** |
| 사람이 화면을 돌아다녀야 의미가 있다 | E2E |

## 4. E2E 규칙

**총 5~10개.** 프로젝트 전체 기준이며 스토리당이 아니다.

E2E는 느리고 잘 깨진다. 100개 쌓이면 그 자체가 짐이 된다. 그래서 **개수를 제한하는 것이
전략의 일부**다.

### 효율화 5규칙 (전부 적용)

| | 규칙 | 이유 |
|---|---|---|
| 1 | **개수를 줄인다** | 효과가 압도적이다. 에러 케이스·권한·경계값은 전부 통합 테스트로 내린다 |
| 2 | **로그인 상태를 재사용한다** | 매 테스트마다 로그인 화면을 클릭하지 않는다. 한 번 로그인해 자격증명을 저장하고 주입 — 보통 이것만으로 절반 이상 빨라진다 |
| 3 | **사전 데이터는 UI가 아니라 API로 만든다** | "게시글이 있는 상태"를 만들려고 글쓰기 화면을 클릭하지 않는다. API로 꽂고 **검증만 UI로** |
| 4 | **고정 대기(`sleep`) 금지** | 느림의 주범이다. 조건 충족 즉시 진행하는 자동 대기를 쓴다 |
| 5 | **로컬에서 전체를 돌리지 않는다** | 태그로 일부만. 전체는 CI에서 |

## 5. 아직 결정하지 않은 것 — 사람이 확정해야 함

constitution 원칙 III(1.1.0): **실재하는 선택지가 둘 이상이면 사람이 확정한다.**

### 5.1 통합 테스트의 DB 준비 방식 ⚠️ 최우선

**이것이 1장의 전략 자체를 성립시키거나 무너뜨린다.** "실제 DB와 붙는다"가 전제이므로,
DB를 무엇으로 준비하는지가 전략의 정합성 문제다.

**결정: Testcontainers** — 테스트 시작 시 **실제 DB를 컨테이너로 띄우고** 끝나면 버린다.
*(사람 확정 2026-07-28)*

**기각한 대안**

| | 기각 이유 |
|---|---|
| 임베디드 DB (H2 등) | **실제 DB가 아니다.** SQL 방언·함수·타입·제약 동작이 다르므로 "테스트는 초록인데 프로덕션에서 터진다"가 실제로 발생한다. 그리고 **마이그레이션 SQL을 손으로 쓰는데**(constitution 원칙 VI) H2에서 통과해도 아무것도 보장하지 못한다 |
| 공유 실제 DB | 테스트가 서로 오염시킨다. **병렬 실행 불가.** 이전 실행의 데이터가 남아 실패한다 |

**채택 근거**

1. **임베디드를 고르면 1장의 전략과 모순된다.** "실제 DB와 붙는 경계"를 보려고 통합 중심을
   골랐는데 가짜 DB를 쓰면 근거가 무너진다
2. 손으로 쓴 마이그레이션 SQL이 **실제로 도는지 확인할 유일한 방법**이다
3. CI가 GitHub Actions이며 Docker를 지원한다 — 추가 인프라가 필요 없다

**받아들인 대가**: Docker를 배워야 한다. 컨테이너 기동 시간이 붙는다.
(배포 환경도 컨테이너 기반일 가능성이 높으므로 어차피 만날 학습이다.)

### 5.2 테스트 간 격리 방식

한 테스트가 넣은 데이터가 다음 테스트에 보이면 테스트가 서로를 깨뜨린다.

**결정: 혼합** — 기본은 트랜잭션 롤백, **커밋 동작·동시성을 보는 테스트만 초기화 방식**.
*(사람 확정 2026-07-28)*

| | 방식 | 적용 |
|---|---|---|
| 기본 | **트랜잭션 롤백** — 트랜잭션 안에서 돌리고 끝나면 되돌린다 | AC 대부분 |
| 예외 | **매번 초기화** — 테이블을 비우고 실제로 커밋한다 | 동시성·커밋 시점 동작 |

**왜 한쪽만 고르지 않는가**

- **롤백만**으로는 **커밋이 일어나지 않으므로 동시성을 테스트할 수 없다.**
  `spec.md` Edge Cases의 **동시 가입 경합**(같은 아이디로 두 요청이 동시에 도착하면 하나만 성공)이
  그 예다. 두 트랜잭션이 **실제로 커밋을 경합**해야 한다.

  > 이 테스트가 특히 중요한 이유: **`username` UNIQUE 제약을 DB가 정말 막아주는지**
  > 확인하는 유일한 테스트다. 3.5에서 *"코드로 막으면 동시 요청에서 깨진다"* 며
  > DB 제약을 고른 판단을 이 테스트가 검증한다.

- **초기화만**으로는 테이블 비우는 시간이 매 테스트마다 붙어 전체가 계속 느려진다.

**예외를 쓰는 테스트는 문서에 명시한다.** 기본과 다르게 동작하므로 이유를 남긴다.
