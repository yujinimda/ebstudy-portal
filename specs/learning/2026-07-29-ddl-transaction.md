# DDL과 트랜잭션 — 그리고 둘의 조합이 왜 DBMS 선택을 결정했나

## 물은 맥락

`ADR-003`(DBMS = PostgreSQL)의 **첫 번째 근거가 "DDL이 트랜잭션 안에서 돈다"** 였고,
`2026-07-29-dbms.md` 노트를 읽은 뒤 *"ddl도 흐릿해.."* 라고 물었다.

> 5.5에 신설했는데(결정 39), **`ADR-003`의 결정적 근거에 쓰인 DDL과 트랜잭션을
> 둘 다 정의하지 않은 상태**였다. 규칙을 만들었다고 지켜지는 것이 아니라는 실물 증거다.

## 설명

### DDL — SQL은 하는 일에 따라 갈린다

**DDL = Data Definition Language = 데이터 정의어.** SQL의 한 종류다.

| 종류 | 무엇을 하나 | 대표 문장 |
|---|---|---|
| **DDL** (정의) | **구조를 만들고 바꾼다** | `CREATE TABLE` · `ALTER TABLE` · `DROP TABLE` · `CREATE INDEX` |
| **DML** (조작) | **데이터를 넣고 바꾼다** | `INSERT` · `UPDATE` · `DELETE` |
| DQL (조회) | 데이터를 읽는다 | `SELECT` |
| DCL (제어) | 권한을 준다 | `GRANT` · `REVOKE` |

*(DQL을 따로 부르지 않고 DML에 포함시키는 문헌도 많다. 구분의 실익이 크지 않다.)*

### 도서관 비유를 이어서

앞 노트에서 **서가 = 데이터베이스**, **사서 = DBMS** 로 놨다. 여기에 얹으면:

- **DDL = 서가를 짜고 칸을 나누는 목공 일** — "3단 서가를 놓고 각 칸에 라벨을 붙여라"
- **DML = 그 칸에 책을 넣고 빼는 사서 일** — "이 책을 2층 3번 칸에 넣어라"

**서가가 없으면 책을 넣을 수 없다.** 그래서 DDL이 먼저다.

### 우리 프로젝트에 그대로 대응한다

```
6.7 마이그레이션 SQL  =  전부 DDL      ← 사람이 직접 쓴다 (원칙 VI)
   V1__create_user.sql   →  CREATE TABLE users (...)
   V3__add_index.sql     →  CREATE UNIQUE INDEX ...

앱이 돌면서 하는 일   =  DML / DQL     ← ORM이 만들어 준다
   가입   →  INSERT INTO users ...
   로그인  →  SELECT * FROM users WHERE ...
```

- **`process.md` 4.7이 "마이그레이션 SQL은 사람이 직접 쓴다"고 한 그 SQL이 DDL이다.**
- **4.11의 *"코드는 되돌리기 쉽고 DB는 어렵다"* 도 이 구분 위에 있다** —
  DML은 잘못 넣으면 그 행만 고치면 되지만, **DDL은 구조를 바꿔서 옛 코드가 아예 안 뜨게 만든다.**
  그래서 파괴적 DDL을 여러 배포로 쪼개는 것(expand-contract)이 필요해진다.
- `ddl-auto=validate`(4.7)의 `ddl`이 바로 이것이다.
  `ddl-auto=update`를 금지한 이유는 **하이버네이트가 어떤 DDL을 실행할지 알 수 없어서**다.

### 트랜잭션

**여러 문장을 한 덩어리로 묶어서 "다 되거나 다 안 되게" 하는 것.**

비유는 **계좌 이체**다. A에서 만원을 빼고 B에 만원을 넣는 **두 작업**인데,
빼기만 하고 서버가 죽으면 **돈이 사라진다.** 그래서 둘을 한 덩어리로 묶는다.

```
BEGIN        ← 덩어리 시작
  A에서 -10000
  B에게 +10000
COMMIT       ← 확정. 이제 진짜 반영된다
```

중간에 문제가 생기면 `ROLLBACK` — **아무 일도 없었던 것처럼 되돌린다.**

**이미 우리 문서에 나와 있었다.** `test-strategy.md` 5.2의 *"기본은 트랜잭션 롤백"* 이 이것이다 —
테스트가 넣은 데이터를 `COMMIT` 하지 않고 `ROLLBACK` 해서 없애므로
다음 테스트가 깨끗한 상태에서 시작한다.

그리고 5.2의 *"롤백만으로는 커밋이 일어나지 않으므로 동시성을 테스트할 수 없다"* 는 문장도
이제 통한다 — **`COMMIT`을 해야 진짜 경합이 일어나기 때문**이다.

### ★ "DDL이 트랜잭션 안에서 돈다"의 실제 의미

마이그레이션 파일 하나에 DDL이 여러 개 들어간다.

```sql
-- V2__create_refresh_token.sql
CREATE TABLE refresh_token (...);                          -- ①
CREATE UNIQUE INDEX ux_refresh_token_hash ON ...;          -- ②
ALTER TABLE refresh_token ADD CONSTRAINT fk_user ...;      -- ③  ← 여기 오타
```

③에서 오타를 냈다고 하자.

| | 결과 | 그다음에 해야 하는 일 |
|---|---|---|
| **PostgreSQL** | ①②③ **전부 취소.** 스키마는 손대지 않은 상태 | **오타만 고치고 다시 실행.** 끝 |
| **MySQL** | ①②는 **이미 확정됨.** 테이블과 인덱스는 생겼고 FK만 없다 | 다시 실행하면 **"테이블이 이미 존재합니다"** 에러. **손으로 지우고 다시 해야 한다** |

**여기서 우리 규칙과 충돌이 생긴다.**
`process.md` 4.7은 **"이미 적용된 마이그레이션 파일은 절대 수정하지 않는다"** 고 정했다.
그런데 MySQL의 반쪽 상태는 **"적용됐다"고도 "안 됐다"고도 말할 수 없다.**
규칙을 적용할 수가 없어진다.

PostgreSQL은 **아무것도 적용되지 않았음이 확실**하므로 파일을 고치는 것이 명확하게 안전하다.

> **이것이 `ADR-003`에서 PostgreSQL을 고른 첫 번째 이유다.**
> 6.7에서 **손으로 SQL을 쓰기로 했으니 오타를 낸다.**
> 오타를 냈을 때 무엇이 남는지가 실제로 중요하다.

### 정직하게 — PostgreSQL에도 예외가 있다

**트랜잭션 안에서 못 도는 DDL이 있다.** 대표적으로
`CREATE INDEX CONCURRENTLY`(운영 중인 테이블을 잠그지 않고 인덱스를 만드는 방법)다.

지금은 쓰지 않지만 4.11의 **expand-contract**(파괴적 변경을 여러 배포로 쪼개기)를
실제로 할 때 만날 수 있다.
**"Postgres는 다 롤백된다"고만 알고 있으면 그때 놀란다.**

### 한 장 정리

```
SQL
├── DDL  구조   CREATE / ALTER / DROP     ← 6.7 마이그레이션, 사람이 쓴다
├── DML  데이터  INSERT / UPDATE / DELETE  ← 앱이 돌면서, ORM이 만든다
├── DQL  조회   SELECT
└── DCL  권한   GRANT / REVOKE

트랜잭션 = BEGIN … COMMIT(확정) / ROLLBACK(되돌리기)
            여러 문장을 "다 되거나 다 안 되게" 묶는다

PostgreSQL:  DDL도 이 묶음 안에서 돈다  →  마이그레이션 실패 시 깨끗하다
MySQL:       DDL은 즉시 확정된다        →  반쪽 적용이 남는다
```
