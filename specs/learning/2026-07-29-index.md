# 인덱스 — 배열의 인덱스와 다른 것

## 물은 맥락

`ADR-003`이 `username` 대소문자 무시를 **`LOWER(username)` 함수 유니크 인덱스**로 구현하기로
정했고, DBMS 노트에 인덱스를 *"미리 만든 색인"* 이라고만 적어두고 넘어갔다.
6.7에서 **사람이 직접 쓸 DDL**에 이것이 들어가므로 짚고 가는 중에 물었다:

> **인덱스 그냥 세는 숫자아냐?**

**타당한 혼동이다.** 프론트엔드에서 `인덱스`는 배열의 위치 번호이고, 그건 실제로 세는 숫자다.
`2026-07-29-ddl-transaction.md`에서 확인한 것과 **반대 방향의 문제**다 —
거기서는 *이미 하는 일에 이름이 붙은 것*(DML)이었고, 여기서는 **아는 단어에 다른 뜻이 있는 것**이다.

관련 결정: `ADR-003`(대소문자 무시 구현) / `data-model.md`(유일 제약) / `research.md` 3·9번
선행 노트: `2026-07-29-dbms.md`, `2026-07-29-ddl-transaction.md`

## 쉬운 말 요약

- **배열의 인덱스는 위치 번호**지만, **DB 인덱스는 책 뒤의 찾아보기(색인)** 다. 다른 것이다.
- 없으면 **50만 권을 처음부터 다 뒤진다.** 있으면 목록에서 바로 찾는다.
- **공짜가 아니다** — 읽기는 빨라지고 **쓰기는 느려진다.** 그래서 찾는 컬럼에만 건다.
- **UNIQUE 제약이 이 인덱스로 구현된다** — 찾기와 중복 막기가 **같은 장치**다.

## 설명

### 같은 단어, 다른 뜻

| | 뜻 |
|---|---|
| **배열의 인덱스** | `arr[3]`의 `3`. **위치 번호. 세는 숫자 맞다** |
| **DB의 인덱스** | **책 뒤에 있는 "찾아보기"(색인)** |

DB 쪽은 배열보다 **책의 색인**에 가깝다. 우리말 `색인`이 오히려 정확한 번역이다.

### 도서관 비유 — 앞 노트를 이어서

서가에 책 50만 권이 있다. **"김영하가 쓴 책 주세요."**

| | 사서가 하는 일 |
|---|---|
| **인덱스 없음** | 첫 권부터 마지막 권까지 꺼내 작가를 확인한다. **50만 번** → **전체 훑기(full scan)** |
| **인덱스 있음** | 작가 이름 순으로 정리된 **별도 카드 목록**에서 "김영하 → 3층 2번 칸"을 찾아 바로 간다 |

**그 카드 목록이 인덱스다.** 책 자체가 아니고, **책을 찾기 위해 따로 만들어 계속 유지하는 것**이다.

### ★ 공짜가 아니다 — 이것이 핵심이다

카드 목록을 만들면 **책을 새로 넣을 때마다 카드도 만들어 꽂아야** 하고, 빼면 카드도 빼야 한다.

| | 인덱스가 있으면 |
|---|---|
| 찾기 (`SELECT`) | **빨라진다** |
| 넣기·고치기·지우기 (`INSERT`/`UPDATE`/`DELETE`) | **느려진다** — 인덱스도 같이 고쳐야 하므로 |
| 저장 공간 | **더 쓴다** |

→ **그래서 아무 컬럼에나 다 걸지 않는다.** "찾는 데 쓰는 컬럼에만" 건다.
인덱스를 많이 걸면 빨라진다고 오해하기 쉬운 지점이다.

## 우리 프로젝트에서 — 여기가 진짜 이야기다

### ① UNIQUE 제약은 인덱스로 구현된다

3.5에서 사람이 이렇게 판단했다:

> `username` 중복 불가 — **DB가 보장해야 한다.** 코드로 막으면 동시 요청에서 깨진다

**그 "DB가 보장하는 장치"가 물리적으로는 유일 인덱스다.**

당연한 결과다 — 중복인지 알려면 **이미 있는지 찾아봐야** 하고, 찾는 도구가 인덱스다.
**찾기와 중복 막기가 같은 장치다.** 둘이 별개 기능이 아니다.

### ② `LOWER(username)` 인덱스가 대소문자 무시를 어떻게 만드나

`ADR-003`이 고른 방식이다. 인덱스를 알면 **왜 되는지**가 보인다.

**인덱스에 저장되는 값이 원본이 아니라 "소문자로 바꾼 결과"다.**

```
넣으려는 값        인덱스에 들어가는 값
kim        →       kim
Kim        →       kim     ← 같은 자리로 가려고 한다
                             → 유일 제약 위반 → DB가 거부
```

`Kim`으로 가입을 시도하면 인덱스는 `kim`을 넣으려 하고, 이미 `kim`이 있으니 **DB가 거부한다.**
**코드가 판단하는 것이 아니다** — 3.5에서 "코드로 막으면 동시 요청에서 깨진다"며
DB에 맡긴 판단이 이렇게 실현된다.

**금지 아이디 목록도 같은 규칙이다**(`data-model.md` 확정) — `admin`이 목록에 있으면
`Admin`·`ADMIN`도 거부되어야 하고, 같은 함수 인덱스로 처리한다.

### ③ "bcrypt로는 조회할 수 없다"의 정체가 이것이었다

`research.md` 3번에서 티켓 식별 값을 SHA-256으로 저장하기로 한 이유다.
정체는 **인덱스로 찾을 수 없다**는 것이었다.

| | 같은 입력 → 해시 | 인덱스로 찾을 수 있나 |
|---|---|---|
| **SHA-256** | **항상 같다** | ✅ 찾을 수 있다 |
| **bcrypt** | **매번 다르다** (솔트) | ❌ 찾을 수가 없다 |

- **비밀번호**는 `username`으로 행을 찾은 **뒤에** 비교한다 → bcrypt로 괜찮다
- **티켓 식별 값**은 **해시 자체로 찾아야** 한다 → bcrypt를 쓸 수 없다

`data-model.md`가 티켓 식별 값에 **유일 제약**을 준 것과 맞아떨어진다.
유일 제약 = 인덱스 = 찾을 수 있음.

### ④ 인덱스는 DDL이다 — 앞 노트가 여기로 이어진다

`CREATE INDEX`는 **DDL**이다(`2026-07-29-ddl-transaction.md`).
그래서 **6.7에서 사람이 손으로 쓴다**(constitution 원칙 VI).

그리고 `ADR-003`에 적어둔 **리스크 1이 정확히 여기다**:

> `ddl-auto=validate`는 컬럼 존재는 검증하지만 **함수 인덱스 일치는 검증하지 않는다.**

엔티티에 `unique = true`만 걸고 실제 인덱스를 잘못 만들면 **아무도 모른다.**
부팅도 되고 테스트도 초록일 수 있다.

→ **그래서 `test-strategy.md` 5.2의 동시 가입 경합 테스트에 `Kim` vs `kim`을 넣는다.**
**그것이 이 인덱스를 확인하는 유일한 장치다.**

### 001에서 만들 인덱스

| 테이블 | 인덱스 | 목적 |
|---|---|---|
| 유저 | `LOWER(username)` **유일** | 로그인 시 찾기 + 대소문자 무시 중복 거부 |
| 재발급 티켓 | 티켓 식별 값(SHA-256) **유일** | 재발급 시 해시로 찾기 |
| 사용불가 아이디 | `LOWER(금지아이디)` **유일** | 가입 시 금지 여부 판정, 대소문자 무시 |

**전부 유일 인덱스다.** 001에는 "찾기만 빠르게 하는" 인덱스가 없다 —
목록·검색·페이징이 없어서다. **그런 인덱스는 002 자유게시판에서 처음 만난다.**
