# 무상태(stateless)와 JWT / 세션

## 물은 맥락

001 인증 스토리의 1번 브레인스토밍. 인증 방식을 세션 vs JWT로 고르는 중에
"실무 JWT는 대부분 완전 무상태가 아니다"라는 설명이 나왔고, **무상태가 무엇인지** 물었다.

관련 결정: `ADR-001` (인증 방식 = JWT, Access + Refresh)
관련 원칙: constitution 보안 요구사항(토큰 만료 필수 · `httpOnly` 쿠키 저장)

## 설명

무상태의 정의는 한 줄이다 — **서버가 요청 사이에 무언가를 기억하는가.**

### 세션 = 클럽 입장 팔찌

팔찌에는 **번호만** 적혀 있다(`abc123`). 들어올 때마다 직원이 **명단을 확인**한다.
"abc123은… 유진, 관리자군요." **명단은 클럽이 갖고 있다.**

→ 서버가 기억한다 = **상태 있음(stateful)**

### JWT = 위조 불가능한 도장이 찍힌 신분증

신분증에 이미 다 적혀 있다 — "유진, 관리자, 15:30까지 유효".
직원은 **도장이 진짜인지만 확인**하면 내용을 믿을 수 있고 **명단이 필요 없다.**

→ 서버가 기억하지 않는다 = **무상태(stateless)**

```
[세션]  요청 → 쿠키(abc123) → 서버가 저장소 조회 → "유진이네"
                                   ↑ 서버가 기억함 (stateful)

[JWT]   요청 → 토큰(유진·관리자·만료) → 서버가 서명만 검증 → 끝
                                   ↑ 조회 없음 (stateless)
```

### 무상태의 장점

| | |
|---|---|
| 서버 확장 | 여러 대로 늘려도 각자 서명만 검증. 세션은 "어느 서버가 그 명단을 갖고 있나" 문제가 생겨 공유 저장소(Redis)가 필요 |
| 속도 | 요청마다 DB 조회가 없다 |

### 무상태의 문제 — 이것이 핵심

**이미 발급한 신분증을 회수할 방법이 없다.** 도장은 이미 찍혀 있고, 유효기간이 지나기를
기다릴 수밖에 없다.

**그것이 "JWT는 로그아웃이 안 된다"의 정체다.** 프론트에서 토큰을 버려도 서버 입장에서
그 토큰은 여전히 유효하다. 계정 탈취 신고가 들어와도 끊을 수단이 없다.

### 그래서 실무 JWT는 절충한다 (Access + Refresh)

| | 수명 | 서버 저장 | 상태 |
|---|---|---|---|
| Access 토큰 | 짧게 (15분~1시간) | ❌ | 무상태 |
| Refresh 토큰 | 길게 (7~30일) | ✅ DB/Redis | **상태 있음** |

- 짧은 신분증(Access)을 주고, **재발급 티켓(Refresh)만 명단에 올린다.**
- 로그아웃 = 명단에서 Refresh를 지운다 → 재발급 차단 → 최대 15분 뒤 완전 차단.

> **결론: 실무의 JWT는 "부분적으로만 무상태"다.**
> 순수 무상태 JWT는 로그아웃을 포기하는 것이고, 실서비스에서 그건 선택지가 아니다.
> 튜토리얼이 잘 알려주지 않는 부분.

### 용어 층 주의 — `세션`은 *방식*의 이름이다

`세션`을 Access 토큰의 별칭으로 오해하기 쉽다. 층이 다르다:

- **방식 A = 세션** → 자격증명이 **하나**: 세션 ID
- **방식 C = JWT** → 자격증명이 **둘**: Access(짧음) + Refresh(김)

"세션은 짧고 Refresh는 길다"처럼 나란히 놓으면 안 된다.
세션은 *방식* 이름이고, Access/Refresh는 옆 방식 *안의* 부품이다.

### 그럼 Refresh를 저장하면 세션과 같아지나 — 아니다

둘 다 서버에 저장하는 것은 맞다. 차이는 **"얼마나 자주 명단을 보나"** 다.

| | 정체 | 수명 | 서버 저장 | **매 요청 조회** |
|---|---|---|---|---|
| 세션 ID | 방식 A의 유일한 자격증명 | 30분 등 | ✅ | ✅ **매번** |
| Access 토큰 | 방식 C의 평소 자격증명 | 15~30분 | ❌ | ❌ 서명만 검증 |
| Refresh 토큰 | 방식 C의 **재발급 티켓** | 7~30일 | ✅ | ❌ **재발급 때만** |

- **세션**: 들어올 때마다 명단 확인 → 요청 100번이면 조회 **100번**
- **Access + Refresh**: 신분증이 15분 유효하니 그동안은 명단 없이 통과.
  15분 지나면 티켓으로 새 신분증을 받고, **그때만** 명단 확인 → 요청 100번이면 조회 **1번**

**저장한다는 사실은 같지만 조회 빈도가 100배 차이난다.** 그것이 서버 부하와 확장성의 차이다.
무상태의 이점을 대부분 유지하면서 로그아웃만 되찾은 구조.

## 서명(signature) — 2026-07-28 추가

3.5 DB 논리 설계 중 *"서명한다는 게 뭔지, 서명을 저장하는 것과 JWT를 저장하는 것이 뭐가 다른지"* 를
물어서 보강한 절.

### JWT는 세 조각이다

```
헤더 . 내용 . 서명
eyJhbGci... . eyJzdWIiOiJob25nMDEiLCJyb2xlIjoiVVNFUiJ9 . SflKxwRJSMeK
```

**먼저 오해 하나: JWT는 암호화가 아니다.** 가운데 `내용`은 그냥 인코딩된 것이라
**누구나 디코딩해서 읽을 수 있다.** `{"sub":"hong01","role":"USER"}` 가 다 보인다.

→ **JWT에 비밀을 담지 않는다.** 담아도 숨겨지지 않는다.

### 서명 = 위조 불가능한 도장

서버만 아는 **비밀키**로 `헤더+내용`을 계산해서 만든 값.

공격자가 내용을 `"role":"ADMIN"` 으로 바꾸면 서명이 안 맞는다. 서버가 다시 계산해 비교하면
다르므로 거부한다. 공격자는 올바른 서명을 만들 수 없다 — 비밀키를 모르기 때문이다.

**"서명을 검증한다"의 뜻:**
받은 토큰의 `헤더+내용`으로 서명을 **다시 계산**해서 받은 서명과 비교한다.
→ **계산만 하면 된다. DB를 볼 필요가 없다.** 이것이 무상태의 정체다.

### 서명은 어디서 일어나나 — 항상 서버

| 시점 | 하는 일 | 누가 |
|---|---|---|
| **발급** (로그인 성공) | 내용을 만들고 비밀키로 서명을 계산해 붙인다 | **서버** |
| **검증** (요청마다) | 서명을 다시 계산해 비교한다 | **서버** |

**브라우저는 절대 서명하지 않는다.** 받아서 보관하고 다시 보내기만 한다.

이유: 비밀키를 브라우저에 주면 누구나 열어볼 수 있고, 그러면 **아무나 `role: ADMIN` 토큰을
만들 수 있다.** 비밀키는 서버에만 있어야 한다.

**그래서 이 비밀키가 시크릿이다** → `.env`, 배포는 플랫폼 환경변수.
constitution 원칙 VII의 첫 실물 사례다. 저장소에 커밋되면 **누구나 관리자 토큰을 위조할 수
있으므로** 유출 시 키를 폐기하고 재발급해야 한다(= 전원 로그아웃).

서명 알고리즘 자체는 직접 구현하지 않는다. 라이브러리가 한다.

### ★ 핵심 — 서명이 알려주지 **못하는** 것

| 서명이 알려주는 것 | 서명이 알려주지 못하는 것 |
|---|---|
| 이 내용이 위조되지 않았다 | **이 사람이 로그아웃했는지** |
| 서버가 발급한 것이 맞다 | 계정이 정지됐는지 |
| 만료 시각이 언제인지 | 관리자가 이 토큰을 취소했는지 |

> **도장이 진짜인 것은 도장을 보면 안다.
> 그런데 그 사람이 어제 탈퇴했다는 것은 도장으로 알 수 없다. 명단을 봐야 안다.**

**서명 유효 ≠ 아직 권한 있음.** 이 한 줄이 Refresh에 명단이 필요한 이유 전부다.

### 그래서 DB에 저장하는 것은 "서명"이 아니다

```
재발급티켓
  id            : 1
  유저id        : 2
  티켓식별값(해시) : a3f9c2...     ← 이 티켓을 찾기 위한 열쇠 (사물함 번호)
  만료시각       : 8/11
  무효화여부      : false        ← ★ 명단의 알맹이
```

**저장의 목적은 토큰을 보관하는 것이 아니라 `"이 티켓이 아직 유효하다"`는 기록을 남기는 것**이다.
로그아웃하면 `무효화여부`가 바뀌거나 행이 사라진다.

열쇠를 해시하는 이유는 비밀번호와 같다 — 원문으로 적어두면 **DB 유출 시 그 열쇠를 그대로
써서 로그인**할 수 있다.

### 두 검사는 목적이 다르다

```
Access 토큰   서명 검증   →  "위조 아닌가?"     →  계산만. DB 안 봄
Refresh 토큰  DB 조회     →  "아직 유효한가?"   →  명단 확인
```

둘을 다 하는 것이 아니라 **각자 다른 질문에 답한다.**
Refresh에서 DB를 보기로 한 이유는 **로그아웃** 하나뿐이다.
