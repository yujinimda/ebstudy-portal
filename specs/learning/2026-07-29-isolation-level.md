# 트랜잭션 격리 수준 — "내 트랜잭션이 무엇을 보는가"

## 물은 맥락

잠금 노트를 마친 뒤 DB 스레드의 마지막 조각으로 이어서 물었다.

`test-strategy.md` 5.2가 격리 방식을 **"트랜잭션 롤백 기본 + 동시성만 초기화"** 로 정했고
잠금 노트가 그 이유(**판정이 `COMMIT` 시점에 일어난다**)를 설명했다.
남은 질문은 **"그러면 그 판정 전에 각 트랜잭션은 무엇을 보고 있었나"** 다.

관련 결정: `test-strategy.md` 5.2 · `data-model.md`(유일 제약을 DB에) ·
`spec.md` Edge Cases(동시 가입 경합) · `process.md` 8.3(조회수 미정)
선행 노트: `2026-07-29-ddl-transaction.md`(트랜잭션) · `2026-07-29-lock.md`(잠금)

## 쉬운 말 요약

- **잠금은 "쓰기 충돌"을 다루고, 격리 수준은 "읽기가 무엇을 보는가"를 다룬다.** 짝이다.
- 서가를 훑는 동안 사서가 책을 꽂고 있다 — **시작할 때의 사진을 보나, 실시간을 보나?** 그게 격리 수준이다.
- **PostgreSQL 기본값(`Read Committed`)으로 001은 충분하다.** "읽고 판단해서 쓰는" 긴 흐름이 없다.
- ★ **동시 가입 경합은 격리 수준으로는 못 막는다. 제약이 막는다.** 이게 3.5 판단이 옳았던 또 하나의 이유다.

## 설명

### 잠금과 짝이다

| | 무엇을 다루나 |
|---|---|
| **잠금** | **쓰기 충돌** — 같은 것을 동시에 고치려 할 때 |
| **격리 수준** | **읽기가 무엇을 보는가** — 남이 바꾼 것을 내가 보나 |

### 비유 — 서가를 훑는 동안 사서가 책을 꽂는다

내가 "소설이 몇 권인지" 세려고 서가를 훑고 있다.
그 사이 사서가 새 책을 꽂고 어떤 책은 빼 간다.

| 내가 세는 방식 | 결과 |
|---|---|
| **시작할 때의 서가 사진**을 보고 센다 | 세는 동안 변화가 안 보인다. 일관된 숫자가 나온다 |
| **지금 실시간 서가**를 본다 | 셀 때마다 숫자가 달라진다 |

**이 선택이 격리 수준이다.**

### 읽기가 이상해지는 3가지

용어가 셋인데 **점점 심해지는 순서**로 외우면 된다.

| | 이름 | 무슨 일 |
|---|---|---|
| 1 | **더러운 읽기** (dirty read) | 남이 **아직 커밋하지 않은** 값을 읽는다. 그가 롤백하면 **나는 존재한 적 없는 값을 본 것** |
| 2 | **반복 불가 읽기** (non-repeatable read) | **같은 행**을 두 번 읽었는데 **값이 달라졌다.** 사이에 남이 고치고 커밋했다 |
| 3 | **유령 읽기** (phantom read) | **같은 조건**으로 두 번 조회했는데 **행 개수가 달라졌다.** 사이에 남이 새 행을 넣고 커밋했다 |

**2와 3의 차이**: 2는 *"그 책의 내용이 바뀌었다"*, 3은 *"책이 한 권 늘었다"* 다.

### 4단계

| 수준 | 더러운 읽기 | 반복 불가 | 유령 |
|---|---|---|---|
| `Read Uncommitted` | 발생 | 발생 | 발생 |
| **`Read Committed`** ← **PostgreSQL 기본** | 막음 | 발생 | 발생 |
| `Repeatable Read` | 막음 | 막음 | 표준은 발생 / **Postgres는 막음** |
| `Serializable` | 막음 | 막음 | 막음 |

**위로 갈수록 안전하고 느리다.** 인덱스·잠금과 **같은 모양의 교환**이다.

> **PostgreSQL 주의**: Postgres의 `Repeatable Read`는 **스냅샷 기반**이라 표준보다 강해서
> 유령 읽기까지 막는다. 대신 **충돌하면 오류를 내고 재시도를 요구한다.**
> → **격리를 올리면 "안전"만 얻는 게 아니라 재시도 코드가 늘어난다.**

### ★ 001은 왜 기본값으로 충분한가

001의 모든 흐름을 보면 이렇다.

| 흐름 | 무엇을 하나 | 격리 수준이 영향을 주나 |
|---|---|---|
| 로그인 | 한 행 읽기 | ❌ |
| **가입** | 한 행 삽입 | ❌ **UNIQUE 제약이 판정한다** |
| 재발급 | 한 행 읽고 한 행 쓰기 (짧다) | ❌ |
| 로그아웃 | 한 행 `UPDATE` | ❌ |

**"읽어서 그 값에 기반해 판단하고 쓰는" 긴 흐름이 하나도 없다.**
그래서 **PostgreSQL 기본값 `Read Committed`로 충분하고, 계획에 격리 수준을 명시하지 않았다.**

### ★★ 여기가 오늘의 핵심 — 동시 가입 경합은 격리로 막는 게 아니다

흔한 오해다. *"격리 수준을 올리면 경합이 해결된다"* — **아니다.**

```
격리를 Serializable 로 올려도:
  A: 'kim' 있나? → (내 스냅샷에는) 없다
  B: 'kim' 있나? → (내 스냅샷에는) 없다      ← 여전히 둘 다 "없다"를 본다
```

**각자 자기 스냅샷을 보므로 "없다"를 보는 것 자체는 막을 수 없다.**
막히는 것은 **오직 커밋 시점에 유일 인덱스가 충돌시킬 때**다(잠금 노트).

> **3.5의 판단이 또 한 번 옳았던 이유다.**
> *"코드로 막으면 동시 요청에서 깨진다"* 는 **격리 수준을 올려도 안 낫는다.**
> **제약만이 막는다.** 그래서 `username` 유일성을 DB 제약에 맡긴 것이 유일한 답이었다.
>
> 오늘 배운 것 중 **가장 실무에서 헷갈리는 지점**이라 표시해 둔다.

### 002에서 만날 자리 — 목록 페이징

```
1페이지 조회 → 1~10번 글
   그 사이 새 글이 올라온다
2페이지 조회 → 10번 글이 또 나온다 (밀려 내려왔다)
```

**유령 읽기의 실물**이다. 게시판에서 흔히 겪는 *"같은 글이 두 페이지에 보인다"* 가 이것이다.

**실무는 격리를 올려서 풀지 않는다** — 목록 조회에 `Serializable`을 걸면 서비스가 못 돈다.
**커서 기반 페이징**(*"몇 번째부터"* 가 아니라 *"이 글 다음부터"*)으로 푼다.
002에서 페이징을 설계할 때 이 노트를 참조한다.

### 지금까지 배운 도구가 전부 같은 모양이다

| | 얻는 것 | 잃는 것 |
|---|---|---|
| 인덱스 | 읽기 속도 | **쓰기 속도** |
| 잠금 | 정확성 | **동시 처리량** |
| **격리 수준 ↑** | **읽기 일관성** | **처리량 + 재시도 코드** |

**공짜인 것이 하나도 없다.** 그래서 *"필요한 만큼만"* 이 전부의 원칙이다.

### 한 장 정리

```
잠금       =  쓰기 충돌을 다룬다
격리 수준   =  읽기가 무엇을 보는가를 다룬다

이상 현상 3가지 (점점 심해지는 순서)
  더러운 읽기    커밋 안 한 값을 봤다
  반복 불가 읽기  같은 행의 값이 바뀌었다
  유령 읽기      행 개수가 바뀌었다

4단계  Read Uncommitted < Read Committed < Repeatable Read < Serializable
       PostgreSQL 기본 = Read Committed   → 001은 이걸로 충분
       올리면 안전하지만 느려지고 재시도 코드가 늘어난다

★ 동시 가입 경합은 격리로 안 막힌다 — 제약이 막는다
★ 002 페이징의 "같은 글이 두 페이지에" = 유령 읽기 → 커서 페이징으로 푼다
```
