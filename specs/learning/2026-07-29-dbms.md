# DBMS — 데이터베이스와 무엇이 다른가

## 물은 맥락

4번 기술 계획에서 **DBMS를 PostgreSQL로 확정하고 `ADR-003`을 쓴 직후**,
*"dbms가 뭐야?"* 를 물었다.

> **순서가 거꾸로였다 (기록해 둔다).**
> Claude가 "PostgreSQL vs MySQL을 고르세요"라고 물을 때 **DBMS라는 단어 자체가 통한다고
> 가정**했다. 개념을 확인하지 않고 그 개념 위에서 결정을 요구한 것이다.
> `process.md` 5.5는 "판단 재료를 먼저 공급한다"고 정했는데, **재료보다 더 아래층인
> 용어를 건너뛰었다.** 4.2 트리거("이게 뭐야"를 물은 지점)가 이 누락을 사후에 잡았다.

관련 결정: `ADR-003`(DBMS = PostgreSQL) / `ADR-002`(기본키 전략) / `data-model.md`(3.5 논리 설계)
관련 원칙: constitution 원칙 VI(되돌릴 수 있는 스키마)

## 설명

### 한 줄

**DBMS = DataBase Management System = 데이터베이스를 관리하는 프로그램.**

핵심은 **데이터베이스와 DBMS가 다른 것**이라는 점이다.

- **데이터베이스** — 데이터가 모여 있는 것. 명사이고 가만히 있다
- **DBMS** — 그 데이터를 넣고 찾고 지키는 **프로그램**. 실제로 일하는 쪽

**PostgreSQL은 DBMS다. 데이터베이스가 아니다.**

### 비유 — 도서관

| 도서관 | DB 용어 |
|---|---|
| 책 한 권 | 데이터 |
| 책이 꽂힌 서가 | **데이터베이스** |
| **사서 + 목록 + 대출 규칙 전체** | **DBMS** |

**서가에 직접 들어가지 않는다. 사서에게 말한다** — "김씨가 쓴 책 주세요."
사서가 목록을 보고 찾아온다. 사서에게 말을 거는 **정해진 말투가 SQL**이다.

### 왜 필요한가 — 이것이 진짜 답이다

"데이터를 저장한다"면 그냥 파일에 써도 된다.
**파일에 직접 쓰면 무엇이 깨지는지**가 DBMS의 정체다.

| 파일로 직접 하면 | DBMS가 대신 하는 일 | **우리가 이미 이걸 믿고 내린 결정** |
|---|---|---|
| 10만 줄에서 `kim`을 찾으려면 **전부 읽어야** 한다 | **인덱스** — 미리 만든 색인으로 바로 찾는다 | `ADR-003`의 `LOWER(username)` 함수 유니크 인덱스 |
| 두 요청이 동시에 고치면 **하나가 사라진다** | **잠금 · 트랜잭션** | `spec.md` Edge Cases의 **동시 가입 경합** |
| "같은 아이디 두 번"을 **막아주지 않는다** | **UNIQUE 제약** — 거부한다 | 3.5에서 *"코드로 막으면 동시 요청에서 깨진다"* 며 **DB에 맡긴 그 판단** |
| 쓰다가 전원이 꺼지면 **반쪽이 남는다** | **원자성** — 다 되거나 아무것도 안 된다 | `ADR-003`에서 **트랜잭션 DDL**을 고른 이유 |
| 누가 무엇을 읽을 수 있는지 못 정한다 | 권한 관리 | |
| 잘못 지우면 되돌릴 수 없다 | 백업 · 복구 | (호스팅 방아쇠와 함께 정할 것) |

> **DBMS는 "우리가 직접 만들지 않기로 한 기능들의 묶음"이다.**
> 3.5에서 *"DB가 막아준다"* 고 믿고 UNIQUE 제약을 맡긴 그 "DB"가 정확히 이것이다.
> 그리고 `test-strategy.md` 5.2의 **동시 가입 경합 테스트**는
> **"DBMS가 정말로 막아주는가"를 확인하는 테스트**다.

### 용어 층 정리

`2026-07-27-stateless-jwt-session.md`에 `세션`의 층을 정리한 절이 있는데, 여기도 같은 혼동이 있다.

| 말 | 뜻 | 우리 프로젝트 |
|---|---|---|
| 데이터 | 값 하나 | `hong01` |
| 행 (row · 레코드) | 한 사람 분의 값 묶음 | 유진의 계정 한 줄 |
| 테이블 | 행이 쌓인 표 | `users`, `refresh_token` |
| **데이터베이스** | 테이블들의 묶음 | `ebstudy_portal` |
| **DBMS** | **데이터베이스를 관리하는 프로그램** | **PostgreSQL** |
| SQL | DBMS에 요청하는 언어 | `SELECT * FROM users WHERE ...` |
| ORM | 자바 객체 ↔ 테이블을 자동 변환하는 도구 | **아직 안 정함** (JPA vs MyBatis) |

**"PostgreSQL을 설치했다"** = DBMS를 깐 것이고, **그 안에 데이터베이스를 여러 개 만들 수 있다.**

**그런데 실무에서는 이 구분을 뭉갠다.** "DB 뭐 써요?"는 사실 "DBMS 뭐 써요?"라는 뜻이고
답은 "포스트그레스요"다. **일상에서 DBMS라는 단어를 거의 쓰지 않기 때문에**
"DBMS를 정해야 합니다"가 낯설게 들리는 것이 자연스럽다.

### 종류 — 앞 노트의 Redis 질문에 대한 답

`2026-07-27-stateless-jwt-session.md`의 `아직 모르는 것`에 이렇게 적혀 있다:

> Redis는 그거 캐시 같은 부분 아니면, 뭔가 저장해가지고 그것만 예외할 수 있는 그런 거 아닌가?

| 종류 | 어떻게 저장하나 | 예 |
|---|---|---|
| **관계형 (RDBMS)** | **표**로 저장하고 표 사이를 **관계**로 잇는다. SQL을 쓴다 | **PostgreSQL** · MySQL · Oracle · SQLite |
| 키-값 | "열쇠 → 값" 하나씩. 아주 빠르다 | **Redis** |
| 문서 | JSON 같은 덩어리째 | MongoDB |

**Redis도 DBMS다.** 캐시가 정체가 아니라 **용도**다 — 주로 메모리에 두고 아주 빠르게 읽으니
캐시로 많이 쓰이는 것이고, **데이터를 저장·조회하는 프로그램이라는 점은 같다.**

그래서 누적 항목 7번 *"실패 횟수 저장 위치 — 서버 메모리 vs Redis"* 는 실은
**"DBMS를 하나 더 둘까?"** 라는 질문이었다. 로컬 우선으로 **서버가 1대로 확정**되면서
메모리로 시작할 수 있게 되었다 — 여러 대면 각 서버의 메모리가 갈라져 공유 저장소가 필요해진다.

**우리가 관계형을 고른 이유**: 데이터가 **표로 정리되고**(`users`, `refresh_token`)
**표 사이의 관계**(유저 ↔ 재발급티켓)가 설계의 핵심이기 때문이다.
그것이 3.5에서 손으로 그린 것이다.

### 그림

```
        ┌──────────────────────────────────────────┐
        │  DBMS  (PostgreSQL)  ← 프로그램, 일한다   │
        │                                          │
        │   인덱스 · 제약 · 트랜잭션 · 권한 · 백업    │
        │                                          │
        │   ┌────────────────────────────────┐     │
        │   │ 데이터베이스 (ebstudy_portal)   │     │
        │   │                                │     │
        │   │   테이블 users                 │     │
        │   │   테이블 refresh_token          │     │
        │   │        ↑ 가만히 있는 데이터      │     │
        │   └────────────────────────────────┘     │
        └──────────────────────────────────────────┘
                     ↑ SQL 로 요청
              자바 앱 (Spring Boot)
                     ↑ ORM 이 여기를 자동 변환 (아직 안 정함)
```

## PostgreSQL · MySQL · Oracle의 차이 — 같은 날 추가로 물음

### 먼저 헷갈리는 것

**MySQL은 오라클 회사 소유이지만 Oracle Database와 다른 제품이다.**
오라클이 2010년에 MySQL을 인수해서 한 회사가 둘을 다 갖고 있다.
이름이 비슷해서가 아니라 **소유주가 같아서** 헷갈린다.

### 한 줄씩

| | 정체 | 돈 |
|---|---|---|
| **PostgreSQL** | 오픈소스. **대학·연구에서 출발**해 "표준을 지키고 엄격하게" 쪽으로 자랐다 | **무료** |
| **MySQL** | 오픈소스이지만 **오라클 소유**. "웹에서 빠르고 쉽게" 쪽으로 자랐다 | 무료판 + 유료판 |
| **Oracle Database** | **상용 제품.** 대기업·은행·통신사의 핵심 시스템용 | **매우 비쌈** |

### 성격 차이 — 어디서 자랐는지가 남아 있다

**MySQL은 "웹사이트를 빠르게 띄우는 것"이 출발점**이었다. 그래서 쉽고 빠르지만
**엄격함을 양보한 역사**가 있다. 옛 버전은 `VARCHAR(10)`에 15자를 넣으면
**조용히 10자로 잘라서 저장**했다 — 에러가 아니라 경고였다.
8.0부터 기본이 엄격 모드로 바뀌었지만 **그 문화가 곳곳에 남아 있다.**

**PostgreSQL은 "표준 SQL을 제대로 구현하는 것"이 출발점**이었다.
잘못된 값을 넣으면 **거부한다.** 느슨함을 기대하면 불편하고,
**DB가 막아주기를 기대하면 믿을 수 있다.**

> 3.5에서 *"코드로 막으면 동시 요청에서 깨진다"* 며 UNIQUE 제약을 DB에 맡겼다.
> **그 신뢰를 어디에 두는지의 차이**다.

**Oracle은 "절대 멈추지 않고 절대 데이터를 잃지 않는 것"이 출발점**이다.
은행 계좌가 틀리면 안 되니까. 대신 돈과 전문 인력이 든다
(오라클 DBA는 별도 직군이다).

### 우리 결정에 실제로 작용한 차이

| | PostgreSQL | MySQL | Oracle |
|---|---|---|---|
| **DDL 트랜잭션** | ✅ 마이그레이션 실패 시 **되돌아간다** | ❌ 반쪽 적용이 남는다 | 부분 지원 |

| 대소문자 무시 아이디 | `LOWER()` 인덱스로 **명시** | 콜레이션으로 **자동**(안 보임) | 명시 |
| 값 검증 엄격함 | 엄격 | 8.0부터 엄격(역사는 느슨) | 엄격 |
| 국내 실무 점유율 | 늘고 있음 | **높음** | 대기업·금융 |
| 비용 | 무료 | 무료 | **비쌈** |

`ADR-003`에서 결정적이었던 것은 **첫 줄**이다. 6.7에서 **마이그레이션 SQL을 손으로 쓰기로**
했으므로, 실패했을 때 반쪽이 남는지 깨끗이 되돌아가는지가 직접 영향을 준다.

> **DDL과 트랜잭션이 무엇인지는 별도 노트에 있다** → `2026-07-29-ddl-transaction.md`.
> 이 표를 쓰는 시점에 두 단어를 정의하지 않고 지나갔고, 바로 다음 질문이 그것이었다.

### Oracle을 후보에서 아예 뺀 이유

돈만이 아니다. **개인이 배우기에 진입 장벽이 다르다** — 설치·라이선스·튜닝이 별도 직군의
일이고, **Testcontainers로 컨테이너를 띄우는 것부터 라이선스가 걸린다.**
`test-strategy.md` 5.1이 Testcontainers를 전제로 하므로 애초에 맞지 않는다.

다만 **회사에서 Oracle을 만날 가능성은 실재한다**(금융·공공·대기업 레거시).
그때 필요한 것은 "Oracle 사용 경험"보다 **SQL과 관계형 모델의 이해**이고,
그것은 PostgreSQL로 쌓으면 그대로 전이된다.
방언 차이(`ROWNUM` 등)는 그때 배우면 되는 종류다.

### "셋 중 뭐가 제일 좋냐"는 질문은 성립하지 않는다

성능 순위가 아니라 **성격 차이**다.

- 은행 코어 시스템 → Oracle
- 트래픽 큰 웹서비스에 이미 MySQL 인력이 있다 → MySQL
- **신규 프로젝트에서 DB가 규칙을 지켜주기를 원한다 → PostgreSQL** ← 우리
