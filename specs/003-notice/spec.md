## 개요

게시판 4종 중 **관리자만 글을 쓰는 유일한 게시판**이다. 목록·상세·페이징·검색은 002가 만든
공통 구조를 그대로 재사용하고, **003이 새로 만드는 것은 상단 고정(알림글) 하나**다.

**포함**: 공지 목록(고정 영역 포함) · 상세 · 조회수 · 관리자 등록/수정/삭제 · 상단 고정 지정

**제외**: 첨부 · 댓글 · 분류(카테고리) 관리 화면 · 메인 페이지의 공지 영역 (→ *Out of Scope*)

**이 스토리의 난점은 하나다 — 상단 고정과 페이징의 상호작용.**
요구사항은 *"고정글은 모든 페이지의 제일 상단에 노출된다"* 와 *"최대 5개, 초과 시 최신 5개만
노출"* 만 말하고, **그 둘이 만나면 생기는 질문 6개에 답하지 않는다**:

| # | 질문 | 요구사항의 답 |
|---|---|---|
| 1 | 2페이지에도 고정글이 보이는가 | **있다** — "모든 페이지" |
| 2 | 고정글이 같은 화면의 일반 목록에도 **중복**으로 나오는가 | **없다** |
| 3 | 글 번호("전체 게시글 수 기준 역순")를 셀 때 고정글을 포함하는가 | **없다** |
| 4 | 6번째 고정글은 **어디에도 안 보이게** 되는가 | **없다** |
| 5 | "개씩 보기 10"에 고정 5개가 포함되는가 | **없다** |
| 6 | 검색·정렬을 하면 고정 영역은 어떻게 되는가 | **없다** |

**2~6은 이 문서에서 판단했다.** 판단 내용과 근거는 각 FR과 *판단한 것 목록*에 있다.
판단하지 않고 넘기면 구현자가 각자 다르게 만들고, 그 차이는 **AC가 없어 아무도 잡지 못한다.**

## 002 에서 상속하는 것 — **여기서 다시 정의하지 않는다**

게시판 4종은 목록 구조가 같다. 002가 그 공통 규칙과 구현을 확정하고, **003은 참조한다.**
같은 규칙을 네 번 쓰면 네 벌이 조금씩 어긋나고, 어긋난 것을 문서로는 발견할 수 없다.

| 상속 항목 | 003에서의 값 |
|---|---|
| 기간 검색(등록일시 `from ~ to`) · **기본 1달 · 최대 1년** | 그대로 |
| 개씩 보기 **기본 10** · 20 · 30 · 40 · 50 | 그대로 (적용 범위만 `FR-011`에서 좁힌다) |
| 정렬 기준 **기본 등록일시** · 분류 · 제목 · 조회수 / 방향 **기본 내림차순** | 그대로 (적용 범위만 `FR-012`에서 좁힌다) |
| 개씩 보기·정렬 **선택 즉시 반영**(검색 버튼 불필요) | 그대로 |
| 페이징 `<<` `<` 1~10 `>` `>>` | 그대로 |
| 글 번호 = **전체 건수 기준 역순**(행 번호 아님) | 모집단만 `FR-009`에서 좁힌다 |
| `new` 아이콘 = 생성 후 N일 이내, 게시판별 설정 | **003은 7일** |
| 상세→목록, 등록/수정 취소→목록 시 **직전 검색조건 유지** | 그대로 |
| 등록/수정 공통: 제목 필수 100자 미만 · 내용 필수 4000자 미만 · **서버 검증** · 확인 절차 | 그대로 |
| 오류 응답 형식(`code` · `traceId`) | 그대로 |

**003이 상속 위에 더하는 것은 4가지뿐이다**: ① 상단 고정 ② 검색어 범위를 제목·내용으로 좁힘
③ 글 등록 주체를 관리자로 제한 ④ 분류 필수.

> **오류 코드 접두사**: 003이 새로 만드는 오류 코드는 `NOTICE_` 로 시작한다.
> **공통 목록 규칙 위반 코드**(기간 상한 초과, 잘못된 페이지 번호 등)는 **002가 확정**하며
> 003은 그 코드를 그대로 쓴다. 아래 AC에서 그런 코드는 *"002가 정한 … 오류 코드"* 로 표기한다.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 누구나 공지 목록을 본다 (Priority: P1) 🎯 MVP

로그인하지 않은 방문자도 공지 목록을 검색·정렬·페이징하며 볼 수 있다.

**Why this priority**: 공지사항은 **읽히려고 존재한다.** 관리자 등록 기능이 없어도 데이터만
있으면 가치가 성립하고, 고정 기능(US2)의 토대이므로 가장 먼저 완결한다.

**Independent Test**: 공지 데이터를 준비한 뒤 **로그아웃 상태로** 목록을 조회해 기본 조회·검색·
페이징이 동작하는지 확인.

**Acceptance Scenarios**:

- **AC-1** 기본 조회
  - **Given** 최근 1달 안에 등록된 공지가 12건 있고 **고정된 공지는 없고**
  - **When** 아무 조건 없이 목록을 조회하면
  - **Then** 200이고 **10건**이 반환되며, **등록일시 내림차순**이고, 총 페이지는 **2**,
    1페이지 첫 행의 글 번호는 **12**다
  - *근거*: 002의 공통 목록 규칙(기본 1달 · 기본 10개 · 기본 등록일시 내림차순 ·
    번호는 전체 건수 기준 역순)이 003에도 실제로 적용되는지 확인한다 (FR-001)

- **AC-2** 검색어 범위는 제목·내용뿐이다
  - **Given** 제목에만 `점검`이 있는 공지 A, 내용에만 `점검`이 있는 공지 B,
    **등록한 관리자 이름이 `점검`인** 공지 C가 각각 있고
  - **When** 검색어 `점검` 으로 조회하면
  - **Then** 200이고 결과에 **A와 B가 포함되고 C는 포함되지 않는다**
  - *근거*: 공지는 관리자만 쓰므로 등록자로 검색할 변별력이 없다. 다른 3개 게시판과
    검색 범위가 다른 유일한 게시판이다 (FR-002)

- **AC-3** 상세를 보고 목록으로 돌아오면 검색조건이 유지된다
  - **Given** 검색어 `점검` · 개씩 보기 `20` · 정렬 `조회수 내림차순` · 2페이지를 조회한 상태이고
  - **When** 목록에서 공지 하나의 상세로 들어갔다가 `목록` 으로 돌아오면
  - **Then** **같은 검색어 · 개씩 보기 · 정렬 · 페이지**의 목록이 표시된다 (FR-001)

- **AC-4** 기간 검색 상한을 넘기면 거부된다
  - **Given** 목록 조회를 준비했고
  - **When** 기간을 **1년 하고 하루**(`from`이 `to`보다 366일 이상 이전)로 지정해 조회하면
  - **Then** 400이고 **002가 정한 기간 상한 초과 오류 코드**로 응답한다
  - *근거*: 상한이 003에서 조용히 풀려 있으면 전 기간 스캔이 가능해진다.
    상속이 말뿐인지 실제인지 확인하는 항목이다 (FR-001)

- **AC-5** 로그인 없이 목록을 볼 수 있다
  - **Given** 로그인하지 않은 상태이고
  - **When** 공지 목록을 조회하면
  - **Then** 200이고 목록이 반환된다 (FR-003)

### User Story 2 - 관리자가 지정한 알림글이 모든 페이지 최상단에 보인다 (Priority: P1) ★

중요한 공지는 목록을 넘겨도 항상 위에 있다.

**Why this priority**: **003이 새로 만드는 유일한 기능**이고, 페이징·번호·정렬·검색 전부와
맞물려 있어 나중에 얹으면 목록 조회를 다시 설계해야 한다.

**Independent Test**: 고정 3건 + 일반 12건을 준비하고 1페이지·2페이지를 각각 조회해
고정 영역·중복·번호·정원을 확인. 고정 6건으로 늘려 노출 규칙을 확인.

> 아래 AC의 공통 사전조건 표기 **`[기본 데이터]`** = *공지 15건이 모두 최근 1달 안에 있고,
> 그중 3건이 고정으로 지정되어 있으며, 개씩 보기는 기본값 10이고 검색 조건은 전부 기본값이다.*

**Acceptance Scenarios**:

- **AC-6** 1페이지 최상단에 고정 영역이 있다
  - **Given** `[기본 데이터]` 이고
  - **When** 1페이지를 조회하면
  - **Then** 200이고 **고정 3건이 일반 목록보다 먼저** 반환되며, 고정 행과 일반 행이
    **서로 구분 가능**하다(고정 여부가 표시된다) (FR-004)

- **AC-7** 2페이지에도 같은 고정 영역이 있다
  - **Given** `[기본 데이터]` 이고
  - **When** **2페이지**를 조회하면
  - **Then** 200이고 **1페이지와 동일한 고정 3건이 동일한 순서로 최상단**에 반환된다
  - *근거*: 요구사항의 *"모든 페이지의 제일 상단"* 을 문자 그대로 못박는다.
    이 항목이 없으면 "1페이지에만"으로 구현되어도 아무 테스트가 실패하지 않는다 (FR-004)

- **AC-8** 고정 공지는 일반 목록에 중복으로 나오지 않는다
  - **Given** `[기본 데이터]` 이고
  - **When** 1페이지와 2페이지를 모두 조회하면
  - **Then** 고정된 3건의 식별자는 **어느 페이지의 일반 목록에도 나타나지 않고**,
    일반 목록의 총 건수는 **12**다(15 − 3)
  - *근거*: 같은 글이 한 화면에 두 번 보이면 사용자는 서로 다른 글로 읽는다.
    그리고 고정 행은 번호 대신 분류명을 쓰므로(`FR-010`) 중복되면
    **같은 글이 번호가 있는 채로도, 없는 채로도** 존재하게 된다 (FR-007)

- **AC-9** 고정이 6개면 최신 5개만 노출된다
  - **Given** 고정으로 지정된 공지가 **6건**이고 등록일시가 서로 다르고
  - **When** 목록을 조회하면
  - **Then** 고정 영역에는 **등록일시가 최신인 5건만** 반환된다 (FR-005)

- **AC-10** 노출에서 밀린 고정 공지는 일반 목록에 나타난다
  - **Given** AC-9 와 같은 상태(고정 6건, 노출 5건)이고
  - **When** 목록을 조회하면
  - **Then** 노출되지 않은 **6번째 고정 공지가 일반 목록에 번호를 가진 행으로 포함**된다
  - *근거*: 고정 영역에서도 빼고 일반 목록에서도 빼면 **그 공지는 어디에서도 볼 수 없다.**
    관리자는 "고정을 눌렀더니 글이 사라졌다"를 겪고 원인을 알 수 없다 (FR-008)

- **AC-11** 6번째 고정 지정이 거부되지 않는다
  - **Given** 이미 고정된 공지가 **5건** 있고 `ADMIN` 으로 로그인했고
  - **When** 여섯 번째 공지를 **고정 체크한 채로** 등록하면
  - **Then** 201이고 등록에 성공한다. **고정 개수 초과 오류를 반환하지 않는다**
  - *근거*: 요구사항은 *"5개를 넘게 등록하면 최신 5개만 노출"* 이라고 **노출 규칙으로** 정했다.
    등록을 막으면 관리자가 기존 고정을 먼저 해제해야 하는 2단계 작업이 되고,
    두 관리자가 동시에 6번째를 지정할 때 **한쪽이 실패**한다.
    노출 규칙으로 두면 동시 지정이 있어도 결과가 항상 결정적이다 (FR-006)

- **AC-12** 고정 행은 번호 대신 분류명을 보여준다
  - **Given** 분류가 `알림` 인 고정 공지와 분류가 `점검` 인 고정 공지가 있고
  - **When** 목록을 조회하면
  - **Then** 두 고정 행의 번호 칸에는 각각 **`알림` · `점검`** 이 표시되고 **숫자 번호가 없다**
  - *근거*: 요구사항의 `(알림)` 을 **고정 표식 문구**가 아니라 **그 공지의 분류명**으로 읽었다.
    고정 문구로 읽으면 분류가 무엇이든 `알림` 으로 덮여 분류 정보가 화면에서 사라진다
    (FR-010) — ⚠️ *판단 항목 J6*

- **AC-13** 글 번호는 고정 노출분을 제외하고 센다
  - **Given** `[기본 데이터]`(전체 15건 · 고정 노출 3건)이고
  - **When** 1페이지를 조회하면
  - **Then** 일반 목록 첫 행의 번호는 **12**이고 마지막 행은 **3**이며,
    2페이지 첫 행은 **2**, 마지막 행은 **1**이다
  - *근거*: 번호의 모집단이 15면 고정 3건이 차지한 번호가 **비어 있는 채로** 사용자에게 보인다
    (12, 11, 10 … 처럼 건너뛴 번호). 번호는 "목록에서 몇 번째 글인가"를 말해야 한다 (FR-009)

- **AC-14** 개씩 보기 정원에 고정 영역이 포함되지 않는다
  - **Given** 고정 5건 · 일반 12건이고 개씩 보기가 **10**이고
  - **When** 1페이지를 조회하면
  - **Then** **고정 5행 + 일반 10행 = 15행**이 반환되고, 총 페이지는 일반 목록 기준 **2**다
  - *근거*: 정원에 포함하면 개씩 보기 10 + 고정 5일 때 **일반 글이 5건만 보이는 페이지**가 되고,
    고정 개수가 바뀔 때마다 페이지 경계가 통째로 흔들린다 (FR-011)

- **AC-15** 사용자가 고른 정렬이 고정 영역에는 적용되지 않는다
  - **Given** `[기본 데이터]` 이고 고정 3건의 조회수가 등록일시 순서와 **반대**이고
  - **When** 정렬을 **조회수 내림차순**으로 바꿔 조회하면
  - **Then** **일반 목록만 조회수 내림차순**으로 정렬되고, **고정 영역은 등록일시 내림차순
    순서를 유지**한다
  - *근거*: 고정은 관리자가 의도한 노출 순서다. 사용자 정렬로 흐트러지면
    "가장 중요한 것을 맨 위에 둔다"는 의도가 화면마다 달라진다 (FR-012)

- **AC-16** 검색을 하면 고정 영역이 사라지고 대신 일반 목록에 편입된다
  - **Given** `[기본 데이터]` 이고 고정 3건 중 1건의 제목에 `점검` 이 있고
  - **When** 검색어 `점검` 으로 조회하면
  - **Then** **고정 영역이 표시되지 않고**, 조건에 맞는 그 고정 공지 1건은
    **일반 목록에 번호를 가진 행으로** 포함된다
  - *근거*: 검색은 "특정 글을 찾겠다"는 의도이고, 조건에 맞지 않는 고정글이 상단에 남으면
    그 화면은 더 이상 검색 결과가 아니다. 다만 **고정 영역을 숨기면서 제외 규칙(`FR-007`)까지
    같이 풀지 않으면** 조건에 맞는 고정 공지가 **검색 결과에서 통째로 빠진다** —
    두 규칙은 반드시 함께 켜지고 함께 꺼진다 (FR-013) — ⚠️ *판단 항목 J5*

- **AC-17** 모든 공지가 고정인 경우
  - **Given** 공지가 총 3건이고 **3건 모두 고정**이고
  - **When** 목록을 조회하면
  - **Then** 200이고 고정 3행이 반환되며, **일반 목록은 0건**, 총 페이지는 **1**,
    빈 목록 안내가 표시되고 오류가 아니다 (FR-007 · FR-009 경계)

- **AC-18** 고정을 해제하면 일반 목록으로 내려온다
  - **Given** 고정된 공지 A가 목록 고정 영역에 노출 중이고 `ADMIN` 으로 로그인했고
  - **When** A를 수정해 **고정 체크를 해제**한 뒤 목록을 다시 조회하면
  - **Then** A는 고정 영역에 없고 **일반 목록에 번호를 가진 행으로** 등록일시 순서에 맞는
    자리에 나타난다 (FR-008 · FR-022)

### User Story 3 - 공지 하나를 읽는다 (Priority: P1)

목록에서 고른 공지의 전문을 본다.

**Why this priority**: 목록만 있고 상세가 없으면 공지를 읽을 수 없다. US1과 함께 최소 가치를 만든다.

**Independent Test**: 공지 하나를 준비해 **로그아웃 상태로** 상세를 조회하고, 조회 전후의
조회수를 비교.

**Acceptance Scenarios**:

- **AC-19** 상세 표시 항목
  - **Given** 분류 `알림`, 제목 `정기 점검 안내`, 내용, 등록한 관리자 이름 `홍관리` 인 공지가 있고
  - **When** 그 공지의 상세를 조회하면
  - **Then** 200이고 **분류 · 제목 · 등록일시 · 등록한 관리자 이름 · 조회수 · 내용**이
    모두 포함된다 (FR-014)

- **AC-20** 로그인 없이 상세를 볼 수 있다
  - **Given** 로그인하지 않은 상태이고
  - **When** 공지 상세를 조회하면
  - **Then** 200이고 내용이 반환된다 (FR-003)

- **AC-21** 고정 공지의 상세도 형식이 같다
  - **Given** 고정으로 지정된 공지가 있고
  - **When** 그 상세를 조회하면
  - **Then** **AC-19와 동일한 항목**이 반환되고, 고정 여부 때문에 표시 항목이 늘거나 줄지 않는다
  - *근거*: 고정은 **목록에서의 노출 방식**이지 글의 종류가 아니다.
    상세를 다르게 만들면 화면이 두 벌이 되고 그 차이를 유지할 이유가 없다 (FR-015)

- **AC-22** 상세를 열면 조회수가 오른다
  - **Given** 조회수가 `7` 인 공지가 있고
  - **When** 그 상세를 1회 조회하면
  - **Then** 조회수가 `8` 이 되고, 같은 사람이 다시 조회하면 `9` 가 된다(중복 방지 없음)
  - *근거*: 요구사항에 중복 카운트 규칙이 없다. **단순 증가**로 정하고 판단으로 남긴다 (FR-016)

- **AC-23** 동시 조회에서 조회수가 유실되지 않는다
  - **Given** 조회수가 `0` 인 공지가 있고
  - **When** **10개의 요청이 동시에** 그 상세를 조회하면
  - **Then** 최종 조회수는 **정확히 10**이다
  - *근거*: "읽고 → 1 더하고 → 쓴다"로 구현하면 동시 요청에서 증가분이 덮어써져 사라진다.
    조회수는 목록 정렬 기준이므로 틀리면 목록 순서가 틀린다 (FR-016)

- **AC-24** 관리자 관리 화면에서 열어도 조회수가 오르지 않는다
  - **Given** 조회수가 `7` 인 공지가 있고 `ADMIN` 으로 로그인했고
  - **When** **관리자 관리 화면의 상세/수정**으로 그 공지를 열면
  - **Then** 조회수가 **`7` 그대로**다
  - *근거*: 관리자가 검수·수정하려고 열 때마다 오르면 조회수가 **독자 수 지표가 아니게 된다**
    (FR-017) — ⚠️ *판단 항목 J9*

- **AC-25** 없는 공지와 삭제된 공지의 응답이 같다
  - **Given** 존재한 적 없는 식별자 `999999` 와, **삭제된** 공지의 식별자가 각각 있고
  - **When** 두 식별자로 각각 상세를 조회하면
  - **Then** 둘 다 404이고 `code=POST_NOT_FOUND` 이며 **상태코드·code·메시지가 모두 같다**
  - *근거*: 응답이 다르면 "그 번호의 공지가 있었다가 지워졌다"를 알려준다.
    constitution 원칙 IV(리소스 존재 여부를 노출하지 않는다) (FR-018)

### User Story 4 - 관리자가 공지를 등록·수정·삭제한다 (Priority: P2)

관리자가 공지를 쓰고 고치고 지우며, 중요한 것은 상단에 고정한다.

**Why this priority**: US1~US3이 있어야 결과를 확인할 수 있다. 다만 이것이 없으면
공지가 데이터베이스에 손으로 넣어야만 생기므로 스토리 완결에는 필수다.

**Independent Test**: `ADMIN` 으로 로그인해 등록 → 목록에서 확인 → 수정 → 삭제 → 404 확인.

**Acceptance Scenarios**:

- **AC-26** 등록 성공
  - **Given** `ADMIN` 으로 로그인했고 활성 분류 `알림` 이 있고
  - **When** 분류 `알림`, 제목 `정기 점검 안내`, 내용(정상), **상단 고정 체크**로 등록하면
  - **Then** 201이고 목록의 **고정 영역**에 그 공지가 나타나며 등록한 관리자 이름이 표시된다
    (FR-019 · FR-022)

- **AC-27** 제목 길이 경계
  - **Given** `ADMIN` 으로 로그인했고
  - **When** 제목을 **99자**로 등록하면 성공(201)하고, **100자**로 등록하면
  - **Then** 400이고 `code=POST_TITLE_LENGTH_INVALID` (허용: 1자 이상 **100자 미만**) (FR-019)

- **AC-28** 내용 길이 경계
  - **Given** `ADMIN` 으로 로그인했고
  - **When** 내용을 **3999자**로 등록하면 성공(201)하고, **4000자**로 등록하면
  - **Then** 400이고 `code=POST_CONTENT_LENGTH_INVALID` (허용: 1자 이상 **4000자 미만**) (FR-019)

- **AC-29** 분류 누락
  - **Given** `ADMIN` 으로 로그인했고
  - **When** 분류를 지정하지 않고 등록하면
  - **Then** 400이고 `code=POST_CATEGORY_REQUIRED` (FR-020)

- **AC-30** 비활성 분류로는 등록할 수 없다
  - **Given** 분류 `이벤트` 가 **사용 안 함(비활성)** 으로 내려가 있고 `ADMIN` 으로 로그인했고
  - **When** 그 분류로 등록하거나 수정하면
  - **Then** 400이고 `code=POST_CATEGORY_NOT_SELECTABLE`
  - *근거*: 비활성은 "더 이상 쓰지 않는다"는 뜻이고, 목록 필터의 분류 선택지에도 없다.
    막지 않으면 **어떤 분류 필터로도 찾을 수 없는 공지**가 생긴다 (FR-020)

- **AC-31** 화면 검증을 우회한 직접 호출도 차단된다
  - **Given** 화면을 거치지 않고 등록 요청을 직접 보낼 수 있는 상태이고 `ADMIN` 으로 로그인했고
  - **When** AC-27 ~ AC-30의 위반 값을 담아 직접 요청하면
  - **Then** 각 AC와 **동일한** 상태코드와 code로 거부된다
  - *근거*: 001 `FR-002`와 같은 원칙. 화면 검증은 편의이고 **서버 검증이 실제 방어선**이다
    (FR-019)

- **AC-32** 분류가 비활성으로 내려가도 기존 공지의 분류명은 유지된다
  - **Given** 분류 `이벤트` 로 등록된 공지가 있고, 그 뒤 `이벤트` 가 비활성으로 내려갔고
  - **When** 목록과 상세를 조회하면
  - **Then** 그 공지의 분류명은 **`이벤트` 로 계속 표시**되고 오류가 나지 않는다
  - *근거*: 과거 게시물을 소급 변경하지 않는다. 요구사항이 *"사용 중인 분류는 삭제하지 않고
    비활성으로 내린다"* 로 정한 이유가 이것이다 (FR-021)

- **AC-33** 다른 관리자가 쓴 공지도 수정·삭제할 수 있다
  - **Given** 관리자 A가 등록한 공지가 있고 **관리자 B**로 로그인했고
  - **When** B가 그 공지를 수정하거나 삭제하면
  - **Then** 성공한다(수정 200 · 삭제 204)
  - *근거*: 공통 규칙 *"본인 글만 수정·삭제"* 는 **사용자가 쓰는 게시판**의 규칙이다.
    공지는 조직의 공식 게시물이고, 작성 관리자가 부재하면 오타 하나도 못 고치는 상태가 된다
    (FR-027) — ⚠️ *판단 항목 J10*

- **AC-34** 삭제하면 목록·상세 어디에서도 보이지 않는다
  - **Given** 공지 A가 목록에 있고 `ADMIN` 으로 로그인했고
  - **When** A를 삭제한 뒤 목록과 A의 상세를 각각 조회하면
  - **Then** 목록에 A가 없고(고정 영역·일반 목록 모두), A의 상세는 **AC-25와 동일한 404**다
    (FR-023)

- **AC-35** 내용에 담긴 스크립트가 실행되지 않는다
  - **Given** `ADMIN` 으로 로그인했고
  - **When** 내용에 스크립트를 포함해 등록한 뒤 그 상세를 화면에서 열면
  - **Then** 스크립트가 **실행되지 않고** 입력한 문자 그대로 보인다
  - *근거*: 관리자만 쓰는 게시판이어도 관리자 계정이 탈취되면 **전 사용자에게 스크립트가
    배포된다.** 공지는 모든 방문자가 보는 화면이라 피해 범위가 게시판 중 가장 넓다 (FR-024)

- **AC-36** 두 관리자가 같은 공지를 동시에 수정
  - **Given** 관리자 A와 B가 같은 공지의 수정 화면을 각각 열었고
  - **When** A가 저장한 뒤 B가 저장하면
  - **Then** **둘 다 성공하고 최종 내용은 B의 것**이며, 충돌 오류를 반환하지 않는다
  - *근거*: 공지 수정은 빈도가 낮고 관리자가 소수다. 낙관적 잠금을 넣으면 충돌 화면과
    병합 안내가 필요한데 **그 화면이 요구사항에 없다.** 대가는 A의 수정이 조용히 덮이는 것
    (FR-025) — ⚠️ *판단 항목 J12*

- **AC-37** 확인 절차와 취소 복귀
  - **Given** 검색어 `점검` · 2페이지를 조회한 뒤 등록 화면에 들어왔고
  - **When** ① `등록` 을 누르면 `"정말로 등록 하시겠습니까?"` 확인 후 진행되고
    ② `취소` 를 누르면 `"작성을 취소하시겠습니까?"` 확인 후 목록으로 돌아가면
  - **Then** ②의 목록은 **검색어 `점검` · 2페이지가 유지된 상태**다.
    삭제도 `"정말로 삭제 하시겠습니까"` 확인 후에만 수행된다 (FR-019)

- **AC-42** 다른 게시판의 분류·없는 분류로는 등록할 수 없다 *(4번 계획 신설)*
  - **Given** `ADMIN` 으로 로그인했고, **자유게시판에만 있는 활성 분류** `잡담` 과
    **존재하지 않는 분류 식별자** `999999` 가 각각 있고
  - **When** 둘 중 어느 것으로든 공지를 등록하거나 수정하면
  - **Then** 400이고 `code=POST_CATEGORY_NOT_SELECTABLE` 이며, 공지가 생성·변경되지 않는다
  - *근거*: `AC-30`(비활성 분류)이 막으려던 사고와 **같은 사고**다 — 공지 목록의 분류 필터는
    **공지사항 분류만** 보여주므로, 다른 게시판 분류로 저장된 공지는 **어떤 분류 필터로도
    찾을 수 없다.** 게다가 고정 행은 번호 칸에 분류명을 쓰므로(`FR-010`) 목록 상단에
    **다른 게시판의 분류명**이 그대로 노출된다. `AC-29`(누락)·`AC-30`(비활성)만으로는
    이 경로가 열려 있다 (FR-029)

- **AC-43** 삭제된 공지의 수정·삭제 요청은 404다 *(4번 계획 신설)*
  - **Given** 삭제된 공지의 식별자가 있고 `ADMIN` 으로 로그인했고
  - **When** 그 식별자로 **수정**을 요청하고, 이어서 **삭제**를 요청하면
  - **Then** 둘 다 404이고 `code=POST_NOT_FOUND` 이며, **`AC-25`의 상세 조회 응답과
    상태코드·code·메시지가 모두 같다**. 403이 아니다
  - *근거*: Edge Cases에 규칙은 적혀 있었으나 **AC가 없어 검증되지 않는 상태**였다.
    검사 순서가 *인증 → 권한 → 존재*여야 하는데, **소유자·존재 확인을 권한 검사보다 먼저
    하면 403이 나가고** 그 순간 *"그 번호의 공지가 있었다"* 가 새어 나간다
    (constitution 원칙 IV). `AC-34`는 **상세 조회**만 보므로 이 경로를 덮지 않는다
    (FR-018 · FR-023)

### User Story 5 - 관리자만 쓸 수 있다 (Priority: P2)

읽기는 누구나, 쓰기는 관리자만. 화면이 아니라 서버가 막는다.

**Why this priority**: 001이 만든 권한 경계가 003에서 **실제로 적용되는지**를 확인하는
스토리다. US4가 있어야 검증 대상이 생긴다.

**Independent Test**: 미인증 · `USER` · `ADMIN` 세 상태로 같은 등록 요청을 보내
401 / 403 / 201 이 갈리는지 확인.

**Acceptance Scenarios**:

- **AC-38** 미인증 등록 요청
  - **Given** 로그인하지 않은 상태이고
  - **When** 공지 등록을 요청하면
  - **Then** 401이고 `code=AUTH_REQUIRED` (001 `AC-21`과 동일한 형태) (FR-026)

- **AC-39** 일반 사용자의 등록·수정·삭제 요청
  - **Given** `USER` 권한으로 로그인했고 **화면에는 등록/수정/삭제 버튼이 보이지 않고**
  - **When** 등록·수정·삭제를 **직접 요청**하면
  - **Then** 셋 다 403이고 `code=AUTH_FORBIDDEN`
  - *근거*: 001 `FR-019`·`AC-26`. 화면에서 버튼을 숨기는 것은 권한 검증이 아니다 (FR-026)

- **AC-40** 미인증으로 관리자 등록 화면에 진입하면 **관리자** 로그인으로 보낸다
  - **Given** 로그인하지 않은 상태이고
  - **When** 관리자 공지 등록 화면 진입을 시도하면
  - **Then** **관리자 로그인 진입점**(사용자 로그인 화면이 아니다)으로 이동하고,
    `ADMIN` 으로 로그인하면 **원래 가려던 공지 등록 화면**으로 복귀한다
  - *근거*: 공통 규칙은 *"미로그인 글 등록 시도 → 로그인 화면 → 로그인 후 글 등록 화면"* 인데,
    공지는 **관리자만 쓴다.** 사용자 로그인 화면으로 보내면 관리자는 거기서 로그인할 수 없고
    (001 `FR-034`가 관리자 진입점을 분리했다) 로그인해도 403으로 튕긴다 (FR-028)
    — ⚠️ *판단 항목 J13*

- **AC-41** 복귀 목적지가 외부 주소면 그리로 가지 않는다
  - **Given** 로그아웃 상태이고 관리자 로그인 화면에 복귀 목적지가 **외부 주소**로 지정되어 있고
  - **When** 로그인을 완료하면
  - **Then** **그 외부 주소로 이동하지 않고** 관리자 기본 화면으로 이동한다
  - *근거*: 001 `FR-035`·`AC-34`(오픈 리다이렉트 방지)가 003의 복귀 경로에도 그대로 적용된다.
    001에서 막았다고 003에서 자동으로 막히는 것이 아니다 — **복귀 목적지를 넘기는 화면이
    003에 새로 생겼다** (FR-028)

### Edge Cases

**상단 고정 · 페이징 경계**

- **고정 0건**: 고정 영역을 렌더링하지 않는다(빈 영역을 남기지 않는다). 일반 목록만 표시된다.
- **고정 정확히 5건**: 5건 전부 노출되고 일반 목록에서는 전부 제외된다(`AC-8`의 규칙 그대로).
- **고정 6건 이상**: 노출 5건 + 나머지는 일반 목록(`AC-9`·`AC-10`).
  고정이 **20건**이어도 규칙은 같다 — 노출 5, 일반 목록 15.
- **전체가 고정글**: 일반 목록 0건, 총 페이지 1, 빈 목록 안내(`AC-17`). 오류가 아니다.
- **일반 목록이 0건인데 고정이 있는 상태에서 2페이지 요청**: 존재하지 않는 페이지다.
  → **1페이지와 동일한 결과**(고정 영역 + 빈 일반 목록)를 반환하고 오류로 처리하지 않는다.
  *(002가 정한 공통 페이지 범위 규칙을 따른다. 002가 400으로 정하면 003도 400이다.)*
- **마지막 페이지의 마지막 공지가 삭제되어 페이지가 사라진 상태에서 그 페이지를 다시 조회**:
  위와 같은 규칙을 따른다.
- **고정 지정과 목록 조회의 경합**: 관리자가 고정을 지정하는 순간 조회 중이던 사용자에게
  즉시 반영되지 않아도 된다. **다음 조회부터 반영**되면 충족이다.
- **두 관리자가 동시에 6번째 고정을 지정**: 둘 다 성공한다(`AC-11`). 노출은 "최신 5개"
  규칙으로 결정되므로 **결과가 항상 하나로 정해진다** — 등록을 막는 설계였다면 여기서
  한쪽이 실패했을 것이다.

**입력 경계**

- 제목 **0자 / 공백만**: 필수 위반으로 400 `POST_TITLE_REQUIRED`.
  앞뒤 공백을 제거한 뒤 길이를 센다.
- 내용 **0자 / 공백만**: 400 `POST_CONTENT_REQUIRED`.
- 제목·내용의 길이는 **문자 수**로 센다(바이트가 아니다). 한글·이모지 1자는 1자다.
- 검색어에 `%` `_` 같은 **부분 일치 특수문자**가 들어와도 **문자 그대로** 찾는다
  (와일드카드로 해석하지 않는다). 해석하면 `%` 하나로 전체가 조회된다.
- 검색어가 **공백만**이면 검색어를 지정하지 않은 것과 같이 처리한다.
- 기간 `from` 이 `to` 보다 **뒤**인 경우: 400. 코드는 002가 정한 공통 코드를 쓴다.

**권한 · 상태 경계**

- **`USER` 로 로그인한 채 목록·상세 조회**: 정상 200. 읽기는 권한과 무관하다.
- **삭제된 공지를 수정 요청**: `AC-25`와 같은 404. 403이 아니다(존재 여부 비노출).
  → **`AC-43`이 이것을 검증한다**(4번 계획 신설. 규칙만 있고 AC가 없었다).
- **고정된 공지를 삭제**: 삭제되고 고정 영역에서도 사라진다. 밀려 있던 6번째 고정글이 있으면
  **다음 조회에서 그 자리를 채운다**(노출 규칙이 매 조회마다 계산되므로 자동으로 성립한다).
- **분류가 비활성으로 내려간 뒤 그 공지를 수정**: 분류를 **바꾸지 않으면** 저장이 성공하는가?
  → **활성 분류로 바꾸도록 요구한다**(400 `POST_CATEGORY_NOT_SELECTABLE`). 근거: 수정은
  "지금의 규칙으로 다시 저장하는 것"이고, 비활성 분류를 통과시키면 `AC-30`이 우회된다.
  — ⚠️ *판단 항목 J11*

- **FR-004**: 관리자가 고정으로 지정한 공지는 목록의 **모든 페이지 최상단**에 일반 목록과

  하는 것이 이 기능의 전부다)*
- **FR-005**: 고정 영역에 노출하는 공지는 **최대 5개**여야 하며, 지정된 고정이 5개를 넘으면
  **등록일시가 최신인 5개만** 노출해야 한다(MUST). *(상단이 고정글로 뒤덮이면 일반 목록이
  화면에서 밀려나 목록의 기능이 사라진다)*
- **FR-006**: 시스템은 6번째 이상의 고정 지정을 **거부해서는 안 된다**(MUST NOT).

- **FR-007**: 고정 영역에 노출 중인 공지를 **같은 화면의 일반 목록에 중복 노출하는 것을

- **FR-008**: 고정으로 지정되었으나 **노출 5개에서 밀린** 공지는 일반 목록에 포함해야 한다(MUST).
  *(고정 영역에서도 빼고 일반 목록에서도 빼면 그 공지는 어디에서도 볼 수 없다)*
- **FR-009**: 일반 목록의 글 번호는 **고정 영역에 노출 중인 공지를 제외한 전체 건수 기준
  역순**으로 계산해야 한다(MUST). *(제외하지 않으면 고정글이 가져간 번호가 목록에서
  건너뛴 채로 보인다)*
- **FR-010**: 고정 영역의 각 행은 번호 대신 **그 공지의 분류명**을 표시해야 한다(MUST).
  *(요구사항의 `(알림)` 을 고정 표식 문구가 아니라 분류명으로 읽었다 — J6)*
- **FR-011**: `개씩 보기` 값은 **일반 목록에만** 적용해야 한다(MUST). 고정 영역의 건수를
  그 정원에 포함하는 것을 금지한다(MUST NOT). *(포함하면 고정 개수가 바뀔 때마다 페이지
  경계가 통째로 흔들리고, 고정 5 + 10개씩 보기에서 일반 글이 5건만 보인다)*
- **FR-012**: 고정 영역 내부의 정렬은 **등록일시 내림차순으로 고정**해야 하며, 사용자가 선택한
  정렬 기준·방향을 고정 영역에 적용하는 것을 금지한다(MUST NOT). *(고정은 관리자가 의도한
  노출 순서다. 사용자 정렬로 흐트러지면 의도가 화면마다 달라진다)*
- **FR-013**: **검색이 적용된 조회**(검색어가 있거나, 분류가 `전체 분류` 가 아니거나, 기간이

  *(두 규칙이 함께 켜지고 함께 꺼지지 않으면 조건에 맞는 고정 공지가 검색 결과에서 통째로
  빠진다 — J5)*

## Success Criteria *(mandatory)*

- **SC-001**: 방문자는 로그인 없이 공지 목록과 전문을 읽을 수 있다.
- **SC-002**: 관리자가 고정으로 지정한 공지는 **사용자가 몇 페이지를 보고 있든** 화면 상단에 있다.
- **SC-003**: 한 화면에 **같은 공지가 두 번 나타나는 경우가 0건**이다.
- **SC-004**: 관리자가 고정을 지정한 뒤 **그 공지가 목록 어디에서도 보이지 않는 경우가 0건**이다.
- **SC-005**: 일반 목록의 글 번호는 **건너뛰거나 중복되지 않는다** — 1페이지 마지막 번호와
  2페이지 첫 번호가 연속이다.
- **SC-006**: 화면을 거치지 않고 직접 요청해도 검증과 권한 규칙이 동일하게 적용된다 —
  **화면 검증 우회로 통과하는 경로가 0건**이다.
- **SC-007**: 관리자가 아닌 요청의 등록·수정·삭제는 **100%** 서버에서 거부된다.
- **SC-008**: 조회수는 동시 접속에서도 **실제 조회 횟수와 일치**한다.
- **SC-009**: 목록 화면에서 공통 규칙(기간·정렬·페이징·검색조건 유지)의 동작이 자유게시판과
  **다르게 보이는 항목이 0건**이다 — 검색어 범위와 고정 영역을 제외하고.

## Assumptions

요구사항에 없거나 불명확해 합리적 기본값을 택한 항목이다. 4번 계획에서 확정되거나 뒤집힐 수 있다.

1. **분류(카테고리) 데이터는 004가 제공한다.** 003은 "활성 분류 목록"을 읽고 참조만 한다.
   003이 분류를 만들거나 고치지 않는다.
2. **공통 목록·등록 구현은 002가 제공한다.** 003은 그 위에 고정 영역만 얹는다.
   002가 확정하기 전에는 003의 `FR-001`·`FR-019`가 가리키는 대상이 비어 있다.
3. **`new` 아이콘 기준일은 7일**이다. 게시판별 설정이 가능해야 한다는 공통 규칙을 따르되
   003의 값은 7일로 둔다.
4. **고정 최대 노출 5개는 003 고정값**이다. 설정으로 빼지 않는다 — 요구사항이 숫자를 명시했고
   바꿔야 할 이유가 나오면 그때 설정으로 승격한다.
5. **"최신 5개"의 기준은 등록일시**다. *"고정으로 지정한 시각"* 이라는 개념을 도입하지 않는다
   (→ *판단 항목 J4*, **`ADR-016`**).
6. **공지에는 첨부와 댓글이 없다.** 요구사항 표에 둘 다 `X` 다.
7. **등록자 표기는 관리자의 이름**이다(아이디가 아니다). 요구사항 3.2의 *"등록한 관리자 이름"*.
8. **공지 삭제는 사용자에게 "없는 것"으로 보이면 충족**이다. 물리 삭제인지 논리 삭제인지는
   데이터 모델에서 정한다(→ **`ADR-010`**).
9. **관리자 목록 화면의 컬럼 구성은 사용자 목록과 같다고 가정**한다. 요구사항 3.3이
   *"목록 + `글 등록` 버튼"* 만 말한다. 004에서 관리자 화면 골격이 확정되면 조정될 수 있다.
10. **고정 여부는 관리자 목록에서도 확인 가능**해야 한다고 가정한다 — 노출 중인 5개와
    밀린 고정글을 구분해 보여준다. 그렇지 않으면 관리자는 `FR-005`가 왜 자기 글을 안 보여주는지
    알 수 없다. *(요구사항에 없는 화면 요소 — J14)*

| **J12** | 동시 수정은 **마지막 저장이 이긴다**(충돌 오류 없음) | 충돌 안내·병합 화면이 요구사항에 없다. 공지 수정은 빈도가 낮고 관리자가 소수다. **대가는 앞선 수정이 조용히 덮이는 것** | `FR-025`·`AC-36` 재작성 · 버전 값 보관이 필요해져 **데이터 모델 변경** |
| **J13** | 미인증으로 관리자 공지 등록 화면 진입 시 **관리자 로그인 진입점**으로 보낸다 | 001 `FR-032`가 진입점을 분리했다. 사용자 로그인 화면으로 보내면 관리자는 거기서 로그인할 수 없고(001 `FR-034`) 로그인해도 403이다 | `FR-028`·`AC-40` 재작성 |
| **J14** | 관리자 목록에서 **노출 중인 고정 5개와 밀린 고정글을 구분해** 보여준다 | 구분이 없으면 관리자는 자기 글이 왜 상단에 없는지 알 수 없다 | Assumptions 10 삭제 · 관리자 화면 요구사항에서 제거 |
| **J15** | 고정 영역은 **매 조회 시점에 계산**한다(미리 저장된 목록이 아니다) | 고정글 삭제·해제 시 밀려 있던 6번째가 자동으로 자리를 채운다. 저장해 두면 그 동기화를 코드가 직접 해야 하고 빠뜨리면 5개 미만이 노출된다 | 고정 노출 목록을 별도로 관리하는 설계가 필요 |
| **J16** | 검색어의 `%` `_` 는 **문자 그대로** 찾는다 | 와일드카드로 해석되면 `%` 한 글자로 전체가 조회된다. 4종 공통 사안이므로 002와 같아야 한다 | 002와 함께 재작성 |
| **J17** | 공지에는 **분류가 필수**다 | 요구사항 3.3 등록 화면에 분류가 있고, 고정 행이 번호 대신 분류명을 쓰므로(J6) 분류가 없으면 **번호 칸이 빈 행**이 생긴다 | `FR-020`·`AC-29` 재작성 · `FR-010` 에 분류 없음 처리 추가 |

> **판단 항목이 17개인 이유를 숨기지 않는다.** 요구사항 3장은 4개 문단이고, 그 4개 문단이
> 페이징·번호·정렬·검색·권한과 만나는 지점을 하나도 규정하지 않았다.
> **판단하지 않고 넘기면 구현자가 각자 다르게 만들고, AC가 없으므로 어느 쪽도 실패하지 않는다.**

<details>
<summary>번호 부여 전 원문 (근거는 ADR로 옮겨졌다)</summary>

> **번호를 붙이지 않는다.** ADR 번호는 프로젝트 전역 연속이고 002·004·005·006이 병렬로
> 작성 중이라 여기서 번호를 정하면 충돌한다. **번호는 통합 단계가 붙인다.**
> 아래는 *무엇을 · 왜 결정해야 하는지*만 적은 것이다.

**후보 1 — 상단 고정의 순서 기준: 등록일시 vs 고정 지정 시각**
- **무엇**: `FR-005`의 *"최신 5개"* 와 `FR-012`의 고정 영역 정렬을 무엇으로 정렬할 것인가.
- **왜 ADR인가**: "고정 지정 시각"을 택하면 **저장할 값이 하나 늘어난다**(데이터 모델 변경).
  이미 데이터가 쌓인 뒤에 바꾸면 기존 공지의 그 값을 무엇으로 채울지 결정해야 한다.
- **실재하는 선택지**: ① 등록일시 ② 고정 지정 시각 ③ 관리자가 지정하는 노출 순서 값
  — ③은 요구사항에 화면이 없으나 실무에서 흔하다. **셋 다 검토되어야 한다.**
- **현재 판단**: ① (J4). 오래된 공지를 다시 고정해도 맨 위로 오지 않는다는 대가가 있다.

**후보 2 — 게시판 게시물의 삭제 방식: 물리 삭제 vs 논리 삭제**
- **무엇**: 삭제된 게시물을 실제로 지우는가, 표시만 하고 남기는가.
- **왜 ADR인가**: 이미 쌓인 데이터를 손대야 하고 **게시판 4종 전부에 동일하게 적용**된다.
  나중에 논리 삭제로 바꾸면 그전에 물리 삭제된 것은 복구할 수 없다.
- **003의 관심사**: `FR-018`(없는 것과 삭제된 것의 응답이 같아야 한다)이 어느 쪽에서도
  성립해야 한다. **003 단독으로 정할 사안이 아니다 — 002 또는 데이터 모델 단계로 올린다.**

**후보 3 — 조회수 증가 규칙: 단순 증가 vs 중복 방지**
- **무엇**: 같은 사람의 반복 조회를 어떻게 셀 것인가, 그리고 동시 증가를 어떻게 보장할 것인가.
- **왜 ADR인가**: 중복 방지를 택하면 **"누가 언제 봤는지"를 저장**해야 해서 데이터가 늘고,
  게시판 4종·모든 상세 조회에 적용된다. 나중에 바꾸면 과거 조회수의 의미가 달라진다.
- **003의 관심사**: `FR-016`. **요구사항 1.4가 이미 "단순 증가로 하고 문서에 남긴다"고
  적었으므로 결정은 사실상 되어 있고, ADR은 그 근거와 대가를 남기기 위한 것**이다.

**후보 4 — 관리자 권한 모델: 역할 기반 전권 vs 작성자 소유권**
- **무엇**: `ADMIN` 이 다른 관리자의 게시물을 수정·삭제할 수 있는가. 댓글 삭제(002)도 같은 축이다.
- **왜 ADR인가**: 권한 검증 코드 전반에 걸치고, 소유권 모델을 나중에 도입하면 **이미 쌓인
  게시물의 소유자 판정 기준**을 정해야 한다. 그리고 "누가 남의 글을 고쳤는가"를 남기려면
  **감사 기록이 필요**해진다.
- **현재 판단**: 역할 기반 전권 (J10). 대가는 관리자 간 상호 견제가 없다는 것.

**후보 5 — 목록 조회(검색·정렬·페이징 + 고정 영역)의 조회 도구**
- **무엇**: `process.md` 6.2 미룬 것 4번(QueryDSL·JOOQ·MyBatis 부분 도입)의 방아쇠는 **002**다.
- **왜 003에 적는가**: 003의 고정 영역은 **한 화면에 서로 다른 두 개의 조회**(고정 5건 +
  일반 페이징)를 합치므로 002의 목록 조회보다 조건이 하나 더 붙는다. **002가 도구를 정할 때
  이 형태가 판단 재료에 포함되어야 한다.** 003이 따로 정하지 않는다.

## Out of Scope

- **분류(카테고리) 관리 화면** — 004. 003은 활성 분류 목록을 읽기만 한다.
- **관리자 화면 골격**(좌측 LNB · 상단 인사·로그아웃) — 004.
- **메인 페이지의 공지 영역**(최신 5개 · `더보기+` · `new`) — 메인 담당 스토리.
  그 스토리가 003의 목록 조회를 재사용할 수 있으나, **메인에 고정 규칙을 적용할지는 003이
  정하지 않는다** — 메인은 페이징이 없어 `FR-004`(모든 페이지 최상단)가 성립하지 않는다.
- **첨부파일 · 댓글** — 공지사항에는 없다.
- **공지 예약 발행 · 노출 기간 설정 · 임시 저장** — 요구사항에 없다.
- **고정글 개수를 관리자가 설정하는 화면** — 5개는 003 고정값이다(Assumptions 4).
- **공지 수정 이력 · 감사 기록** — **`ADR-017`**가 뒤집히면 필요해진다.
