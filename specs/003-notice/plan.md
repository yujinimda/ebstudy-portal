## Summary

**만들 것**: 002가 확정한 공통 목록·등록 구조 위에 **상단 고정(알림글) 하나**를 얹은 공지사항.
읽기는 누구나, 쓰기는 `ADMIN` 만.

**기술 접근**: 공지 목록 한 번의 요청이 **서로 다른 두 개의 조회**를 반환한다 —
**고정 영역**(등록일시 내림차순 최신 5건, 페이징·정렬·정원과 무관)과
**일반 목록**(고정 노출분을 제외한 페이징 결과). 이 둘을 **하나의 트랜잭션·하나의 스냅샷**에서
계산하는 것이 이 스토리의 설계 전부다.

**이 스토리를 관통하는 설계 축**: **고정 규칙 5개는 한 덩어리이고, 함께 켜지고 함께 꺼진다.**

```
① 일반 목록에서 제외(FR-007)   ② 밀린 것은 일반 목록에 편입(FR-008)
③ 번호 모집단에서 제외(FR-009) ④ 개씩 보기 정원에서 제외(FR-011)
⑤ 검색 시 고정 영역 숨김 + ①③ 동시 해제(FR-013)
```

**다섯 중 하나만 어긋나면 글이 사라지거나 두 번 보인다.** ①만 켜고 ②를 빠뜨리면
6번째 고정글이 **어디에도 없고**, ⑤에서 ①을 함께 끄지 않으면 조건에 맞는 고정 공지가
**검색 결과에서 통째로 빠진다**. 각각을 검증하는 AC가 있어도 **함께 성립하는지는 따로 봐야 한다** —
`AC-8`·`AC-10`·`AC-13`·`AC-14`·`AC-16`이 그 다섯이고, 계약 문서가 이 다섯을 한 절에 모아 뒀다.

### 이 계획이 상위 문서에 되돌리는 것 — **규칙의 공백 1건**

`test-strategy.md` 4장이 **E2E 총 5~10개를 프로젝트 전체 기준**으로 정했는데,
**그 예산을 스토리별로 배분하는 규칙도, 합계를 판정하는 자리도 없다.**

| | |
|---|---|
| 무엇이 문제인가 | 스토리 6개가 **병렬로** 계획을 쓰고 있다. 각자 *"우리는 2개니까 범위 안"* 이라고 판정하면 **아무도 위반하지 않는데 합계는 넘는다.** 001(7) + 003(2) = 9이고 남은 4개 스토리에 1개다 |
| 왜 지금 드러났나 | 001은 **혼자였기 때문에** 자기 개수만 세면 됐다. 3.9의 경고도 *"001이 7개를 쓴다"* 까지였고 **다음 스토리가 무엇을 해야 하는지는 적히지 않았다** |
| 003이 한 것 | 자기 몫을 **5개에서 2개로 깎았다**(아래 *E2E 예산*). 그래도 구조적으로는 해결되지 않는다 |
| 제안 (003이 정하지 않는다) | ① 통합 단계에 **전 스토리 E2E 목록을 합산해 판정하는 자리**를 둔다(6번 태스크 분해 또는 통합 검증) ② 또는 002가 **게시판 공통 흐름 E2E를 소유**하고 003~006은 **자기 스토리에만 있는 것**만 E2E로 둔다 — 003의 2개 중 `AC-3`이 정확히 그 대상이다 |

**`test-strategy.md`를 여기서 고치지 않는다.** 거버넌스 1항이 *"`process.md`를 먼저 고치고
동기화한다"* 이고, 병렬 워크트리에서 전역 문서를 고치면 다른 스토리의 편집과 충돌한다.

## 데이터 모델 — 003 추가분 *(제안. 사람이 `specs/data-model.md`에서 확정한다)*

### 0. 먼저 정해져야 하는 것 — **003이 정할 수 없는 것 두 개**

### 2. 물리 설계 제안 — 컬럼 타입 · NULL · 기본값

001 물리 설계의 전역 규칙(`snake_case` · `BIGINT GENERATED ALWAYS AS IDENTITY` ·
`TIMESTAMPTZ`)을 그대로 따른다.

| 속성 | 타입 | NULL | 기본값·제약 | 근거 |
|---|---|---|---|---|
| 식별자 | `BIGINT GENERATED ALWAYS AS IDENTITY` | NOT NULL | PK | 001 1절 |
| 분류 참조 | `BIGINT` | NOT NULL | **FK → 분류, `ON DELETE RESTRICT`** + 인덱스 | 아래 3절 |
| 제목 | **`VARCHAR(99)`** | NOT NULL | — | *"100자 미만"* 이므로 최대 **99자**. 001이 `username`을 `VARCHAR(11)`("12자 미만")로 둔 것과 같은 규칙 — **DB가 마지막 방어선**이다 |
| 내용 | **`VARCHAR(3999)`** | NOT NULL | — | 같은 규칙. `TEXT`로 두면 상한이 사라진다 |
| 등록 관리자 참조 | `BIGINT` | NOT NULL | **FK → 유저** (삭제 규칙은 **`ADR-011`**) | 아래 3절 |
| 등록일시 | `TIMESTAMPTZ` | NOT NULL | `now()` | 001 1절 |
| 상단 고정 여부 | `BOOLEAN` | NOT NULL | **`false`** | 기본값이 없으면 삽입 때마다 명시해야 하고, 한 번 빠뜨리면 `NULL` 이 되어 **고정인지 알 수 없는 공지**가 생긴다(001 재발급티켓의 `무효화 여부`와 같은 판단) |
| 조회수 | `BIGINT` | NOT NULL | **`0`** + **`CHECK (조회수 >= 0)`** | 음수 조회수는 어떤 경로로도 정상이 아니다. 값이 음수로 보이면 **증가 로직이 아니라 덮어쓰기가 일어난 것**이라 `CHECK`가 그 사고를 부팅이 아니라 **쓰기 시점에** 잡는다 |

**⚠️ `VARCHAR(n)`과 애플리케이션의 "문자 수"가 어긋날 수 있다 — 기록해 둔다.**
Postgres `VARCHAR(n)`은 **코드포인트**를 세고, 스펙의 *"이모지 1자는 1자"*(Edge Cases)는
사람이 보는 **글자(grapheme)** 를 뜻한다. 국기·가족 이모지처럼 **코드포인트 여러 개가 한 글자**인
입력에서 **애플리케이션은 통과시키는데 DB가 거부**할 수 있다.
그러면 400이 아니라 **제약 위반 예외 → 5xx** 가 나가고 **원칙 IV(에러 누수)와 부딪힌다.**
→ **대응은 위험 6번**. 001이 비밀번호에서 만났던 *"길이를 무엇으로 세는가"* 문제와 같은 종류다.

### 3. 외래키 두 개 — 삭제 규칙이 서로 다르다

| FK | 대상 | 규칙 | 왜 |
|---|---|---|---|
| 분류 참조 | 분류(**004 소유**) | **`ON DELETE RESTRICT`** | 요구사항이 *"이미 사용 중인 분류는 삭제하지 않고 비활성으로 내린다"* 로 정했다. **RESTRICT는 그 규칙을 DB가 강제하는 형태**다 — 코드가 실수로 삭제를 시도하면 DB가 막는다. `CASCADE`면 분류 하나를 지우는 순간 **그 분류의 공지가 전부 사라진다** |
| 등록 관리자 참조 | 유저(001 소유) | **미정 → `ADR-011`** | `CASCADE`는 **불가**하다 — 관리자 계정을 지우면 그가 쓴 공지가 전부 사라진다. 남는 선택지는 ① `RESTRICT`(공지가 있으면 계정을 못 지운다) ② `SET NULL` + **작성자 이름 스냅샷 컬럼**. ②는 컬럼이 늘고 `FR-014`의 표시 값이 조인이 아니라 저장 값이 된다 |

**`ON DELETE RESTRICT`는 인덱스를 요구한다.** 001 물리 설계 5.5가 잡아낸 함정과 같다 —
**PostgreSQL은 FK 컬럼(자식 쪽)에 인덱스를 자동으로 만들지 않는데**, 부모를 지우거나
*"이 분류를 쓰는 공지가 있나"* 를 판정하는 방향은 **자식을 찾는 방향**이다.

### 4. 인덱스 — **조회 패턴에서 도출한다**

먼저 003이 실제로 던지는 조회를 전부 적는다. 인덱스는 여기서 나온다.

| # | 조회 | 언제 | 형태 |
|---|---|---|---|
| Q1 | **고정 노출 5건** | **목록 조회마다**(검색이 적용되지 않은 경우) | `WHERE 고정=true ORDER BY 등록일시 DESC, 식별자 DESC LIMIT 5` |
| Q2 | **일반 목록 1페이지분** | 목록 조회마다 | `WHERE 기간 [AND 분류] [AND (제목 LIKE OR 내용 LIKE)] [AND 식별자 NOT IN (Q1)] ORDER BY <정렬>, 식별자 DESC LIMIT/OFFSET` |
| Q3 | **일반 목록 총건수** | 목록 조회마다 (번호·총페이지 계산) | Q2와 같은 조건의 `COUNT(*)` |
| Q4 | 단건 조회 | 상세 · 수정 · 삭제 | `WHERE 식별자 = ?` |
| Q5 | 조회수 증가 | 상세 조회마다 | `UPDATE ... SET 조회수 = 조회수 + 1 WHERE 식별자 = ?` |
| Q6 | 관리자 목록의 **고정 전체**(밀린 것 포함) | 관리자 목록 조회마다 | `WHERE 고정=true ORDER BY 등록일시 DESC, 식별자 DESC` |

**도출한 인덱스**

| # | 인덱스 | 어느 조회 | 왜 이 형태인가 |
|---|---|---|---|
| **1** | **부분 인덱스** — `(등록일시 DESC, 식별자 DESC) WHERE 상단고정 = true` | **Q1 · Q6** | 목록을 열 때마다 도는 조회인데 **대상이 전체 공지의 극히 일부**(보통 0~10건)다. 부분 인덱스면 **인덱스 자체가 그 몇 건**이라 `LIMIT 5`가 인덱스만으로 끝난다. `상단고정` 단독 인덱스는 **값이 2종뿐이라 선택도가 낮아** 도움이 안 된다 — 조건을 인덱스 정의로 올리는 것이 정답이다 |
| **2** | `(등록일시 DESC, 식별자 DESC)` | **Q2 · Q3의 기본 경로** | 기본값 조회(기간 1달 + 등록일시 내림차순 + 페이징)가 **압도적 다수**다. `식별자 DESC`를 붙이는 이유는 **002 `AC-10`의 결정적 2차 정렬** — 없으면 등록일시가 같은 글에서 페이징이 깨져 **1페이지 글이 2페이지에 또 나온다** |
| **3** | `분류 참조` | Q2의 분류 필터 · **3절의 RESTRICT** | FK 인덱스는 **자동으로 생기지 않는다**(001 5.5의 4번). 004의 *"사용 중인 분류인가"* 판정도 이 인덱스를 쓴다 |
| — | 정렬 기준별 인덱스(조회수·제목·분류) | Q2의 **비기본 정렬** | **두지 않는다** → 아래 |
| — | 검색어 인덱스 | Q2의 `LIKE` | **둘 수 없다** → 아래 |

**두지 않는 인덱스와 그 근거** — *적어두지 않으면 나중에 "빠뜨린 것"과 구분되지 않는다*
(001 물리 설계 5.5의 규칙을 그대로 따른다).

| | 왜 두지 않나 | 방아쇠 |
|---|---|---|
| `조회수` | **매 상세 조회마다 갱신되는 컬럼**이다. 인덱스를 걸면 **읽기 1건마다 인덱스도 갱신**되어 `Q5`가 비싸진다. 공지는 건수가 작고(수백~수천) 조회수 정렬은 사용 빈도가 낮다 | 공지 1만 건 이상 + 조회수 정렬이 실사용에서 흔해지는 시점 |
| `제목` · `분류`(정렬용) | 같은 이유의 반대쪽 — **정렬 요구는 있지만 데이터가 작다.** 인덱스 3개를 더 만들면 쓰기가 비싸지고 얻는 것이 없다 | 위와 같다 |
| **검색어(제목·내용 부분 일치)** | **B-tree가 원리적으로 듣지 않는다.** `LIKE '%키워드%'` 는 앞이 열려 있어 인덱스를 탈 수 없다. **스캔 범위의 상한은 인덱스가 아니라 기간 상한 1년**(`FR-001`)이 담당한다 — 그것이 002 `AC-3`이 상한을 둔 진짜 이유다 | `pg_trgm` GIN 인덱스. **게시판 4종 공통이므로 002 소관**이며 003이 먼저 도입하지 않는다 |
| `상단 고정 여부` 단독 | 값 2종. 1번 부분 인덱스가 대신한다 | — |

**인덱스 이름은 001의 규칙을 따른다** — `ix_<테이블>_<컬럼>` · `uk_<테이블>_<의미>` ·

## 목록 조회의 형태 — **한 화면, 두 개의 조회**

003의 설계가 실제로 걸리는 지점은 여기 하나다.

### 순서

```
1. "검색이 적용된 조회인가?" 판정                    ← 순수 함수 (단위)
2. 적용됐다 → 고정 영역 없음. 제외 규칙도 해제. 일반 목록만 조회하고 끝
   적용되지 않았다 → 3으로
3. Q1로 고정 노출 5건과 그 식별자 목록을 확정         ← 이 목록이 4·5의 입력이다
4. Q3: 3의 식별자를 제외한 총건수 T                   ← 번호와 총페이지의 모집단
5. Q2: 3의 식별자를 제외한 페이지 1장                 ← 개씩 보기는 여기에만 적용
6. 번호 매기기: 첫 행 = T − (page−1) × size, 이후 −1  ← 순수 함수 (단위)
```

**3·4·5는 반드시 하나의 트랜잭션(같은 스냅샷) 안에서 돈다.** 나누면 그 사이에 다른 관리자가
고정을 지정·해제할 때 **3에서 뺀 글이 5에 없고**(그 공지가 화면에서 사라진다) 또는
**3에 없는 글이 5에 있다**(같은 글이 두 번 보인다). `AC-8`과 `AC-10`이 **동시에** 깨지는데,
각각을 검증하는 테스트는 **순차 실행이라 통과한다.**

### 세 개의 순수 규칙 — 단위 테스트 대상

| | 입력 → 출력 | 왜 떼어내나 |
|---|---|---|
| `SearchApplied` | (검색어, 분류, 기간) → **적용/미적용** | `FR-013`의 방아쇠다. **이 판정 하나가 고정 영역 표시와 제외 규칙 둘을 동시에 켜고 끈다** — 두 곳에서 따로 판정하면 어긋나고, 어긋나면 고정 공지가 검색 결과에서 통째로 빠지거나 상단에 그대로 남는다. **판정 자리를 물리적으로 하나로 만든다** |
| `PinnedSelector` | (고정 공지 목록) → **노출 5건 + 밀린 것** | 경계가 0 / 5 / 6 / 전량이고 **등록일시 동률**까지 있다. DB를 띄우지 않고 훑는 것이 맞다 |
| `ListNumbering` | (총건수 T, 페이지 p, 크기 s) → **첫 번호** | `AC-1`·`AC-13`·`AC-14`·`AC-17`이 전부 이 한 줄의 결과다. 검증: 15건·고정 3 → T=12 → 1페이지 12…3, 2페이지 2…1 |

### 등록일시 동률 — **스펙이 답하지 않은 곳**

`AC-9`는 *"등록일시가 서로 다르고"* 를 Given에 두었다. **같으면?**
고정 6건 중 5건을 고르는데 5·6번째의 등록일시가 같으면 **어느 쪽이 노출될지 정해지지 않는다.**
→ **`ORDER BY 등록일시 DESC, 식별자 DESC` 로 계약에 못박는다.** 002 `AC-10`이 일반 목록에
결정적 2차 정렬을 요구한 것과 **같은 문제이고 같은 해법**이다. 스펙 변경이 아니라
**스펙이 비워 둔 곳을 계약이 채운 것**이므로 계약 문서에 적고 미해결 5로 올린다.

| | 안 |

| 7 | **분류 조회 엔드포인트와 식별자 형태**(숫자 id vs 코드) · **게시판 귀속 방식** | **004** | `FR-029`·`AC-42`의 *"이 게시판의 분류인가"* 를 무엇으로 판정할지 정해지지 않는다. 003 계약은 **숫자 id + 게시판 귀속 컬럼**을 가정했다 |
| 8 | **본문 XSS 렌더 E2E를 002가 소유하는가** | **002 / 통합 단계** | 003이 `AC-35`를 컴포넌트 단위로 내린 전제가 *"브라우저 실행 검증은 공통 렌더러에 1개"* 다. 아무도 두지 않으면 **브라우저에서 실행되는지 확인하는 테스트가 프로젝트에 하나도 없다** |
| 9 | **E2E 전역 예산의 스토리별 배분 규칙** | 사람 / 통합 단계 | 스토리마다 자기 개수만 세어 **합계가 조용히 초과**된다. 위 *이 계획이 상위 문서에 되돌리는 것* |

**1·2·3·7·8은 003이 기다리는 것이고, 4·5·6·9는 사람이 판단할 것이다.**
**셋 이상이 003 단독으로 해소되지 않으므로 이 계획을 "미해결 0건"으로 선언하지 않는다.**

> **번호를 붙이지 않는다.** ADR 번호는 프로젝트 전역 연속이고 002·004·005·006이 병렬로

> 스펙의 후보 1~5는 그대로 유효하다.

**후보 6 — 게시물 저장 구조: 게시판 4종 공통 테이블 vs 게시판별 테이블**

- **무엇**: 공지·자유·갤러리·문의의 게시물을 **한 테이블 + 게시판 구분**으로 둘 것인가,
  **게시판마다 테이블**로 나눌 것인가.
- **왜 ADR인가**: **이미 쌓인 게시물을 이관**해야 바꿀 수 있고, 4종 전부의 조회·권한·인덱스가
  이 선택 위에 세워진다. `data-model.md`의 **판단 도구 1**(*"이 둘은 같은 개념인가"*)이
  정면으로 걸리는 자리다 — 네 게시판은 목록 구조가 같지만 **첨부·댓글·비밀글·상단 고정이
  전부 다르다.**
- **실재하는 선택지**: ① 공통 테이블 + 게시판 구분 컬럼 + 전용 확장 테이블
  ② 게시판별 독립 테이블 ③ 공통 테이블 + 전용 컬럼을 nullable로 섞기
  — ③은 *"항상 비어 있는 컬럼"* 을 만들고 `data-model.md` 리뷰 체크리스트가
  **테이블을 잘못 나눈 신호**로 규정한 것이다. **셋 다 검토되어야 한다.**
- **003의 관심사**: 상단 고정 여부가 **003에만 있는 속성**이라 ①·③의 갈림에 직접 걸린다.
  **003이 결정하지 않는다 — 002/데이터 모델로 올린다.**

**후보 7 — 게시물의 작성자 참조와 계정 삭제 규칙**

- **무엇**: 게시물의 작성자 외래키를 **`RESTRICT`**(작성자를 지울 수 없다)로 둘 것인가,
  **`SET NULL` + 작성자 이름 스냅샷**으로 둘 것인가.
- **왜 ADR인가**: 4종 전부에 적용되고, 나중에 스냅샷으로 바꾸면 **이미 쌓인 게시물의 작성자
  이름을 어디서 채울지** 정해야 한다. `CASCADE`는 검토 대상이 아니다 —
  **계정 하나를 지우면 그가 쓴 게시물이 전부 사라진다.**
- **003의 관심사**: `FR-014`가 *"등록한 관리자 이름"* 을 상세의 필수 표시 항목으로 요구한다.
  `RESTRICT`면 **공지를 쓴 관리자는 퇴사해도 계정을 지울 수 없고**, 스냅샷이면
  **관리자가 개명해도 옛 공지에는 옛 이름이 남는다.** 둘 다 대가가 있다.
- **왜 지금 적는가**: **회원 탈퇴가 범위 밖이라 당장 발생하지 않는다.** 001이 재발급 티켓의
  `ON DELETE CASCADE`를 **같은 이유로 미리 정한** 선례가 있다 — 외래키 삭제 규칙은
  테이블을 만들 때 함께 써야 나중에 `ALTER`로 고치지 않는다.
