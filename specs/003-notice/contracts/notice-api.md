# API 계약 — 003 공지사항

> `/speckit-plan` Phase 1 산출물. **AC와 1:1로 대응시킨 계약**이며,
> 7번에서 코덱스가 **이 문서와 `spec.md`만 보고** 테스트를 작성한다(구현 코드를 보지 않는다).

**공통 오류 형식**: RFC 9457 Problem Details + `code`/`traceId` 확장.
**001이 만든 공통 생성기를 그대로 쓴다** — 003은 **오류 코드만 추가**한다.

```json
HTTP 4xx/5xx
Content-Type: application/problem+json
{
  "type": "/errors/<범주>",
  "title": "...",
  "status": 400,
  "detail": "사람이 읽는 메시지",
  "instance": "/api/admin/notices",
  "code": "POST_TITLE_LENGTH_INVALID",
  "traceId": "a3f9c2",
  "errors": [{ "field": "title", "reason": "길이 오류" }]
}
```

## 0. 이 계약이 소유하지 않는 것

| | 누가 소유하나 | 003은 |
|---|---|---|
| 목록 파라미터 이름 · 공통 목록 오류 코드 · 페이지 응답 스키마 · 정렬 2차 기준 | **002** | 그대로 쓴다. **아래 표기는 002 초안 기준의 가정**이며 002 확정 시 이 문서를 동기화한다 (`plan.md` 미해결 1·2) |
| 분류(카테고리) 조회 · 분류 식별자의 형태 · 게시판 귀속 | **004** | **참조만 한다.** 003은 분류 조회 엔드포인트를 정의하지 않는다 (`plan.md` 미해결 7) |
| 인증 · 401/403 응답 · 오류 응답 형식 · `traceId` | **001 (구현 완료)** | 그대로 상속한다 |

> **오류 코드 접두사**: 003이 새로 만드는 코드는 전부 **`NOTICE_`** 로 시작한다.
> **공통 목록 규칙 위반**(기간 상한·잘못된 개씩 보기·잘못된 정렬·없는 분류 필터 등)은
> **002의 `BOARD_` 코드**를 그대로 쓰고 003이 다시 정의하지 않는다.

## 0.1 엔드포인트와 권한 — 전수

| # | 메서드 · 경로 | 무엇 | **권한** | 조회수 |
|---|---|---|---|---|
| 1 | `GET /api/notices` | 사용자 목록(고정 영역 포함) | **불필요** (`FR-003`) | — |
| 2 | `GET /api/notices/{id}` | 사용자 상세 | **불필요** (`FR-003`) | **+1** (`FR-016`) |
| 3 | `GET /api/admin/notices` | 관리자 목록 | **`ADMIN`** | — |
| 4 | `GET /api/admin/notices/{id}` | 관리자 상세(수정 화면의 원본) | **`ADMIN`** | **증가하지 않는다** (`FR-017`) |
| 5 | `POST /api/admin/notices` | 등록 | **`ADMIN`** | — |
| 6 | `PUT /api/admin/notices/{id}` | 수정 | **`ADMIN`** | — |
| 7 | `DELETE /api/admin/notices/{id}` | 삭제 | **`ADMIN`** | — |

- **읽기(1·2)는 인증을 요구하지 않는다.** `USER` 로 로그인한 채 호출해도 200이다.
- **쓰기(5·6·7)와 관리자 조회(3·4)는 `ADMIN` 만.** 미인증 **401** `AUTH_REQUIRED`,
  `USER` **403** `AUTH_FORBIDDEN` (001 `AC-21`·`AC-22`와 같은 형태 — `AC-38`·`AC-39`).
- **`ADMIN` 은 작성자와 무관하게 6·7을 수행할 수 있다**(`FR-027`·`AC-33` — J10).
  **소유자 검사가 없다는 것이 계약이다.** 넣으면 `AC-33`이 거짓이 된다.

## 0.2 검사 순서 — **인증 → 권한 → 존재 → 입력 검증**

**순서가 계약이다.** 뒤집으면 응답이 바뀐다.

| 상황 | 응답 | AC |
|---|---|---|
| 미인증이 삭제된 공지를 수정 요청 | **401** — 존재를 판정하기 전에 끊는다 | `AC-38` |
| `USER` 가 삭제된 공지를 수정 요청 | **403** — 권한이 먼저다 | `AC-39` |
| `ADMIN` 이 삭제된 공지를 수정 요청 | **404** `POST_NOT_FOUND`. **403이 아니다** | **`AC-43`** |
| `ADMIN` 이 삭제된 공지에 **잘못된 제목**으로 수정 요청 | **404** — 존재가 입력 검증보다 먼저다. 400이 아니다 | **`AC-43`** |

> **존재 확인을 권한 검사보다 먼저 하면 `USER` 에게 404가 나가고**, 그 순간
> *"그 번호의 공지가 없다"* 를 일반 사용자에게 알려준다. 반대로 **권한 통과 후에 403을 주면**
> *"있긴 있다"* 를 알려준다. constitution 원칙 IV.

## 1. `GET /api/notices` — 사용자 목록

**인증**: 불필요 (`FR-003` · `AC-5`)

### 요청 파라미터 — **전부 002가 소유한다**

| 이름 | 기본값 | 비고 |
|---|---|---|
| `from` · `to` | **최근 1달** | 최대 1년 (`AC-4`) |
| `categoryId` | 없음(= 전체 분류) | **공지사항 분류만 유효** |
| `keyword` | 없음 | **003은 제목·내용에만 적용**(`FR-002`·`AC-2`). 등록자에 적용하지 않는다 |
| `page` | **`0`** | **0 기반**이다 — 첫 페이지가 `0`. 002 계약에 맞춘다 *(통합 단계 정정)* |
| `size` | **10** | 10·20·30·40·50 (`AC-14`) |
| `sort` | `CREATED_AT` | `CREATED_AT` · `CATEGORY` · `TITLE` · `VIEW_COUNT` |
| **`direction`** | `DESC` | `DESC` · `ASC`. **이름이 `order`가 아니다** — 002 계약이 `direction`이다 *(통합 단계 정정)* |

> ⚠️ *(통합 단계 정정 2026-07-31)* 원문은 `page` 기본값을 `1`, 정렬 방향 파라미터 이름을
> `order`로 적었다. **002 계약은 `page` 기본값 `0`(0 기반)·이름 `direction`** 이다.
> 이 표의 머리글이 *"전부 002가 소유한다"* 라고 적어 놓고 값이 002와 달랐다 —
> 게시판마다 다른 이름을 쓰면 5단계 **공통 목록 훅이 성립하지 않는다.**
> `ADR-012`(페이징 방식)가 이 계약을 확정한다.

### 200 응답

```json
{
  "pinnedVisible": true,
  "pinned": [
    { "id": 41, "categoryName": "알림", "title": "정기 점검 안내",
      "createdAt": "2026-07-30T09:00:00+09:00", "viewCount": 128, "new": true }
  ],
  "items": [
    { "id": 33, "number": 12, "categoryName": "점검", "title": "…",
      "createdAt": "2026-07-29T10:00:00+09:00", "viewCount": 4, "new": true }
  ],
  "page": { "page": 1, "size": 10, "totalElements": 12, "totalPages": 2 },
  "appliedConditions": {
    "from": "2026-06-30", "to": "2026-07-31", "categoryId": null, "keyword": null,
    "size": 10, "sort": "등록일시", "order": "내림차순"
  }
}
```

| 규약 | AC | 왜 |
|---|---|---|
| **`pinned`와 `items`는 별도 배열이다** | `AC-6` | 한 배열 + 플래그로 두면 화면이 다시 갈라야 하고, **`number` 유무가 행마다 달라 타입이 흔들린다.** 배열을 나누면 *"고정은 페이징·정원과 무관"* 이라는 규칙이 **응답 형태에 그대로 드러난다** *(Claude 판단 — 사람 검증 필요)* |
| **`pinned[]` 행에는 `number` 필드가 없다** | **`AC-12`** | 번호 대신 `categoryName` 을 쓴다(`FR-010` — J6). **`number: 0` 이나 `number: null` 이 아니라 필드 자체를 두지 않는다** — `null` 로 두면 화면이 그것을 번호로 그리다 빈칸을 만든다 |
| **`items[]` 행에는 `number` 가 반드시 있다** | `AC-13` | |
| **`page.totalElements` 는 일반 목록 기준**이다 | `AC-13`·`AC-14`·`AC-17` | 고정 노출분을 뺀 수. **전체 건수가 아니다** — `AC-13`의 15건·고정 3건에서 이 값은 **12**다 |
| **`pinnedVisible: false` 이면 `pinned` 는 빈 배열**이고, **제외 규칙도 함께 해제**된다 | **`AC-16`** | 아래 ★2 |
| `new` 는 **서버가 판정한 값**이다 | 002 상속 | 화면이 계산하면 브라우저 시계에 의존한다 |
| `appliedConditions` 를 되돌려준다 | 002 `AC-1` 상속 · `AC-3` | 기본값이 서버·화면 두 곳에 생기면 언젠가 어긋난다 |

### 고정 영역의 산출 규칙

```
정렬     등록일시 DESC, 식별자 DESC        ← 2차 기준이 없으면 동률에서 비결정적
개수     최대 5                            FR-005 · AC-9
조건     검색이 적용되지 않은 조회에서만    FR-013 · AC-16
페이지   모든 페이지에서 동일               FR-004 · AC-7
```

**`식별자 DESC` 는 스펙에 없고 이 계약이 채운 것이다** — `AC-9`의 Given이
*"등록일시가 서로 다르고"* 라 **동률일 때 어느 쪽이 노출될지 정해지지 않았다.**
002 `AC-10`이 일반 목록에 결정적 2차 정렬을 요구한 것과 같은 문제다 (`plan.md` 미해결 5).

### "검색이 적용된 조회"의 정의 — `FR-013`의 방아쇠

**셋 중 하나라도 참이면 적용된 것이다.**

| | 판정 |
|---|---|
| 검색어 | **공백을 제거한 뒤 비어 있지 않다** (공백만이면 미적용 — Edge Cases) |
| 분류 | `전체 분류`(미지정)가 **아니다** |
| 기간 | **기본 1달과 다르다** |

> **★ "파라미터가 왔는가"로 판정하지 않는다.** 화면이 기본 기간을 명시적으로 실어 보낼 수
> 있고, 그러면 **아무것도 검색하지 않았는데 고정 영역이 사라진다.** **값으로 판정한다.**
> 판정하는 자리는 **하나뿐이어야 한다** — 고정 영역 표시와 중복 제외 규칙이
> **같은 판정 결과를 공유**해야 하기 때문이다(★2).

### 오류

| 응답 | 조건 | `code` | AC |
|---|---|---|---|
| 400 | 기간이 1년을 초과 | **002 코드**(초안 `BOARD_SEARCH_PERIOD_TOO_LONG`) | **`AC-4`** |
| 400 | `from` 이 `to` 보다 뒤 | **002 코드**(초안 `BOARD_SEARCH_PERIOD_INVALID`) | Edge Cases |
| 400 | 허용되지 않은 `size` | **002 코드**(초안 `BOARD_PAGE_SIZE_NOT_ALLOWED`) | 002 상속 |
| 400 | 허용되지 않은 `sort`·`order` | **002 코드**(초안 `BOARD_SORT_NOT_ALLOWED`) | 002 상속 |
| 400 | 존재하지 않는 분류 필터 | **002 코드**(초안 `BOARD_CATEGORY_NOT_FOUND`) | 002 상속 |
| 200 | **마지막 페이지를 넘어선 요청** | — | Edge Cases. **002가 정한 규칙을 따른다**(초안: 빈 목록 + 200). 고정 영역은 그대로 반환된다 |

**검색어의 `%` `_` 는 문자 그대로 찾는다**(Edge Cases · J16). 와일드카드로 해석하면

## 2. `GET /api/notices/{id}` — 사용자 상세

**인증**: 불필요 (`FR-003` · `AC-20`)

### 200 응답 — **표시 항목은 `FR-014`의 6개 + 식별자뿐이다**

```json
{ "id": 41, "categoryName": "알림", "title": "정기 점검 안내",
  "createdAt": "2026-07-30T09:00:00+09:00", "authorName": "홍관리",
  "viewCount": 129, "content": "…" }
```

| 규약 | AC |
|---|---|
| 분류 · 제목 · 등록일시 · **등록한 관리자 이름** · 조회수 · 내용 | `AC-19` |
| **고정 여부에 따라 필드가 늘거나 줄지 않는다** | **`AC-21`** |
| **`pinned` 필드를 두지 않는다** — 고정은 *목록에서의 노출 방식*이지 글의 속성이 아니다 | `AC-21`(`FR-015`) |
| 분류가 나중에 비활성으로 내려가도 `categoryName` 은 **그대로 표시**된다 | `AC-32`(`FR-021`) |
| 응답의 `viewCount` 는 **이번 조회를 포함한 값**이다(7 → `8`) | `AC-22` |

### 조회수 증가

| | 규칙 | AC |
|---|---|---|
| 증가 방식 | **원자적 증가.** `읽고 → +1 → 쓴다` 를 금지한다 | **`AC-23`** |
| 중복 방지 | **없다.** 같은 사람이 다시 열면 또 오른다 | `AC-22`(J8) |
| 실패해도 | **본문 조회는 성공해야 한다** — 조회수는 부수 효과이고 본문이 목적이다 *(Claude 판단)* |

> **`AC-23`이 요구하는 것은 "10개 요청 → 정확히 10"이다.** 엔티티를 로드해 값을 더하고
> 저장하면 동시 요청에서 **증가분이 덮여 사라진다.** 조회수는 목록 정렬 기준이므로
> 틀리면 **목록 순서가 틀린다.**

### 오류

| 응답 | 조건 | `code` | AC |
|---|---|---|---|
| **404** | 존재한 적 없는 식별자 | `POST_NOT_FOUND` | **`AC-25`** |
| **404** | **삭제된 공지 — 위와 상태코드·`code`·메시지가 모두 같다** | `POST_NOT_FOUND` | **`AC-25`** · `AC-34` |

**무엇이 같아야 하는지 못박는다** (001 계약의 `AC-2`/`AC-3` 통일과 같은 방식):

| | 항목 |
|---|---|
| **같아야 한다** | 상태코드(**404**) · `Content-Type` · `type` · `title` · `code` · `detail` · **`errors` 유무**(둘 다 없다) |
| **달라도 된다** | `traceId`(요청마다 다른 것이 정상) · `instance`(요청 경로에 식별자가 들어간다) |

**각각 404인 것만 확인하는 테스트로는 부족하다 — 두 응답을 서로 비교하는 테스트를 둔다.**

## 3. `GET /api/admin/notices` — 관리자 목록

**인증**: 필요 + **`ADMIN`**

### 200 응답 — **고정 영역을 분리하지 않는다**

```json
{
  "items": [
    { "id": 41, "number": 15, "categoryName": "알림", "title": "…",
      "createdAt": "…", "authorName": "홍관리", "viewCount": 128,
      "pinnedState": "EXPOSED" }
  ],
  "page": { "page": 1, "size": 10, "totalElements": 15, "totalPages": 2 }
}
```

| `pinnedState` | 뜻 |
|---|---|
| `EXPOSED` | 고정이고 **사용자 화면의 고정 영역에 노출 중**(최신 5개 안) |
| `OVERFLOW` | 고정이지만 **5개에서 밀려 일반 목록에 있다** |
| `NONE` | 고정이 아니다 |

> **★ 사용자 목록과 형태가 다른 것이 의도다** *(Claude 판단 — 사람 검증 필요. spec Assumptions
> 9·10 · J14)*. 관리자 화면의 목적은 *"관리 대상 전체를 본다"* 이므로 고정 영역을 분리하면
> **밀린 고정글이 일반 목록에 섞여 관리자가 고정 전체를 한눈에 볼 수 없다.**
> `pinnedState` 가 `OVERFLOW` 를 **이름으로 드러내지 않으면**, 관리자는 자기가 고정한 글이
> 왜 상단에 없는지 알 수 없다 — `FR-005`가 관리자에게 설명 없이 동작하는 상태가 된다.
>
> **따라서 `number` 는 모든 행에 있고 모집단은 전체 건수다**(고정을 빼지 않는다).
> `FR-009`의 제외 규칙은 **사용자 목록의 규칙**이고, 관리자 목록에는 고정 영역이 없으므로
> 뺄 대상 자체가 없다.

| 응답 | 조건 | `code` | AC |
|---|---|---|---|
| 401 | 미인증 | `AUTH_REQUIRED` | `AC-38` 계열 |
| 403 | `USER` 권한 | `AUTH_FORBIDDEN` | `AC-39` 계열 |

## 4. `GET /api/admin/notices/{id}` — 관리자 상세 (수정 화면의 원본)

**인증**: 필요 + **`ADMIN`**

```json
{ "id": 41, "categoryId": 3, "categoryName": "알림", "title": "…", "content": "…",
  "createdAt": "…", "authorName": "홍관리", "viewCount": 128, "pinned": true }
```

| 규약 | AC |
|---|---|
| **조회수가 증가하지 않는다** | **`AC-24`** (`FR-017` — J9) |
| `categoryId` 와 `pinned` 가 있다 — **수정 화면이 분류 선택과 체크박스를 그린다** | `FR-022` |

> 같은 데이터를 다른 목적으로 읽으므로 코드를 재사용하고 싶어지는데, **재사용하는 순간
> `AC-24`가 조용히 깨진다.** 관리자가 검수·수정하려고 열 때마다 조회수가 오르면
> **조회수가 독자 수 지표가 아니게 된다.**
> 테스트는 **사용자 → 관리자 → 사용자**를 이어서 호출해 `7 → 8 → 8 → 9` 를 확인한다.

## ★ 이 계약에서 가장 깨지기 쉬운 부분

### ★1 — 고정 규칙 다섯은 **한 덩어리**다

| # | 규칙 | FR | AC | 이것만 빠지면 |
|---|---|---|---|---|
| 1 | 노출 중인 고정글을 **일반 목록에서 제외** | `FR-007` | `AC-8` | 같은 글이 **한 화면에 두 번** — 번호 있는 행과 없는 행으로 |
| 2 | **밀린 고정글은 일반 목록에 편입** | `FR-008` | `AC-10` | 6번째 고정글이 **어디에도 없다.** 관리자는 "고정을 눌렀더니 글이 사라졌다"를 겪는다 |
| 3 | **번호 모집단에서 고정 노출분 제외** | `FR-009` | `AC-13` | 번호가 **건너뛴 채로** 보인다 |
| 4 | **개씩 보기 정원에 고정 미포함** | `FR-011` | `AC-14` | 고정 5 + 10개씩 보기에서 **일반 글이 5건만** 보이고, 고정 개수가 바뀔 때마다 **페이지 경계가 통째로 흔들린다** |
| 5 | **검색 시 고정 숨김 + 1·3 동시 해제** | `FR-013` | `AC-16` | 조건에 맞는 고정 공지가 **검색 결과에서 통째로 빠진다** |

**1과 2는 반대 방향이고 5는 1을 끈다.** 셋이 한 판정(★2)에서 나오지 않으면 어긋난다.
**각각을 검증하는 테스트가 전부 초록인데 화면이 틀려 있는 것**이 이 계약에서 가장 흔한 실패다.

### ★2 — 두 조회는 **하나의 스냅샷**에서 나온다

```
1  "검색이 적용됐는가" 판정 ── 한 곳에서만
2  적용 → 고정 없음 + 제외 해제. 일반 목록만
   미적용 → 3
3  고정 노출 5건과 그 식별자 목록을 확정
4  그 식별자를 제외한 총건수          ← 번호·총페이지의 모집단
5  그 식별자를 제외한 페이지 1장      ← 개씩 보기는 여기에만
```

**3·4·5는 같은 트랜잭션에서 돈다.** 나누면 그 사이에 다른 관리자가 고정을 지정·해제할 때
**3에서 뺀 글이 5에 없거나**(화면에서 사라진다) **3에 없는 글이 5에 있다**(두 번 보인다).
**고정 영역을 별도 엔드포인트로 쪼개지 않는 이유가 이것이다** — 쪼개면 이 보장이
원리적으로 불가능해진다.

### ★3 — 조회수는 **세 경로가 서로 다르게** 동작한다

| 경로 | 조회수 | 틀리기 쉬운 이유 |
|---|---|---|
| `GET /api/notices/{id}` | **+1, 원자적** | 엔티티를 로드해 더하면 동시 요청에서 **유실**된다 (`AC-23`) |
| `GET /api/admin/notices/{id}` | **증가 안 함** | 사용자 상세와 **같은 서비스를 재사용하면 조용히 깨진다** (`AC-24`) |
| `PUT /api/admin/notices/{id}` | **건드리지 않음** | 전 컬럼 `UPDATE` 면 **그 사이 오른 값이 되돌아간다** (`AC-23`이 수정 경로로 깨진다) |

**셋을 한 자리에서 관리하지 않는다.** 공유하는 순간 하나를 고치면 다른 하나가 깨진다.

### ★4 — 고정 행에는 `number` 필드가 **없다**

`null` 이나 `0` 이 아니라 **필드 자체를 두지 않는다**(`AC-12`).
`null` 로 두면 화면이 그것을 번호 칸에 그리려다 **빈 칸**을 만들고, `FR-010`이 요구한
**분류명 표시**가 조용히 사라진다. 스펙이 이 칸에 분류명을 넣기로 한 이유(J6)는
*"고정 문구로 덮으면 분류 정보가 화면에서 사라진다"* 이므로 **여기서 사라지면 같은 결과**다.

### ★5 — 403과 404의 갈림 (0.2절)

**인증 → 권한 → 존재 → 입력 검증.** 순서가 하나만 바뀌어도 존재 여부가 샌다.

### ★6 — 등록일시 동률

고정 노출 5건 선정과 일반 목록 정렬 **둘 다** `식별자 DESC` 를 2차 기준으로 갖는다.
없으면 고정 5·6번째가 **매 조회마다 바뀔 수 있고**, 일반 목록은 **페이징이 깨진다**
(1페이지 글이 2페이지에 또 나온다 — 002 `AC-10`).

> **`AC-41`의 판정을 003이 새로 만들지 않는다.** 001 `FR-035`·`AC-34`가 만든 **목적지 판정
> 순수 함수를 그대로 호출**한다. 003이 추가하는 것은 *"관리자 복귀 경로도 그 함수를
> 통과하는가"* 하나이므로 **단위 테스트로 충분하다** — 001 계획이 같은 판단을 이미
> 문서화했다(*"E2E로 변형 전부를 돌리면 느리고, 판정은 순수 함수라 단위가 맞다"*).
> **001에서 막았다고 003에서 자동으로 막히는 것이 아니다** — 목적지를 넘기는 화면이
> 003에 새로 생겼다.
